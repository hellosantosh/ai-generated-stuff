23A state-changing tool, for contrast

Everything so far has been read-only. This section shows what changes when a tool spends a customer's money — and how little of it is about the code.

23.1The two-step shape

ToolTierRole
brokerage_order_previewT1 Read-only. Computes cost, commission, resulting buying power, blockers, and warnings. Issues the confirmationToken. May be called freely, which means it is called — the customer sees the numbers before anyone asks them to commit.
brokerage_order_placeT3 Places the order. Requires the token, an idempotency key, and an explicit human confirmation bound to the exact arguments.
 
customer: "buy 100 apple in my roth"

  1. brokerage_accounts_list              → acct_01HQ8Z4M2X9K3P7R (Roth IRA, canTrade: true)
  2. brokerage_order_preview              → canPlace: true, estimatedCost 24,875.00 USD,
                                             buyingPowerAfter 59,485.20 USD,
                                             confirmationToken "cnf_…", expires 14:36:20Z
  3. agent presents the confirmation      → rendered from confirmationTemplate, not from JSON
  4. customer approves                    → runtime hashes the arguments and binds the approval
  5. brokerage_order_place                → orderId ord_…, status NEW, isTerminal false
  6. brokerage_order_get (after 2 s)      → status PARTIALLY_FILLED, 40 of 100 at 248.61

23.2The descriptor

brokerage_order_placePlace a real order — trades money
TIER 3 DESTRUCTIVE IDEMPOTENT VIA KEY OPEN WORLD brokerage:orders:write APPROVAL: CONFIRM RATE 10/min KILL SWITCH

Note the title: "Place a real order — trades money". It appears in the approval dialog and in every audit export. Titles for tier 3 tools name the consequence, not the operation (TS-NAM-09), because the person reading it at speed is deciding whether to authorize something real.

idempotentHint is true only because idempotencyKey is required: placing the same order twice with the same key places one order. Without the key this would be false, and the runtime would be unable to retry a timeout safely. openWorldHint is true because the order reaches a market venue outside the firm's control, whose behavior is not enumerable.

23.4The failure that matters most

A timeout on brokerage_order_place leaves the outcome unknown. The order may be live in the market. The error says so, in the only words that reliably produce the right next action: 

{ "error": {
    "code": "TIMEOUT",
    "domainCode": "ORDER_OUTCOME_UNKNOWN",
    "message": "The order was sent but no acknowledgment was received within 5 seconds. It may or may not have been placed.",
    "retryable": true,
    "remediation": "Do not tell the customer the order failed. Either retry brokerage_order_place with the SAME idempotencyKey, which will return the original result if the order was placed, or call brokerage_orders_list to check. Never place a second order with a new key.",
    "details": { "idempotencyKey": "3f2b1c88-9a41-4e2d-8b77-5c1e9d4a6f20" },
    "traceId": "01HQ9F6Q9S3U7W0Z1C4E6G8J" } }
Three sentences, three prevented incidents

"Do not tell the customer the order failed" prevents a false negative the customer acts on. "Retry with the SAME idempotencyKey" prevents a duplicate trade. "Never place a second order with a new key" closes the loophole a model will otherwise find when the retry also times out. This is what TS-ERR-02 means by remediation: an instruction, in the imperative, written by someone who has thought about what goes wrong.

24Composition: five questions, one catalog

The test of a catalog is not whether each tool is good but whether the set answers real questions without the model needing to know anything the firm has not told it. Five questions, traced.

24.1"What do I own?"

brokerage_accounts_list  {}
  → 3 accounts; customer says "the Roth"  → acct_01HQ8Z4M2X9K3P7R
brokerage_positions_list { accountId: "acct_01HQ8Z4M2X9K3P7R" }
  → 3 positions, totals, asOf, DELAYED_15M

What the descriptors did: the accounts description said it is the only source of account identifiers, so the model did not invent one. The positions description said quantity is signed, so the short position was reported as short. The basis field meant the answer was "as of 14:32, prices delayed up to 15 minutes" rather than a bare number.

24.2"Did my Apple order go through?"

brokerage_orders_list { accountId: "…", symbol: "AAPL", status: "WORKING" }
  → 1 order, PARTIALLY_FILLED, 200 of 500 at 245.88, isTerminal false

What the descriptors did: the positions description's exclusion — "do not use to check whether a trade went through" — routed the question to orders rather than positions, which is the single most common misroute in this domain. filledQuantity and remainingQuantity made "partly, 200 of 500" expressible; status alone would not have.

24.3"How much can I spend in my Roth?"

brokerage_balances_get { accountId: "acct_01HQ8Z4M2X9K3P7R" }
  → applicable 12,180.00 USD
    applicableReason "Settled cash. This is a retirement account and cannot
                      borrow, so margin buying power does not apply."

What the descriptors did: everything. Four figures were available and the tool named the right one and said why. A catalog without applicable would have required the model to know that a Roth IRA cannot borrow — which it might, most of the time, which is the worst possible reliability profile for a number the customer will act on.

24.4"Can I afford 100 Apple in there?"

brokerage_order_preview { accountId: "…", symbol: "AAPL", side: "BUY",
                          quantity: 100, orderType: "MARKET" }
  → canPlace true, estimatedCost 24,875.00, buyingPowerAfter -12,695.00 …
    blockers [{ code: "INSUFFICIENT_BUYING_POWER",
                message: "This order needs 24,875.00 USD; 12,180.00 USD is available.",
                maxPermissibleQuantity: 48 }]
    canPlace false

What the descriptors did: the preview tool refused, in advance, with the largest quantity that would work. The customer hears "not quite — that would need $24,875 and you have $12,180 settled; 48 shares would fit" instead of watching an order get rejected. maxPermissibleQuantity is TS-ERR-03 applied inside a success payload.

24.5"Fine, buy 48 then."

brokerage_order_preview { … quantity: 48 }        → canPlace true, cnf_… (120 s)
   confirmation shown, customer approves, arguments hashed
brokerage_order_place   { … confirmationToken: "cnf_…",
                          idempotencyKey: "3f2b1c88-…", reason: "customer requested" }
   → ord_01HQ9F8R2T5V8X1A, status NEW, isTerminal false,
     statusExplanation "Your order for 48 shares of AAPL has been accepted and
                        is working. It has not filled yet."
brokerage_order_get     { … }  after nextPollAfterSeconds = 2
   → FILLED, 48 at 248.57, isTerminal true

What the descriptors did: statusExplanation stopped "accepted" being reported as "bought". isTerminal stopped the polling loop at the right moment. The idempotency key meant a retry would have been safe. The audit record carries the confirmation the customer saw, their approval, the argument hash, and the descriptor version that produced the prose the model read.

24.6The same five questions against a mirrored REST surface

QuestionWhat happensRoot cause
"What do I own?"Short position reported as a holding; option exposure understated 100×Conventions never stated (§6.1)
"Did my order go through?"Answered from positions: "you own 200 Apple", which is true and not the questionNo exclusions (§6.2 part 3)

Every one of those failures is silent. None throws, none is logged as an error, and none fails a contract test. They are visible only in the conversation, which is why §16.2's silent wrongness rate is the metric this standard is ultimately trying to move.

25The anti-pattern catalog

Twelve failures seen repeatedly in first-generation tool catalogs, each with the rule it breaks. A reviewer who memorizes this section will catch most of what arrives at an architecture board.

25.1The kitchen-sink tool

One tool, four behaviors

{
  "name": "brokerage_orders_manage",
  "inputSchema": { "properties": {
    "action": { "enum": ["list", "get",
                          "place", "cancel"] },
    "params": { "type": "object" }
  }},
  "annotations": {
    "readOnlyHint": false,   // wrong for 2 of 4
    "destructiveHint": true // wrong for 2 of 4
  }
}

Four tools, four accurate contracts

brokerage_orders_list    T1  read-only
brokerage_order_get      T1  read-only
brokerage_order_preview  T1  read-only
brokerage_order_place    T3  confirm + token
brokerage_order_cancel   T3  confirm

// Each has its own description, risk tier,
// approval policy, rate limit, audit event,
// kill switch, and evaluation.

Breaks: TS-NAM-06, TS-ANN-02, TS-INP-01 (the open params object), and the entire control model — approval policy cannot be written against a tool whose risk depends on an argument the model chose.

The pattern behind the patterns

Eleven of these twelve are the same mistake: optimizing for the convenience of the team building the tool rather than the reliability of the caller consuming it. One tool is easier to ship than four. Passing the upstream payload through is easier than shaping it. A generic error is easier than a mapped taxonomy. Each shortcut moves work from a place where it can be tested to a place where it can only be hoped for.
