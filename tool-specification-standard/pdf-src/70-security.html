15Security and trust

Tools give a probabilistic system a set of hands. Everything in this section follows from that one sentence, and none of it is satisfied by securing the transport.

15.1Principles

PrincipleIn practice
The agent has no authority of its own Every action is performed as a principal, with that principal's scopes, subject to that principal's entitlements. There is no service account that "the assistant" uses to read customer accounts — that account would be a standing breach waiting for a prompt.
Least privilege, per invocation The scopes required are declared per tool and checked per invocation against the specific resource in the arguments, not once per session.
Everything the model produces is untrusted input Arguments are validated and authorized as though they came from an anonymous internet client, because in the relevant sense they did.
Everything a tool returns is untrusted input to the model Customer-supplied and counterparty-supplied strings are data. They are marked, neutralised, and never interpreted as instruction.
Controls live where they cannot be talked out of In the gateway and the implementation. Not in the description, not in the annotations, not in the system prompt — all three are inputs to a system that can be persuaded.

15.2Identity and authorization

RuleLevelRequirement
TS-SEC-02NEVER A tool MUST NOT accept an argument that asserts identity, role, tenancy, or entitlement. Identity arrives out of band, from the identity plane. A tool with an onBehalfOf parameter has delegated its access control to a language model.
TS-SEC-08MUST The implementation MUST authorize the principal against the specific resource named in the arguments, on every invocation. Holding brokerage:positions:read authorises reading your positions, not a position identifier you were able to produce.
TS-SEC-10NEVER A token presented to the gateway MUST NOT be forwarded verbatim to a downstream system. Exchange it for a token whose audience is that system, scoped to this operation. Pass-through re-uses a credential outside the audience it was issued for and destroys the ability to attribute a downstream action.
TS-SEC-03NEVER Credentials of any kind MUST NOT appear in arguments, results, errors, or descriptions. Anything in those four places will be logged, retained in conversation history, and may be transmitted to a model provider.

15.2.1The confused deputy

The gateway is a deputy: it holds authority the agent does not, and it acts on the agent's instructions. The classic failure is a gateway that authenticates the agent, authorises the tool, and then performs an operation against a resource the principal never had access to — because nothing re-checked the resource.

In this domain the attack is trivially expressible: a customer asks their assistant about "account acct_01HQ9F3M7X2K8P4T", an identifier they obtained, guessed, or found. Every layer above the implementation sees a well-formed request from an authenticated customer to a tool they are entitled to use. Only TS-SEC-08 stops it.

15.3Untrusted content in results

Tool results are read by a model as part of its instruction stream. Any field whose content originates outside the firm's control is therefore an injection vector — and a brokerage domain has more of these than teams expect:

FieldWritten by
Account nicknameThe customer, free text
Order memo, client order identifierThe customer or an integrating application
Instrument name and descriptionA market data vendor
Transfer memo, beneficiary nameA counterparty at another institution
Corporate action notes, document titlesExternal sources, unvalidated
Upstream error textA vendor system, occasionally verbatim from a third party

TS-SEC-11 MUST Free-text content that did not originate in a system the firm controls MUST be neutralised before it is returned: length-capped, stripped of control characters and markup, and MUST be delimited and labelled as customer-supplied or externally-supplied data in the text rendering. It MUST NOT be interpolated into a sentence that reads as narration by the tool.

15.4Tenancy and isolation

  • Every cache key, idempotency key, and rate-limit bucket is scoped by principal and tenant. A shared idempotency namespace lets one customer's key collide with another's, which is a data-disclosure bug wearing an availability bug's clothes.
  • Cross-tenant aggregates — "how many customers hold Tesla" — are a different tool, at a different tier, for a different audience, with a different entitlement. Never a parameter on a customer-facing tool.
  • Test fixtures and sandbox data never share an identifier space with production. A model that has seen acct_TEST0001 in an example will eventually send it.

15.5Loop, abuse, and cost protection

SignalControl
Identical invocation repeated within a conversation Return the cached result and increment a counter; after three, return RATE_LIMITED with remediation "you have already called this; use the result you have". Agents loop, and the loop is usually invisible to the customer.
High-fan-out across accounts or symbols Per-principal quota plus a per-conversation ceiling. Offer the summarize tool in the remediation.
Repeated ENTITLEMENT_DENIED or NOT_FOUND Alert. This is the signature of enumeration, whether the agent is being manipulated or is simply confused.
Approval denied, then retried with altered arguments Alert and block the conversation. An agent that reformulates a declined trading action is the highest-signal event in the estate.

15.6Kill switch and degradation

TS-SEC-12 MUST Every tier 2 and tier 3 tool MUST be disableable within 60 seconds, by capability, by audience, and globally, without a deployment. The disabled state MUST return NOT_SUPPORTED with a remediation the agent can relay — "order placement through the assistant is temporarily unavailable; the customer can trade in the app" — rather than an opaque failure.

15.7Third-party and vendor tools

Tools the firm did not write are a supply chain, and the descriptor is the payload. Three controls, none optional:

RuleLevelRequirement
TS-SEC-09MUST Every descriptor's content hash MUST be recorded at approval. Runtimes MUST pin the approved hash and MUST refuse to present or invoke a tool whose descriptor has changed without a new approval — for internal tools too, but decisively for external ones.
TS-SEC-13MUST Third-party tools MUST be reviewed against this standard before admission, MUST be re-reviewed on every descriptor change, and MUST be assumed to have mis-stated their annotations — the firm assigns the risk tier independently, from observed behaviour, not from the vendor's claim.
TS-SEC-14MUST A third-party tool MUST NOT be presented to an agent in the same context as a firm tier 3 tool unless the combination has been explicitly assessed. The risk is not either tool; it is that one tool's output can steer the other's invocation.

16Observability, audit, and supervision

Two distinct obligations live here. One is operational: is the tool healthy. The other is novel and more demanding: is the agent using it well — a question no traditional API ever had to answer about its callers.

16.1The audit record

TS-OBS-01 MUST Every invocation — successful, failed, denied, or refused at policy — MUST emit exactly one audit record containing the fields below, retained for the period named in the tool's recordKeeping.retention.

FieldContent
traceId, conversationId, turnId Correlation across the whole interaction, not just this call.

toolName, toolVersion, descriptorHash The descriptor hash is not optional. Without it you cannot reconstruct what the model was told when it made the call, which is the first question asked in any investigation.

outcomesuccess, error code and domainCode, or the policy decision.
resultDigestA hash of the result plus its size and record count. The full payload is retained separately where classification and retention permit.

TS-OBS-02 MUST For tier 3 tools the audit record MUST be sufficient to reconstruct the decision: the arguments, the confirmation exactly as the principal saw it, their response, the result, and the descriptor version that produced the prose the model read. "The agent placed an order" is not a record; it is a summary of one.

Silent wrongness rate: invocations that succeeded, returned valid data, and produced a wrong answer for the customer. It cannot be measured from telemetry — it requires sampling conversations and having a domain expert read them. Budget for it. Every failure mode this standard is most worried about, from an undocumented signed quantity to a stale mark, shows up here and nowhere else.

17Versioning and lifecycle

The consumer of a tool contract cannot read a changelog, cannot be scheduled for an upgrade, and does not have a version pin of its own. That removes most of the usual options and makes the remaining rule very simple: additive change, or a new tool.

17.1What is a breaking change

ChangeVerdict
Adding an optional input parameter with a safe defaultCompatible
Adding a field to the output schemaCompatible
Adding a member to an output enumCompatible — consumers are told to treat unrecognised members as unknown (§17.2)
Relaxing a constraint (raising a maximum, widening a pattern)Compatible
Clarifying prose without changing behaviourCompatible — and encouraged; this is the cheapest fix available
Making an optional parameter requiredBreaking
Removing or renaming any field, input or outputBreaking
Adding a member to an input enumBreaking in effect — it changes what the model will send, and callers of the old contract never learn about it. Treat as a minor version and re-run evaluations.
Tightening a constraintBreaking
Changing a unit, a convention, or a signBreaking, and dangerous — nothing fails, answers just become wrong
Changing default behaviour on omissionBreaking
Raising the risk tier or adding an approval requirementCompatible technically, breaking operationally — announce it

17.2Versioning rules

RuleLevelRequirement
TS-VER-01MUST governance.version MUST be semantic. Patch for prose and non-behavioural fixes; minor for compatible additions; major only alongside a new tool name (TS-VER-03).
TS-VER-02MUST Output enumerations MUST be documented as open: the description states that new members may appear and how to treat one. Order status is the canonical case — an unrecognised status means working, never terminal, and getting that default backwards tells a customer their order is dead when it is live.
TS-VER-03MUST A breaking change MUST be published as a new tool name with a _v2 suffix, running alongside the original. The two coexist for the full deprecation window.
TS-VER-04MUST Any change to prose, schema, or behaviour MUST re-run the tool's evaluation suite before publication (§27.3). A description edit is a behaviour change: it is the input that determines whether the tool is selected at all.

17.3Deprecation

  1. Announce. Set lifecycle: deprecated with deprecation.{since, sunset, successor, migrationNote}. Minimum window: 90 days, or one full regulatory reporting cycle, whichever is longer.
  2. Stop new grants. The catalogue no longer offers the tool to audiences that do not already have it. Existing consumers are unaffected.
  3. Warn out of band. Results carry a deprecation notice in _meta, which the runtime logs. The description is not changed — deprecation prose in the description costs tokens on every turn, and a model told a tool is deprecated behaves unpredictably rather than migrating.
  4. Measure. Track invocations by audience. Contact the owner of each remaining consumer directly.
  5. Retire. At sunset, set lifecycle: retired. The tool returns NOT_SUPPORTED naming the successor for a further 90 days, then is withdrawn. The name is never reused (TS-NAM-11).

17.4The runtime constraint register

Tool-calling runtimes impose their own limits — name length and character set, maximum number of tools, maximum schema depth, whether output schemas are honoured, whether annotations are surfaced. These change without notice and are not the firm's to control.

TS-VER-05 MUST The platform team MUST maintain a register of the constraints imposed by every runtime the firm publishes to, MUST enforce the intersection of those constraints in the linter, and MUST re-validate the entire catalogue whenever a runtime's constraints change. A tool that silently stops being offered because a name grew too long for one runtime is an outage nobody will attribute correctly.
