1The descriptor

Eight top-level fields. No others — extensions go inside _meta under a namespaced key (TS-GEN-02). 

{
  "name":        "brokerage_positions_list",       // MUST  ^[a-z][a-z0-9_]{2,63}$ · permanent · §5
  "title":       "List the holdings in an account", // MUST  ≤60 chars · for humans approving/auditing · §5.4
  "description": "Returns the current open holdings …", // MUST  7 parts · ≤2,000 chars · §6

  "inputSchema": {                             // MUST  closed object schema · §7
    "type": "object",
    "properties": { /* every one described */ },
    "required": ["accountId"],                 //       explicit, even when empty
    "additionalProperties": false              //       always false
  },

  "outputSchema": { /* … */ },                  // MUST  required by this standard · §8

  "annotations": {                             // MUST  all four, explicitly · §9
    "readOnlyHint":    true,                    //       changes nothing, anywhere
    "destructiveHint": false,                   //       may be irreversible
    "idempotentHint":  true,                    //       repeat call has no extra effect
    "openWorldHint":   false                    //       reaches outside the firm
  },

  "icons": [ /* … */ ],                        // MAY   decorative only, never semantic

  "_meta": {                                   // MUST  never enters the model's context · §10
    "com.example.tooling/governance": { /* version, lifecycle, riskTier, owner,
        conformanceLevel, dataClassification, containsPii, piiFields, entitlements,
        approval, recordKeeping, cost, rateLimit, dependencies, availability,
        evaluation, deprecation */ }
  }
}
The ratio test

About half the document is prose addressed to a model and a quarter is metadata addressed to a governance process. If yours inverts that, it is an API endpoint wearing a costume.

Why the vocabulary is closed

It lets the linter check annotations against the name, lets policy be written against a name rather than an argument, and lets a reviewer infer a tool's shape before reading a word of prose. Extensions go to the ARB and are granted for new shapes, never for synonyms.

Titles

Yes

"Get order status"
"List the holdings in an account"
"Place a real order — trades money"
Sentence case · ≤60 chars · no trailing period · tier 3 names the consequence, not the operation.

No

"OMS order status retrieval (v2)"
"Order cancellation"
"View order" on a tool that cancels
A title that misstates the operation is a control failure, not a typo.

3The description

The model sees only name, title, description, and the input schema — including every property description. Nothing else. It reads them on every turn.

The seven parts

#PartWriteTest
1Purpose MUST One sentence, active voice, starts with the verb. Could a domain reader say what comes back?
2Use when MUST The questions this answers, phrased the way a customer phrases them. At least two real user phrasings?
3Do not use MUST Nearest neighbors, by exact wire name, with the distinction. Is every tool a confused reader might pick named here?
4Argument semantics Provenance of identifiers, units, cross-field rules. Could a careful caller still supply a well-formed but wrong value?
5Result orientation MUST Shape in a sentence, domain conventions, what empty means. Can the reader compute the right answer from the payload alone?
6Effects, freshness, cost MUST State change, money, staleness, rate limits. Would a compliance reviewer be surprised by an omission?
7Failure guidance The failures a caller can act on, and what to do. For each code: retry, change an argument, or stop?

Descriptions are attack surface

A description is an instruction injected into an agent's context. It is static, reviewed, signed, and hash-pinned — never generated at runtime, never templated with request data (TS-DSC-07, TS-SEC-09). It never instructs the agent about anything but itself (TS-DSC-06, TS-DSC-10).

Shape rules

Root {"type":"object"} + explicit properties + explicit required + "additionalProperties": false. A no-argument tool still declares all four.
Size≤ 12 top-level properties, ≤ 2 levels deep SHOULD. Beyond that the tool is doing two jobs.
NameslowerCamelCase, domain vocabulary, and the same name means the same thing in every tool in the catalog.
BooleansNamed positively, defaulting to the conservative value: includeClosed: false, never excludeClosed: false.
IdentifiersOpaque, prefixed, pattern-constrained — acct_, ord_, inst_.
BoundsEvery array declares maxItems; every free-text string declares maxLength.
RequiredOnly if the tool cannot proceed without it. Marking a field required to make the model "think about it" makes it invent a value.
DefaultsThe narrow, least-surprising choice — and stated in prose, not only in default.

Enumerated values are SCREAMING_SNAKE_CASE and match Appendix D of the standard exactly. Where an enumeration is long or grows often, use a pattern plus a prose pointer to the tool that enumerates valid values. Where it is short and consequential — status, side, time in force, account type — spell it out. When two shapes genuinely differ, the answer is two tools, not a union.

Cut from every payload

Nulls · internal identifiers · hypermedia links · derivations the model can safely redo · per-row repetition of accountId, currency, asOf · pre-formatted display strings.

Numbers

Money, quantities Decimal strings — "62137.50". Never IEEE-754.
CurrencyISO 4217, at the value or the envelope.
FormattingNone in structuredContent. No separators, symbols, or parenthesized negatives.
TimestampsRFC 3339 with explicit UTC offset. Dates that are dates name their time zone.

Empty, partial, stale, truncated

SituationRequired behavior
EmptyisError: false, empty array, and prose saying what the emptiness means. A model shown a bare [] reports an outage about half the time.
Not foundNOT_FOUND for a get; an empty collection for a list. "That order does not exist" and "you have no orders" are different customer answers.
Truncatedtruncated: true and words in the text: "showing 25 of 340". Tell the reader how to narrow, not how to page — a model follows a cursor once, maybe twice, then summarizes what it has as if it were everything.
PartialOnly where the missing part is separable and disclosed. Name what is missing, in the text.
Partial, and the number gates a decision Fail instead. Balances, buying power, anything a trade depends on, must never be returned partially computed (TS-OUT-11).
StaleReturn it with an honest asOf and basis, plus stale: true past the freshness target. Let the reader decide; do not decide by hiding it.

6Annotations, risk tiers, approval

Annotations are advisory — never a control

An annotation is an assertion by whoever wrote the descriptor. For a third-party tool it is self-certification. No security control may depend on one. Controls derive from the risk tier, which the firm sets, reviews, records, and signs. Where the two disagree, the linter fails the build and a human decides which was wrong.

The four hints — defaults are pessimistic

AnnotationDefaultTrue means
readOnlyHintfalse Changes nothing anywhere — caches, counters, search history included.
destructiveHinttrue May be irreversible or overwrite state. Only meaningful when not read-only.
idempotentHintfalse Repeating the identical call has no additional effect. This is what tells a runtime a timeout is safe to retry.
openWorldHinttrue Reaches outside the firm's controlled domain.

All four stated explicitly, even at their defaults — an omission means the reviewer cannot tell whether the author decided or forgot.

Quick classification

Reads only, closed domainT0/T1
Touches customer or position dataT1
Reversible, non-financial writeT2
Moves money or creates exposureT3
Cancels a live orderT3
Disputed at reviewthe higher tier
Cancellation is tier 3

It feels like undoing something. It is not: an order that does not fill in a moving market is a realized economic difference, and you cannot un-cancel.

Entitlements are enforced three times

(a) catalog visibility — an agent is never offered a tool its principal cannot use; (b) the gateway, before invocation; (c) the implementation, against the specific resource in the arguments. (c) is the one that stops cross-customer access and the one most often skipped.

8Errors

Domain and business failures are execution errors: a successful transport response with isError: true. Never raised as transport or protocol errors — those get retried blindly, are often invisible to the model, and reach the customer as "something went wrong".

The fifteen codes

CodeRetryMeans & what the caller does
INVALID_ARGUMENTNo Malformed or schema-violating. Fix the argument; details.violations names it by JSON Pointer.
NOT_FOUNDNo Absent or outside the grant — deliberately indistinguishable, so the tool cannot enumerate identifiers. List first; do not guess another id.
AUTHENTICATION_REQUIREDAfter re-auth Absent, expired, or revoked credentials. The agent cannot fix this.
ENTITLEMENT_DENIEDNo Authenticated, not permitted. Ask the customer to grant access; never retry.
APPROVAL_REQUIREDAfter approval Present the confirmation, re-invoke with the token.
APPROVAL_DENIEDNo A human declined. Stop. Rephrasing and retrying turns one declined trade into three.
PRECONDITION_FAILEDSometimes Stale confirmation token, missing idempotency key, version mismatch. details names it.
CONFLICTNo State does not permit it — already filled, account closed. Re-read the entity first.
BUSINESS_RULE_VIOLATIONNo Well-formed, permitted, and the domain said no. The request was fine; the world declined. Explain, do not retry.
RATE_LIMITEDAfter the wait Honor retryAfterSeconds. Recurrence means the agent is looping.
TIMEOUTIf idempotent Retry only with an idempotency key or a true idempotentHint; otherwise re-read state to find out whether it happened.
UPSTREAM_UNAVAILABLEWith backoff details.system names which, so the agent can say what is unavailable rather than apologizing vaguely.
DATA_INCOMPLETEWith backoff Computable only partially, and the tool refused to return a misleading figure. Distinct from upstream failure: the tool did reach its sources.
NOT_SUPPORTEDNo Well-formed request for something this tool does not do. remediation names the tool that does.
INTERNAL_ERROROnce traceId and nothing else of substance. Common occurrence means errors are being mapped lazily.
The distinction that matters most

INVALID_ARGUMENT = the caller is wrong; change the argument and it works. BUSINESS_RULE_VIOLATION = the caller is fine and reality declined — insufficient buying power, market closed, instrument halted. A tool that conflates them makes every agent built on it worse: it retries a doomed order, then tells the customer "invalid request" when the honest answer was "the market is closed".

Remediation rules

  • An instruction in the imperative, naming the argument to change or the tool to call instead. Apologies are not remediation.
  • State the permissible bound — the max quantity, the valid window, the required level. "Too large" without "how large" forces a guessing loop.
  • Where a retry is futile, say "do not retry" explicitly. Models are biased toward retrying; retryable: false alone is markedly weaker.
  • Enumerate every validation violation, not just the first.

Never in an error payload

  • Stack traces, exception classes, line numbers → INTERNAL_ERROR + traceId
  • Raw upstream text, vendor codes, SQL → a mapped taxonomy code
  • Hostnames, queue names, topology → details.system as a business name
  • Full account numbers, government ids, dates of birth → the masked form
  • Any data about another principal → nothing; return NOT_FOUND
  • Whether an id exists but is not permitted → NOT_FOUND, uniformly

9Decisions you will make repeatedly

One tool or two?

If…Then
Stating the user question takes two sentences with an "or" in the middleTwo tools
One argument value makes it destructiveTwo tools — annotations, tier, approval, and audit cannot all be right at once
You are reaching for oneOf with more than three branchesTwo tools
The two candidates differ only in cardinality (one vs many)One tool — a list that returns everything a get would
A common question needs ≥3 calls plus a domain convention the model must knowOne composite — move the knowledge into the tool where it can be tested
You cannot write the one sentence that distinguishes two toolsMerge or re-scope, and put that sentence in both descriptions

Does it need an idempotency key?

create · place · update · replace → yes, required, deduped ≥24 h, replay returns the original result, same key + different arguments → CONFLICT.  ·  cancel · delete → naturally idempotent.  ·  Read tools → no.  ·  Say it in the description too: models supply a key far more reliably when told what it is for than when it merely appears in the schema.

How long will it take?

DurationPattern
< 10 sSynchronous. Declare the latency class.
10 s – minutesJob pattern: ..._start returns a jobId; ..._status reports progress. The start tool is not read-only even if the result is.
Minutes – hoursJob pattern + out-of-band notification. The agent must not poll in a loop; return nextPollAfterSeconds.
Any timeoutState explicitly whether the underlying operation may still complete. "May still have been placed" is a different instruction from "was not placed", and the agent cannot work it out.

Polling anything with a lifecycle

Return isTerminal and say in the description that a terminal entity must never be polled again — this one flag removes most wasteful polling. Return nextPollAfterSeconds scaled to the entity (2 s for a market order, 60 s for a transfer). Prefer telling the customer the firm will notify them over having an agent hold a conversation open as a timer.

10Security, audit, versioning

The five security principles

The agent has no authority of its own Every action runs as a principal, with that principal's scopes. There is no service account "the assistant" uses to read customer accounts — that account is a standing breach waiting for a prompt.
Least privilege, per invocation Scopes declared per tool, checked per invocation, against the specific resource — not once per session.
Model output is untrusted input Validate and authorize arguments as though they came from an anonymous internet client, because in the relevant sense they did.
Tool output is untrusted input to the model Customer- and counterparty-supplied strings are data, never instruction.
Controls live where they cannot be talked out of The gateway and the implementation. Not the description, not the annotations, not the system prompt — all three are inputs to a system that can be persuaded.

Non-negotiables

  • No argument asserts identity, role, or tenancy (TS-SEC-02)
  • Authorize the specific resource in the arguments, every call (TS-SEC-08)
  • Never forward an inbound token downstream — exchange it for one audienced to that system (TS-SEC-10)
  • No credentials in arguments, results, errors, or descriptions (TS-SEC-03)
  • Confirmation tokens: bound to principal + tool + argument hash, ≤120 s, single use (TS-SEC-01)
  • Kill switch for every T2+ tool, ≤60 s, no deployment (TS-SEC-12)
  • Descriptor hashes pinned; a changed hash is refused, not tolerated (TS-SEC-09)
  • Never ask for credentials or one-time codes through a tool's request for input (TS-SEC-05)

Untrusted text in this domain

Account nickname · order memo and client order id · instrument name and description · transfer memo and beneficiary name · corporate action notes · upstream error text.

Length-cap it, strip control characters and markup, delimit and label it as untrusted in the text rendering, and never interpolate it into a sentence that reads as narration by the tool (TS-SEC-11).

Alert on these

  • Identical invocation repeated 3× in a conversation
  • Repeated ENTITLEMENT_DENIED or NOT_FOUND — the signature of enumeration
  • Approval denied, then retried with altered arguments — the highest-signal event in the estate; block the conversation
  • Descriptor hash mismatch at a runtime

The audit record — one per invocation, every path

traceId · conversationId · turnId · principal and how the identity was established · agent and version · toolName · toolVersion · descriptorHash · validated arguments with piiFields masked · outcome (success, or code + domainCode, or the policy decision) · resultDigest with size and record count · approval (mode, who, when, the argument hash they approved, or the decline) · entitlements presented and the decision · latencyMs · upstreamCalls.

The descriptor hash is not optional

Without it you cannot reconstruct what the model was told when it made the call — the first question asked in any investigation. For tier 3, the record must also carry the confirmation exactly as the principal saw it and their response. "The agent placed an order" is a summary of a record, not a record.

A breaking change is a new tool name with a _v2 suffix, running alongside the original for the full window. The model has no upgrade schedule.

Deprecation, in order

  1. Announce — lifecycle: deprecated + {since, sunset, successor, migrationNote}. Minimum 90 days or one reporting cycle.
  2. Stop new grants — no longer offered to audiences that do not already have it.
  3. Warn out of band — a notice in the result's _meta. Do not change the description: it costs tokens every turn, and a model told a tool is deprecated behaves unpredictably rather than migrating.
  4. Measure — track by audience, contact each remaining consumer.
  5. Retire — NOT_SUPPORTED naming the successor for 90 days, then withdraw. The name is never reused.

Evaluation thresholds

Selection accuracy≥95% (T1), ≥98% (T3)
Refusal accuracy≥95%, ≥99% (T3)
Argument accuracy≥98%
Interpretation accuracy≥98%; 100% on domain conventions

Every suite carries: nearest-neighbor confusions · convention traps (short position, option contracts, unsettled cash, retirement account, partial fill, rejection) · empty and degraded results · refusals · injection. Re-run on every change, including a change to nothing but the prose.

The pattern behind the patterns

Twelve of the thirteen are the same mistake: optimizing for the convenience of the team building the tool rather than the reliability of the caller consuming it. Each shortcut moves work from a place where it can be tested to a place where it can only be hoped for.

14Review checklist

The working document for a review meeting. Items in bold are gating: a failure means the tool does not ship. Full version with commentary is Appendix E of the standard.

Identity & description

  • TS-NAM-01 Name matches the grammar; domain segment present; final segment in the vocabulary
  • TS-NAM-02 Globally unique; never used before
  • TS-NAM-07 Title ≤60 chars, human-readable, names the consequence at tier 3
  • TS-DSC-01 Purpose, "use when", "do not use", result orientation, effects
  • TS-DSC-05 Nearest neighbors named by exact wire name
  • TS-DSC-02 ≤2,000 characters
  • TS-DSC-06 No instructions about agent behavior outside this tool
  • TS-DSC-07 Static, reviewed, not templated at runtime
  • §18.3 Every domain convention that could produce a wrong answer is stated

Schemas

  • TS-INP-01 Closed object; explicit required; additionalProperties: false
  • TS-INP-09 Every finite-valued parameter is an enum from Appendix D
  • TS-INP-07 Identifiers prefixed and pattern-constrained
  • TS-INP-08 maxItems on arrays, maxLength on free text
  • TS-INP-14 Every parameter description says more than its type
  • TS-INP-12 Defaults are the conservative choice
  • TS-INP-17 No identity, credential, query language, discriminator, or safety flag
  • TS-INP-16 No parameter the tool cannot honor
  • TS-OUT-01 Output schema declared; both content and structuredContent on every path
  • TS-OUT-03 asOf and basis on every figure that can change
  • TS-OUT-07 completeness present; truncation stated in the text
  • TS-OUT-13 Money and quantities are decimal strings with a currency
  • §8.6 Empty is success; partial is disclosed or refused

Errors

  • TS-ERR-01 Domain failures are execution errors, not transport errors
  • TS-ERR-02 Imperative remediation naming the next action
  • TS-ERR-03 Constraint violations state the permissible bound
  • TS-ERR-06 Every upstream failure mapped and tested; default branch alerts
  • §11.5 No stack traces, hostnames, upstream prose, or unmasked identifiers
  • §11.3 INVALID_ARGUMENT and BUSINESS_RULE_VIOLATION not conflated

Classification & control

  • TS-ANN-01 All four annotations, consistent with the operation verb
  • TS-ANN-03 Risk tier declared and defensible; state-changing ⇒ tier 2+
  • TS-ANN-04 Tier 3 has a confirmation template a human can act on
  • TS-ANN-05 Approval bound to an argument hash, and expires
  • TS-SEC-07 Non-idempotent tools require a key; dedupe 24 h
  • TS-SEC-02 No identity accepted from the caller
  • TS-SEC-08 Resource-level authorization shown by a negative test
  • TS-SEC-10 No token passed through downstream
  • TS-SEC-11 Externally-sourced free text neutralized and labeled
  • TS-SEC-12 Kill switch for tier 2+, tested

Governance & evidence

  • TS-GOV-01 Named owning team with a paging escalation path
  • TS-GOV-02 Minimum necessary data; classification and PII mapped
  • TS-GOV-03 Entitlements at catalog, gateway, and implementation
  • TS-GOV-04 Per-principal rate limit declared
  • TS-OBS-01 Audit record on every path, including the descriptor hash
  • TS-VER-04 Evaluation suite exists and has run against this version
  • §27.3 Selection, refusal, argument, interpretation thresholds met
  • TS-SEC-09 Descriptor hash registered with the catalog
  • TS-CAT-05 Exceptions recorded with a compensating control and an expiry

Catalog fit

  • TS-CAT-01 Answers one question a user actually asks
  • TS-CAT-02 The agent's catalog stays within 25 tools
  • §12.5 One sentence distinguishes it from its nearest neighbor — in both descriptions
  • §12.3 No common question needs ≥3 calls plus a convention the model must know

Six questions to ask out loud

  1. "Read me the description." Unreadable aloud, or ninety seconds long, or no sentence starting "Do not use" — not ready.
  2. "What is the nearest tool, and what sentence tells them apart?" A pause is a confusability problem.
  3. "What does the customer see if this is wrong?" A specific wrong sentence, not "an error".
  4. "Show me the negative test" where the customer asks for someone else's account. Not the code — the test.
  5. "Who is paged at 2am, and what do they turn off?"
  6. "What did the evaluation say about the cases where it should refuse?" Selection accuracy is easy to score well on. Refusal accuracy is where the risk lives.
