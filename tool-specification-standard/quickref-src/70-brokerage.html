Conventions the model must be told

Every row is a fact that turns a correct payload into an incorrect customer answer if the reader does not know it. Discharge each one in the description, in the payload, or by moving the work into the tool.

Confusable pairs — put the distinguishing sentence in both descriptions

positions_list ↔ orders_list An order becomes a position only when it fills. "Did my trade go through" is orders; "what do I own" is positions.
balances_get ↔ positions_list Balances are cash and buying power; positions are holdings.
balances_get ↔ transactions_list A balance is a state; a transaction is an event. "Why did my cash drop" is transactions.
orders_list ↔ executions_list One order, many executions at different prices. "What price did I get" may need executions.
order_check ↔ order_preview ↔ order_place "Can I?" / "What exactly would happen?" (and a token) / does it. Only the third trades.

The timeout remediation, verbatim — three sentences, three prevented incidents

"Do not tell the customer the order failed. Either retry brokerage_order_place with the same idempotencyKey, which will return the original result if the order was placed, or call brokerage_orders_list to check. Never place a second order with a new key."

The kitchen-sink tool
one tool, an action enum		 Annotations, risk tier, approval policy, and the audit record all become wrong at once. The audit says orders_manage when what happened was a cancellation. TS-NAM-06
The dryRun flag One token in a model-generated object is the only thing between a simulation and a real trade. TS-INP-13

The rename Six years of audit records silently change meaning. A record-keeping defect, not a refactor. TS-NAM-11
The pattern behind the patterns

Twelve of the thirteen are the same mistake: optimizing for the convenience of the team building the tool rather than the reliability of the caller consuming it. Each shortcut moves work from a place where it can be tested to a place where it can only be hoped for.
