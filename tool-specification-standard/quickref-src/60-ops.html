10Security, audit, versioning

The five security principles

The agent has no authority of its own Every action runs as a principal, with that principal's scopes. There is no service account "the assistant" uses to read customer accounts — that account is a standing breach waiting for a prompt.
Least privilege, per invocation Scopes declared per tool, checked per invocation, against the specific resource — not once per session.
Model output is untrusted input Validate and authorize arguments as though they came from an anonymous internet client, because in the relevant sense they did.
Tool output is untrusted input to the model Customer- and counterparty-supplied strings are data, never instruction.
Controls live where they cannot be talked out of The gateway and the implementation. Not the description, not the annotations, not the system prompt — all three are inputs to a system that can be persuaded.

Non-negotiables

  • No argument asserts identity, role, or tenancy (TS-SEC-02)
  • Authorize the specific resource in the arguments, every call (TS-SEC-08)
  • Never forward an inbound token downstream — exchange it for one audienced to that system (TS-SEC-10)
  • No credentials in arguments, results, errors, or descriptions (TS-SEC-03)
  • Confirmation tokens: bound to principal + tool + argument hash, ≤120 s, single use (TS-SEC-01)
  • Kill switch for every T2+ tool, ≤60 s, no deployment (TS-SEC-12)
  • Descriptor hashes pinned; a changed hash is refused, not tolerated (TS-SEC-09)
  • Never ask for credentials or one-time codes through a tool's request for input (TS-SEC-05)

Untrusted text in this domain

Account nickname · order memo and client order id · instrument name and description · transfer memo and beneficiary name · corporate action notes · upstream error text.

Length-cap it, strip control characters and markup, delimit and label it as untrusted in the text rendering, and never interpolate it into a sentence that reads as narration by the tool (TS-SEC-11).

Alert on these

  • Identical invocation repeated 3× in a conversation
  • Repeated ENTITLEMENT_DENIED or NOT_FOUND — the signature of enumeration
  • Approval denied, then retried with altered arguments — the highest-signal event in the estate; block the conversation
  • Descriptor hash mismatch at a runtime

The audit record — one per invocation, every path

traceId · conversationId · turnId · principal and how the identity was established · agent and version · toolName · toolVersion · descriptorHash · validated arguments with piiFields masked · outcome (success, or code + domainCode, or the policy decision) · resultDigest with size and record count · approval (mode, who, when, the argument hash they approved, or the decline) · entitlements presented and the decision · latencyMs · upstreamCalls.

The descriptor hash is not optional

Without it you cannot reconstruct what the model was told when it made the call — the first question asked in any investigation. For tier 3, the record must also carry the confirmation exactly as the principal saw it and their response. "The agent placed an order" is a summary of a record, not a record.

Metrics worth the instrumentation

Selection accuracyWas this the right tool for the question? Sampled and human-labeled. The most valuable metric in the estate
Refusal accuracyCorrectly left alone when it should not answer
Repeat-call rate>15% = descriptor defect. Fix the prose, not the agent
Truncation rateHigh = wrong granularity
Post-call correctionUser corrects the agent right after this tool returns
Error rate by codeA rise in BUSINESS_RULE_VIOLATION is a market condition; a rise in INVALID_ARGUMENT is a descriptor defect
Approval decline rateNear zero means the confirmation is being rubber-stamped
Silent wrongnessSucceeded, valid data, wrong answer. Only measurable by reading conversations. Budget for it

Breaking vs compatible

Optional input parameter with a safe defaultok
New output fieldok
New member of an output enumok
Relaxing a constraintok
Clarifying proseencouraged
Optional → requiredbreaking
Removing or renaming any fieldbreaking
New member of an input enumbreaking in effect
Tightening a constraintbreaking
Changing a unit, convention, or signbreaking & dangerous
Changing omission behaviorbreaking
Raising the risk tierannounce it

A breaking change is a new tool name with a _v2 suffix, running alongside the original for the full window. The model has no upgrade schedule.

Deprecation, in order

  1. Announce — lifecycle: deprecated + {since, sunset, successor, migrationNote}. Minimum 90 days or one reporting cycle.
  2. Stop new grants — no longer offered to audiences that do not already have it.
  3. Warn out of band — a notice in the result's _meta. Do not change the description: it costs tokens every turn, and a model told a tool is deprecated behaves unpredictably rather than migrating.
  4. Measure — track by audience, contact each remaining consumer.
  5. Retire — NOT_SUPPORTED naming the successor for 90 days, then withdraw. The name is never reused.

Evaluation thresholds

Selection accuracy≥95% (T1), ≥98% (T3)
Refusal accuracy≥95%, ≥99% (T3)
Argument accuracy≥98%
Interpretation accuracy≥98%; 100% on domain conventions

Every suite carries: nearest-neighbor confusions · convention traps (short position, option contracts, unsettled cash, retirement account, partial fill, rejection) · empty and degraded results · refusals · injection. Re-run on every change, including a change to nothing but the prose.
