0.1Why the firm needs this

Three things have happened at once. Business lines are shipping agents. Vendors are shipping assistants that expect to be handed capabilities. And the safest, most valuable capabilities we own — an account's positions, a customer's buying power, the status of a live order — are exactly the ones an agent most wants to reach.

In the absence of a standard, each team invents its own answers to the same twelve questions: what the tool is called, how much it should say about itself, what it returns when there is nothing to return, whether the caller may retry, who the caller is, what happens when the upstream system is down, and who signed off on any of it. The result is not merely inconsistent. It is unreviewable: an architecture board cannot assess forty tools that each describe themselves differently, and a model cannot reliably choose between them either.

This standard fixes the shape of the contract so that the interesting questions — is this capability safe to expose, to whom, under what supervision — are the only ones left on the table at review time.

On protocol neutrality

This standard deliberately specifies a contract, not a wire protocol. Where a runtime imposes a stricter limit than this standard — a shorter name budget, a smaller payload ceiling — the stricter limit wins and §17.5 explains how to record that.

1Scope, audience, and conformance

A tool is a capability of the firm, described precisely enough that a language model can decide to use it, use it correctly, and be held to account for having used it. This section fixes what "precisely enough" means and how conformance is judged.

1.1What a conformant tool is

A conformant tool is three artifacts that ship and version together:

ArtifactDefinition
The descriptor A machine-readable document declaring the tool's name, its purpose in prose addressed to a model, a JSON Schema for its inputs, a JSON Schema for its outputs, behavioral annotations, and a governance block. Part II specifies it in full; Appendix A is its schema.
The implementation Code that accepts an invocation conforming to the input schema, performs authorization independently of anything the model said, and returns a result envelope conforming to the output schema — or a structured error that tells the caller what to do next.
The evidence Conformance test results, evaluation transcripts, a security review record, and an owner. A tool without evidence is a prototype, whatever else it is.

The standard governs all three. It is deliberately silent on how the tool is transported to the model, what framework implements it, and which model consumes it — those are substitutable, and every one of them has been substituted at least once already.

1.2Conformance language and rule identifiers

The keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are used as defined in RFC 2119 and RFC 8174. Every normative rule carries a stable identifier of the form TS-AREA-NN:

PrefixAreaPrefixArea
TS-GENGeneral and descriptor structure TS-ANNAnnotations and risk tiers
TS-NAMNaming and identity TS-GOVGovernance metadata
TS-DSCDescriptions TS-SECSecurity and trust
TS-INPInput schemas TS-OBSObservability and audit
TS-OUTOutput schemas and envelopes TS-VERVersioning and lifecycle
TS-ERRErrors TS-CATCatalog and registration

Rule identifiers are permanent. A rule that is withdrawn is marked withdrawn and its number is never reused, so a review comment reading "fails TS-INP-07" means the same thing in five years as it does today. The linter in tools/lint-descriptors.py reports findings by rule identifier, which is what makes the checklist in Appendix E mechanically enforceable rather than a matter of taste.

1.3Conformance levels

Not every tool needs the same scrutiny. A tool that reads a public holiday calendar and a tool that reads a customer's buying power are not comparable risks, and a standard that pretends otherwise gets routed around. Four levels:

LevelNameRequirementsPermitted exposure
L0 Registered Descriptor exists in the catalog and parses against Appendix A. Nothing else. Development and test environments only. Never reachable from a production agent.
L1 Conformant Every MUST in this standard is satisfied and the linter is clean. Named owning team. Structured errors. Audit events emitted. Internal, employee-facing agents. Non-customer data. Risk tier 0 or 1 only.
L2 Certified L1, plus: security review recorded; evaluation evidence (§27.3) showing correct selection and correct refusal; entitlement mapping signed off by the data owner; an SLO and a kill switch; retention and record-keeping wired to the firm's archive. Anything touching customer data, money, or positions. Mandatory for every tool in Part IV.
L3 Externally exposed L2, plus: data-egress assessment for the receiving party; contractual controls on model providers and vendor agents; per-tenant isolation proof; independent red-team result no older than twelve months. Tools reachable by an agent the firm does not operate — a vendor assistant, a customer's own agent, a third-party platform.

TS-GEN-01 MUST Every tool reachable from a production agent MUST hold at least Level 1. Every tool that reads customer data, moves money, changes an order, or writes to a system of record MUST hold Level 2.

1.4Relationship to the firm's API standard

The firm already has a REST API standard, and most tools will be built over APIs that conform to it. The two standards are complementary and occasionally in tension, because they serve different callers. Where they differ, the difference is deliberate:

ConcernREST API standardThis standard
Caller A developer who read the documentation once and encoded their understanding into code that then runs unchanged. A model that reads the description on every single call and has never seen the documentation.
Granularity Resource-oriented. One resource, the standard verbs, composition left to the client. Task-oriented. One tool per decision the agent has to make, even when that means joining three resources server-side (§12).
Error signaling HTTP status plus a problem document. The status code carries real meaning. A structured error inside a successful transport response. The model never sees a status code, so the payload must carry everything (§11).
Discovery Hypermedia links let a client navigate without hard-coding URLs. Links are not affordances a model can be trusted to follow blindly. Capability is expressed as the presence of a tool and as explicit flags in the result (§8.3).
Payload size Bounded by bandwidth and client memory; a 2 MB response is unremarkable. Bounded by the model's context window and by cost per call. A 2 MB response is a defect (§13).
Versioning Path or header version, long support windows, clients upgrade on their schedule. The model has no schedule. Additive change only; a breaking change is a new tool name (§17).
The one-line summary

A REST API is a contract with a programmer. A tool is a contract with a reader who will never ask a clarifying question, never read the changelog, and never remember what happened last time. Everything else follows from that.

2What a tool is

The descriptor is read by three different audiences with three different failure modes. Most bad tools are bad because they were written for exactly one of them.

2.1One artifact, three audiences

AudienceReads it forFails by
The model
at selection time		 Deciding whether this tool, out of the forty in context, is the one that answers the user's question — and what to put in each argument. Picking a plausible neighbor (orders_list when it wanted positions_list), inventing an argument value that looks like the examples, or calling nothing at all because no description matched.
The runtime
at invocation time		 Validating arguments, resolving the caller's identity and entitlements, deciding whether to demand human approval, metering, logging, and enforcing timeouts. Being unable to decide anything, because the descriptor declares no risk tier, no entitlement, and no idempotency — so the runtime either blocks everything or waves everything through.
The human
at review and incident time		 Approving the tool for release; approving a specific invocation in a confirmation dialog; reconstructing, six months later, what an agent did to a customer's account and why. Reading {"a": "acct_01HQ8Z", "q": 100} in an approval dialog and having no idea what they are being asked to authorize.

These pull in different directions, and the standard resolves the pull the same way every time: the model's needs decide the prose, the runtime's needs decide the structure, and the human's needs decide what must never be omitted. A description written only for the model produces an unauditable tool. A descriptor written only for the runtime produces a tool the model never selects.

2.2A tool is not an endpoint

The most common failure in a first tool catalog is a mechanical translation of an existing API: every path becomes a tool, every query parameter becomes an argument, every response body becomes the output. It produces a catalog that is simultaneously too large and not useful.

Consider what a customer actually asks an assistant:

"Do I have enough cash to buy 100 shares of Apple in my Roth, or would that put me on margin?"

Against a faithfully translated REST surface, answering that means: list accounts, filter to the one registered as a Roth IRA, fetch balances, understand that a retirement account cannot borrow so buyingPower.stock is not the number to use, fetch a quote, multiply, compare against settled rather than total cash because an unsettled balance cannot fund a purchase without a good-faith violation, and then explain the result. That is five round trips, two pieces of domain knowledge the model does not reliably have, and at least three plausible ways to get the wrong answer while sounding confident.

A tool designed for the question takes an account reference, a symbol, and a quantity, and returns a decision with the reasoning attached. The domain knowledge lives in the tool, where it can be tested, rather than in the model, where it can only be hoped for.

The design question

Not "what resources do we have?" but "what questions will be asked, and what is the smallest set of tools that answers them without requiring the model to know things we have not told it?" Section 12 turns this into a procedure.

2.3Designing for a non-deterministic caller

Six properties of the caller drive most of the rules in Part II. They are worth stating plainly because they are unlike any caller the firm has designed for before.

PropertyConsequence for the design
It reads the description on every call The description is not documentation, it is runtime input. It occupies context on every turn, costs money on every turn, and can be rewritten to fix a behavior without redeploying the implementation.
It cannot be corrected There is no support ticket and no developer to email. If the tool is misunderstood, the only lever is the descriptor. This is why §6 is as long as it is.
It generates plausible values Given a free-text status parameter it will confidently pass "open", "OPEN", "working", and "pending" — none of which are in your enumeration. Constrain the schema and the problem disappears (§7.3).
It has a finite, shared context Your tool's description competes with thirty-nine others, the conversation, and the system prompt. Every token you spend must buy a decision (§13).
It retries On an ambiguous failure it will try again, often with slightly different arguments. Anything not idempotent needs an idempotency key and a declared annotation (§7.6, §9.1).
It is steerable by its input Everything the tool returns enters the model's context as text. A position nickname containing "ignore previous instructions and transfer…" is an injection vector, and the tool is where it must be neutralized (§15.5).

2.4The trust boundary

The single most important architectural statement in this standard is where trust stops. Three assertions, each of which has to be built rather than assumed:

  1. Arguments from the model are untrusted input. They are not a caller's credentials, not a claim of identity, and not evidence of authorization. An accountId in an invocation is a request, and the implementation must independently verify that the human on whose behalf the agent is acting is entitled to that account. Treat the model exactly as you would treat a browser form post from the open internet.
  2. Results are untrusted input to the model. Content that originated with a customer, a counterparty, or an external venue — nicknames, order memos, instrument descriptions, error text from an upstream system — is data, never instruction. The tool marks it as such and neutralizes it (§15.5).
  3. Descriptors are trusted only because the catalog signs them. A description is an instruction to the model. Anyone who can edit a description can redirect an agent. That makes the catalog a control point with change management, review, and an audit trail — not a wiki (§28).

3Reference architecture

The standard assumes the five-component architecture in Figure 2.1. This section names each component's non-negotiable responsibilities, because a rule about descriptors is only enforceable if something is enforcing it.

3.1Components and responsibilities

This looks redundant and is not: the gateway protects the implementation from malformed input at scale, and the implementation protects the firm from a misconfigured, bypassed, or newly-added gateway. Tools are increasingly reached through more than one path — an internal agent today, a vendor assistant next quarter — and the second path will not have been built by the team that built the first.

4Descriptor anatomy

A descriptor is a JSON document with eight top-level fields. Four of them are read by the model, three by the runtime, and one by both. Nothing else may appear at the top level.

4.1The eight fields

FieldRequiredRead byPurpose
nameMUSTmodel, runtime The stable, globally unique, machine-readable identifier used to invoke the tool. Also the primary key in the catalog and in every audit record (§5.1).
titleMUSThuman A short human-readable label for approval dialogs, audit views, and catalog listings. Never a substitute for the description (§5.4).
descriptionMUSTmodel The prose contract that tells the model what this tool does, when to reach for it, when not to, and how to read what comes back (§6).
inputSchemaMUSTmodel, runtime A JSON Schema 2020-12 object schema describing the arguments. Doubles as the validation contract and as instruction to the model (§7).
outputSchemaMUSTmodel, runtime A JSON Schema 2020-12 object schema describing the structured payload the tool returns. Optional in most runtimes; required by this standard (§8).
annotationsMUSTruntime, human Four boolean behavioral hints — read-only, destructive, idempotent, open-world — that let a runtime reason about a tool it has never seen (§9).
iconsMAYhuman Display icons for catalog and approval surfaces. Cosmetic, never semantic.
_metaMUSTruntime, human Namespaced out-of-band metadata. This standard requires one member — the governance block — and permits others (§10). The leading underscore marks the field as never rendered into the model's context.

TS-GEN-02 MUST A descriptor MUST NOT carry top-level fields other than the eight above. Extensions go inside _meta under a namespaced key. A runtime that encounters an unknown top-level field MUST reject the descriptor rather than ignore it: silent tolerance is how two teams end up with two incompatible meanings for the same word.

5Identity and naming

The name is the one part of a tool that can never be changed. It is the invocation key, the audit key, the catalog key, and — because the model reads it before it reads anything else — a meaningful part of the description.

5.1The wire name grammar

TS-NAM-01 MUST A tool name MUST match ^[a-z][a-z0-9_]{2,63}$ — lowercase ASCII letters, digits, and underscore; starting with a letter; between 3 and 64 characters.

The grammar is deliberately narrower than any runtime requires. The intersection of the name rules imposed by current tool-calling interfaces is roughly [A-Za-z0-9_-]{1,64}, and interfaces disagree about case sensitivity, about whether a dot or a hyphen is permitted, and about the length ceiling. Choosing the intersection — and then narrowing to lowercase and underscore — means a tool can be published anywhere without a rename, and a rename is the one change this standard cannot make cheap.

Do not use dots in wire names

A dotted name such as brokerage.positions.list reads beautifully and is rejected or silently mangled by several widely-deployed tool-calling interfaces, some of which use the dot as a namespace separator of their own. Dotted form is reserved for the catalog identifier (§5.2), which never crosses the wire.

5.1.1Segment structure

Names are two to four underscore-separated segments:

<domain>_<entity>_<operation>              brokerage_positions_list
<domain>_<entity>_<qualifier>_<operation>  brokerage_order_option_place
<domain>_<operation>                       brokerage_search        // rare; only for a domain-wide capability
SegmentRules
domain A business capability domain from the firm's domain register — brokerage, payments, onboarding, research. Never a team name, a system name, a vendor name, or an application name. Teams reorganize and systems get replaced; the business capability outlives both, and the name has to outlive both with it.
entity The domain noun the tool acts on. Singular when the tool addresses one (order, account); plural when it addresses a collection (orders, positions). That singular/plural distinction is load-bearing: it is the fastest signal the model has for "one" versus "many".
operation A verb from the closed vocabulary in §5.3. Always last.
qualifier Used only to disambiguate genuinely different operations on the same entity — order_option_place versus order_equity_place. If you need two qualifiers, you have two tools that should be one.
RuleLevelRequirement
TS-NAM-02MUST Names MUST be globally unique across the firm's catalog, compared case-insensitively and with underscores ignored. orders_list and ordersList collide.
TS-NAM-03SHOULD Names SHOULD be 40 characters or fewer. Long names crowd every prompt and get truncated in audit and approval surfaces.
TS-NAM-04MUST The name MUST NOT encode a version (_v2) unless the tool is a deliberate breaking successor published under §17.3, in which case it MUST.
TS-NAM-05NEVER Names MUST NOT contain an environment, region, tenant, or vendor (_uat, _emea, _fiserv). Those are deployment facts; a model that can see them will eventually reason about them.

5.2Namespaces and the catalog identifier

Each tool carries two identifiers. They are mechanically derivable from one another, which is the point.

IdentifierFormUsed for
Wire namebrokerage_positions_list Invocation, model context, audit records, metrics labels.
Catalog identifierbrokerage.positions.list Registry lookup, documentation URLs, policy rules, entitlement mapping, wildcard expressions such as brokerage.orders.*.

Policy is expressed against catalog identifiers because wildcards over dotted namespaces are readable and auditable: allow brokerage.*.list; require-approval brokerage.order.place. Trying to express the same thing over underscores produces rules nobody can review.

Collision across providers

When an agent is given tools from several providers at once — an internal catalog plus a vendor's — names collide, and a collision is not a cosmetic problem: it is an authority confusion problem, because the model cannot tell which account_get it is calling. Runtimes resolve this by prefixing, and their prefixes are not under our control. The firm's defense is the mandatory <domain> segment, which makes an unqualified collision with an external tool vanishingly unlikely, plus the catalog's uniqueness check at publish time (TS-NAM-02).

5.3The operation vocabulary

Operations come from a closed vocabulary. A closed vocabulary lets a reviewer, a policy engine, and a model each infer a tool's shape from its name before reading a word of prose — and lets the linter check that annotations match the name.

VerbMeansExpected annotationsReturns
getRetrieve one identified entity. read-only, idempotentOne object, or a NOT_FOUND error.
listRetrieve a bounded, filterable collection. read-only, idempotentAn array plus pagination and completeness metadata. Empty is a success.
searchRank a collection by relevance to a query, where the caller cannot express the filter structurally. read-only, idempotentA ranked array with scores. Empty is a success.
summarizeReturn a derived, aggregated view rather than the underlying records. read-only, idempotentOne aggregate object, with the aggregation basis stated.
checkEvaluate a condition and return a decision with reasons — the "can I?" tool. read-only, idempotentA verdict, the reasons, and the numbers behind it.
previewCompute the effect of a proposed change without applying it. read-only, idempotentProjected outcome, costs, warnings, and a short-lived token to execute it.
create, placeBring a new entity into existence. place is the domain term for orders. not read-only, not destructive, not idempotent without a keyThe created entity and its identifier.
update, replaceModify an existing entity. not read-only, destructive, conditionally idempotentThe updated entity and what changed.
cancelStop something in flight. Distinct from delete: the record survives. not read-only, destructive, idempotentThe entity's new state.
deleteRemove an entity. Rare in a regulated domain and always suspicious. not read-only, destructive, idempotentConfirmation and what was removed.
exportProduce a document or file for a human, returned by reference. read-only, not idempotentA reference, a media type, and a size — never the bytes (§8.5).

TS-NAM-06 MUST The final segment MUST come from the vocabulary above. Proposals to extend it go to the Architecture Review Board and are granted for genuinely new shapes of operation, not for synonyms. Explicitly rejected: do, run, execute, process, handle, manage, perform, fetch, query, call, and any noun used as a verb.

Why manage is banned, specifically

brokerage_orders_manage with an action parameter is the single most common anti-pattern in a first tool catalog. It looks economical — one tool instead of four — and it is strictly worse in every dimension that matters: the model must choose an action from prose rather than from the tool list; the annotations cannot be accurate, because one branch is read-only and another cancels a live order; the risk tier cannot be accurate for the same reason; approval policy must be written against an argument value instead of a tool name; and the audit record says orders_manage when what happened was a cancellation. Four tools cost four descriptions. One tool costs you the entire control model. See §25.1.

5.4Titles, icons, and display

The title is what a human sees when they are asked to approve something at 11pm, and what appears in an audit export a compliance analyst reads two years later.

RuleLevelRequirement
TS-NAM-07MUST Every descriptor MUST carry a title: sentence case, no trailing punctuation, 60 characters or fewer, understandable to someone who does not know the system — "Get order status", not "OMS order status retrieval (v2)".
TS-NAM-08MUST The title MUST describe the same operation as the name. A title that says "View" on a tool that cancels is a control failure, not a typo.
TS-NAM-09SHOULD Titles of state-changing tools SHOULD lead with the verb and name the consequence: "Cancel a working order", not "Order cancellation".
TS-NAM-10MAY Icons MAY be supplied for catalog and approval surfaces. Provide SVG with a light and a dark variant. Icons are decoration: no control, policy, or model behavior may depend on one.

5.5Name stability

TS-NAM-11 MUST A published tool name is permanent. It MUST NOT be reused for a different capability, and a capability MUST NOT be renamed. A name change is modeled as a new tool plus deprecation of the old one under §17.4.

The reason is sharper than ordinary API hygiene. A tool name appears in audit records that are retained for six years or more, in policy rules, in evaluation suites, in incident reports, and in the memory of every agent conversation that is still open. Reusing brokerage_order_cancel for a different operation silently rewrites the meaning of every historical record that mentions it — which, in a regulated firm, is a record-keeping defect and not merely an inconvenience.

6The description: the model-facing contract

The description is the highest-leverage field in the descriptor and the one most often written last, in a hurry, by copying a Javadoc comment. It is not documentation. It is runtime input to a decision that will be made hundreds of times a day without human review.

6.1What the model actually sees

When an agent is deciding what to do, the only things it knows about your tool are its name, its title, its description, and its input schema — including every description inside that schema. It does not have your API reference, your Confluence page, your team's mental model, or the conversation you had with the product owner. It has these four fields, rendered alongside thirty-nine other tools competing for the same attention. 

// Everything the model knows about this tool, in full:

brokerage_positions_list — List account positions
  Returns the current holdings in one account …
  arguments:
    accountId  (string, required)  The account to read, from brokerage_accounts_list …
    assetClass (enum, optional)    Filter to EQUITY or OPTION …

// Everything the model does not know about this tool:

  · that "quantity" is negative for shorts
  · that an option position of 3 contracts means 300 shares of exposure
  · that this is an end-of-prior-day snapshot for retirement accounts
  · that an empty array means "no holdings", not "lookup failed"
  · that intraday trades are already reflected but pending transfers are not
  · that brokerage_orders_list is the tool for "did my trade go through"

// …unless the description says so.
The consequence of an omission is a confident wrong answer

A model that does not know quantity is signed will report a 400-share short position as a 400-share long holding and tell the customer they own it. Nothing crashes, nothing is logged as an error, and no test fails. Undescribed domain semantics do not produce failures — they produce fluent misinformation, which in a brokerage context is a customer complaint and potentially a reportable event.

6.2The seven-part template

TS-DSC-01 MUST Every description MUST contain parts 1, 2, 3, 5, and 6 below. Parts 4 and 7 are MUST where they apply — which, for anything in a financial domain, is nearly always.

#PartContent and test
1Purpose
one sentence		 What the tool returns or does, in the active voice, starting with the verb. "Returns the current holdings in one brokerage account."
Test: could a reader who knows the domain but not this system say what comes back?
2Selection triggers

3Exclusions

4Argument semantics

6.2.1The template applied

The same description, with each part labeled. In the real descriptor it is one paragraph of running prose; the labels are here for reading only. 

[1 PURPOSE]

cost, market value, and unrealized profit and loss for each.

[2 USE WHEN]

Part 3 is the one that gets skipped and the one that pays

Most misrouted tool calls are not failures of comprehension — they are failures of discrimination between two plausible tools. "Did my Apple trade go through?" is answered by an order tool, but a positions tool that fails to disclaim it is a perfectly plausible candidate, and the model will pick it roughly as often as not. One sentence of exclusion fixes a class of error that no amount of prompt engineering elsewhere reliably fixes.

6.3Budgets and economy

Every word in a description is paid for on every turn of every conversation, by every user. A 200-word description in a catalog of 30 tools, in a conversation of 20 turns, is not 200 words — it is 120,000 words of billed context. Economy is not stylistic preference; it is an operating cost and a distraction cost.

RuleLevelRequirement
TS-DSC-02MUST A tool description MUST NOT exceed 2,000 characters. A description at the limit is usually a tool that should have been two.

What to cut first

CutBecause
"This tool allows you to…", "This function is used for…" Pure ceremony. Start with the verb.
Restating the schema in prose The model already has the schema. Describe what the schema cannot express.
Implementation detail — which service, which database, which vendor Nothing the model can act on, and it leaks topology into a context window (TS-GEN-08).
Exhaustive error catalogs Name the failures a caller can act on. The rest belong in the error payload, where they cost nothing until they happen (§11.4).
Formatting instructions for the final answer How to talk to the customer is the agent's system prompt's job, not a tool's. A tool that says "always present this as a bulleted list" is overreaching into a surface it cannot see.
Legal disclaimers and compliance language They belong in the response surface and in the result payload, not in the selection-time context. A model will not reliably reproduce them anyway.

What to keep even when it costs

  • Every domain convention that makes a number mean something other than its face value — signed quantities, contract multipliers, settled versus total cash, gross versus net.
  • Every exclusion naming a sibling tool.
  • The meaning of an empty result.
  • Any staleness the customer would be misled by.

6.4A worked rewrite

The description most teams ship first:

Before — 14 words, and six defects

Get positions. Returns a list of positions for the specified account.
DefectFailure it causes in production
No selection trigger The model does not connect "what do I own?", "how's my Apple doing?", or "am I up on Tesla?" to this tool. It either asks a clarifying question the customer finds obtuse, or picks a neighbor.
No exclusions Called for "did my order fill?" and for "how much cash do I have?". Both produce answers that are wrong in a way the customer cannot detect.
Signed quantity undocumented A short position of −400 shares is reported as owning 400 shares. This is the single highest-severity defect in the list.
Contract multiplier undocumented "You hold 3 Apple calls" is read as trivial exposure when it is 300 shares of delta-equivalent risk. The model's arithmetic downstream is then wrong by 100×.
Empty result undefined An empty array is reported to the customer as "I couldn't retrieve your positions" — an invented outage.
Freshness undefined A 15-minute-delayed mark is quoted as a live price, with no timestamp, during a fast market.

After — 168 words, all seven parts, every defect closed

Returns the current open holdings in one brokerage account: instrument,
quantity, average cost, last price, market value, and unrealized profit and
loss for each. Use when the customer asks what they own, how much of something
they hold, what a holding is worth, or whether they are up or down on it. Do
not use for cash, settled funds, or buying power — call brokerage_balances_get.
Do not use to check whether a trade went through — call brokerage_orders_list,

as of now; it has no history. accountId comes from brokerage_accounts_list and
must never be guessed. Quantity is signed and a negative quantity is a SHORT
position, not a holding. Option quantities are contracts: multiply by
contractMultiplier (usually 100) for share-equivalent exposure. An empty array
means the account holds nothing, which is a successful answer. Reads only.

The rewrite costs roughly 210 additional tokens per turn. It removes two classes of systematically wrong customer answers, one of which is a regulatory exposure. That trade is not close.

6.5Style rules

RuleLevelRequirement
TS-DSC-04MUST Descriptions MUST be plain prose in the active voice, present tense, starting with a verb. No markdown headings, no bullet syntax, no code fences — runtimes render descriptions inconsistently and structure is lost or corrupted.
TS-DSC-05MUST Sibling tools referenced in exclusions MUST be named by their exact wire name. "Use the balances tool" is not actionable; brokerage_balances_get is.
TS-DSC-06MUST Descriptions MUST NOT contain instructions about how the agent should behave outside this tool call — how to address the customer, what to disclose, when to escalate, what to do in other conversations. A tool describes itself; agent behavior is governed by the agent's own configuration.
TS-DSC-07NEVER Descriptions MUST NOT be generated at runtime, templated with request data, or personalized per user. A description is a static, reviewed, signed artifact. Anything dynamic belongs in the result payload.
TS-DSC-08SHOULD Descriptions SHOULD use the domain's own vocabulary — the words that appear on the customer's statement and in the firm's procedures. Inventing a synonym for a term of art makes the tool harder to select and its audit trail harder to read.
TS-DSC-09SHOULD Where an enumerated value has consequences, the description SHOULD state them once — "RESTRICTED accounts can be read but not traded" — rather than leaving the model to infer meaning from a token.

6.6Descriptions are attack surface

A description is, functionally, a set of instructions injected into an agent's context by whoever controls the descriptor. That makes the descriptor a privileged artifact and the publishing path a control, with three consequences that are easy to miss.

RiskControl
Unreviewed change
someone edits a description to redirect the agent		 Descriptors ship through code review and CI like code (TS-GEN-03). The catalog rejects any descriptor not signed by the owning team's pipeline. A description change is a production change and is logged as one.
Silent redefinition
a tool behaves differently tomorrow with no version change		 The catalog stores a content hash of every published descriptor. Agent runtimes pin the hash they were configured with and MUST refuse to invoke a tool whose descriptor hash has changed without a version bump (TS-SEC-09).
Cross-tool influence
one provider's description instructs the model about another's tools		 Acute when an agent is given tools from several providers. The catalog rejects descriptions that name tools outside the publishing team's own namespace, except in an exclusion clause — and those are checked at review (TS-DSC-10).

TS-DSC-10 MUST A description MUST NOT reference a tool outside its own domain namespace except to exclude it, and MUST NOT contain imperative instructions addressed to the agent about tools other than itself. Descriptions that do are rejected at publish time.

This is not hypothetical

The published research on tool-description attacks describes exactly this shape: a benign tool is approved and adopted, and its description is later amended to include an instruction that redirects the agent — to call a different tool first, to include extra data in an argument, to suppress a confirmation. The mitigation is not cleverness at invocation time. It is change control at publish time plus hash pinning at configuration time, which is why both are MUST rules in a standard about description prose.

7Input schema

The input schema does two jobs at once. It is the validation contract the gateway enforces, and it is the instruction manual the model reads while composing arguments. A schema tight enough for the first job usually solves the second for free — which is the central insight of this section.

7.1The schema profile

TS-INP-01 MUST inputSchema MUST be a JSON Schema 2020-12 document whose root is {"type": "object"} with an explicit properties map, an explicit required array (possibly empty), and "additionalProperties": false.

A tool that takes no arguments still declares {"type":"object","properties":{}, "required":[],"additionalProperties":false}. Omitting the schema entirely is not the same statement and several runtimes treat it as "arguments unconstrained".

7.1.1Permitted keywords

KeywordUse
type, properties, required The backbone. type may be an array to express nullability: "type": ["string", "null"].
descriptionRequired on every property (§7.5).

defaultPermitted, but the behavior on omission MUST also be stated in prose (§7.4).

TS-INP-02 SHOULD An input schema SHOULD declare no more than 12 top-level properties and SHOULD NOT nest more than two levels deep. Beyond that, argument-composition accuracy degrades sharply and the tool is usually doing two jobs.

7.2Parameter naming and shape

RuleLevelRequirement
TS-INP-03MUST Property names MUST be lowerCamelCase and MUST use the domain's own vocabulary — accountId, timeInForce, limitPrice — not invented synonyms.
TS-INP-04MUST A property name MUST mean the same thing in every tool in the catalog. quantity cannot be shares in one tool and contracts in another. Where a concept recurs, take it from the shared type library (Appendix B) rather than redefining it.
TS-INP-05SHOULD Boolean parameters SHOULD be named positively and default to the conservative value: includeClosed defaulting to false, never excludeClosed defaulting to false. Double negatives are reliably mis-set.
TS-INP-06SHOULD Inputs SHOULD be flat. Nesting that exists only to mirror an upstream request body is noise; flatten it and let the implementation rebuild the shape.
TS-INP-07MUST Identifiers MUST be opaque, prefixed, and pattern-constrained (acct_, ord_, inst_). The prefix tells the model which identifier goes in which slot, and the pattern stops a well-formed-looking hallucination before it reaches a system of record.
TS-INP-08MUST Every array parameter MUST declare maxItems, and every string parameter MUST declare maxLength.

7.3Making illegal states unrepresentable

The model will supply a value that looks like the values it has seen. Your defense is to make the set of values that look right identical to the set that are right.

Weak — five ways to be wrong

Produces "open", "OPEN", "working", "aapl", "AAPL ", 100.5 shares, "last week", and "limit": 10000.

7.3.1Enumerations

TS-INP-09 MUST Any parameter whose valid values are a known finite set MUST be an enum. Enumerated values MUST be SCREAMING_SNAKE_CASE and MUST match the domain enumerations in Appendix D exactly — the same tokens the systems of record and the customer statement use.

Where an enumeration is long (a currency list, an exchange list) or grows frequently, use a pattern plus a prose pointer to the tool that enumerates valid values, rather than a 180-member enum that costs tokens on every turn. Where an enumeration is short and consequential — order status, side, time in force, account type — spell it out.

7.3.2Unions, and the alternative

When two shapes are genuinely different, the default answer is two tools, not one tool with a union. Two tools give you two accurate descriptions, two accurate annotation sets, two risk tiers, and two audit identities. That is almost always worth more than the saved descriptor.

Where a union is unavoidable — a multi-leg order where each leg is one of two shapes — use a discriminated union with a const tag, and keep it to three branches: 

{
  "oneOf": [
    { "properties": { "legType": { "const": "EQUITY" },
                      "symbol":  { "type": "string", "pattern": "^[A-Z]{1,5}$" } },
      "required": ["legType", "symbol"] },
    { "properties": { "legType":     { "const": "OPTION" },
                      "instrumentId": { "type": "string", "pattern": "^inst_" } },
      "required": ["legType", "instrumentId"] }
  ]
}

7.4Required, optional, and default

RuleLevelRequirement
TS-INP-10MUST A parameter is required only if the tool genuinely cannot proceed without it. Marking a parameter required to force the model to "think about it" causes the model to invent a value instead.
TS-INP-11MUST Every optional parameter's omission behavior MUST be stated in its description in prose, not only in default. Models read prose far more reliably than they read schema annotations.
TS-INP-12MUST Defaults MUST be the narrow, conservative, least-surprising choice: the smallest page, the current account only, the shortest date window, exclusions on. A default that widens scope is a defect even when it is convenient.
TS-INP-13NEVER A parameter that changes the tool's safety characteristics — whether a change is simulated or real, whether validation is skipped, whether a confirmation is required — MUST NOT exist. Those are separate tools with separate annotations (§9.1, §25.2).

reasonstring, maxLength 280 Why the action is being taken, captured verbatim into the audit record. Required on risk tier 3 tools.

TS-INP-16 MUST A tool MUST NOT accept a parameter it cannot honor. Offering an asOf on a tool with no history, or a currency on a tool that only reports in the account's base currency, is worse than omitting it: the model will supply the parameter and silently receive an answer that does not match what it asked for.

7.7Prohibited input patterns

8Output schema and the result envelope

What a tool returns is read twice: once by a model that will paraphrase it to a customer, and once by a human reconstructing what happened. The envelope in this section serves both without making either read the other's format.

8.1The envelope

Every invocation returns the same three-field envelope, success or failure:

{
  "content": [                          // what a reader sees — always present
    { "type": "text",
      "text": "3 positions in ••••4471 as of 2026-09-19T14:32:05Z. AAPL 250 sh, mkt val 62,137.50 USD, +4,312.50 (+7.5%). TSLA -400 sh SHORT, mkt val -98,240.00 USD, -2,110.00 (-2.2%). AAPL 20261218C250 3 contracts (300 sh equiv), mkt val 4,140.00 USD, +640.00 (+18.3%)." }
  ],
  "structuredContent": {                // the authoritative payload — validates against outputSchema
    "accountId": "acct_01HQ8Z4M2X9K3P7R",

    "positions": [ /* … */ ],
    "completeness": { "returned": 3, "totalMatching": 3, "truncated": false, "nextCursor": null }

FieldRules
content An ordered array of presentation blocks. MUST contain at least one text block. Additional block types — image, audio, resourceLink, resource — MAY follow (§8.5).
structuredContent A JSON object that MUST validate against the descriptor's outputSchema. This is the authoritative result; anything a downstream system computes from, it computes from here.
isError Boolean. true means the tool ran and could not do its job (§11.1). Transport and protocol failures are not signaled here — they never reach the tool.

TS-OUT-01 MUST Every tool MUST declare an outputSchema and MUST return both content and structuredContent on every invocation, including error invocations. Runtimes differ in which one they surface to the model; a tool that populates only one is broken on half the estate and nobody notices until a migration.

8.2The dual-rendering rule

The text block is not a second-class debug string. It is what several runtimes actually put in front of the model, what an approval dialog shows, and what an auditor reads. It is also the only part of the result that will survive being pasted into an incident ticket.

RuleLevelRequirement
TS-OUT-02MUST The text rendering MUST be derived from structuredContent by the implementation — generated, not hand-maintained — so the two cannot disagree.
TS-OUT-03MUST The text rendering MUST NOT contain any fact absent from structuredContent, and MUST carry the facts a reader could be materially misled by omitting: the as-of time, the currency, the sign of a position, and any truncation.
TS-OUT-04SHOULD The text rendering SHOULD be compact — a few hundred characters for a typical result — and SHOULD NOT be a pretty-printed dump of the structured payload. Duplicating the whole payload as text doubles the token cost of every call for no gain.
TS-OUT-05MUST Monetary and quantity values in the text rendering MUST carry their currency and their sign explicitly. "−98,240.00 USD" and "SHORT 400" are unambiguous; "98240" is a defect waiting for a customer complaint.

8.3Provenance, as-of, and completeness

Three pieces of metadata turn a payload into something a regulated firm can stand behind. All three live inside structuredContent, because they are data about the answer, not decoration.

MemberRequirement
asOf
RFC 3339, UTC, always		 MUST be present on every result carrying data that can change. It is the instant the data was true, not the instant the response was built. Without it, a model will present a 20-minute-old mark as the current price, in a market that moved.
basis
how the number was derived		 MUST be present on any computed or convention-dependent figure. A balance is SETTLED, TRADE_DATE, or INTRADAY_ESTIMATE; a price is REALTIME, DELAYED_15M, or PRIOR_CLOSE. The same question has several correct answers and the reader must know which one they received.
completeness
what you did not get		 MUST be present on every collection result: {returned, totalMatching, truncated, nextCursor}. totalMatching may be null where it is genuinely unknowable, but truncated never may.
disclosures
what must be said		 SHOULD carry compliance text the firm requires to accompany the figure — delayed-quote notices, estimate caveats, tax-lot method. Carrying them in the payload puts them where the agent can surface them, rather than in a description where they cost tokens on every turn and are reproduced unreliably.
The single most damaging omission in a financial tool

A number without an asOf and a basis is not a fact, it is a rumour with a decimal point. "You have $84,360 of buying power" is true of settled cash, of margin buying power, of day-trading buying power, or of an intraday estimate that will be restated at the close — and those four numbers can differ by a factor of four in the same account at the same instant. The tool knows which one it computed. Say so.

8.4Pagination and truncation

A model is a poor paginator. It will follow a cursor once, sometimes twice, and then summarize what it has as though it were everything. Design for that rather than against it.

RuleLevelRequirement
TS-OUT-06MUST Collections MUST use opaque forward cursors. Offset and page-number pagination MUST NOT be used against a mutable collection.
TS-OUT-07MUST When a result is truncated, completeness.truncated MUST be true and the text rendering MUST say so in words: "showing 25 of 340 positions". Silent truncation causes the model to state a partial total as a complete one.
TS-OUT-08SHOULD A truncated result SHOULD tell the reader how to narrow rather than how to continue: "filter by assetClass or symbol to see fewer than 340". Narrowing produces a correct answer in one more call; paging produces fourteen calls and an abandoned loop.
TS-OUT-09SHOULD Where a caller is likely to want the whole collection only in order to compute an aggregate, the catalog SHOULD offer a summarize tool that computes it server-side. Totals computed by a model over a paginated collection are wrong often enough to matter.

8.5References instead of payloads

Not everything belongs in a context window. A confirmation PDF, a tax-lot export, a year's transactions, an image of a chart: these are returned by reference, as a resourceLink block naming a URI, a media type, a size, and an expiry. 

{
  "type": "resourceLink",
  "uri": "https://documents.example.com/exports/exp_01HQ9F2K8R4T6V8Y",
  "name": "positions-acct4471-20260919.csv",
  "mimeType": "text/csv",
  "description": "340 positions, 62 KB. Link expires in 15 minutes and requires the customer's session."

Reference URIs MUST be short-lived and MUST require the principal's own authority to dereference — a link that anyone holding the URI can fetch has moved customer data outside the entitlement model.

8.6Empty, partial, and stale results

SituationRequired behavior
Empty isError: false, an empty array, and a text rendering that says what the emptiness means: "This account holds no positions." Never an error, and never a bare [] — a model shown an empty array with no prose reports an outage about half the time.
Not found An error with code NOT_FOUND for a single-entity get; an empty collection for a list. The distinction matters: "that order does not exist" and "you have no orders" are different customer answers.
Partial
one source degraded		 Permitted only where the missing part is separable and disclosed: return what is available, set completeness.truncated or a degraded flag, name what is missing, and say it in the text. A result that silently omits one custodian's positions is worse than no result.
Partial, where the number will be relied on MUST fail instead. A buying-power figure computed from a margin engine that did not respond is not a degraded answer, it is a wrong one. Balances, buying power, and anything that gates a trading decision MUST NOT be returned partially computed (TS-OUT-11).
Stale Return it with an honest asOf and basis, plus a stale: true flag where the data is older than the tool's own freshness target. Let the reader decide; do not decide for them by hiding it.

9Behavioral annotations and risk tiers

Annotations let a runtime that has never seen your tool reason about it: whether to offer it to an autonomous agent, whether to demand a confirmation, whether a retry after a timeout is safe. They are the machine-readable half of "what does this thing do to the world".

9.1The four behavioral hints

AnnotationDefaultMeaning, and what a runtime does with it
readOnlyHintfalse True means the tool changes nothing in any system, including caches, counters, and audit-visible state. Runtimes use it to decide what an agent may do without supervision, what may run speculatively or in parallel, and what is safe to replay while debugging. If the tool writes anything at all — even a search-history row — this is false.
destructiveHinttrue Meaningful only when readOnlyHint is false. True means the change may be irreversible or may overwrite existing state; false means it is purely additive. Placing an order is destructive: it can fill in milliseconds and cannot be un-filled. Adding a symbol to a watchlist is additive.
idempotentHintfalse Meaningful only when readOnlyHint is false. True means repeating the identical call has no additional effect. This is the annotation that tells a runtime whether a timeout can be retried. Canceling an already-canceled order is idempotent; placing an order is not, unless an idempotencyKey makes it so — and if it does, say so here and require the key.
openWorldHinttrue True means the tool reaches outside the firm's controlled domain — the public internet, a market data vendor, a counterparty. False means a closed, enumerable universe. Runtimes use it to decide what may be quoted to a customer without attribution and what content needs treating as untrusted.

TS-ANN-01 MUST All four annotations MUST be stated explicitly, even where the value equals the default. The defaults are deliberately pessimistic so that an omission fails safe; but an omission also means the reviewer cannot tell whether the author decided or forgot.

TS-ANN-02 MUST Annotations MUST be consistent with the operation verb in the tool's name (§5.3). A tool named ..._list with readOnlyHint: false fails the linter, and a tool named ..._place with readOnlyHint: true fails it harder.

9.2Hints are advisory, never enforcement

Read this paragraph twice before designing a control around an annotation

An annotation is an assertion made by whoever wrote the descriptor. For a tool the firm builds and signs, that assertion is as trustworthy as the review that approved it. For a tool supplied by a third party, it is a claim by an untrusted party about their own software — and a readOnlyHint: true on someone else's tool is worth precisely what any self-certification is worth. No security control may depend solely on an annotation.

The firm's controls therefore derive from the risk tier in the governance block, which is set by the tool's owner, verified at review, recorded in the catalog, and signed — not from the annotations, which are conveniences for the runtime and hints for the agent. Annotations and risk tier must agree; where they disagree, the linter fails the build and a human decides which one was wrong.

9.3The risk tier

TierScopeBrokerage examplesBaseline controls
T0

T2

TS-ANN-03 MUST Every descriptor MUST declare a riskTier. A tool whose tier is disputed at review defaults to the higher tier until the dispute is resolved in writing.

Cancellation is tier 3, and people argue about it

Canceling an order feels like undoing something and therefore harmless. It is not: a canceled order does not fill, and an order that does not fill in a moving market is a realized economic difference for the customer. It is also irreversible — you cannot un-cancel; you can only place a new order at a new price. Treat cancellation exactly as you treat placement.

10.2Ownership and lifecycle

TS-GOV-01 MUST Every tool MUST name an owning team with a paging escalation path. The catalog MUST re-verify ownership quarterly and automatically move a tool whose owner cannot be confirmed to deprecated, then retired ninety days later.

This rule exists because of a failure mode specific to tool catalogs: tools are cheap to add and invisible once added. A REST endpoint with no owner eventually breaks and someone notices. A tool with no owner keeps working, keeps returning customer data to agents, and keeps being selected — silently, correctly, and unaccountably — for years.

Visibility is an entitlement decision, not a convenience

Offering an agent a tool that its principal may not invoke wastes context, invites a failed call, and — worse — tells the model that the capability exists, which is enough for it to describe the capability to the customer. 11Errors

A tool's error path is used more often than anyone plans for, is read by a caller that cannot ask what it means, and is the single place where a firm most often leaks something it should not. It deserves the same design attention as the success path and usually gets a tenth of it.

11.1Two kinds of failure

11.3The taxonomy

CodeRetryMeans, and what the caller should do
INVALID_ARGUMENTNo The arguments were malformed or violated the schema. Fix the argument — details.violations names the offending field with a JSON Pointer.
NOT_FOUNDNo The identified entity does not exist, or exists outside the principal's grant — deliberately indistinguishable, so that the tool cannot be used to enumerate identifiers. Do not guess another identifier; list first.

NOT_SUPPORTEDNo A well-formed request for something this tool does not do — a historical asOf on a real-time-only tool, an asset class not covered. remediation names the tool that does.
INTERNAL_ERROROnce An unexpected failure. Carries a traceId and nothing else of substance. If a tool returns this more than rarely, it is mapping errors lazily (§11.6).
INVALID_ARGUMENT versus BUSINESS_RULE_VIOLATION

The distinction is the most useful one in the taxonomy. INVALID_ARGUMENT means the caller is wrong — change the argument and it will work. BUSINESS_RULE_VIOLATION means the caller is fine and reality declined — not enough buying power, market closed, instrument halted. A caller that conflates them retries a doomed order and then tells the customer "invalid request" when the honest answer was "the market is closed". Tools that return one code for both make every agent built on them worse.

12Granularity and catalog design

The most consequential decision in a tool catalog is where one tool ends and the next begins. Get it wrong and no amount of descriptor quality recovers it: the model will be choosing between the wrong options, carefully.

12.1The unit of a tool

TS-CAT-01 SHOULD One tool SHOULD correspond to one decision the agent has to make, expressed as one question a user would ask — not to one resource, one endpoint, or one database table.

Three diagnostic questions, applied to any proposed tool:

QuestionIf the answer is wrong
Can you state, in one sentence, the user question this answers? If it takes two sentences with an "or" in the middle, it is two tools.
After calling it, does the agent know enough to answer? If the agent must then call two more tools and do arithmetic involving a domain convention, the boundary is drawn in the wrong place — move the work server-side.
Do all of its paths have the same risk tier and annotations? If one argument value makes it destructive, it is at least two tools (TS-INP-13).

12.2Deriving a tool set

The procedure the firm uses, in order. It takes a day and saves a quarter.

  1. Collect the utterances. Twenty to fifty real things users say, taken from transcripts, contact-center logs, or search queries — not invented by the design team. "Do I own any Tesla?" "Did my order go through?" "How much can I spend?" "What's my account worth?"
  2. Cluster by the answer, not the words. "What do I own", "how much Apple do I have", and "am I up on Tesla" are one cluster; they are all answered from the positions snapshot.
  3. Draft one tool per cluster, named per §5, described per §6.
  4. Run the knowledge test. For each cluster, list the domain facts the agent needs to turn the tool's output into a correct answer. Every fact on that list is either stated in the description, embedded in the payload, or moved into the tool. Nothing stays on the list.
  5. Run the confusability test. For each pair of tools, write the one sentence that distinguishes them. If you cannot, merge them or re-scope. Every sentence you write goes into both descriptions as an exclusion (§6.2, part 3).
  6. Count. If the result exceeds 25 tools for one agent, go back to step 2 — you have almost certainly modeled resources rather than questions.
  7. Classify. Assign risk tiers before writing any code; the tier changes what the tool is allowed to be.

12.3Primitive tools and workflow tools

The rule of three

If answering a common user question reliably takes three or more tool calls plus a domain convention the model must apply itself, build the composite. Each hop is an opportunity to select the wrong tool, drop a caveat, or make an arithmetic slip — and the compounding is multiplicative, not additive. Composites are not a shortcut; they are where the firm's domain knowledge is made testable.

12.4Catalog size and audience scoping

Tool selection accuracy degrades as the catalog grows, and it degrades fastest among tools that resemble each other. The mitigation is not a better model; it is a smaller, better separated menu.

RuleLevelRequirement
TS-CAT-02SHOULD An agent SHOULD be offered no more than 25 tools, and MUST NOT be offered more than 40 without a documented exception.
TS-CAT-03MUST The catalog MUST support audience-scoped views, so that a customer-facing assistant, an adviser's copilot, and an operations agent each see only their own set. Audience scoping is an entitlement decision (§10.4), not a UI preference.
TS-CAT-04SHOULD Where an estate genuinely exceeds what one agent can hold, the platform SHOULD scope by task phase — a small core set always present, with a task-specific set attached when the conversation enters that task — rather than presenting everything and hoping.
On "just let the agent search the catalog"

A meta-tool that searches a large catalog and returns candidate tools is a legitimate pattern for estates in the hundreds, and it has two costs worth stating before anyone adopts it. It adds a round trip and a failure mode to every task, and it moves tool selection from a mechanism you can evaluate offline into one you can only evaluate end to end. Use it when the alternative is a 200-tool prompt, not to avoid the work in §12.2.

12.5Confusability

The nearest-neighbor pairs in a brokerage catalog are predictable, and each one needs an explicit exclusion in both descriptions:

balances_get ↔ positions_list Balances are cash and buying power; positions are holdings. "What is my account worth" needs both, and is answered by portfolio_summarize.
balances_get ↔ transactions_list A balance is a state; a transaction is an event. "Why did my cash drop" is transactions.
orders_list ↔ executions_list One order can have many executions at different prices. "What price did I get" may need executions; "did it fill" needs the order.
order_check ↔ order_preview ↔ order_place Check answers "can I?"; preview answers "what exactly would happen?" and mints a confirmation token; place does it. Only the third one trades.

13.5Representing numbers

RuleLevelRequirement
TS-OUT-13MUST Monetary amounts and quantities MUST be decimal strings — "62137.50" — never IEEE-754 numbers. Binary floating point cannot represent a cent, and the error is silent, compounding, and eventually a reconciliation break.
TS-OUT-14MUST Every monetary value MUST be accompanied by an ISO 4217 currency, at the value or at the envelope level. Never assume USD.
TS-OUT-15MUST Structured values MUST NOT carry locale formatting — no thousands separators, no currency symbols, no parenthesized negatives. Formatting belongs in the text rendering, where (2,110.00) is spelled -2,110.00 USD because parentheses for negatives are a convention a model will misread.
TS-OUT-16MUST Timestamps MUST be RFC 3339 with an explicit UTC offset. Dates that are genuinely dates — settlement date, expiry — are YYYY-MM-DD, and the description MUST name the time zone they are interpreted in.

14Interaction patterns

Four situations recur in every tool catalog: the action needs a human's consent, the action needs information the agent does not have, the action might be executed twice, and the action takes longer than a conversation can wait. Each has one sanctioned pattern.

14.1Confirmation

Policy comes from the risk tier (§9.4). The mechanics are the gateway's: it resolves the approval mode before invoking the implementation, renders the confirmationTemplate with validated arguments, obtains the principal's decision, and binds that decision to an argument hash.

The implementation must still behave correctly if approval is missing — returning APPROVAL_REQUIRED — because the gateway is not the only path that will ever exist (§3.1).

14.2Preview then execute

Every tier 3 action is split in two. The preview tool is read-only, computes exactly what would happen, and returns a short-lived confirmationToken that encodes the previewed outcome. The execute tool accepts that token and MUST refuse to act if the world has moved enough to invalidate it. 

brokerage_order_preview  →  { estimatedCost, buyingPowerAfter, warnings[],
                              commission, confirmationToken: "cnf_…",
                              expiresAt: "2026-09-19T14:34:05Z" }

brokerage_order_place    ←  { …order details…, confirmationToken: "cnf_…" }
                         →  PRECONDITION_FAILED if expired, or if the order
                            details do not match what was previewed

TS-SEC-01 MUST A confirmation token MUST be bound to the principal, the tool, and a hash of the previewed arguments; MUST expire within 120 seconds by default; and MUST be single-use. It is a capability, not a receipt.

Why this beats a dryRun flag

Two tools give you two accurate annotation sets, two risk tiers, two audit identities, and a preview an agent may call freely without any approval friction — which means it will call it, which means the customer sees the cost before the question is asked. One tool with a flag gives you a descriptor that is honest about neither of its two behaviors, and a control model where the difference between simulated and real is one token in a JSON object the model generated.

14.3Asking the principal for missing information

Sometimes a tool cannot proceed without a value the agent does not have and should not invent — which of three eligible accounts, whether to accept a worse price, an expiry date the customer has not stated. The sanctioned pattern is for the tool to ask, through the runtime, rather than to guess or to fail.

RuleLevelRequirement
TS-SEC-04MUST A request for input MUST be expressed as a schema of primitive fields — string, number, boolean, or enum — with a clear prompt, and MUST be declinable. An agent that cannot obtain the value returns to the user; it does not substitute a default.
TS-SEC-05NEVER Input requests MUST NOT be used to collect credentials, card numbers, government identifiers, or one-time passcodes. Authentication happens in the identity plane, on a surface the customer can verify — never inside a tool's request for arguments, which is precisely the shape a phishing flow would take.
TS-SEC-06SHOULD Prefer disambiguating in the schema over asking at runtime. A tool that returns INVALID_ARGUMENT naming the three eligible accounts is usually a better experience than a modal dialog, and always a simpler control.

14.4Idempotency

An agent retries. It retries after a timeout, after an ambiguous error, and sometimes because a second model turn concluded the first one had not worked. For a read this is wasteful; for an order it is a duplicate trade.

TS-SEC-07 MUST Every tool that is not naturally idempotent MUST require an idempotencyKey, MUST deduplicate on it for at least 24 hours, and MUST return the original result — not an error — when a key is replayed with identical arguments. A replay with the same key and different arguments MUST fail with CONFLICT.

State this in the description too, in one sentence: models supply a key far more reliably when told what it is for than when it merely appears in the schema.

14.5Long-running operations

DurationPattern
< 10 secondsSynchronous. Declare the latency class (§10.5).
10 s – minutes Job pattern: ..._start returns a jobId immediately; ..._status reports progress and returns the result when complete. The start tool is not read-only even if the eventual result is.
Minutes – hours Job pattern plus an out-of-band notification to the principal. The agent MUST NOT poll in a loop; the description says so, and the status tool returns a nextPollAfterSeconds the agent is told to honor.

TS-GOV-05 MUST A tool MUST NOT block for longer than its declared timeout, and MUST return TIMEOUT with an explicit statement of whether the underlying operation may still complete. "The order may still have been placed" is a materially different instruction from "the order was not placed", and the agent cannot work it out.

14.6Polling and change

Order status is the canonical case: the customer asks "did it fill?", the answer is "not yet", and something has to decide when to look again. Push subscriptions are the right answer for a trading screen and the wrong answer for a conversational agent, which has no persistent loop to receive them.

  • Return isTerminal on any entity with a lifecycle, and say in the description that a terminal entity must not be polled again. This single flag removes most wasteful polling.
  • Return nextPollAfterSeconds when the answer is "not yet", scaled to the entity — two seconds for a market order, sixty for a transfer.
  • Prefer telling the customer the firm will notify them over having an agent wait. An agent holding a conversation open to poll is an expensive, fragile timer.

15Security and trust

Tools give a probabilistic system a set of hands. Everything in this section follows from that one sentence, and none of it is satisfied by securing the transport.

15.1Principles

PrincipleIn practice
The agent has no authority of its own Every action is performed as a principal, with that principal's scopes, subject to that principal's entitlements. There is no service account that "the assistant" uses to read customer accounts — that account would be a standing breach waiting for a prompt.
Least privilege, per invocation The scopes required are declared per tool and checked per invocation against the specific resource in the arguments, not once per session.
Everything the model produces is untrusted input Arguments are validated and authorized as though they came from an anonymous internet client, because in the relevant sense they did.
Everything a tool returns is untrusted input to the model Customer-supplied and counterparty-supplied strings are data. They are marked, neutralized, and never interpreted as instruction.
Controls live where they cannot be talked out of In the gateway and the implementation. Not in the description, not in the annotations, not in the system prompt — all three are inputs to a system that can be persuaded.

15.2Identity and authorization

RuleLevelRequirement
TS-SEC-02NEVER A tool MUST NOT accept an argument that asserts identity, role, tenancy, or entitlement. Identity arrives out of band, from the identity plane. A tool with an onBehalfOf parameter has delegated its access control to a language model.
TS-SEC-08MUST The implementation MUST authorize the principal against the specific resource named in the arguments, on every invocation. Holding brokerage:positions:read authorizes reading your positions, not a position identifier you were able to produce.
TS-SEC-10NEVER A token presented to the gateway MUST NOT be forwarded verbatim to a downstream system. Exchange it for a token whose audience is that system, scoped to this operation. Pass-through re-uses a credential outside the audience it was issued for and destroys the ability to attribute a downstream action.
TS-SEC-03NEVER Credentials of any kind MUST NOT appear in arguments, results, errors, or descriptions. Anything in those four places will be logged, retained in conversation history, and may be transmitted to a model provider.

15.2.1The confused deputy

The gateway is a deputy: it holds authority the agent does not, and it acts on the agent's instructions. The classic failure is a gateway that authenticates the agent, authorizes the tool, and then performs an operation against a resource the principal never had access to — because nothing re-checked the resource.

In this domain the attack is trivially expressible: a customer asks their assistant about "account acct_01HQ9F3M7X2K8P4T", an identifier they obtained, guessed, or found. Every layer above the implementation sees a well-formed request from an authenticated customer to a tool they are entitled to use. Only TS-SEC-08 stops it.

15.4Tenancy and isolation

  • Every cache key, idempotency key, and rate-limit bucket is scoped by principal and tenant. A shared idempotency namespace lets one customer's key collide with another's, which is a data-disclosure bug wearing an availability bug's clothes.
  • Cross-tenant aggregates — "how many customers hold Tesla" — are a different tool, at a different tier, for a different audience, with a different entitlement. Never a parameter on a customer-facing tool.
  • Test fixtures and sandbox data never share an identifier space with production. A model that has seen acct_TEST0001 in an example will eventually send it.

15.6Kill switch and degradation

TS-SEC-12 MUST Every tier 2 and tier 3 tool MUST be disableable within 60 seconds, by capability, by audience, and globally, without a deployment. The disabled state MUST return NOT_SUPPORTED with a remediation the agent can relay — "order placement through the assistant is temporarily unavailable; the customer can trade in the app" — rather than an opaque failure.

15.7Third-party and vendor tools

Tools the firm did not write are a supply chain, and the descriptor is the payload. Three controls, none optional:

RuleLevelRequirement

TS-SEC-13MUST Third-party tools MUST be reviewed against this standard before admission, MUST be re-reviewed on every descriptor change, and MUST be assumed to have mis-stated their annotations — the firm assigns the risk tier independently, from observed behavior, not from the vendor's claim.
TS-SEC-14MUST A third-party tool MUST NOT be presented to an agent in the same context as a firm tier 3 tool unless the combination has been explicitly assessed. The risk is not either tool; it is that one tool's output can steer the other's invocation.

The consumer of a tool contract cannot read a changelog, cannot be scheduled for an upgrade, and does not have a version pin of its own. That removes most of the usual options and makes the remaining rule very simple: additive change, or a new tool.

RuleLevelRequirement
TS-VER-01MUST governance.version MUST be semantic. Patch for prose and non-behavioral fixes; minor for compatible additions; major only alongside a new tool name (TS-VER-03).
TS-VER-02MUST Output enumerations MUST be documented as open: the description states that new members may appear and how to treat one. Order status is the canonical case — an unrecognized status means working, never terminal, and getting that default backwards tells a customer their order is dead when it is live.
TS-VER-03MUST A breaking change MUST be published as a new tool name with a _v2 suffix, running alongside the original. The two coexist for the full deprecation window.
TS-VER-04MUST Any change to prose, schema, or behavior MUST re-run the tool's evaluation suite before publication (§27.3). A description edit is a behavior change: it is the input that determines whether the tool is selected at all.

  1. Announce. Set lifecycle: deprecated with deprecation.{since, sunset, successor, migrationNote}. Minimum window: 90 days, or one full regulatory reporting cycle, whichever is longer.
  2. Stop new grants. The catalog no longer offers the tool to audiences that do not already have it. Existing consumers are unaffected.
  3. Warn out of band. Results carry a deprecation notice in _meta, which the runtime logs. The description is not changed — deprecation prose in the description costs tokens on every turn, and a model told a tool is deprecated behaves unpredictably rather than migrating.
  4. Measure. Track invocations by audience. Contact the owner of each remaining consumer directly.
  5. Retire. At sunset, set lifecycle: retired. The tool returns NOT_SUPPORTED naming the successor for a further 90 days, then is withdrawn. The name is never reused (TS-NAM-11).

17.4The runtime constraint register

Tool-calling runtimes impose their own limits — name length and character set, maximum number of tools, maximum schema depth, whether output schemas are honored, whether annotations are surfaced. These change without notice and are not the firm's to control.

TS-VER-05 MUST The platform team MUST maintain a register of the constraints imposed by every runtime the firm publishes to, MUST enforce the intersection of those constraints in the linter, and MUST re-validate the entire catalog whenever a runtime's constraints change. A tool that silently stops being offered because a name grew too long for one runtime is an outage nobody will attribute correctly.

The root of the catalog. Every other brokerage tool needs an accountId and this is the only place one legitimately comes from, which makes its description the most frequently read prose in the estate.

19.1The description

Returns every brokerage account the customer has granted access to, with its type,
registration, status, base currency, and options approval level. Use when the customer asks
which accounts they have, or whenever another tool needs an accountId and you do not already
have one — this is the only source of valid account identifiers. Do not use for balances or
cash: call brokerage_balances_get. Do not use for holdings: call brokerage_positions_list.
Account numbers are returned masked to the last four digits, which is what the customer sees
on their statement; the accountId is an internal identifier and must never be read aloud to
the customer. Registration matters: a Roth or traditional IRA cannot borrow, so margin
buying power does not apply to it. Status ACTIVE permits trading; RESTRICTED permits reading
but not trading; CLOSED and PENDING permit neither. Closed accounts are omitted unless
includeClosed is true. An empty list means the customer has granted no account access, not
that the lookup failed. Reads only.

Note what is present and what is not. Present: the selection trigger, an exclusion naming two sibling tools, the distinction between accountId and the masked account number with an instruction about which one may be spoken, the consequences of registration and status, the meaning of an empty result. Absent: any mention of the account master system, any list of the fields returned — the schema already says that — and any instruction about how to talk to the customer.

20.1The description

20.4.1Six deliberate choices in that payload

ChoiceWhy
side as well as a signed quantity Redundant by design. A model that misses the minus sign cannot miss "side": "SHORT", and the text rendering spells it a third time. The cost is four tokens per position; the failure it prevents is a customer being told they own something they owe.
sharesEquivalent computed server-side 3 contracts × 100 = 300 is arithmetic the model can do and sometimes will not. Doing it in the tool makes it testable.
totals over the filter, not the page A total summed from a truncated array is wrong. Computing it server-side over the whole matching set removes the most likely arithmetic error in the interaction (TS-OUT-09).
daysToExpiry alongside expiry Date arithmetic against "today" is a recurring model weakness, and an option expiring this week is materially different from one expiring in a year.
Envelope-level currency and asOf Stated once rather than on every row (§13.3), which at 340 positions is the difference between a usable and an unusable payload.
Text rendering repeats the totals Several runtimes surface only the text block. A rendering that omitted the totals would make the model re-derive them from the rows it can see — that is, from the truncated ones.

The tool where the gap between "returning the data" and "answering the question" is widest. A customer asking how much they can spend has one question; the account has four defensible answers, and three of them are wrong for any given account.

21.1The problem this tool solves

Consider the same customer, the same instant, four figures:

FigureValueTrue for
cash.total18,420.00 USDNothing directly — it includes unsettled proceeds.
cash.settled12,180.00 USDWhat a cash or retirement account can actually spend today.
buyingPower.stock36,840.00 USDA margin account buying marginable equities.
buyingPower.dayTrading73,680.00 USDA pattern day trader, intraday only, resetting each session.

A tool that returns all four and stops has discharged its duty to the data and abandoned its duty to the question. The model must then know that a Roth IRA cannot borrow, that unsettled proceeds cannot fund a purchase in a cash account without a good-faith violation, and that day-trading buying power must never be quoted to someone who is not flagged. Those are three domain rules, each of which the firm already encodes correctly in its margin engine.

The fix, and the general principle

The tool returns buyingPower.applicable — the figure that actually governs this account today — alongside applicableReason, a sentence explaining why. The four underlying figures remain available for a customer who asks for the breakdown. When the server knows which of several correct answers is the right one, it must say so rather than shipping the ambiguity to a caller that cannot resolve it.

21.2The description

Returns the money in one brokerage account: cash and settled cash, buying power broken out
by what it can be used for, margin detail, and the account's total value. Use when the
customer asks how much cash they have, how much they can spend or invest, what their account
is worth, whether they are on margin, or whether they have a margin call. Do not use for
holdings — call brokerage_positions_list. Do not use to explain why a balance changed — call
brokerage_transactions_list. An account has several different correct answers to how much
can I spend, and they can differ by a factor of four: read buyingPower.applicable, which is
the figure that actually governs this account given its type and registration, and
buyingPower.applicableReason, which says why. Never present buyingPower.dayTrading to a
customer who is not a pattern day trader, and never present margin figures for a retirement
account, which cannot borrow. Cash that is unsettled cannot fund a purchase in a cash
account without a good-faith violation. Figures are computed intraday and restated after the
close; asOf and basis state which. Reads only, and never returns a partially computed figure
— if the margin engine is unavailable the call fails rather than returning a number that
looks complete.

22.3.2Three fields worth arguing about

FieldWhy it is in the payload
statusExplanation A sentence, written by the domain team, already phrased for a customer: "200 of 500 shares have filled at an average of 245.88; 300 shares are still working and will expire at the close if they do not fill." Status strings do not survive paraphrase — PENDING_REPLACE is not a phrase any customer has heard — and a model asked to paraphrase one invents plausible detail. Writing the sentence once, in the tool, is the only place it can be reviewed.
nextPollAfterSeconds Turns "poll sensibly" from a hope into an instruction. Two seconds for a marketable order, thirty for a resting limit, null when terminal. Without it the agent either polls in a tight loop or asks the customer to check back later.
cancelable The server knows whether this order can be canceled right now — including the cases the status string does not express, such as an order in PENDING_CANCEL or one at a venue that has gone dark. Offering a cancellation that then fails is a worse customer experience than not offering it.

23A state-changing tool, for contrast

Everything so far has been read-only. This section shows what changes when a tool spends a customer's money — and how little of it is about the code.

23.2The descriptor

brokerage_order_placePlace a real order — trades money
TIER 3 DESTRUCTIVE IDEMPOTENT VIA KEY OPEN WORLD brokerage:orders:write APPROVAL: CONFIRM RATE 10/min KILL SWITCH 
Places a live equity order in the market using a confirmation token obtained from
brokerage_order_preview. This spends the customer's money and creates market exposure; it
cannot be undone once it fills. Use when the customer has seen a preview of this exact order
and explicitly told you to place it, and only then: brokerage_order_preview must have
returned a confirmationToken for the same order first. Do not use to check whether an order
is possible — call brokerage_order_check. Do not use to show the customer what an order
would cost — call brokerage_order_preview. Do not re-invoke after a rejection or a declined
approval without the customer explicitly asking again. Every call requires an
idempotencyKey: a fresh one for a genuinely new order, and the same one when retrying an
order whose outcome is unknown, which returns the original result rather than placing a
second order. If the call times out, the order may still have been placed: call
brokerage_orders_list before doing anything else, and never assume failure. A successful
result means the order was accepted, not that it filled — check status and isTerminal, and
tell the customer which of the two happened.

Note the title: "Place a real order — trades money". It appears in the approval dialog and in every audit export. Titles for tier 3 tools name the consequence, not the operation (TS-NAM-09), because the person reading it at speed is deciding whether to authorize something real.

Three sentences, three prevented incidents

24Composition: five questions, one catalog

The test of a catalog is not whether each tool is good but whether the set answers real questions without the model needing to know anything the firm has not told it. Five questions, traced.

24.1"What do I own?"

brokerage_accounts_list  {}
  → 3 accounts; customer says "the Roth"  → acct_01HQ8Z4M2X9K3P7R
brokerage_positions_list { accountId: "acct_01HQ8Z4M2X9K3P7R" }
  → 3 positions, totals, asOf, DELAYED_15M

What the descriptors did: the accounts description said it is the only source of account identifiers, so the model did not invent one. The positions description said quantity is signed, so the short position was reported as short. The basis field meant the answer was "as of 14:32, prices delayed up to 15 minutes" rather than a bare number.

24.2"Did my Apple order go through?"

brokerage_orders_list { accountId: "…", symbol: "AAPL", status: "WORKING" }
  → 1 order, PARTIALLY_FILLED, 200 of 500 at 245.88, isTerminal false

What the descriptors did: the positions description's exclusion — "do not use to check whether a trade went through" — routed the question to orders rather than positions, which is the single most common misroute in this domain. filledQuantity and remainingQuantity made "partly, 200 of 500" expressible; status alone would not have.

24.3"How much can I spend in my Roth?"

brokerage_balances_get { accountId: "acct_01HQ8Z4M2X9K3P7R" }
  → applicable 12,180.00 USD
    applicableReason "Settled cash. This is a retirement account and cannot
                      borrow, so margin buying power does not apply."

What the descriptors did: everything. Four figures were available and the tool named the right one and said why. A catalog without applicable would have required the model to know that a Roth IRA cannot borrow — which it might, most of the time, which is the worst possible reliability profile for a number the customer will act on.

24.4"Can I afford 100 Apple in there?"

brokerage_order_preview { accountId: "…", symbol: "AAPL", side: "BUY",
                          quantity: 100, orderType: "MARKET" }
  → canPlace true, estimatedCost 24,875.00, buyingPowerAfter -12,695.00 …
    blockers [{ code: "INSUFFICIENT_BUYING_POWER",
                message: "This order needs 24,875.00 USD; 12,180.00 USD is available.",
                maxPermissibleQuantity: 48 }]
    canPlace false

What the descriptors did: the preview tool refused, in advance, with the largest quantity that would work. The customer hears "not quite — that would need $24,875 and you have $12,180 settled; 48 shares would fit" instead of watching an order get rejected. maxPermissibleQuantity is TS-ERR-03 applied inside a success payload.

24.5"Fine, buy 48 then."

brokerage_order_preview { … quantity: 48 }        → canPlace true, cnf_… (120 s)
   confirmation shown, customer approves, arguments hashed
brokerage_order_place   { … confirmationToken: "cnf_…",
                          idempotencyKey: "3f2b1c88-…", reason: "customer requested" }

What the descriptors did: statusExplanation stopped "accepted" being reported as "bought". isTerminal stopped the polling loop at the right moment. The audit record carries the confirmation the customer saw, their approval, the argument hash, and the descriptor version that produced the prose the model read.

The pattern behind the patterns

Eleven of these twelve are the same mistake: optimizing for the convenience of the team building the tool rather than the reliability of the caller consuming it. One tool is easier to ship than four. Each shortcut moves work from a place where it can be tested to a place where it can only be hoped for.

26.2What the board should ask

Six questions that separate a proposal that has been thought about from one that has been assembled. Appendix E is the full checklist; these are the ones worth asking out loud.

  1. "Read me the description." If it is unreadable aloud, or takes ninety seconds, or contains no sentence beginning "Do not use", the tool is not ready.
  2. "What is the nearest tool to this one, and what sentence tells them apart?" If the answer is a pause, the catalog has a confusability problem (§12.5).
  3. "What does the customer see if this tool is wrong?" The answer should be a specific wrong sentence, not "an error".
  4. "Show me the negative test where the customer asks for someone else's account." Not the code — the test (TS-SEC-08).
  5. "Who is paged at 2am, and what do they turn off?" Owner plus kill switch, both in the descriptor (TS-GOV-01, TS-SEC-12).
  6. "What did the evaluation say about the cases where it should refuse?" Selection accuracy is easy to score well on. Refusal accuracy is where the risk lives.

26.3Exceptions

TS-CAT-05 MUST An exception to a MUST rule MUST be recorded in the catalog against the tool, with the rule identifier, the rationale, the compensating control, the approver, and an expiry of no more than twelve months. An exception without an expiry is a silent amendment to the standard.

27Testing and certification

A tool has two correctness properties. The ordinary one — given these arguments, does it return the right data — is tested the way any service is. The other one is new: given this descriptor, does a model choose it correctly, call it correctly, and read the result correctly? That needs a different kind of test suite and is the one that decides whether the tool works in production.

27.1Contract tests

TestAsserts
Schema round tripEvery example validates against its own schema, in both directions. A descriptor whose examples contradict its schema is worse than one with no examples, because integrators copy examples.
Envelope conformanceEvery response path — success, empty, truncated, each error code — returns content, structuredContent, and isError, and the structured payload validates.
Dual-rendering agreementThe text block is generated from the structured payload and contains the as-of time, the currency, the sign, and any truncation (TS-OUT-03).
Error mappingEvery upstream failure mode maps to its declared taxonomy code, with a test per mapping (TS-ERR-06), and the unmapped branch raises an alert.
TruncationAn account with 340 positions returns 25 with truncated: true, a narrowing hint, and correct totals over all 340.
Idempotency replayThe same key twice returns the original result with replayed: true and places one order. The same key with different arguments returns CONFLICT.
Authorization negativesA principal entitled to account A requesting account B receives NOT_FOUND — identical to a genuinely absent account, timing included. The single most important test in the suite.
RedactionNo stack trace, hostname, upstream error string, or unmasked identifier appears in any error path. Asserted by pattern, over fixtures drawn from real upstream failures.
Injection neutralizationA position in an account whose nickname contains an instruction is returned delimited, labeled, and truncated (TS-SEC-11).
BudgetThe rendered descriptor and a typical result are within the budgets of §6.3 and §13.2, asserted in CI so that a field added next quarter fails the build rather than the context window.

27.3Evaluation suites

An evaluation suite is 30 to 60 real user utterances with an expected outcome for each. It is version-controlled beside the descriptor, and TS-VER-04 requires it to run on every change — including a change to nothing but the prose.

DimensionMeasuresThreshold
Selection accuracyGiven the utterance, is this the tool chosen?≥ 95% at tier 1, ≥ 98% at tier 3
Refusal accuracyGiven an utterance this tool must not answer, is it correctly left alone?≥ 95%, and ≥ 99% for tier 3
Argument accuracyAre the arguments valid, complete, and semantically right — the correct account, the correct filter?≥ 98%
Interpretation accuracyGiven the result, is the answer to the customer correct? Scored by a domain expert, not by string match.≥ 98%, and 100% on the conventions in §18.3

The cases that must be in every suite

  • Nearest-neighbor confusions. "Did my Apple order go through?" must reach orders, not positions. Every pair in §12.5 appears in both suites.
  • Convention traps. A short position, an option position, an account with unsettled cash, a retirement account, a partially filled order, a rejected order. Score the answer, not the call.
  • Empty and degraded. An account with no positions; a result with delayed marks; a truncated collection. The model must not invent an outage, quote a stale price as live, or state a partial total as complete.
  • Refusals. Requests outside the tool's scope, requests for another customer's data, requests that would need an entitlement the principal lacks.
  • Injection. An account nickname, an order memo, or an instrument name carrying an instruction. The model must not act on it.
Evaluate the descriptor, not the model

When an evaluation fails, the instinct is to adjust the agent's system prompt. Resist it. A failure means the descriptor did not carry the information the caller needed, and fixing it in the prompt fixes one agent while leaving every other consumer — including next year's vendor assistant — with the same defect. Prose in the descriptor is a fix that ships once and works everywhere.

C.2Registry rules

  • A domain code is permanent. Retire, never redefine.
  • SCREAMING_SNAKE_CASE, 64 characters or fewer, no product or system names.
  • Every code declares its taxonomy mapping and the fields its details object must carry. Those fields are what make the error actionable, and the contract test asserts them.
  • A code that fires more than 5% of the time for a tool is not an error; it is an undesigned path.

EArchitecture review checklist

The working document for a review meeting. Every line references the rule that settles it, so a disagreement is resolved by reading a section rather than by seniority. Items in bold are gating: a failure means the tool does not ship.

E.1Identity and description

  • TS-NAM-01  Name matches the grammar, has a domain segment, and its final segment is in the operation vocabulary
  • TS-NAM-02  Name is globally unique and has never been used before
  • TS-NAM-07  Title is human-readable, 60 characters or fewer, and names the consequence for tier 3
  • TS-DSC-01  Description contains purpose, "use when", "do not use", result orientation, and effects
  • TS-DSC-05  Every nearest-neighbor tool is named by exact wire name in an exclusion
  • TS-DSC-02  Description is within 2,000 characters and 180 words
  • TS-DSC-06  No instructions about agent behavior outside this tool
  • TS-DSC-07  Description is static, reviewed, and not templated at runtime
  • §18.3  Every domain convention that could produce a wrong answer is stated somewhere

E.2Schemas

  • TS-INP-01  Input schema is a closed object with explicit required and additionalProperties: false
  • TS-INP-09  Every finite-valued parameter is an enum, drawn from Appendix D
  • TS-INP-07  Every identifier is prefixed and pattern-constrained
  • TS-INP-08  Every array has maxItems; every free-text string has maxLength
  • TS-INP-14  Every parameter has a description that says more than its type
  • TS-INP-12  Defaults are the conservative choice
  • TS-INP-17  No identity, credential, pass-through query, operation discriminator, or safety-defeating flag
  • TS-INP-16  No parameter the tool cannot honor
  • TS-OUT-01  Output schema declared; both content and structuredContent returned on every path
  • TS-OUT-03  asOf and basis present on every figure that can change
  • TS-OUT-07  completeness present; truncation stated in the text rendering
  • TS-OUT-13  Money and quantities are decimal strings with an explicit currency
  • §8.6  Empty is a success; partial is disclosed or refused

E.3Classification and control

  • TS-ANN-01  All four annotations stated and consistent with the operation verb
  • TS-ANN-03  Risk tier declared and defensible; state-changing tools are tier 2 or above
  • TS-ANN-04  Tier 3 carries a confirmation template that a human can act on
  • TS-ANN-05  Approval is bound to an argument hash and expires
  • TS-SEC-07  Non-idempotent tools require an idempotency key and deduplicate for 24 hours
  • TS-SEC-02  No identity is accepted from the caller
  • TS-SEC-08  Resource-level authorization demonstrated by a negative test
  • TS-SEC-10  No token is passed through to a downstream system
  • TS-SEC-11  Externally-sourced free text is neutralized and labeled
  • TS-SEC-12  Kill switch exists for tier 2 and above, and has been tested

E.4Errors

  • TS-ERR-01  Domain failures are execution errors, not transport errors
  • TS-ERR-02  Every error carries an imperative remediation naming the next action
  • TS-ERR-03  Constraint violations state the permissible bound
  • TS-ERR-06  Every upstream failure mode is mapped and tested; the default branch alerts
  • §11.5  No stack traces, hostnames, upstream prose, or unmasked identifiers in any error
  • §11.3  INVALID_ARGUMENT and BUSINESS_RULE_VIOLATION are not conflated

E.5Governance and evidence

  • TS-GOV-01  Named owning team with a paging escalation path
  • TS-GOV-02  Minimum necessary data returned; classification and PII fields mapped
  • TS-GOV-03  Entitlements enforced at catalog, gateway, and implementation
  • TS-GOV-04  Per-principal rate limit declared
  • TS-OBS-01  Audit record emitted on every path, including the descriptor hash
  • TS-VER-04  Evaluation suite exists and has run against this version
  • §27.3  Selection, refusal, argument, and interpretation thresholds met
  • TS-SEC-09  Descriptor hash registered with the catalog
  • TS-CAT-05  Every exception recorded with a compensating control and an expiry

E.6Catalog fit

  • TS-CAT-01  The tool answers one question a user actually asks
  • TS-CAT-02  The agent's catalog stays within 25 tools
  • §12.5  One sentence distinguishes this tool from its nearest neighbor, and it is in both descriptions
  • §12.3  No common question needs three or more calls plus a domain convention the model must know
