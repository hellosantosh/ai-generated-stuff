Four situations recur in every tool catalog: the action needs a human's consent, the action needs information the agent does not have, the action might be executed twice, and the action takes longer than a conversation can wait. Each has one sanctioned pattern.

14.1 Confirmation

Policy comes from the risk tier (§9.4). The mechanics are the gateway's: it resolves the approval mode before invoking the implementation, renders the confirmationTemplate with validated arguments, obtains the principal's decision, and binds that decision to an argument hash.

The implementation must still behave correctly if approval is missing — returning APPROVAL_REQUIRED — because the gateway is not the only path that will ever exist (§3.1).

14.2 Preview then execute

Every tier 3 action is split in two. The preview tool is read-only, computes exactly what would happen, and returns a short-lived confirmationToken that encodes the previewed outcome. The execute tool accepts that token and MUST refuse to act if the world has moved enough to invalidate it.

text TS-SEC-01 — MUST#A32A2Asolid2#F4F5F7#FFFFFF

A confirmation token MUST be bound to the principal, the tool, and a hash of the previewed arguments; MUST expire within 120 seconds by default; and MUST be single-use. It is a capability, not a receipt.

 Why this beats a dryRun flag

Two tools give you two accurate annotation sets, two risk tiers, two audit identities, and a preview an agent may call freely without any approval friction — which means it will call it, which means the customer sees the cost before the question is asked. One tool with a flag gives you a descriptor that is honest about neither of its two behaviors, and a control model where the difference between simulated and real is one token in a JSON object the model generated.

14.3 Asking the principal for missing information

Sometimes a tool cannot proceed without a value the agent does not have and should not invent — which of three eligible accounts, whether to accept a worse price, an expiry date the customer has not stated. The sanctioned pattern is for the tool to ask, through the runtime, rather than to guess or to fail.

RuleLevelRequirement
TS-SEC-04RedMUST A request for input MUST be expressed as a schema of primitive fields — string, number, boolean, or enum — with a clear prompt, and MUST be declinable. An agent that cannot obtain the value returns to the user; it does not substitute a default.
TS-SEC-05GreyNEVER Input requests MUST NOT be used to collect credentials, card numbers, government identifiers, or one-time passcodes. Authentication happens in the identity plane, on a surface the customer can verify — never inside a tool's request for arguments, which is precisely the shape a phishing flow would take.
TS-SEC-06YellowSHOULD Prefer disambiguating in the schema over asking at runtime. A tool that returns INVALID_ARGUMENT naming the three eligible accounts is usually a better experience than a modal dialog, and always a simpler control.

14.4 Idempotency

An agent retries. It retries after a timeout, after an ambiguous error, and sometimes because a second model turn concluded the first one had not worked. For a read this is wasteful; for an order it is a duplicate trade.

TS-SEC-07 — MUST#A32A2Asolid2#F4F5F7#FFFFFF

Every tool that is not naturally idempotent MUST require an idempotencyKey, MUST deduplicate on it for at least 24 hours, and MUST return the original result — not an error — when a key is replayed with identical arguments. A replay with the same key and different arguments MUST fail with CONFLICT.

State this in the description too, in one sentence: models supply a key far more reliably when told what it is for than when it merely appears in the schema.

A tool MUST NOT block for longer than its declared timeout, and MUST return TIMEOUT with an explicit statement of whether the underlying operation may still complete. "The order may still have been placed" is a materially different instruction from "the order was not placed", and the agent cannot work it out.

14.6 Polling and change

Order status is the canonical case: the customer asks "did it fill?", the answer is "not yet", and something has to decide when to look again. Push subscriptions are the right answer for a trading screen and the wrong answer for a conversational agent, which has no persistent loop to receive them.

  • Return isTerminal on any entity with a lifecycle, and say in the description that a terminal entity must not be polled again. This single flag removes most wasteful polling.
  • Return nextPollAfterSeconds when the answer is "not yet", scaled to the entity — two seconds for a market order, sixty for a transfer.
  • Prefer telling the customer the firm will notify them over having an agent wait. An agent holding a conversation open to poll is an expensive, fragile timer.
