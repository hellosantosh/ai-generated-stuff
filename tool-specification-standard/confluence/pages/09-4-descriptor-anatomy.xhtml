A descriptor is a JSON document with eight top-level fields. Four of them are read by the model, three by the runtime, and one by both. Nothing else may appear at the top level.

4.1 The eight fields

FieldRequiredRead byPurpose
nameRedMUSTmodel, runtime The stable, globally unique, machine-readable identifier used to invoke the tool. Also the primary key in the catalog and in every audit record (§5.1).
titleRedMUSThuman A short human-readable label for approval dialogs, audit views, and catalog listings. Never a substitute for the description (§5.4).
descriptionRedMUSTmodel The prose contract that tells the model what this tool does, when to reach for it, when not to, and how to read what comes back (§6).
inputSchemaRedMUSTmodel, runtime A JSON Schema 2020-12 object schema describing the arguments. Doubles as the validation contract and as instruction to the model (§7).
outputSchemaRedMUSTmodel, runtime A JSON Schema 2020-12 object schema describing the structured payload the tool returns. Optional in most runtimes; required by this standard (§8).
annotationsRedMUSTruntime, human Four boolean behavioral hints — read-only, destructive, idempotent, open-world — that let a runtime reason about a tool it has never seen (§9).
iconsBlueMAYhuman Display icons for catalog and approval surfaces. Cosmetic, never semantic.
_metaRedMUSTruntime, human Namespaced out-of-band metadata. This standard requires one member — the governance block — and permits others (§10). The leading underscore marks the field as never rendered into the model's context.

A descriptor MUST NOT carry top-level fields other than the eight above. Extensions go inside _meta under a namespaced key. A runtime that encounters an unknown top-level field MUST reject the descriptor rather than ignore it: silent tolerance is how two teams end up with two incompatible meanings for the same word.

4.3 Descriptor rules

RuleLevelRequirement
TS-GEN-03RedMUST The descriptor is the source of truth and MUST be version-controlled in the owning team's repository, published to the catalog by an automated pipeline, and never edited in the catalog's user interface.
TS-GEN-04RedMUST Descriptor, implementation, and tests MUST version and deploy together. A descriptor describing behavior that is not yet deployed is a defect of the same severity as a wrong answer.
TS-GEN-05RedMUST Descriptors MUST be generated or validated by the conformance linter in CI. A build that emits a non-conformant descriptor fails.
TS-GEN-06YellowSHOULD Schemas SHOULD be derived from the implementation's types rather than hand-written alongside them, so that drift is impossible rather than merely discouraged. Prose fields are hand-written; shapes are generated.
TS-GEN-07RedMUST A descriptor MUST be self-contained: every $ref resolves either within the document or to a schema the catalog publishes and pins by immutable version. No unresolvable references, no network-dependent resolution at invocation time.
TS-GEN-08GreyNEVER A descriptor MUST NOT embed credentials, internal hostnames, connection strings, or system topology. It is read by a model and may be logged in full.
