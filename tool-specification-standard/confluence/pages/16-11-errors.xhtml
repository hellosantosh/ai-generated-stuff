A tool's error path is used more often than anyone plans for, is read by a caller that cannot ask what it means, and is the single place where a firm most often leaks something it should not. It deserves the same design attention as the success path and usually gets a tenth of it.

11.1 Two kinds of failure

KindExamplesHandling
Transport or protocol failure
the tool never ran		 Tool name not found · malformed invocation · gateway unreachable · authentication to the gateway failed Handled by the runtime. The model may never see it. Not modeled by this standard.
Execution error
the tool ran and could not do the job		 Account not found · not entitled · insufficient buying power · market closed · upstream margin engine down · rate limit exceeded Returned as a successful transport response with isError: true and a structured error payload the model reads and acts on.
TS-ERR-01 — MUST#A32A2Asolid2#F4F5F7#FFFFFF

Domain and business failures MUST be returned as execution errors inside the envelope, never raised as transport or protocol errors. A protocol error is frequently retried blindly by the runtime, is often invisible to the model, and reaches the customer as "something went wrong" — which is the least useful true statement available.

FieldRequiredRules
codeRedMUST One of the fifteen values in §11.3. Closed set; the only field safe to branch on.
domainCodeYellowSHOULD A specific, stable, registered code from Appendix C. This is what a customer-facing surface localizes and what analytics group by.
messageRedMUST One or two sentences a person could read. States what happened, including the numbers that make it concrete. Contains no internal identifiers, no stack, no upstream prose (§11.5).
retryableRedMUST Whether repeating the identical call could succeed. Explicitly boolean: a caller that must infer retryability from prose will infer it wrongly, and its wrong inference is a retry storm.
retryAfterSecondsWhen retryable How long to wait. Present on RATE_LIMITED and UPSTREAM_UNAVAILABLE.
remediationRedMUST What to do next, as an instruction (§11.4).
detailsYellowSHOULD Structured, code-specific facts — which field failed, which limit was hit, what the maximum permissible value would have been. This is what turns a dead end into a second, correct attempt.
traceIdRedMUST The correlation identifier. The only value in the payload that ties a customer's complaint to a log line, and the only internal identifier permitted to cross out.

11.3 The taxonomy

CodeRetryMeans, and what the caller should do
INVALID_ARGUMENTNo The arguments were malformed or violated the schema. Fix the argument — details.violations names the offending field with a JSON Pointer.
NOT_FOUNDNo The identified entity does not exist, or exists outside the principal's grant — deliberately indistinguishable, so that the tool cannot be used to enumerate identifiers. Do not guess another identifier; list first.
AUTHENTICATION_REQUIREDAfter re-auth Credentials absent, expired, or revoked. The agent cannot fix this; the principal must re-authenticate.
ENTITLEMENT_DENIEDNo Authenticated, but not permitted — a missing scope or an unapproved account. Ask the customer to grant access; never retry.
APPROVAL_REQUIREDAfter approval A human confirmation is needed and was not present. Present the confirmation and re-invoke with the token.
APPROVAL_DENIEDNo A human declined. Stop. Do not rephrase and retry — this is the failure mode that turns a declined trade into three declined trades.
PRECONDITION_FAILEDSometimes A required precondition was not met — a stale confirmation token, a missing idempotency key, a version mismatch. details names it.
CONFLICTNo The entity's state does not permit the operation: the order already filled, the account is closed. Re-read the entity before doing anything else.
BUSINESS_RULE_VIOLATIONNo Well-formed and permitted, but the domain said no — insufficient buying power, market closed, options level too low, instrument halted. The request was fine; the world declined. Explain it to the customer rather than retrying.
RATE_LIMITEDYes, after wait Quota exhausted. Honor retryAfterSeconds. If it recurs, the agent is looping and should stop.
TIMEOUTIf idempotent The operation did not complete in budget. Retry only if idempotentHint is true or an idempotency key was supplied — otherwise re-read state to find out whether it happened.
UPSTREAM_UNAVAILABLEYes, with backoff A system of record is down or degraded. details.system names which, so the agent can tell the customer what is unavailable rather than apologizing vaguely.
DATA_INCOMPLETEYes, with backoff The answer could be computed only partially and the tool refused to return a misleading figure (§8.6). Distinct from UPSTREAM_UNAVAILABLE because the tool did reach its sources.
NOT_SUPPORTEDNo A well-formed request for something this tool does not do — a historical asOf on a real-time-only tool, an asset class not covered. remediation names the tool that does.
INTERNAL_ERROROnce An unexpected failure. Carries a traceId and nothing else of substance. If a tool returns this more than rarely, it is mapping errors lazily (§11.6).
INVALID_ARGUMENT versus BUSINESS_RULE_VIOLATION

The distinction is the most useful one in the taxonomy. INVALID_ARGUMENT means the caller is wrong — change the argument and it will work. BUSINESS_RULE_VIOLATION means the caller is fine and reality declined — not enough buying power, market closed, instrument halted. A caller that conflates them retries a doomed order and then tells the customer "invalid request" when the honest answer was "the market is closed". Tools that return one code for both make every agent built on them worse.

TS-ERR-02RedMUST remediation MUST be an instruction in the imperative, naming the argument to change or the tool to call instead. Apologies are not remediation.
TS-ERR-03RedMUST Where a constraint was violated, the error MUST state the permissible value or bound — the maximum quantity, the valid window, the required approval level. An error that says "too large" without saying how large is permitted forces a guessing loop.
TS-ERR-04RedMUST Where a retry is futile, remediation MUST say so explicitly — "do not retry". Models are biased toward retrying, and an explicit prohibition is markedly more effective than retryable: false alone.
TS-ERR-05RedMUST Validation failures MUST enumerate every violation, not just the first. One round trip per invalid field is a conversation the customer watches.

11.5 Redaction

An error payload enters a context window, is retained in conversation history, may be forwarded to a model provider, and is frequently pasted into a support ticket. Treat every byte of it as published.

Never includeInstead
Stack traces, exception class names, line numbers INTERNAL_ERROR plus a traceId. The stack belongs in the log, correlated by that identifier.
Raw upstream error text, vendor error codes, SQL fragments A mapped taxonomy code. Upstream prose is unversioned, occasionally contains customer data, and is written for a different reader.
Internal hostnames, queue names, service topology details.system with a stable business-capability label ("margin engine"), never an infrastructure name.
Full account numbers, government identifiers, dates of birth The masked form the customer sees on their statement (••••4471).
Any data about a principal other than the caller Nothing. If the error would disclose that another customer exists, the correct answer is NOT_FOUND.
Whether an identifier exists but is not permitted NOT_FOUND, uniformly. Distinguishing the two turns a tool into an enumeration oracle.

Most tools wrap something. The mapping from that something's failures to this taxonomy is a design artifact that belongs in the tool's tests, not an afterthought in a catch block.
