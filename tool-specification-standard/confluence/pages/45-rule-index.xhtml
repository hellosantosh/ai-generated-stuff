Every normative rule in the standard, with its level and the section that defines it. Cite these identifiers in reviews and pull requests.

Rule identifiers are permanent

A withdrawn rule is marked withdrawn and its number is never reused, so a review comment reading "fails TS-INP-07" means the same thing in five years as it does today. The linter reports findings by these identifiers.

TS-GEN  ·  General and descriptor structure
TS-GEN-01RedMUST1.3Every tool reachable from a production agent MUST hold at least Level 1. Every tool that reads customer data, moves money, changes an order, or writes to a system of record MUST hold Level 2.
TS-GEN-02RedMUST4.1A descriptor MUST NOT carry top-level fields other than the eight above. Extensions go inside _meta under a namespaced key. A runtime that encounters an unknown top-level field MUST reject the descriptor rather than ignore it: silent tolerance is…
TS-GEN-03RedMUST4.3The descriptor is the source of truth and MUST be version-controlled in the owning team's repository, published to the catalog by an automated pipeline, and never edited in the catalog's user interface.
TS-GEN-04RedMUST4.3Descriptor, implementation, and tests MUST version and deploy together. A descriptor describing behavior that is not yet deployed is a defect of the same severity as a wrong answer.
TS-GEN-05RedMUST4.3Descriptors MUST be generated or validated by the conformance linter in CI. A build that emits a non-conformant descriptor fails.
TS-GEN-06YellowSHOULD4.3Schemas SHOULD be derived from the implementation's types rather than hand-written alongside them, so that drift is impossible rather than merely discouraged. Prose fields are hand-written; shapes are generated.
TS-GEN-07RedMUST4.3A descriptor MUST be self-contained: every $ref resolves either within the document or to a schema the catalog publishes and pins by immutable version. No unresolvable references, no network-dependent resolution at invocation time.
TS-GEN-08GreyNEVER4.3A descriptor MUST NOT embed credentials, internal hostnames, connection strings, or system topology. It is read by a model and may be logged in full.
TS-NAM  ·  Naming and identity
TS-NAM-01RedMUST5.1A tool name MUST match ^[a-z][a-z0-9_]{2,63}$ — lowercase ASCII letters, digits, and underscore; starting with a letter; between 3 and 64 characters.
TS-NAM-02RedMUST5.1.1Names MUST be globally unique across the firm's catalog, compared case-insensitively and with underscores ignored. orders_list and ordersList collide.
TS-NAM-03YellowSHOULD5.1.1Names SHOULD be 40 characters or fewer. Long names crowd every prompt and get truncated in audit and approval surfaces.
TS-NAM-04RedMUST5.1.1The name MUST NOT encode a version (_v2) unless the tool is a deliberate breaking successor published under §17.3, in which case it MUST.
TS-NAM-05GreyNEVER5.1.1Names MUST NOT contain an environment, region, tenant, or vendor (_uat, _emea, _fiserv). Those are deployment facts; a model that can see them will eventually reason about them.
TS-NAM-06RedMUST5.3The final segment MUST come from the vocabulary above. Proposals to extend it go to the Architecture Review Board and are granted for genuinely new shapes of operation, not for synonyms.
TS-NAM-07RedMUST5.4Every descriptor MUST carry a title: sentence case, no trailing punctuation, 60 characters or fewer, understandable to someone who does not know the system — "Get order status", not "OMS order status retrieval (v2)".
TS-NAM-08RedMUST5.4The title MUST describe the same operation as the name. A title that says "View" on a tool that cancels is a control failure, not a typo.
TS-NAM-09YellowSHOULD5.4Titles of state-changing tools SHOULD lead with the verb and name the consequence: "Cancel a working order", not "Order cancellation".
TS-NAM-10BlueMAY5.4Icons MAY be supplied for catalog and approval surfaces. Provide SVG with a light and a dark variant. Icons are decoration: no control, policy, or model behavior may depend on one.
TS-NAM-11RedMUST5.5A published tool name is permanent. It MUST NOT be reused for a different capability, and a capability MUST NOT be renamed. A name change is modeled as a new tool plus deprecation of the old one under §17.4.
TS-DSC  ·  Descriptions
TS-DSC-01RedMUST6.2Every description MUST contain parts 1, 2, 3, 5, and 6 below. Parts 4 and 7 are where they apply — which, for anything in a financial domain, is nearly always.
TS-DSC-02RedMUST6.3A tool description MUST NOT exceed 2,000 characters. A description at the limit is usually a tool that should have been two.
TS-DSC-03RedMUST6.3A parameter description MUST NOT exceed 240 characters. Anything longer belongs in the tool description, where it is read once rather than per parameter.
TS-DSC-04RedMUST6.5Descriptions MUST be plain prose in the active voice, present tense, starting with a verb. No markdown headings, no bullet syntax, no code fences — runtimes render descriptions inconsistently and structure is lost or corrupted.
TS-DSC-05RedMUST6.5Sibling tools referenced in exclusions MUST be named by their exact wire name. "Use the balances tool" is not actionable; brokerage_balances_get is.
TS-DSC-06RedMUST6.5Descriptions MUST NOT contain instructions about how the agent should behave outside this tool call — how to address the customer, what to disclose, when to escalate, what to do in other conversations. A tool describes itself;
TS-DSC-07GreyNEVER6.5Descriptions MUST NOT be generated at runtime, templated with request data, or personalized per user. A description is a static, reviewed, signed artifact. Anything dynamic belongs in the result payload.
TS-DSC-08YellowSHOULD6.5Descriptions SHOULD use the domain's own vocabulary — the words that appear on the customer's statement and in the firm's procedures. Inventing a synonym for a term of art makes the tool harder to select and its audit trail harder to read.
TS-DSC-09YellowSHOULD6.5Where an enumerated value has consequences, the description SHOULD state them once — "RESTRICTED accounts can be read but not traded" — rather than leaving the model to infer meaning from a token.
TS-DSC-10RedMUST6.6A description MUST NOT reference a tool outside its own domain namespace except to exclude it, and MUST NOT contain imperative instructions addressed to the agent about tools other than itself. Descriptions that do are rejected at publish time.
TS-INP  ·  Input schemas
TS-INP-01RedMUST7.1inputSchema MUST be a JSON Schema 2020-12 document whose root is {"type": "object"} with an explicit properties map, an explicit required array (possibly empty), and "additionalProperties": false.
TS-INP-02YellowSHOULD7.1.2An input schema SHOULD declare no more than 12 top-level properties and SHOULD NOT nest more than two levels deep. Beyond that, argument-composition accuracy degrades sharply and the tool is usually doing two jobs.
TS-INP-03RedMUST7.2Property names MUST be lowerCamelCase and MUST use the domain's own vocabulary — accountId, timeInForce, limitPrice — not invented synonyms.
TS-INP-04RedMUST7.2A property name MUST mean the same thing in every tool in the catalog. quantity cannot be shares in one tool and contracts in another. Where a concept recurs, take it from the shared type library (Appendix B) rather than redefining it.
TS-INP-05YellowSHOULD7.2Boolean parameters SHOULD be named positively and default to the conservative value: includeClosed defaulting to false, never excludeClosed defaulting to false. Double negatives are reliably mis-set.
TS-INP-06YellowSHOULD7.2Inputs SHOULD be flat. Nesting that exists only to mirror an upstream request body is noise; flatten it and let the implementation rebuild the shape.
TS-INP-07RedMUST7.2Identifiers MUST be opaque, prefixed, and pattern-constrained (acct_, ord_, inst_). The prefix tells the model which identifier goes in which slot, and the pattern stops a well-formed-looking hallucination before it reaches a system of record.
TS-INP-08RedMUST7.2Every array parameter MUST declare maxItems, and every string parameter MUST declare maxLength.
TS-INP-09RedMUST7.3.1Any parameter whose valid values are a known finite set MUST be an enum. Enumerated values MUST be SCREAMING_SNAKE_CASE and MUST match the domain enumerations in Appendix D exactly — the same tokens the systems of record and the customer statement…
TS-INP-10RedMUST7.4A parameter is required only if the tool genuinely cannot proceed without it. Marking a parameter required to force the model to "think about it" causes the model to invent a value instead.
TS-INP-11RedMUST7.4Every optional parameter's omission behavior MUST be stated in its description in prose, not only in default. Models read prose far more reliably than they read schema annotations.
TS-INP-12RedMUST7.4Defaults MUST be the narrow, conservative, least-surprising choice: the smallest page, the current account only, the shortest date window, exclusions on. A default that widens scope is a defect even when it is convenient.
TS-INP-13GreyNEVER7.4A parameter that changes the tool's safety characteristics — whether a change is simulated or real, whether validation is skipped, whether a confirmation is required — MUST NOT exist. Those are separate tools with separate annotations (§9.1, §25.2).
TS-INP-14RedMUST7.5Every property in an input schema MUST carry a description. A property description MUST NOT restate the type, and MUST state, where applicable: where the value comes from, its unit or convention, and what happens if it is omitted.
TS-INP-15RedMUST7.6Where a tool needs one of the reserved parameter concepts, it MUST use the standard name and shape rather than inventing an equivalent.
TS-INP-16RedMUST7.6A tool MUST NOT accept a parameter it cannot honor. Offering an asOf on a tool with no history, or a currency on a tool that only reports in the account's base currency, is worse than omitting it: the model will supply the parameter and silently…
TS-INP-17RedMUST7.7An input schema MUST NOT contain any of the patterns below. Each is rejected at review and by the linter; the right-hand column is the reason, not a mitigation.
TS-OUT  ·  Output and envelopes
TS-OUT-01RedMUST8.1Every tool MUST declare an outputSchema and MUST return both content and structuredContent on every invocation, including error invocations. Runtimes differ in which one they surface to the model;
TS-OUT-02RedMUST8.2The text rendering MUST be derived from structuredContent by the implementation — generated, not hand-maintained — so the two cannot disagree.
TS-OUT-03RedMUST8.2The text rendering MUST NOT contain any fact absent from structuredContent, and MUST carry the facts a reader could be materially misled by omitting: the as-of time, the currency, the sign of a position, and any truncation.
TS-OUT-04YellowSHOULD8.2The text rendering SHOULD be compact — a few hundred characters for a typical result — and SHOULD NOT be a pretty-printed dump of the structured payload. Duplicating the whole payload as text doubles the token cost of every call for no gain.
TS-OUT-05RedMUST8.2Monetary and quantity values in the text rendering MUST carry their currency and their sign explicitly. "−98,240.00 USD" and "SHORT 400" are unambiguous; "98240" is a defect waiting for a customer complaint.
TS-OUT-06RedMUST8.4Collections MUST use opaque forward cursors. Offset and page-number pagination MUST NOT be used against a mutable collection.
TS-OUT-07RedMUST8.4When a result is truncated, completeness.truncated MUST be true and the text rendering MUST say so in words: "showing 25 of 340 positions". Silent truncation causes the model to state a partial total as a complete one.
TS-OUT-08YellowSHOULD8.4A truncated result SHOULD tell the reader how to narrow rather than how to continue: "filter by assetClass or symbol to see fewer than 340". Narrowing produces a correct answer in one more call; paging produces fourteen calls and an abandoned loop.
TS-OUT-09YellowSHOULD8.4Where a caller is likely to want the whole collection only in order to compute an aggregate, the catalog SHOULD offer a summarize tool that computes it server-side.
TS-OUT-10RedMUST8.5Binary content and any text payload over 100 KB MUST be returned by reference rather than inline. Reference URIs MUST be short-lived and MUST require the principal's own authority to dereference — a link that anyone holding the URI can fetch has…
TS-OUT-11RedMUST8.6Balances, buying power, and anything that gates a trading decision MUST NOT be returned partially computed; the tool fails instead.
TS-OUT-12RedMUST13.2Every tool MUST enforce a result size ceiling in code and MUST truncate with disclosure (TS-OUT-07) rather than returning an unbounded payload. "The customer has 340 positions" is not an excuse; it is the case the ceiling exists for.
TS-OUT-13RedMUST13.5Monetary amounts and quantities MUST be decimal strings — "62137.50" — never IEEE-754 numbers. Binary floating point cannot represent a cent, and the error is silent, compounding, and eventually a reconciliation break.
TS-OUT-14RedMUST13.5Every monetary value MUST be accompanied by an ISO 4217 currency, at the value or at the envelope level. Never assume USD.
TS-OUT-15RedMUST13.5Structured values MUST NOT carry locale formatting — no thousands separators, no currency symbols, no parenthesized negatives. Formatting belongs in the text rendering, where (2,110.00) is spelled -2,110.00 USD because parentheses for negatives are…
TS-OUT-16RedMUST13.5Timestamps MUST be RFC 3339 with an explicit UTC offset. Dates that are genuinely dates — settlement date, expiry — are YYYY-MM-DD, and the description MUST name the time zone they are interpreted in.
TS-ERR  ·  Errors
TS-ERR-01RedMUST11.1Domain and business failures MUST be returned as execution errors inside the envelope, never raised as transport or protocol errors.
TS-ERR-02RedMUST11.4remediation MUST be an instruction in the imperative, naming the argument to change or the tool to call instead. Apologies are not remediation.
TS-ERR-03RedMUST11.4Where a constraint was violated, the error MUST state the permissible value or bound — the maximum quantity, the valid window, the required approval level. An error that says "too large" without saying how large is permitted forces a guessing loop.
TS-ERR-04RedMUST11.4Where a retry is futile, remediation MUST say so explicitly — "do not retry". Models are biased toward retrying, and an explicit prohibition is markedly more effective than retryable: false alone.
TS-ERR-05RedMUST11.4Validation failures MUST enumerate every violation, not just the first. One round trip per invalid field is a conversation the customer watches.
TS-ERR-06RedMUST11.6Every upstream failure mode MUST have an explicit mapping with a test. A default branch that maps everything unrecognized to INTERNAL_ERROR is permitted and MUST raise an alert when it fires: an unmapped upstream failure is a contract change nobody…
TS-ANN  ·  Annotations and risk tiers
TS-ANN-01RedMUST9.1All four annotations MUST be stated explicitly, even where the value equals the default. The defaults are deliberately pessimistic so that an omission fails safe;
TS-ANN-02RedMUST9.1Annotations MUST be consistent with the operation verb in the tool's name (§5.3). A tool named ..._list with readOnlyHint: false fails the linter, and a tool named ..._place with readOnlyHint: true fails it harder.
TS-ANN-03RedMUST9.3Every descriptor MUST declare a riskTier. A tool whose tier is disputed at review defaults to the higher tier until the dispute is resolved in writing.
TS-ANN-04RedMUST9.4.1Tier 3 tools MUST supply a confirmationTemplate that renders, in the principal's language: the action, the identified account in customer-facing terms, the instrument in words, the quantity and the money, the reversibility, and the material…
TS-ANN-05RedMUST9.4.1Approval MUST be bound to the exact argument set that was displayed. The runtime MUST hash the validated arguments, present them, and refuse execution if anything differs.
TS-ANN-06RedMUST9.4.1Approvals MUST expire — 120 seconds is the default for trading actions — and MUST NOT be reusable for a second invocation.
TS-ANN-07GreyNEVER9.4.1A tool MUST NOT be able to lower its own approval requirement through an argument, a description, or a returned instruction. Approval policy is resolved from the catalog, before the implementation is reached.
TS-GOV  ·  Governance metadata
TS-GOV-01RedMUST10.2Every tool MUST name an owning team with a paging escalation path. The catalog MUST re-verify ownership quarterly and automatically move a tool whose owner cannot be confirmed to deprecated, then retired ninety days later.
TS-GOV-02RedMUST10.3A tool MUST return the minimum data that answers its question. Returning an entire upstream record because it was convenient is a data-minimization failure, and in an agent context the data does not merely sit in a response object — it enters a…
TS-GOV-03RedMUST10.4Entitlements MUST be enforced at three points: (a) catalog visibility — an agent is not offered a tool its principal cannot use; (b) the gateway, before invocation; (c) the implementation, against the specific resource named in the arguments.
TS-GOV-04RedMUST10.5Every tool MUST declare a rate limit per principal. Where a tool is expensive in money or in upstream capacity, the description SHOULD say so plainly — a model told that a tool is slow and expensive will use it more sparingly, which is a cheaper…
TS-GOV-05RedMUST14.5A tool MUST NOT block for longer than its declared timeout, and MUST return TIMEOUT with an explicit statement of whether the underlying operation may still complete.
TS-SEC  ·  Security and trust
TS-SEC-01RedMUST14.2A confirmation token MUST be bound to the principal, the tool, and a hash of the previewed arguments; MUST expire within 120 seconds by default; and MUST be single-use. It is a capability, not a receipt.
TS-SEC-02GreyNEVER15.2A tool MUST NOT accept an argument that asserts identity, role, tenancy, or entitlement. Identity arrives out of band, from the identity plane. A tool with an onBehalfOf parameter has delegated its access control to a language model.
TS-SEC-03GreyNEVER15.2Credentials of any kind MUST NOT appear in arguments, results, errors, or descriptions. Anything in those four places will be logged, retained in conversation history, and may be transmitted to a model provider.
TS-SEC-04RedMUST14.3A request for input MUST be expressed as a schema of primitive fields — string, number, boolean, or enum — with a clear prompt, and MUST be declinable. An agent that cannot obtain the value returns to the user; it does not substitute a default.
TS-SEC-05GreyNEVER14.3Input requests MUST NOT be used to collect credentials, card numbers, government identifiers, or one-time passcodes. Authentication happens in the identity plane, on a surface the customer can verify — never inside a tool's request for arguments,…
TS-SEC-06YellowSHOULD14.3Prefer disambiguating in the schema over asking at runtime. A tool that returns INVALID_ARGUMENT naming the three eligible accounts is usually a better experience than a modal dialog, and always a simpler control.
TS-SEC-07RedMUST14.4Every tool that is not naturally idempotent MUST require an idempotencyKey, MUST deduplicate on it for at least 24 hours, and MUST return the original result — not an error — when a key is replayed with identical arguments.
TS-SEC-08RedMUST15.2The implementation MUST authorize the principal against the specific resource named in the arguments, on every invocation. Holding brokerage:positions:read authorizes reading your positions, not a position identifier you were able to produce.
TS-SEC-09RedMUST15.7Every descriptor's content hash MUST be recorded at approval. Runtimes MUST pin the approved hash and MUST refuse to present or invoke a tool whose descriptor has changed without a new approval — for internal tools too, but decisively for external…
TS-SEC-10GreyNEVER15.2A token presented to the gateway MUST NOT be forwarded verbatim to a downstream system. Exchange it for a token whose audience is that system, scoped to this operation.
TS-SEC-11RedMUST15.3Free-text content that did not originate in a system the firm controls MUST be neutralized before it is returned: length-capped, stripped of control characters and markup, and MUST be delimited and labeled as customer-supplied or externally-supplied…
TS-SEC-12RedMUST15.6Every tier 2 and tier 3 tool MUST be disableable within 60 seconds, by capability, by audience, and globally, without a deployment.
TS-SEC-13RedMUST15.7Third-party tools MUST be reviewed against this standard before admission, MUST be re-reviewed on every descriptor change, and MUST be assumed to have mis-stated their annotations — the firm assigns the risk tier independently, from observed…
TS-SEC-14RedMUST15.7A third-party tool MUST NOT be presented to an agent in the same context as a firm tier 3 tool unless the combination has been explicitly assessed. The risk is not either tool; it is that one tool's output can steer the other's invocation.
TS-OBS  ·  Observability and audit
TS-OBS-01RedMUST16.1Every invocation — successful, failed, denied, or refused at policy — MUST emit exactly one audit record containing the fields below, retained for the period named in the tool's recordKeeping.retention.
TS-OBS-02RedMUST16.1For tier 3 tools the audit record MUST be sufficient to reconstruct the decision: the arguments, the confirmation exactly as the principal saw it, their response, the result, and the descriptor version that produced the prose the model read.
TS-OBS-03RedMUST27.4Tier 3 tools and every L3 exposure MUST be red-teamed before release and at least annually thereafter, by a team that did not build them.
TS-VER  ·  Versioning and lifecycle
TS-VER-01RedMUST17.2governance.version MUST be semantic. Patch for prose and non-behavioral fixes; minor for compatible additions; major only alongside a new tool name (TS-VER-03).
TS-VER-02RedMUST17.2Output enumerations MUST be documented as open: the description states that new members may appear and how to treat one. Order status is the canonical case — an unrecognized status means working, never terminal, and getting that default backwards…
TS-VER-03RedMUST17.2A breaking change MUST be published as a new tool name with a _v2 suffix, running alongside the original. The two coexist for the full deprecation window.
TS-VER-04RedMUST17.2Any change to prose, schema, or behavior MUST re-run the tool's evaluation suite before publication (§27.3). A description edit is a behavior change: it is the input that determines whether the tool is selected at all.
TS-VER-05RedMUST17.4The platform team MUST maintain a register of the constraints imposed by every runtime the firm publishes to, MUST enforce the intersection of those constraints in the linter, and MUST re-validate the entire catalog whenever a runtime's constraints…
TS-CAT  ·  Catalog and registration
TS-CAT-01YellowSHOULD12.1One tool SHOULD correspond to one decision the agent has to make, expressed as one question a user would ask — not to one resource, one endpoint, or one database table.
TS-CAT-02YellowSHOULD12.4An agent SHOULD be offered no more than 25 tools, and MUST NOT be offered more than 40 without a documented exception.
TS-CAT-03RedMUST12.4The catalog MUST support audience-scoped views, so that a customer-facing assistant, an adviser's copilot, and an operations agent each see only their own set. Audience scoping is an entitlement decision (§10.4), not a UI preference.
TS-CAT-04YellowSHOULD12.4Where an estate genuinely exceeds what one agent can hold, the platform SHOULD scope by task phase — a small core set always present, with a task-specific set attached when the conversation enters that task — rather than presenting everything and…
TS-CAT-05RedMUST26.3An exception to a MUST rule MUST be recorded in the catalog against the tool, with the rule identifier, the rationale, the compensating control, the approver, and an expiry of no more than twelve months.
TS-CAT-06RedMUST28.1Be the single system of record for descriptors, serving them by name and version, with content hashes, to every runtime in the firm.
TS-CAT-07RedMUST28.1Accept descriptors only from an authenticated publishing pipeline, never from a user interface, and MUST reject any that fail the linter or the meta-schema (TS-GEN-03, TS-GEN-05).
TS-CAT-08RedMUST28.1Enforce global name uniqueness at publish time and refuse to reuse a retired name (TS-NAM-02, TS-NAM-11).
TS-CAT-09RedMUST28.1Serve audience-scoped views resolved against the principal's entitlements, so a tool a principal cannot use is never placed in an agent's context (TS-GOV-03).
TS-CAT-10RedMUST28.1Retain every published version indefinitely. An audit record naming a tool version is meaningless if that version cannot be retrieved.
TS-CAT-11YellowSHOULD28.1Expose ownership, risk tier, lifecycle, dependencies, invocation volume, and evaluation results as a browsable inventory — the artifact a regulator asks for when they ask what the firm's agents can do.
