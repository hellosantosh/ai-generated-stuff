20.2 Input schema

json
DecisionReasoning
symbol matches the underlying A customer asking "how am I doing on Apple" means the shares and the calls. Matching only the exact instrument would answer a question nobody asked, and the model has no way to know it got a partial answer.
detail rather than a field list Three named levels the model chooses between reliably, versus an open field list it composes badly and which would make the output schema unstable (§13.3.1).
pageSize maximum of 100 Above 100 the result exceeds the token budget in §13.2 regardless of detail. The ceiling is in the schema so the model cannot ask for a payload the tool would have to truncate anyway.
No asOf This tool has no history. Accepting a parameter it cannot honor would be worse than not offering it: the model would use it, and silently receive current data labeled with a past date (TS-INP-16).
No sortBy Largest market value first is right for essentially every question a customer asks. A sort parameter would add a decision the model has to make on every call in exchange for almost nothing.

20.4.1 Six deliberate choices in that payload

ChoiceWhy
side as well as a signed quantity Redundant by design. A model that misses the minus sign cannot miss "side": "SHORT", and the text rendering spells it a third time. The cost is four tokens per position; the failure it prevents is a customer being told they own something they owe.
sharesEquivalent computed server-side 3 contracts × 100 = 300 is arithmetic the model can do and sometimes will not. Doing it in the tool makes it testable.
totals over the filter, not the page A total summed from a truncated array is wrong. Computing it server-side over the whole matching set removes the most likely arithmetic error in the interaction (TS-OUT-09).
daysToExpiry alongside expiry Date arithmetic against "today" is a recurring model weakness, and an option expiring this week is materially different from one expiring in a year.
Envelope-level currency and asOf Stated once rather than on every row (§13.3), which at 340 positions is the difference between a usable and an unusable payload.
Text rendering repeats the totals Several runtimes surface only the text block. A rendering that omitted the totals would make the model re-derive them from the rows it can see — that is, from the truncated ones.

Account holds nothing— Not an error. Empty array, totals of zero, and a text rendering that says "This account holds no positions."
Market data unavailable— Not an error. basis becomes PRIOR_CLOSE, a disclosure is added, and the text says the marks are from the prior close.

The last row is the one that matters

An outage that returns an empty list instead of an error tells the customer they own nothing. It is the highest-severity failure this tool has, it is entirely silent, and it is what happens by default in any implementation that treats "no rows returned" and "no rows retrieved" as the same condition. The remediation text says so explicitly because the model is the last line of defense against it.
