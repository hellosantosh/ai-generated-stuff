The consumer of a tool contract cannot read a changelog, cannot be scheduled for an upgrade, and does not have a version pin of its own. That removes most of the usual options and makes the remaining rule very simple: additive change, or a new tool.

17.1 What is a breaking change

ChangeVerdict
Adding an optional input parameter with a safe defaultCompatible
Adding a field to the output schemaCompatible
Adding a member to an output enumCompatible — consumers are told to treat unrecognized members as unknown (§17.2)
Relaxing a constraint (raising a maximum, widening a pattern)Compatible
Clarifying prose without changing behaviorCompatible — and encouraged; this is the cheapest fix available
Making an optional parameter requiredBreaking
Removing or renaming any field, input or outputBreaking
Adding a member to an input enumBreaking in effect — it changes what the model will send, and callers of the old contract never learn about it. Treat as a minor version and re-run evaluations.
Tightening a constraintBreaking
Changing a unit, a convention, or a signBreaking, and dangerous — nothing fails, answers just become wrong
Changing default behavior on omissionBreaking
Raising the risk tier or adding an approval requirementCompatible technically, breaking operationally — announce it

17.2 Versioning rules

RuleLevelRequirement
TS-VER-01RedMUST governance.version MUST be semantic. Patch for prose and non-behavioral fixes; minor for compatible additions; major only alongside a new tool name (TS-VER-03).
TS-VER-02RedMUST Output enumerations MUST be documented as open: the description states that new members may appear and how to treat one. Order status is the canonical case — an unrecognized status means working, never terminal, and getting that default backwards tells a customer their order is dead when it is live.
TS-VER-03RedMUST A breaking change MUST be published as a new tool name with a _v2 suffix, running alongside the original. The two coexist for the full deprecation window.
TS-VER-04RedMUST Any change to prose, schema, or behavior MUST re-run the tool's evaluation suite before publication (§27.3). A description edit is a behavior change: it is the input that determines whether the tool is selected at all.

17.3 Deprecation

  1. Announce. Set lifecycle: deprecated with deprecation.{since, sunset, successor, migrationNote}. Minimum window: 90 days, or one full regulatory reporting cycle, whichever is longer.
  2. Stop new grants. The catalog no longer offers the tool to audiences that do not already have it. Existing consumers are unaffected.
  3. Warn out of band. Results carry a deprecation notice in _meta, which the runtime logs. The description is not changed — deprecation prose in the description costs tokens on every turn, and a model told a tool is deprecated behaves unpredictably rather than migrating.
  4. Measure. Track invocations by audience. Contact the owner of each remaining consumer directly.
  5. Retire. At sunset, set lifecycle: retired. The tool returns NOT_SUPPORTED naming the successor for a further 90 days, then is withdrawn. The name is never reused (TS-NAM-11).

17.4 The runtime constraint register

Tool-calling runtimes impose their own limits — name length and character set, maximum number of tools, maximum schema depth, whether output schemas are honored, whether annotations are surfaced. These change without notice and are not the firm's to control.

The platform team MUST maintain a register of the constraints imposed by every runtime the firm publishes to, MUST enforce the intersection of those constraints in the linter, and MUST re-validate the entire catalog whenever a runtime's constraints change. A tool that silently stops being offered because a name grew too long for one runtime is an outage nobody will attribute correctly.
