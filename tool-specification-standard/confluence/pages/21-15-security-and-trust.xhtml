15.1 Principles

PrincipleIn practice
The agent has no authority of its own Every action is performed as a principal, with that principal's scopes, subject to that principal's entitlements. There is no service account that "the assistant" uses to read customer accounts — that account would be a standing breach waiting for a prompt.
Least privilege, per invocation The scopes required are declared per tool and checked per invocation against the specific resource in the arguments, not once per session.
Everything the model produces is untrusted input Arguments are validated and authorized as though they came from an anonymous internet client, because in the relevant sense they did.
Everything a tool returns is untrusted input to the model Customer-supplied and counterparty-supplied strings are data. They are marked, neutralized, and never interpreted as instruction.
Controls live where they cannot be talked out of In the gateway and the implementation. Not in the description, not in the annotations, not in the system prompt — all three are inputs to a system that can be persuaded.

15.2 Identity and authorization

RuleLevelRequirement
TS-SEC-02GreyNEVER A tool MUST NOT accept an argument that asserts identity, role, tenancy, or entitlement. Identity arrives out of band, from the identity plane. A tool with an onBehalfOf parameter has delegated its access control to a language model.
TS-SEC-08RedMUST The implementation MUST authorize the principal against the specific resource named in the arguments, on every invocation. Holding brokerage:positions:read authorizes reading your positions, not a position identifier you were able to produce.
TS-SEC-10GreyNEVER A token presented to the gateway MUST NOT be forwarded verbatim to a downstream system. Exchange it for a token whose audience is that system, scoped to this operation. Pass-through re-uses a credential outside the audience it was issued for and destroys the ability to attribute a downstream action.
TS-SEC-03GreyNEVER Credentials of any kind MUST NOT appear in arguments, results, errors, or descriptions. Anything in those four places will be logged, retained in conversation history, and may be transmitted to a model provider.

15.2.1 The confused deputy

The gateway is a deputy: it holds authority the agent does not, and it acts on the agent's instructions. The classic failure is a gateway that authenticates the agent, authorizes the tool, and then performs an operation against a resource the principal never had access to — because nothing re-checked the resource.

In this domain the attack is trivially expressible: a customer asks their assistant about "account acct_01HQ9F3M7X2K8P4T", an identifier they obtained, guessed, or found. Every layer above the implementation sees a well-formed request from an authenticated customer to a tool they are entitled to use. Only TS-SEC-08 stops it.

15.3 Untrusted content in results

Tool results are read by a model as part of its instruction stream. Any field whose content originates outside the firm's control is therefore an injection vector — and a brokerage domain has more of these than teams expect:

15.4 Tenancy and isolation

  • Every cache key, idempotency key, and rate-limit bucket is scoped by principal and tenant. A shared idempotency namespace lets one customer's key collide with another's, which is a data-disclosure bug wearing an availability bug's clothes.
  • Cross-tenant aggregates — "how many customers hold Tesla" — are a different tool, at a different tier, for a different audience, with a different entitlement. Never a parameter on a customer-facing tool.
  • Test fixtures and sandbox data never share an identifier space with production. A model that has seen acct_TEST0001 in an example will eventually send it.

15.5 Loop, abuse, and cost protection

SignalControl
Identical invocation repeated within a conversation Return the cached result and increment a counter; after three, return RATE_LIMITED with remediation "you have already called this; use the result you have". Agents loop, and the loop is usually invisible to the customer.
High-fan-out across accounts or symbols Per-principal quota plus a per-conversation ceiling. Offer the summarize tool in the remediation.
Repeated ENTITLEMENT_DENIED or NOT_FOUND Alert. This is the signature of enumeration, whether the agent is being manipulated or is simply confused.
Approval denied, then retried with altered arguments Alert and block the conversation. An agent that reformulates a declined trading action is the highest-signal event in the estate.

15.6 Kill switch and degradation

TS-SEC-12 — MUST#A32A2Asolid2#F4F5F7#FFFFFF

Every tier 2 and tier 3 tool MUST be disableable within 60 seconds, by capability, by audience, and globally, without a deployment. The disabled state MUST return NOT_SUPPORTED with a remediation the agent can relay — "order placement through the assistant is temporarily unavailable; the customer can trade in the app" — rather than an opaque failure.

15.7 Third-party and vendor tools

Tools the firm did not write are a supply chain, and the descriptor is the payload. Three controls, none optional:

RuleLevelRequirement
TS-SEC-09RedMUST Every descriptor's content hash MUST be recorded at approval. Runtimes MUST pin the approved hash and MUST refuse to present or invoke a tool whose descriptor has changed without a new approval — for internal tools too, but decisively for external ones.
TS-SEC-13RedMUST Third-party tools MUST be reviewed against this standard before admission, MUST be re-reviewed on every descriptor change, and MUST be assumed to have mis-stated their annotations — the firm assigns the risk tier independently, from observed behavior, not from the vendor's claim.
TS-SEC-14RedMUST A third-party tool MUST NOT be presented to an agent in the same context as a firm tier 3 tool unless the combination has been explicitly assessed. The risk is not either tool; it is that one tool's output can steer the other's invocation.
