3API Conventions

These rules apply to every endpoint. Reading this section once will save you from rediscovering the same eight things across five sections of reference material.

3.1Hypermedia and HATEOAS

Every representation carries a _links object: a map keyed by link relation, each value carrying at least an href. 

{
  "orderId": "ord_01HQ9D4N7Q1S5U8X",
  "status":  "PARTIALLY_FILLED",
  "_links": {
    "self":       { "href": "https://api.brokerage.example.com/v1/accounts/acct_…/orders/ord_…" },
    "cancel":     { "href": "…/orders/ord_…", "method": "DELETE", "title": "Cancel the unfilled 200 shares" },
    "replace":    { "href": "…/orders/ord_…", "method": "PATCH" },
    "executions": { "href": "…/orders/ord_…/executions" }
  }
}

The contract has three parts, and the third is the one that pays for the other two:

  1. One bookmarked URL. Clients hard-code GET / and discover everything else by following relations.
  2. No URL construction. Never build a URL by concatenating strings. Follow the href you were given, verbatim — including its query parameters.
  3. Links are state-dependent. A FILLED order has no cancel link. An account without options approval has no place-option-order link. Branch on the presence of a link, not on a status string.
Why point 3 matters more than it looks

Status enumerations grow. If your UI enables its Cancel button when status ∈ {NEW, PARTIALLY_FILLED}, then the day a PENDING_ROUTE status ships, your button silently disappears for orders that are in fact cancellable. If instead it enables on "cancel" in _links, it keeps working — the server already knows the answer, and it is telling you.

RelationMeaning
selfCanonical URL of this resource.
nextThe next page. Absent on the last page (§3.4).
account, order, instrumentNavigate to a related resource.
balances, positions, orders, transactions, executionsSub-collections of an account or order.

3.2Errors: RFC 9457 problem details

Every error response uses application/problem+json: 

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type":     "https://developer.brokerage.example.com/problems/insufficient-buying-power",
  "title":    "Insufficient buying power",
  "status":   422,
  "detail":   "Order requires 123,750.00 USD of stock buying power; 84,360.20 USD available.",
  "instance": "/v1/accounts/acct_01HQ8Z4M2X9K3P7R/orders",
  "required":  { "amount": "123750.00", "currency": "USD" },
  "available": { "amount": "84360.20",  "currency": "USD" },
  "traceId":  "01HQ9D5P8R2T6V9Y0B3D5F7H"
}
FieldHow to treat it
typeThe only field safe to branch on. A stable, dereferenceable URI identifying the problem class. It will not change without a version bump.
title, detailHuman-facing prose. Reworded without notice, and localized in future. Display it; never parse it.
instanceWhich request this was about.
traceIdLog this on every failure. It is the first thing support will ask for and the only way to find the request in our logs.
errors[]Field-level failures on validation problems, each with an RFC 6901 JSON Pointer.
ExtensionsProblem types add their own fields — required/available here, requiredLevel on an options-approval failure. Documented per type in Appendix A.

Status code semantics

StatusMeaning in this API
400Malformed syntax or schema validation failure. The request never reached business logic.
401Token missing, expired, malformed, or revoked. Refresh once and retry; if that fails, re-authorize.
403Authenticated but not permitted — missing scope, or an options strategy above the account's approval level.
404No such resource, or it exists outside your grant. Deliberately indistinguishable, so the API cannot be used to enumerate account identifiers.
409Conflicting state — the account is restricted, or the order already reached a terminal state.
412If-Match did not match. The resource changed after you read it (§3.6).
422Well-formed but unacceptable — insufficient buying power, price outside collar, market closed, untradable instrument.
428A required precondition header was not supplied.
429Rate limited. Honor Retry-After (§3.7).
503Upstream venue or clearing system unavailable. Retryable with backoff.
400 versus 422 is not cosmetic

A 400 means your code is wrong — fix it and the request will work. A 422 means your code is fine and the world said no: not enough buying power, market closed, instrument halted. The first is a bug to fix; the second is a condition to surface to the customer. Treating them identically produces an application that shows "Invalid request" when the honest answer is "the market is closed".

3.3Decimals, money, and why nothing is a float

Prices, quantities, and monetary amounts are transmitted as JSON strings: 

{ "limitPrice": "412.50", "quantity": "300", "netLiquidation": "184320.55" }

This is not stylistic. JSON numbers are IEEE-754 doubles in most parsers, and a double cannot represent 0.1 exactly. In a domain where a share count and a limit price multiply into a cash obligation, that error is a defect with a dollar value attached.

LanguageUseNever
Javanew BigDecimal("412.50")double, Double.parseDouble, or BigDecimal.valueOf(double)
PythonDecimal("412.50")float, or Decimal(0.1) from a float literal
JavaScriptdecimal.js / big.js, or keep the stringNumber(), parseFloat, or arithmetic on either
Goshopspring/decimalfloat64
The subtle Java trap

BigDecimal.valueOf(0.1) and new BigDecimal(0.1) both route through a double and inherit its error before BigDecimal ever sees the value. Only the String constructor is safe. The same applies to Python's Decimal(0.1) versus Decimal("0.1").

Other formats follow the same principle of being unambiguous on the wire:

Timestamps
RFC 3339, UTC, explicit offset: 2026-08-17T14:31:02Z. Sub-second precision on executions.
Dates
ISO 8601 calendar dates for trade and settlement dates: 2026-08-19. These are exchange-local dates, not instants.
Currency
ISO 4217 alphabetic codes. Every monetary field either carries a currency or sits beside one.
Identifiers
Opaque, prefixed, sortable strings (acct_, ord_, pos_, txn_, exec_, inst_). Do not parse them; the prefix is a debugging affordance, not an API.

3.4Pagination

Collections use opaque forward cursors. Request a page size with limit (1–200, default 50); follow the next link for more. 

GET /v1/accounts/acct_…/transactions?from=2026-08-01&limit=50

{ "items": [ … ],
  "_links": {
    "self": { "href": "…/transactions?from=2026-08-01&limit=50" },
    "next": { "href": "…/transactions?from=2026-08-01&limit=50&cursor=eyJvIjoxMjAwfQ" }
  } }

No next link means you have reached the end. Cursors are opaque: their encoding is not part of the contract and will change. Do not construct, parse, or persist them.

Why cursors rather than offsets

Offset pagination is unstable against a moving dataset. Between page 1 and page 2 of your transaction history, a settlement can insert a back-dated row — and with OFFSET 50 you silently skip a record. Cursors are anchored to a position in a stable ordering, so insertions do not shift the window out from under you.

Rows can still legitimately repeat across pages when settlement back-dates an entry. Reconcile on transactionId, which is permanent and unique.

3.5Idempotency

Every unsafe, non-idempotent operation — in practice, placing and amending orders — requires an Idempotency-Key header carrying a client-generated UUIDv4. 

POST /v1/accounts/acct_…/orders
Idempotency-Key: 6f1c2a90-3f5b-4c1e-9c2a-8d7b6e5f4a30
ScenarioResult
First request with a key201 The order is created.
Replay, same key, identical body200 The original order is returned with Idempotency-Replayed: true. No second order.
Replay, same key, different body422 idempotency-key-reuse. Nothing is created.
Key older than 24 hoursTreated as new. Keys are retained for 24 hours.
Generate the key once, per intent

The key must be created before the first attempt and reused verbatim on every retry of that same order intent. Generating a fresh UUID inside a retry loop defeats the entire mechanism and is the exact bug it exists to prevent.

The failure being defended against is specific: a socket timeout on a market order is indistinguishable, from the client's side, from a rejection. The order may have been accepted and routed. Retrying without a key doubles the customer's position; retrying with one is safe.

3.6Optimistic concurrency with ETags

Order reads return a strong ETag. Order mutations — PATCH and DELETE — require If-Match. 

# 1. Read, and keep the validator
GET /v1/accounts/acct_…/orders/ord_…
→ 200 OK
  ETag: W/"ord-7-1755441062"

# 2. Mutate, asserting you saw that exact version
PATCH /v1/accounts/acct_…/orders/ord_…
If-Match: W/"ord-7-1755441062"
Content-Type: application/merge-patch+json

{ "limitPrice": "413.25" }
OutcomeMeaning
200The order was unchanged since your read. The amendment was accepted, and a new ETag is returned.
412The order changed after your read. Re-read it and decide again — do not blindly retry with the newer ETag, or you will amend an order whose state you never evaluated.
428You omitted If-Match. Rejected rather than defaulted, on purpose.
The race this closes

You read an order showing 100 of 300 shares filled and decide to reprice the remaining 200. While you are deciding, it fills completely. Without If-Match, your amendment lands against an order you believe is working, and the outcome depends on timing you cannot observe. With it, you get a 412 and a chance to look again.

ETag also works for cheap polling: send it as If-None-Match on a GET and receive 304 Not Modified with no body when nothing has changed. That is what keeps a one-second poll inside the rate limit.

3.7Rate limits and backoff

Every response carries the current quota state, per RFC 9913:

RateLimit: "default";r=94;t=51          # 94 requests remain, window resets in 51s
RateLimit-Policy: "default";q=120;w=60  # 120 requests per 60-second window
PolicyQuotaApplies to
default120 / minuteAll read endpoints.
orders-write60 / minutePlace, amend, cancel.
order-poll1 / second per orderGET on a single order. Use the event stream instead.
streams5 concurrentOpen SSE connections per grant.

On 429, wait Retry-After seconds and retry with full jitter — a random delay between zero and your computed cap, rather than a fixed backoff: 

delay = random_between(0, min(2^attempt × base, cap))
Why jitter, specifically

When a venue hiccups, every client fails at once and every client retries at once. Fixed backoff preserves that synchronization and reproduces the thundering herd on each round, turning a two-second blip into a sustained outage. Randomizing the delay spreads the retries out. Ignoring Retry-After repeatedly escalates to a temporary suspension of the client.

3.8Versioning and compatibility

The major version is pinned in the server path (/v1). Within a major version, the following are considered backward-compatible and ship without notice:

  • New endpoints, and new optional request fields.
  • New fields in a response object.
  • New members in an enumeration — including new OrderStatus values.
  • New link relations in _links.
  • New problem type URIs.

Which places two obligations on your client:

  1. Ignore unknown properties. Configure your deserializer to tolerate them — Jackson's FAIL_ON_UNKNOWN_PROPERTIES=false, or an equivalent. A strict parser will break on a purely additive change.
  2. Tolerate unknown enum values. Do not map to a closed enum that throws. Treat an unrecognized OrderStatus as working, and rely on _links to know what you may do with it.

Breaking changes — removing a field, changing a type, tightening validation — require a new major version. The previous version is supported for at least 12 months after the successor ships.
