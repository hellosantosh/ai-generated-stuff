5Trading APIs

Placing, amending, and cancelling stock and option orders. Everything in this section requires the orders:write scope and an ACTIVE account, and everything in this section moves real money in production.

5.1The order lifecycle

An order is a resource with a state machine. Understanding it is the difference between an integration that reconciles cleanly and one that quietly loses track of fills.

StateTerminal?Meaning
PENDING_NEWNoAccepted by us, not yet acknowledged by the venue.
NEWNoLive on the book. Working, unfilled.
PARTIALLY_FILLEDNoSome quantity filled; the remainder is still working.
PENDING_REPLACE / PENDING_CANCELNoAn amendment or cancellation is in flight at the venue.
FILLEDYesFully executed.
CANCELLEDYesCancelled. May carry a non-zero filledQuantity if it partially filled first.
REJECTEDYesRefused. rejectReason carries a machine-readable code.
EXPIREDYesTime in force elapsed — a DAY order at the close, or a GTD order past its date.
REPLACEDYesSuperseded by an amendment. Follow the link to the replacement.
SUSPENDEDNoHeld — a trading halt in the instrument, or a compliance hold on the account.
Three things that regularly surprise people

A 201 is not a fill. It means the order was accepted and routed. Terminal state arrives later, via the event stream, a webhook, or a poll.

Cancellation is a request, not a guarantee. The order moves to PENDING_CANCEL and only reaches CANCELLED once the venue acknowledges. A fill already in flight can still land — a "cancelled" order can end up FILLED.

An order can be rejected after acceptance. We accept and route it; the venue refuses it a moment later. That surfaces as a later REJECTED state, not as an error on the original call.

5.2Placing an order safely

POST/v1/accounts/{accountId}/orders
Requires orders:write  ·  Idempotency-Key header required

The request body is a discriminated union on assetClass: EQUITY for single-leg stock and ETF orders, OPTION for single- and multi-leg listed option orders.

Validation order

The service validates in this sequence and stops at the first failure, so a rejection tells you the first thing wrong, not everything wrong: 

schema  →  instrument tradability  →  market / session eligibility
        →  options approval level  →  buying power and margin
        →  risk limits             →  route to venue

The safe submission pattern

// 1. Generate the idempotency key ONCE, before the first attempt.
key = uuid4()

// 2. Preview, so the customer confirms real numbers rather than an estimate.
preview = POST /orders/preview  {order}
if (!preview.valid) { show preview.warnings; stop }

// 3. Submit. Retry ONLY with the same key — never regenerate it in the loop.
retry (max 4, full jitter) {
  response = POST /orders  {order}  Idempotency-Key: key
}

// 4. A 201 means routed, not filled. Confirm terminal state separately.
watch(response.orderId)  // SSE stream, webhook, or ETag-conditional poll

Market orders and gaps

A MARKET order guarantees execution, not price. On an illiquid name, at the open, or during a halt resumption, the fill can be far from the last quote. Prefer marketable limits for anything the customer would be upset to see filled 8% away, and surface the preview's estimated cost before submitting.

5.4Options trading

Option orders carry a legs array — one entry for a single-leg order, up to four for a combination. Multi-leg orders are priced and routed as one unit; legs never fill independently.

Approval levels

LevelPermits (cumulative)
LEVEL_1Covered calls, cash-secured puts.
LEVEL_2Long calls and puts.
LEVEL_3Spreads and other defined-risk multi-leg strategies.
LEVEL_4Uncovered (naked) short options.

An order above the account's level is rejected with 403 options-level-insufficient, which carries requiredLevel and currentLevel so you can tell the customer exactly what to request.

Open and close are explicit

side on an option leg is one of BUY_TO_OPEN, BUY_TO_CLOSE, SELL_TO_OPEN, SELL_TO_CLOSE. The distinction drives margin treatment and position netting and cannot be inferred from buy/sell alone — selling a call you hold closes a position; selling one you do not is a naked short requiring LEVEL_4.

Single leg

{ "assetClass": "OPTION",
  "strategy":   "SINGLE",
  "legs": [ { "instrumentId": "inst_op_AAPL_20261218C00250000",
              "side": "BUY_TO_OPEN", "ratio": 1 } ],
  "quantity":    "5",          // 5 contracts
  "orderType":   "LIMIT",
  "limitPrice":  "12.40",      // per contract → 12.40 × 5 × 100 = 6,200 outlay
  "priceEffect": "DEBIT",
  "timeInForce": "DAY" }

Vertical spread — priced as a unit

{ "assetClass": "OPTION",
  "strategy":   "VERTICAL",
  "legs": [
    { "instrumentId": "inst_op_AAPL_20261218C00250000", "side": "BUY_TO_OPEN",  "ratio": 1 },
    { "instrumentId": "inst_op_AAPL_20261218C00260000", "side": "SELL_TO_OPEN", "ratio": 1 }
  ],
  "quantity":    "10",          // 10 SPREADS = 20 contracts
  "orderType":   "NET_DEBIT",
  "netPrice":    "3.15",         // always positive
  "priceEffect": "DEBIT",        // direction lives here, not in the sign
  "timeInForce": "DAY" }
Two ways to get option sizing badly wrong

quantity is strategy units, not contracts. A quantity of 10 on a two-leg vertical is ten spreads — twenty contracts — with each leg scaled by its ratio. Reading it as contracts halves your intended position, or doubles it, depending on which way you err.

Declaring strategy is not cosmetic. It is what causes the risk engine to apply spread margin instead of margining each leg independently. The identical legs submitted as CUSTOM get the short call margined as if naked, which typically demands an order of magnitude more buying power — often the difference between an order being accepted and rejected.

Resolving contracts

GET/v1/instruments/{underlyingSymbol}/option-chain
Requires instruments:read  ·  always narrow with expiration

Option contracts carry a 21-character OSI symbol — AAPL  261218C00250000: six characters of root (space-padded), six digits of YYMMDD, C or P, then eight digits of strike × 1000. It is a useful checksum on your own logic, but the instrumentId is what you place orders against.

POST/v1/accounts/{accountId}/orders/preview
Requires orders:write  ·  creates nothing, takes no idempotency key

5.6Amending and cancelling

PATCH/v1/accounts/{accountId}/orders/{orderId}
DELETE/v1/accounts/{accountId}/orders/{orderId}
Requires orders:write  ·  If-Match required on both

Amendment uses JSON Merge Patch (RFC 7386). Only quantity, limitPrice, stopPrice, trailingAmount, trailingPercent, netPrice, timeInForce, and goodTilDate are amendable. Changing the instrument, the side, or the leg structure is a different order: cancel and place a new one. 

PATCH /v1/accounts/acct_…/orders/ord_…
If-Match: W/"ord-7-1755441062"
Content-Type: application/merge-patch+json

{ "quantity": "200", "limitPrice": "413.25" }

New quantity must be at least what has already filled. Amendment is best-effort against a live venue: a 200 means the amendment was accepted for routing, and the order may still fill at the old price if that fill was already in flight.

Cancellation is idempotent — cancelling an already-cancelled order returns 200 with the cancelled order rather than an error.

5.7Streaming order events and webhooks

GET/v1/accounts/{accountId}/orders/events
Requires orders:read  ·  text/event-stream

A Server-Sent Events stream of order transitions and executions. Prefer this over polling.

BehaviorDetail
ResumeSend Last-Event-ID on reconnect to replay from just after that event. Retention is 5 minutes.
HeartbeatA comment frame every 15 seconds. Treat 45 seconds of silence as a dead connection and reconnect.
DeliveryAt-least-once. Deduplicate on eventId.
Limit5 concurrent streams per grant.

Webhooks

For server-side integrations that would rather be called than hold a connection open, register a webhook and receive the same OrderEvent payload by POST.

  • Signed with Webhook-Signature: HMAC-SHA256 over the raw request body, keyed by your webhook secret. Verify before parsing, and compare in constant time.
  • Return 2xx within 5 seconds. Non-2xx and timeouts are retried with exponential backoff for 24 hours.
  • Delivery is at-least-once, so handlers must be idempotent on eventId.
Verify the signature over raw bytes

Compute the HMAC over the body exactly as received, before any JSON parse and re-serialize. Round-tripping through a parser reorders keys and normalizes whitespace, which changes the bytes and breaks the signature — and the usual "fix" for that is to skip verification, which is how forged fill events get accepted.
