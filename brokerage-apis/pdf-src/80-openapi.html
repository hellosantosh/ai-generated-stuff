7OpenAPI 3.2.0 Specification

Every endpoint in this document is described by a machine-readable OpenAPI 3.2.0 document. It is the normative artifact: where this prose and the specification disagree, the specification wins.

7.2What 3.2.0 gives us that 3.1 did not

Five 3.2.0 additions earn their place in this document. Each is used because it lets the description state something that previously needed a vendor extension or a prose footnote.

$self — document identity

openapi: 3.2.0
$self: https://api.brokerage.example.com/openapi/brokerage-api.yaml

Gives the document a stable, self-assigned URI that also acts as the base for reference resolution — so $ref targets resolve identically whether the file is read from disk, a CDN, or a build pipeline. Previously the base URI was wherever the file happened to be fetched from, which made references environment-dependent.

Hierarchical tags: summary, parent, kind

tags:
  - name: accounts
    summary: Accounts
    kind: nav
  - name: balances
    summary: Balances
    parent: accounts        # nests under Accounts in navigation
    kind: nav
  - name: trade-enabled
    summary: Trade-enabled
    kind: audience         # an audience facet, not a nav node

The API description now expresses its own navigation hierarchy instead of delegating that to renderer-specific extensions like x-tagGroups. kind separates structural navigation from cross-cutting facets — here, which operations need a write grant.

The query method

/instruments:
  get:   # simple lookups by query string
  query: # structured screens with a request body — safe, idempotent, cacheable

HTTP QUERY is a safe, idempotent method that carries a request body. A structured instrument screen — exchanges, sectors, market-cap bounds, sort order — is too large and too nested for a query string, but it is still unambiguously a read. Before 3.2.0 the only way to describe it was as a POST, which misrepresents the semantics and defeats caching. A POST /instrument-screener alias remains for clients that cannot issue QUERY, notably browser fetch().

itemSchema for streaming

content:
  text/event-stream:
    itemSchema:            # describes ONE event, not the whole stream
      type: object
      properties:
        id:    { type: string }
        event: { type: string, enum: [order.accepted, execution, …] }
        data:
          type: string
          contentMediaType: application/json
          contentSchema: { $ref: '#/components/schemas/OrderEvent' }

Unlike schema, which would describe the entire stream as an array, itemSchema applies to each item independently — which is what a streaming consumer actually processes as bytes arrive. It makes the order event stream properly describable for the first time.

oauth2MetadataUrl and the device flow

securitySchemes:
  oauth2:
    type: oauth2
    oauth2MetadataUrl: https://auth.brokerage.example.com/.well-known/oauth-authorization-server
    flows:
      authorizationCode: { … }
      deviceAuthorization:      # declarable for the first time in 3.2.0
        deviceAuthorizationUrl: …

oauth2MetadataUrl points tooling at the RFC 8414 authorization server metadata document, so endpoints, supported PKCE methods, and grant types are discovered rather than hard-coded into the description and left to drift.

A 3.1/3.2 detail that silently breaks clients

OpenAPI 3.1 replaced its bespoke schema dialect with JSON Schema 2020-12, and nullable: true is not a JSON Schema keyword — it was a 3.0-ism. Left in a 3.1 or 3.2 document it is silently ignored, so a field you believe is nullable validates as non-nullable and your generated client throws on a legitimate null.

The correct spelling is a type union: type: [string, "null"], or oneOf: [{$ref: …}, {type: "null"}] when the base type comes from a $ref. This specification uses the correct form throughout; it is worth grepping any 3.1+ document you inherit for nullable.

7.4Validating and generating from the specification

Validate

# Against the official 3.2 meta-schema — the authoritative check.
curl -sL -o oas32.json https://spec.openapis.org/oas/3.2/schema/2025-09-17
python3 - <<'PY'
import json, yaml
from jsonschema import Draft202012Validator
meta = json.load(open('oas32.json'))
doc  = yaml.safe_load(open('openapi/brokerage-api.yaml'))
errors = list(Draft202012Validator(meta).iter_errors(doc))
print('VALID' if not errors else f'{len(errors)} error(s)')
for e in errors[:10]:
    print(' /' + '/'.join(map(str, e.absolute_path)), '::', e.message[:200])
PY

# Linting and style. Note: 3.2.0 support varies by tool and version —
# check before trusting a "valid" from anything but the meta-schema.
npx @redocly/cli lint openapi/brokerage-api.yaml
Validate the examples too

A specification can be structurally valid and still carry examples that contradict their own schemas — which is worse than no examples, because integrators copy them. Walk every examples block, resolve its sibling schema, and validate the two against each other in CI. Doing exactly that on this document is what surfaced the nullable problem described above.

Generate clients

# Most generators do not yet target 3.2.0. Downgrade for generation only —
# the 3.2-specific fields ($self, query, itemSchema, tag parent/kind) are
# additive, so dropping them yields a valid 3.1 document.
npx @redocly/cli bundle openapi/brokerage-api.yaml -o build-3.1.yaml

npx @openapitools/openapi-generator-cli generate \
    -i build-3.1.yaml -g java    -o clients/java
npx @openapitools/openapi-generator-cli generate \
    -i build-3.1.yaml -g python  -o clients/python
npx @openapitools/openapi-generator-cli generate \
    -i build-3.1.yaml -g typescript-fetch -o clients/typescript
Audit generated code for decimal handling

Generators map type: string to a native string, which is correct here — but some apply a "helpful" numeric coercion when they see a numeric-looking pattern or format. Check that every price and quantity lands in BigDecimal, Decimal, or a string, and never in double. See §3.3.
