2Authentication and Authorization

Every request to this API carries an OAuth 2.1 access token obtained through the authorization code flow with PKCE. This section explains how to get one, how to keep it fresh, and what each moving part is actually defending against.

2.1Why OAuth 2.1 with PKCE

Neither reference brokerage uses this scheme. Webull signs requests with an app key and secret; Interactive Brokers maintains a stateful session and offers OAuth 1.0a to third parties. Both work. Both also put the integrator in possession of a credential that is long-lived, unscoped, and awkward to revoke without breaking every deployment at once.

OAuth 2.1 changes three things that matter in a brokerage context:

PropertyShared-secret signingOAuth 2.1 bearer token
Blast radius One secret, full capability, indefinite lifetime. Leak it and the attacker can trade until someone notices. 15-minute access token, limited to granted scopes. Leaked read scope cannot place an order.
Consent Implicit. Whoever holds the secret has whatever the account has. Explicit and per-application. The customer sees exactly which permissions they are granting, and to whom.
Revocation Rotate the secret, redeploy everything that used it. Revoke one grant from a settings screen. Nothing else is affected.

OAuth 2.1 is a consolidation of OAuth 2.0 plus a decade of security best current practice. For our purposes the load-bearing changes are:

  • PKCE is mandatory for all clients, not just public ones. Previously PKCE was a mobile-app mitigation; 2.1 makes it universal because authorization codes leak through more channels than anyone originally modeled — referrer headers, browser history, OS-level URL handlers, and logging middleware.
  • The implicit grant is removed. It returned an access token directly in a URL fragment, where it landed in history and logs. There is no supported way to obtain a token without a back-channel exchange.
  • The resource owner password credentials grant is removed. It required the application to handle the customer's actual brokerage password. We will never ask for one, and neither should you.
  • Redirect URIs must match exactly, by string comparison. No wildcards, no prefix matching — those were reliably exploitable for code interception.
  • Bearer tokens must not travel in query strings. Always the Authorization header.
Never do this

Do not build a screen that collects a customer's brokerage username and password and replays them. That pattern — credential sharing — is what OAuth exists to eliminate. It defeats multi-factor authentication, makes revocation impossible, and puts your application in scope for a class of liability it does not want.

2.2Client registration and client types

Registration yields a client_id and a set of exactly-matched redirect URIs. Whether you also receive a credential depends on what you are building.

Client typeExamplesAuthentication at the token endpoint
Public Single-page apps, mobile apps, desktop apps, CLI tools None. PKCE alone. A secret shipped inside a binary or a JavaScript bundle is not a secret — it only creates the illusion of one.
Confidential Server-side web applications, backend services private_key_jwt — you sign a short-lived assertion with a private key whose public half we hold. Preferred over a shared secret because the credential never crosses the wire.

Confidential clients still use PKCE. The two protect different links in the chain: client authentication proves which application is redeeming the code, while PKCE proves it is the same instance that started the flow.

2.4PKCE mechanics: verifier, challenge, and what it defends

PKCE (RFC 7636, pronounced "pixy") binds an authorization code to the specific client instance that requested it.

Generating the pair

# code_verifier — 43 to 128 characters from [A-Z a-z 0-9 - . _ ~]
# 32 random bytes, base64url-encoded without padding, yields exactly 43.
code_verifier  = BASE64URL_NOPAD(random_bytes(32))
code_challenge = BASE64URL_NOPAD(SHA256(ASCII(code_verifier)))
code_challenge_method = "S256"
RequirementRule
Entropy sourceA cryptographically secure RNG. SecureRandom, secrets, crypto.randomBytes — never Math.random() or a seeded PRNG.
Challenge methodS256 only. The plain method sends the verifier itself as the challenge, which defends against nothing. This server rejects it.
LifetimeOne verifier per authorization attempt. Never reuse one, and discard it once the code is redeemed.
StorageHeld only in the client instance that started the flow — session storage for a web app, memory for a native app. It is never transmitted until step 8.

PKCE and state solve different problems

They are frequently confused, and sending only one leaves a real hole. Send both.

ParameterAttack it preventsHow
state CSRF on the redirect. An attacker tricks the victim's browser into completing a flow that binds the attacker's account to the victim's session. An unguessable value generated by the client, echoed back by the server, and compared before the code is used.
code_verifier Authorization code interception. A malicious app registers the same custom URL scheme, or the code leaks via a referrer, log, or browser history. The code alone cannot be redeemed. The token endpoint requires the pre-image of the challenge, which the interceptor never saw.
Compare in constant time

Verify state with a constant-time comparison (MessageDigest.isEqual, secrets.compare_digest, crypto.timingSafeEqual), not ==. The timing leak is small, but the habit is what matters — the same code path tends to get reused for comparisons where it is not small.

Read the granted scope, do not assume it

The scope in the response is authoritative and may be narrower than what you requested — the customer can decline individual permissions on the consent screen. Drive your UI from the granted scope. An application that hides its trade button when orders:write was not granted is far better than one that shows it and surfaces a 403 later.

2.6Access tokens: structure, lifetime, and validation

Access tokens are RS256-signed JWTs valid for 15 minutes. Present one on every API request: 

GET /v1/accounts HTTP/1.1
Host: api.brokerage.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6IjIwMjYtMDgifQ…
Accept: application/json

Claims

{
  "iss": "https://auth.brokerage.example.com",   // issuer
  "sub": "user_01HQ8Z1A2B3C4D5E",                // the customer
  "aud": "https://api.brokerage.example.com",    // intended resource server
  "exp": 1755443402,                              // expiry, epoch seconds
  "iat": 1755442502,
  "jti": "01HQ9D4N7Q1S5U8X9Z2A4C6E",            // unique id, for revocation lists
  "scope": "accounts:read orders:read orders:write",
  "client_id": "your-client-id",
  "accounts": ["acct_01HQ8Z4M2X9K3P7R"]              // accounts in scope for this grant
}
If you validate tokens yourself

A resource server verifying these directly must check the signature against the JWKS at /.well-known/jwks.json (cached, keyed by kid), and then verify iss, aud, and exp. Skipping the aud check is the classic mistake: it lets a token minted for a different resource server be replayed against yours.

A client should not parse the token at all. Treat it as opaque, send it, and handle 401.

Why 15 minutes

Short enough that a leaked token has a small window; long enough that a normal session does not spend its time refreshing. The pairing matters more than the number: a short access token plus a rotating refresh token gives you both a small exposure window and a session that survives without re-prompting the customer.

2.7Refresh tokens, rotation, and reuse detection

POSThttps://auth.brokerage.example.com/oauth2/token
Requires the offline_access scope to have been granted
grant_type=refresh_token
&refresh_token=v1.MTo3ZjNhOWIyYy0…
&client_id=your-client-id

Refresh tokens are opaque, valid for 90 days of inactivity, and rotate on every use. The response always contains a new refresh_token; the one you sent is dead the instant the response is generated.

Persist the new token before you use the new access token

Rotation makes the write ordering safety-critical. If your process crashes after receiving RT₃ but before durably storing it, you hold a dead RT₂ and the customer must re-authorize. Write the new refresh token to durable storage first — atomically, via write-to-temp-then-rename or a transaction — and only then proceed. The example clients in Section 6 all do this.

Concurrency

Two threads refreshing the same token simultaneously will trip reuse detection and revoke the family. Serialize refresh behind a mutex, and have the losing caller wait for and reuse the winner's result rather than issuing its own request. This is the single most common production bug in OAuth clients with rotation enabled.

2.8Scopes and least privilege

ScopeGrants
accounts:readThe account list and account metadata. Account numbers are masked.
accounts:read:fullUnmasked account numbers. Subject to additional review — request it only if you have a concrete need, such as ACAT transfer initiation.
positions:readOpen positions, cost basis, and unrealized P&L.

Ask for less

Request the narrowest set that makes your application work, and request additional scopes later through a fresh authorization when the customer reaches a feature that needs them. A portfolio dashboard that asks for orders:write on first launch reads as a red flag, and consent rates reflect that.

2.9Sender-constrained tokens with DPoP

A bearer token is, definitionally, usable by whoever bears it. DPoP (RFC 9449) binds a token to a key pair your client holds, so a stolen token is inert without the private key.

Each request carries a DPoP proof JWT, signed with your private key, covering the HTTP method and URI plus a unique nonce and timestamp: 

GET /v1/accounts/acct_01HQ8Z4M2X9K3P7R/orders HTTP/1.1
Authorization: DPoP eyJhbGciOiJSUzI1NiIsInR5cCI6ImRwb3Arand0Ii…
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7…

DPoP is required for orders:write on accounts above the institutional risk threshold, and recommended for every integration that can manage a key pair. Request it by including a dpop_jkt parameter on the authorization request; the issued token then carries a cnf confirmation claim and will be rejected if presented as a plain bearer token.

2.10Revocation, logout, and token hygiene

POSThttps://auth.brokerage.example.com/oauth2/revoke
token=v1.MTo3ZjNhOWIyYy0…&token_type_hint=refresh_token&client_id=your-client-id

Revoking a refresh token invalidates the whole family, including outstanding access tokens. Returns 200 OK whether or not the token existed — per RFC 7009, so the endpoint cannot be used as a token oracle.

PracticeReason
Revoke on logoutDropping tokens on the floor leaves a live account credential in whatever logs, crash dumps, or backups happened to capture it.
Never log tokensRedact Authorization headers and token responses in every logger, APM agent, and error reporter. This is the most common way tokens leak in practice.
Encrypt at restKeychain or Keystore on device; a managed secret store on a server. File storage, if unavoidable, must be owner-only (mode 0600).
Never in URLsQuery strings land in access logs, referrer headers, and browser history. Header only.
One grant per user per appDo not share a token across customers or pool credentials. The sub claim is what makes an audit trail meaningful.

2.11Device authorization for input-constrained clients

Where a redirect-based browser flow is not possible — a TV app, a headless terminal, an embedded device — use the device authorization grant (RFC 8628): 

1. POST /oauth2/device_authorization  →  device_code, user_code, verification_uri, interval
2. Display the user_code and verification_uri to the customer
3. Poll POST /oauth2/token with grant_type=urn:ietf:params:oauth:grant-type:device_code
      // authorization_pending → keep polling at `interval`
      // slow_down            → increase the interval by 5s and continue
      // access_denied        → the customer declined; stop
4. On success: access_token + refresh_token, exactly as in §2.5
Scope restriction

The device flow does not grant orders:write. Its user code is short and typed by hand, which makes it a weaker binding than a full redirect flow — acceptable for read access, not for placing trades.
