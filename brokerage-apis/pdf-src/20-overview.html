1Overview

This document specifies a REST API for the brokerage domain: reading accounts and positions, tracking orders and settled activity, and trading stocks and listed equity options. It is written for the engineers who will build against it, and it states not only what each endpoint does but why it was shaped that way.

1.1What this API is for, and what it deliberately excludes

The surface covers the operations a trading application actually needs on a customer's behalf: enumerate their accounts, read balances and holdings, place and manage stock and option orders, and reconcile what happened afterwards. Everything is scoped to a single authenticated customer's grant.

Three areas are intentionally out of scope, and no endpoint here touches them:

ExcludedWhy, and where it belongs instead
Institutional application process Account opening, entity onboarding, and suitability review are a compliance workflow, not a trading API. They are governed by different regulation, run on human timescales, and carry PII this surface never handles.
Futures trading Futures carry a different margin model (SPAN rather than Reg T), different contract identifiers, and different exchange plumbing. Folding them into the same order resource would compromise both.
Crypto trading Different custody model, 24/7 sessions, no settlement cycle, and a separate regulatory regime. It shares almost nothing with an equity order except the word "buy".

A small instruments surface is included even though it was not requested, for a practical reason: an option order references a contract by instrumentId, and without a way to resolve AAPL Dec-18-2026 250 Call into that identifier the trading endpoints cannot be used at all. It is kept minimal and marked as supporting.

1.2Environments and base URLs

EnvironmentBase URLBehavior
Sandbox https://api.sandbox.brokerage.example.com/v1 Paper money, simulated fills against a delayed book. Functionally identical surface. Use it for development, conformance, and CI.
Production https://api.brokerage.example.com/v1 Live orders against real money and a real customer's account.
Authorization https://auth.brokerage.example.com OAuth 2.1 authorization server. Separate host from the resource API by design.
Recommendation

Make the base URL a deployment configuration value with sandbox as the default, so that reaching production is an explicit act rather than something a missing environment variable can cause. The example clients in Section 6 are written this way.

1.3The design contract at a glance

ConcernDecision
StyleResource-oriented REST over HTTPS with JSON representations. Nouns as paths, HTTP methods as verbs, status codes as outcomes.
HypermediaEvery representation carries a _links map. Clients bookmark the API root and discover everything else (§3.1).
AuthorizationOAuth 2.1 authorization code grant with mandatory PKCE (S256), optionally DPoP-bound (§2).
ErrorsRFC 9457 application/problem+json, with a stable, dereferenceable type URI to branch on (§3.2).
Money and quantitiesDecimal strings plus an ISO 4217 currency. Never IEEE-754 floats (§3.3).
TimeRFC 3339 timestamps, always UTC, always with an explicit offset.
PaginationOpaque forward cursors, surfaced as a next link rather than a page number (§3.4).
Safe retriesIdempotency-Key required on every unsafe, non-idempotent operation (§3.5).
ConcurrencyStrong ETag plus mandatory If-Match on order mutation (§3.6).
Rate limitsRFC 9913 RateLimit headers; Retry-After on 429 (§3.7).
VersioningMajor version in the path (/v1). Additive changes ship without a bump, so clients must tolerate unknown fields and enum values (§3.8).

1.4Reference implementations we borrowed from

Two production brokerage APIs informed this design. Where their choices are good, we followed them; where they reflect history rather than intent, we did not.

SourceWhat we adoptedWhat we changed
Webull
developer.webull.com		 Clear separation of trading, market data, and account concerns. Explicit open/close semantics on option orders. A dedicated preview step before submission. Webull authenticates with an app key and HMAC request signing. We use OAuth 2.1 instead, so the customer grants scoped access without the application ever holding a long-lived shared secret.
Interactive Brokers
interactivebrokers.com/docs/web-api		 Rich order types, multi-leg combination orders priced as a unit, and a portfolio model that separates ledger, positions, and summary. IBKR relies on a stateful session that must be kept alive by periodic /tickle calls, and on OAuth 1.0a for third parties. We use stateless bearer tokens: no session to keep warm, no request signing ceremony.
On the OAuth choice

Neither reference API uses OAuth 2.1 with PKCE today. Adopting it here is a deliberate departure, and Section 2.1 makes the argument for it. The short version: request signing forces every integrator to hold a credential that can do everything forever, while a scoped, expiring, revocable token lets a customer grant read-only access to one application and full trading access to another — and take either back without changing a secret.
