Errors & status codes

Every error response is an RFC 9457 problem document. This page is the complete catalogue, plus what to actually do about each one.

The shape of an error

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type":     "https://developer.brokerage.example.com/problems/insufficient-buying-power",
  "title":    "Insufficient buying power",
  "status":   422,
  "detail":   "Order requires 123,750.00 USD of stock buying power; 84,360.20 USD available.",
  "instance": "/v1/accounts/acct_01HQ8Z4M2X9K3P7R/orders",
  "required":  { "amount": "123750.00", "currency": "USD" },
  "available": { "amount": "84360.20",  "currency": "USD" },
  "traceId":  "01HQ9D5P8R2T6V9Y0B3D5F7H"
}
FieldHow to treat it
typeThe only field safe to branch on. A stable, dereferenceable URI identifying the problem class. It will not change without a version bump.
title, detailHuman-facing prose. Reworded without notice and localized in future. Display it; never parse it.
instanceWhich request this was about.
traceIdLog this on every failure. It is the first thing support will ask for and the only way to find your request in our logs.
errors[]Field-level failures on validation problems, each with an RFC 6901 JSON Pointer.
ExtensionsEach problem type adds its own fields, listed in the catalogue below.
Branch on type, not on status

Several distinct problems share a status code — 422 covers buying power, market hours, price collars, and idempotency conflicts. The status tells you the broad category; the type tells you what to do.

Status code semantics

StatusMeaningRetryable?
400Malformed syntax or schema validation failure. Never reached business logic.No — fix the request.
401Token missing, expired, malformed, or revoked.Once, after refreshing. Then re-authorize.
403Authenticated but not permitted — missing scope, or a strategy above the account's options level.No — re-authorize with a wider scope.
404No such resource, or it exists outside your grant. Deliberately indistinguishable.No.
409Conflicting state — account restricted, or the order already terminal.No — re-read and re-decide.
412If-Match did not match. The resource changed after you read it.No — re-read and re-decide.
422Well-formed but unacceptable — buying power, market hours, collars, untradable instrument.No — surface it to the customer.
428A required precondition header was not supplied.No — add If-Match.
429Rate limited.Yes — honor Retry-After.
502 503 504Upstream venue or clearing system unavailable.Yes — backoff with full jitter.
400 versus 422 is not cosmetic

A 400 means your code is wrong — fix it and the request works. A 422 means your code is fine and the world said no: not enough buying power, market closed, instrument halted. Treating them identically produces an application that shows "Invalid request" when the honest answer is "the market is closed".

Rate limits

Every response carries the current quota state, per RFC 9913:

RateLimit: "default";r=94;t=51          # 94 requests remain, window resets in 51s
RateLimit-Policy: "default";q=120;w=60  # 120 requests per 60-second window
PolicyQuotaApplies to
default120 / minuteAll read endpoints.
orders-write60 / minutePlace, amend, cancel.
order-poll1 / second per orderSingle-order reads. Use the event stream instead.
streams5 concurrentOpen SSE connections per grant.

Retry strategy

Retry only what is safe to retry, and randomize when you do. 

delay = random_between(0, min(2^attempt × base, cap))
MethodRetry policy
GET, HEADSafe. Always retryable on 429 and 5xx.
DELETEIdempotent. Retryable — cancelling an already-cancelled order returns the cancelled order, not an error.
POST (orders)Retryable only with the same Idempotency-Key. Without one, a retry after a timeout can double the position.
PATCHRetryable with the same Idempotency-Key, but on 412 re-read first — do not retry with a fresh ETag you have not evaluated.
Why full jitter

When a venue hiccups, every client fails at once and every client retries at once. Fixed backoff preserves that synchronization and reproduces the thundering herd on each round, turning a two-second blip into a sustained outage. Randomizing the delay between zero and your cap spreads the retries out.

Repeatedly ignoring Retry-After escalates to a temporary suspension of the client.

Handling errors well

  • Log traceId on every failure. Without it, a support conversation starts from nothing.
  • Never log the Authorization header. Redact it in every logger, APM agent, and error reporter.
  • Distinguish "your bug" from "the world said no." A 422 usually deserves a message the customer can act on, not a generic failure toast.
  • Treat an unknown type as unhandled, not as success. New problem types ship without a version bump; fall through to a generic handler that surfaces title and detail.
  • After a 5xx on order placement, reconcile before resubmitting. The order may exist. Query by clientOrderId, or replay the same Idempotency-Key, which returns the original order rather than creating a second one.
