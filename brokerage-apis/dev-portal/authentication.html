Authentication

Every request carries an OAuth 2.1 access token obtained through the authorization code flow with PKCE. This page covers how to get one, how to keep it fresh, and what each moving part actually defends against.

Why OAuth 2.1 with PKCE

A scoped, expiring, revocable token beats a long-lived shared secret in three ways that matter when real money is involved:

PropertyShared-secret signingOAuth 2.1 bearer token
Blast radius One secret, full capability, indefinite lifetime. Leak it and an attacker can trade until someone notices. 15-minute access token limited to granted scopes. A leaked read scope cannot place an order.
Consent Implicit — whoever holds the secret has whatever the account has. Explicit and per-application. The customer sees exactly what they are granting.
Revocation Rotate the secret, redeploy everything that used it. Revoke one grant from a settings screen. Nothing else is affected.

OAuth 2.1's load-bearing changes, all of which this server enforces:

  • PKCE is mandatory for every client, not just public ones.
  • The implicit grant is gone. No token is ever returned in a URL fragment.
  • The password grant is gone. There is no supported way to trade a username and password for a token.
  • Redirect URIs match exactly, by string comparison. No wildcards, no prefix matching.
  • Tokens never travel in query strings. Authorization header only.
Never collect brokerage credentials

Do not build a screen that takes a customer's brokerage username and password and replays them. Credential sharing is exactly what OAuth exists to eliminate: it defeats multi-factor authentication, makes revocation impossible, and puts your application in scope for liability it does not want.

PKCE mechanics

PKCE (RFC 7636) binds an authorization code to the specific client instance that requested it.

RequirementRule
Entropy sourceA cryptographically secure RNG — SecureRandom, secrets, crypto.randomBytes. Never Math.random().
Challenge methodS256 only. The plain method sends the verifier as the challenge and defends against nothing; this server rejects it.
Verifier length43–128 characters. 32 random bytes, base64url-encoded without padding, gives exactly 43.
LifetimeOne verifier per authorization attempt. Never reuse; discard once the code is redeemed.

PKCE and state solve different problems

They are frequently confused, and sending only one leaves a real hole. Send both.

ParameterAttack preventedHow
state CSRF on the redirect — an attacker completes a flow in the victim's browser, binding their account to the victim's session. An unguessable value you generate, the server echoes, and you compare before using the code.
code_verifier Authorization code interception — a malicious app claims the same URL scheme, or the code leaks via a referrer or log. The code alone cannot be redeemed; the token endpoint requires the pre-image of the challenge.
Compare state in constant time

Use MessageDigest.isEqual, secrets.compare_digest, or crypto.timingSafeEqual — not ==. The timing leak here is small, but the same comparison code gets reused where it is not.

Access tokens

POSThttps://auth.brokerage.example.com/oauth2/token
Content-Type: application/x-www-form-urlencoded · no client secret for public clients

Access tokens are RS256-signed JWTs valid for 15 minutes. Present one on every request: 

GET /v1/accounts HTTP/1.1
Host: api.brokerage.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6IjIwMjYtMDgifQ…
Accept: application/json
Clients should treat tokens as opaque

Do not parse the JWT in a client. Send it and handle 401. Only a resource server validating tokens itself needs to verify the signature against /.well-known/jwks.json and check iss, aud, and exp — skipping the aud check is the classic mistake, since it lets a token minted for another service be replayed against yours.

Refresh tokens and rotation

POST https://auth.brokerage.example.com/oauth2/token

grant_type=refresh_token&refresh_token=v1.MTo3ZjNhOWIyYy0…&client_id=your-client-id

Refresh tokens are opaque, valid for 90 days of inactivity, and rotate on every use. The response always contains a new refresh_token; the one you sent dies the instant the response is generated.

Persist the new token before using the new access token

If your process crashes after receiving the new refresh token but before durably storing it, you hold a dead one and the customer must re-authorize. Write it to storage first, atomically (write-temp-then-rename or a transaction), and only then proceed.

Also serialize concurrent refreshes behind a lock. Two threads refreshing the same token will trip reuse detection and revoke the family — the single most common production bug in OAuth clients with rotation enabled.

offline_accessIssues a refresh token. Without it, access ends when the access token expires.
Ask for less

Request the narrowest set that works, and ask for more later through a fresh authorization when the customer reaches a feature that needs it. A portfolio dashboard that requests orders:write on first launch reads as a red flag, and consent rates reflect that.

Sender-constrained tokens (DPoP)

A bearer token is usable by whoever bears it. DPoP (RFC 9449) binds a token to a key pair you hold, so a stolen token is inert without the private key. 

GET /v1/accounts/acct_01HQ8Z4M2X9K3P7R/orders HTTP/1.1
Authorization: DPoP eyJhbGciOiJSUzI1NiIsInR5cCI6ImRwb3Arand0Ii…
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7…

Required for orders:write on accounts above the institutional risk threshold, recommended for everyone who can manage a key pair. Request it with a dpop_jkt parameter on the authorization request; the issued token then carries a cnf claim and is rejected if presented as a plain bearer token.

PracticeReason
Revoke on logoutDropping tokens on the floor leaves a live account credential in whatever logs or backups captured it.
Never log tokensRedact Authorization headers in every logger, APM agent, and error reporter. This is how tokens actually leak.

Device authorization

For clients that cannot host a browser redirect — a TV app, a headless terminal, an embedded device — use the device authorization grant (RFC 8628): 

1. POST /oauth2/device_authorization  →  device_code, user_code, verification_uri, interval
2. Display user_code and verification_uri to the customer
3. Poll POST /oauth2/token with grant_type=urn:ietf:params:oauth:grant-type:device_code
      authorization_pending → keep polling at `interval`
      slow_down            → add 5s to the interval and continue
      access_denied        → the customer declined; stop
4. On success: access_token + refresh_token, as above
No trading over the device flow

The device grant does not issue orders:write. Its short, hand-typed user code is a weaker binding than a full redirect flow — acceptable for read access, not for placing trades.
