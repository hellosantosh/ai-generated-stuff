1Overview

This document specifies a REST API for the brokerage domain: reading accounts and positions, tracking orders and settled activity, and trading stocks and listed equity options. It is written for the engineers who will build against it, and it states not only what each endpoint does but why it was shaped that way.

1.1What this API is for, and what it deliberately excludes

The surface covers the operations a trading application actually needs on a customer's behalf: enumerate their accounts, read balances and holdings, place and manage stock and option orders, and reconcile what happened afterwards. Everything is scoped to a single authenticated customer's grant.

Three areas are intentionally out of scope, and no endpoint here touches them:

ExcludedWhy, and where it belongs instead
Institutional application process Account opening, entity onboarding, and suitability review are a compliance workflow, not a trading API. They are governed by different regulation, run on human timescales, and carry PII this surface never handles.
Futures trading Futures carry a different margin model (SPAN rather than Reg T), different contract identifiers, and different exchange plumbing. Folding them into the same order resource would compromise both.
Crypto trading Different custody model, 24/7 sessions, no settlement cycle, and a separate regulatory regime. It shares almost nothing with an equity order except the word "buy".

A small instruments surface is included even though it was not requested, for a practical reason: an option order references a contract by instrumentId, and without a way to resolve AAPL Dec-18-2026 250 Call into that identifier the trading endpoints cannot be used at all. It is kept minimal and marked as supporting.

1.4Reference implementations we borrowed from

Two production brokerage APIs informed this design. Where their choices are good, we followed them; where they reflect history rather than intent, we did not.

SourceWhat we adoptedWhat we changed
Webull
developer.webull.com		 Clear separation of trading, market data, and account concerns. Explicit open/close semantics on option orders. A dedicated preview step before submission. Webull authenticates with an app key and HMAC request signing. We use OAuth 2.1 instead, so the customer grants scoped access without the application ever holding a long-lived shared secret.

On the OAuth choice

Neither reference API uses OAuth 2.1 with PKCE today. Adopting it here is a deliberate departure, and Section 2.1 makes the argument for it. The short version: request signing forces every integrator to hold a credential that can do everything forever, while a scoped, expiring, revocable token lets a customer grant read-only access to one application and full trading access to another — and take either back without changing a secret.

2Authentication and Authorization

Every request to this API carries an OAuth 2.1 access token obtained through the authorization code flow with PKCE. This section explains how to get one, how to keep it fresh, and what each moving part is actually defending against.

2.1Why OAuth 2.1 with PKCE

Neither reference brokerage uses this scheme. Webull signs requests with an app key and secret; Interactive Brokers maintains a stateful session and offers OAuth 1.0a to third parties. Both work. Both also put the integrator in possession of a credential that is long-lived, unscoped, and awkward to revoke without breaking every deployment at once.

OAuth 2.1 changes three things that matter in a brokerage context:

PropertyShared-secret signingOAuth 2.1 bearer token
Blast radius One secret, full capability, indefinite lifetime. Leak it and the attacker can trade until someone notices. 15-minute access token, limited to granted scopes. Leaked read scope cannot place an order.
Consent Implicit. Whoever holds the secret has whatever the account has. Explicit and per-application. The customer sees exactly which permissions they are granting, and to whom.
Revocation Rotate the secret, redeploy everything that used it. Revoke one grant from a settings screen. Nothing else is affected.

OAuth 2.1 is a consolidation of OAuth 2.0 plus a decade of security best current practice. For our purposes the load-bearing changes are:

  • PKCE is mandatory for all clients, not just public ones. Previously PKCE was a mobile-app mitigation; 2.1 makes it universal because authorization codes leak through more channels than anyone originally modeled — referrer headers, browser history, OS-level URL handlers, and logging middleware.
  • The implicit grant is removed. It returned an access token directly in a URL fragment, where it landed in history and logs. There is no supported way to obtain a token without a back-channel exchange.
  • The resource owner password credentials grant is removed. It required the application to handle the customer's actual brokerage password. We will never ask for one, and neither should you.
  • Redirect URIs must match exactly, by string comparison. No wildcards, no prefix matching — those were reliably exploitable for code interception.
  • Bearer tokens must not travel in query strings. Always the Authorization header.
Never do this

Do not build a screen that collects a customer's brokerage username and password and replays them. That pattern — credential sharing — is what OAuth exists to eliminate. It defeats multi-factor authentication, makes revocation impossible, and puts your application in scope for a class of liability it does not want.

2.2Client registration and client types

Registration yields a client_id and a set of exactly-matched redirect URIs. Whether you also receive a credential depends on what you are building.

Client typeExamplesAuthentication at the token endpoint
Public Single-page apps, mobile apps, desktop apps, CLI tools None. PKCE alone. A secret shipped inside a binary or a JavaScript bundle is not a secret — it only creates the illusion of one.
Confidential Server-side web applications, backend services private_key_jwt — you sign a short-lived assertion with a private key whose public half we hold. Preferred over a shared secret because the credential never crosses the wire.

Confidential clients still use PKCE. The two protect different links in the chain: client authentication proves which application is redeeming the code, while PKCE proves it is the same instance that started the flow.

2.4PKCE mechanics: verifier, challenge, and what it defends

PKCE (RFC 7636, pronounced "pixy") binds an authorization code to the specific client instance that requested it.

Generating the pair

# code_verifier — 43 to 128 characters from [A-Z a-z 0-9 - . _ ~]
# 32 random bytes, base64url-encoded without padding, yields exactly 43.
code_verifier  = BASE64URL_NOPAD(random_bytes(32))
code_challenge = BASE64URL_NOPAD(SHA256(ASCII(code_verifier)))
code_challenge_method = "S256"
RequirementRule
Entropy sourceA cryptographically secure RNG. SecureRandom, secrets, crypto.randomBytes — never Math.random() or a seeded PRNG.
Challenge methodS256 only. The plain method sends the verifier itself as the challenge, which defends against nothing. This server rejects it.
LifetimeOne verifier per authorization attempt. Never reuse one, and discard it once the code is redeemed.
StorageHeld only in the client instance that started the flow — session storage for a web app, memory for a native app. It is never transmitted until step 8.

PKCE and state solve different problems

They are frequently confused, and sending only one leaves a real hole. Send both.

ParameterAttack it preventsHow
state CSRF on the redirect. An attacker tricks the victim's browser into completing a flow that binds the attacker's account to the victim's session. An unguessable value generated by the client, echoed back by the server, and compared before the code is used.
code_verifier Authorization code interception. A malicious app registers the same custom URL scheme, or the code leaks via a referrer, log, or browser history. The code alone cannot be redeemed. The token endpoint requires the pre-image of the challenge, which the interceptor never saw.
Compare in constant time

Verify state with a constant-time comparison (MessageDigest.isEqual, secrets.compare_digest, crypto.timingSafeEqual), not ==. The timing leak is small, but the habit is what matters — the same code path tends to get reused for comparisons where it is not small.

2.6Access tokens: structure, lifetime, and validation

Access tokens are RS256-signed JWTs valid for 15 minutes. Present one on every API request: 

GET /v1/accounts HTTP/1.1
Host: api.brokerage.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6IjIwMjYtMDgifQ…
Accept: application/json

Claims

{
  "iss": "https://auth.brokerage.example.com",   // issuer
  "sub": "user_01HQ8Z1A2B3C4D5E",                // the customer
  "aud": "https://api.brokerage.example.com",    // intended resource server
  "exp": 1755443402,                              // expiry, epoch seconds
  "iat": 1755442502,
  "jti": "01HQ9D4N7Q1S5U8X9Z2A4C6E",            // unique id, for revocation lists
  "scope": "accounts:read orders:read orders:write",
  "client_id": "your-client-id",
  "accounts": ["acct_01HQ8Z4M2X9K3P7R"]              // accounts in scope for this grant
}
If you validate tokens yourself

A resource server verifying these directly must check the signature against the JWKS at /.well-known/jwks.json (cached, keyed by kid), and then verify iss, aud, and exp. Skipping the aud check is the classic mistake: it lets a token minted for a different resource server be replayed against yours.

A client should not parse the token at all. Treat it as opaque, send it, and handle 401.

Why 15 minutes

Short enough that a leaked token has a small window; long enough that a normal session does not spend its time refreshing. The pairing matters more than the number: a short access token plus a rotating refresh token gives you both a small exposure window and a session that survives without re-prompting the customer.

2.7Refresh tokens, rotation, and reuse detection

POSThttps://auth.brokerage.example.com/oauth2/token
Requires the offline_access scope to have been granted
grant_type=refresh_token
&refresh_token=v1.MTo3ZjNhOWIyYy0…
&client_id=your-client-id

Refresh tokens are opaque, valid for 90 days of inactivity, and rotate on every use. The response always contains a new refresh_token; the one you sent is dead the instant the response is generated.

Persist the new token before you use the new access token

Rotation makes the write ordering safety-critical. If your process crashes after receiving RT₃ but before durably storing it, you hold a dead RT₂ and the customer must re-authorize. Write the new refresh token to durable storage first — atomically, via write-to-temp-then-rename or a transaction — and only then proceed. The example clients in Section 6 all do this.

Concurrency

Two threads refreshing the same token simultaneously will trip reuse detection and revoke the family. Serialize refresh behind a mutex, and have the losing caller wait for and reuse the winner's result rather than issuing its own request. This is the single most common production bug in OAuth clients with rotation enabled.

Request the narrowest set that makes your application work, and request additional scopes later through a fresh authorization when the customer reaches a feature that needs them. A portfolio dashboard that asks for orders:write on first launch reads as a red flag, and consent rates reflect that.

2.9Sender-constrained tokens with DPoP

A bearer token is, definitionally, usable by whoever bears it. DPoP (RFC 9449) binds a token to a key pair your client holds, so a stolen token is inert without the private key.

Each request carries a DPoP proof JWT, signed with your private key, covering the HTTP method and URI plus a unique nonce and timestamp: 

GET /v1/accounts/acct_01HQ8Z4M2X9K3P7R/orders HTTP/1.1
Authorization: DPoP eyJhbGciOiJSUzI1NiIsInR5cCI6ImRwb3Arand0Ii…
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7…

DPoP is required for orders:write on accounts above the institutional risk threshold, and recommended for every integration that can manage a key pair. Request it by including a dpop_jkt parameter on the authorization request; the issued token then carries a cnf confirmation claim and will be rejected if presented as a plain bearer token.

2.10Revocation, logout, and token hygiene

POSThttps://auth.brokerage.example.com/oauth2/revoke

Revoking a refresh token invalidates the whole family, including outstanding access tokens. Returns 200 OK whether or not the token existed — per RFC 7009, so the endpoint cannot be used as a token oracle.

PracticeReason
Revoke on logoutDropping tokens on the floor leaves a live account credential in whatever logs, crash dumps, or backups happened to capture it.
Never log tokensRedact Authorization headers and token responses in every logger, APM agent, and error reporter. This is the most common way tokens leak in practice.
Encrypt at restKeychain or Keystore on device; a managed secret store on a server. File storage, if unavoidable, must be owner-only (mode 0600).

2.11Device authorization for input-constrained clients

Where a redirect-based browser flow is not possible — a TV app, a headless terminal, an embedded device — use the device authorization grant (RFC 8628): 

1. POST /oauth2/device_authorization  →  device_code, user_code, verification_uri, interval
2. Display the user_code and verification_uri to the customer
3. Poll POST /oauth2/token with grant_type=urn:ietf:params:oauth:grant-type:device_code
      // authorization_pending → keep polling at `interval`
      // slow_down            → increase the interval by 5s and continue
      // access_denied        → the customer declined; stop
4. On success: access_token + refresh_token, exactly as in §2.5
Scope restriction

The device flow does not grant orders:write. Its user code is short and typed by hand, which makes it a weaker binding than a full redirect flow — acceptable for read access, not for placing trades.

3API Conventions

These rules apply to every endpoint. Reading this section once will save you from rediscovering the same eight things across five sections of reference material.

3.1Hypermedia and HATEOAS

Every representation carries a _links object: a map keyed by link relation, each value carrying at least an href. 

{
  "orderId": "ord_01HQ9D4N7Q1S5U8X",
  "status":  "PARTIALLY_FILLED",
  "_links": {
    "self":       { "href": "https://api.brokerage.example.com/v1/accounts/acct_…/orders/ord_…" },
    "cancel":     { "href": "…/orders/ord_…", "method": "DELETE", "title": "Cancel the unfilled 200 shares" },
    "replace":    { "href": "…/orders/ord_…", "method": "PATCH" },
    "executions": { "href": "…/orders/ord_…/executions" }
  }
}

The contract has three parts, and the third is the one that pays for the other two:

  1. One bookmarked URL. Clients hard-code GET / and discover everything else by following relations.
  2. No URL construction. Never build a URL by concatenating strings. Follow the href you were given, verbatim — including its query parameters.
  3. Links are state-dependent. A FILLED order has no cancel link. An account without options approval has no place-option-order link. Branch on the presence of a link, not on a status string.
Why point 3 matters more than it looks

Status enumerations grow. If your UI enables its Cancel button when status ∈ {NEW, PARTIALLY_FILLED}, then the day a PENDING_ROUTE status ships, your button silently disappears for orders that are in fact cancellable. If instead it enables on "cancel" in _links, it keeps working — the server already knows the answer, and it is telling you.

RelationMeaning
selfCanonical URL of this resource.
nextThe next page. Absent on the last page (§3.4).
account, order, instrumentNavigate to a related resource.
balances, positions, orders, transactions, executionsSub-collections of an account or order.

Status code semantics

StatusMeaning in this API
400Malformed syntax or schema validation failure. The request never reached business logic.
401Token missing, expired, malformed, or revoked. Refresh once and retry; if that fails, re-authorize.
403Authenticated but not permitted — missing scope, or an options strategy above the account's approval level.
404No such resource, or it exists outside your grant. Deliberately indistinguishable, so the API cannot be used to enumerate account identifiers.

400 versus 422 is not cosmetic

A 400 means your code is wrong — fix it and the request will work. A 422 means your code is fine and the world said no: not enough buying power, market closed, instrument halted. The first is a bug to fix; the second is a condition to surface to the customer. Treating them identically produces an application that shows "Invalid request" when the honest answer is "the market is closed".

3.3Decimals, money, and why nothing is a float

Prices, quantities, and monetary amounts are transmitted as JSON strings: 

{ "limitPrice": "412.50", "quantity": "300", "netLiquidation": "184320.55" }

This is not stylistic. JSON numbers are IEEE-754 doubles in most parsers, and a double cannot represent 0.1 exactly. In a domain where a share count and a limit price multiply into a cash obligation, that error is a defect with a dollar value attached.

LanguageUseNever
Javanew BigDecimal("412.50")double, Double.parseDouble, or BigDecimal.valueOf(double)

The subtle Java trap

BigDecimal.valueOf(0.1) and new BigDecimal(0.1) both route through a double and inherit its error before BigDecimal ever sees the value. Only the String constructor is safe. The same applies to Python's Decimal(0.1) versus Decimal("0.1").

Other formats follow the same principle of being unambiguous on the wire:

Timestamps
RFC 3339, UTC, explicit offset: 2026-08-17T14:31:02Z. Sub-second precision on executions.
Dates
ISO 8601 calendar dates for trade and settlement dates: 2026-08-19. These are exchange-local dates, not instants.
Currency
ISO 4217 alphabetic codes. Every monetary field either carries a currency or sits beside one.
Identifiers
Opaque, prefixed, sortable strings (acct_, ord_, pos_, txn_, exec_, inst_). Do not parse them; the prefix is a debugging affordance, not an API.

3.4Pagination

Collections use opaque forward cursors. Request a page size with limit (1–200, default 50); follow the next link for more. 

GET /v1/accounts/acct_…/transactions?from=2026-08-01&limit=50

{ "items": [ … ],
  "_links": {
    "self": { "href": "…/transactions?from=2026-08-01&limit=50" },
    "next": { "href": "…/transactions?from=2026-08-01&limit=50&cursor=eyJvIjoxMjAwfQ" }
  } }

No next link means you have reached the end. Cursors are opaque: their encoding is not part of the contract and will change. Do not construct, parse, or persist them.

Why cursors rather than offsets

Offset pagination is unstable against a moving dataset. Between page 1 and page 2 of your transaction history, a settlement can insert a back-dated row — and with OFFSET 50 you silently skip a record. Cursors are anchored to a position in a stable ordering, so insertions do not shift the window out from under you.

Rows can still legitimately repeat across pages when settlement back-dates an entry. Reconcile on transactionId, which is permanent and unique.

3.5Idempotency

Every unsafe, non-idempotent operation — in practice, placing and amending orders — requires an Idempotency-Key header carrying a client-generated UUIDv4. 

POST /v1/accounts/acct_…/orders
Idempotency-Key: 6f1c2a90-3f5b-4c1e-9c2a-8d7b6e5f4a30
ScenarioResult
First request with a key201 The order is created.
Replay, same key, identical body200 The original order is returned with Idempotency-Replayed: true. No second order.
Replay, same key, different body422 idempotency-key-reuse. Nothing is created.
Key older than 24 hoursTreated as new. Keys are retained for 24 hours.
Generate the key once, per intent

The key must be created before the first attempt and reused verbatim on every retry of that same order intent. Generating a fresh UUID inside a retry loop defeats the entire mechanism and is the exact bug it exists to prevent.

The failure being defended against is specific: a socket timeout on a market order is indistinguishable, from the client's side, from a rejection. The order may have been accepted and routed. Retrying without a key doubles the customer's position; retrying with one is safe.

3.6Optimistic concurrency with ETags

Order reads return a strong ETag. Order mutations — PATCH and DELETE — require If-Match. 

# 1. Read, and keep the validator
GET /v1/accounts/acct_…/orders/ord_…
→ 200 OK
  ETag: W/"ord-7-1755441062"

# 2. Mutate, asserting you saw that exact version
PATCH /v1/accounts/acct_…/orders/ord_…
If-Match: W/"ord-7-1755441062"
Content-Type: application/merge-patch+json

{ "limitPrice": "413.25" }
OutcomeMeaning
200The order was unchanged since your read. The amendment was accepted, and a new ETag is returned.
412The order changed after your read. Re-read it and decide again — do not blindly retry with the newer ETag, or you will amend an order whose state you never evaluated.
428You omitted If-Match. Rejected rather than defaulted, on purpose.
The race this closes

You read an order showing 100 of 300 shares filled and decide to reprice the remaining 200. While you are deciding, it fills completely. Without If-Match, your amendment lands against an order you believe is working, and the outcome depends on timing you cannot observe. With it, you get a 412 and a chance to look again.

ETag also works for cheap polling: send it as If-None-Match on a GET and receive 304 Not Modified with no body when nothing has changed. That is what keeps a one-second poll inside the rate limit.

3.7Rate limits and backoff

Every response carries the current quota state, per RFC 9913:

RateLimit: "default";r=94;t=51          # 94 requests remain, window resets in 51s
RateLimit-Policy: "default";q=120;w=60  # 120 requests per 60-second window
PolicyQuotaApplies to
default120 / minuteAll read endpoints.
orders-write60 / minutePlace, amend, cancel.
order-poll1 / second per orderGET on a single order. Use the event stream instead.
streams5 concurrentOpen SSE connections per grant.

On 429, wait Retry-After seconds and retry with full jitter — a random delay between zero and your computed cap, rather than a fixed backoff: 

delay = random_between(0, min(2^attempt × base, cap))
Why jitter, specifically

When a venue hiccups, every client fails at once and every client retries at once. Fixed backoff preserves that synchronization and reproduces the thundering herd on each round, turning a two-second blip into a sustained outage. Randomizing the delay spreads the retries out. Ignoring Retry-After repeatedly escalates to a temporary suspension of the client.

3.8Versioning and compatibility

The major version is pinned in the server path (/v1). Within a major version, the following are considered backward-compatible and ship without notice:

  • New endpoints, and new optional request fields.
  • New fields in a response object.
  • New members in an enumeration — including new OrderStatus values.
  • New link relations in _links.
  • New problem type URIs.

Which places two obligations on your client:

  1. Ignore unknown properties. Configure your deserializer to tolerate them — Jackson's FAIL_ON_UNKNOWN_PROPERTIES=false, or an equivalent. A strict parser will break on a purely additive change.
  2. Tolerate unknown enum values. Do not map to a closed enum that throws. Treat an unrecognized OrderStatus as working, and rely on _links to know what you may do with it.

Breaking changes — removing a field, changing a type, tightening validation — require a new major version. The previous version is supported for at least 12 months after the successor ships.

5Trading APIs

Placing, amending, and cancelling stock and option orders. Everything in this section requires the orders:write scope and an ACTIVE account, and everything in this section moves real money in production.

5.1The order lifecycle

An order is a resource with a state machine. Understanding it is the difference between an integration that reconciles cleanly and one that quietly loses track of fills.

StateTerminal?Meaning
PENDING_NEWNoAccepted by us, not yet acknowledged by the venue.
NEWNoLive on the book. Working, unfilled.
PARTIALLY_FILLEDNoSome quantity filled; the remainder is still working.
PENDING_REPLACE / PENDING_CANCELNoAn amendment or cancellation is in flight at the venue.
FILLEDYesFully executed.
CANCELLEDYesCancelled. May carry a non-zero filledQuantity if it partially filled first.
REJECTEDYesRefused. rejectReason carries a machine-readable code.
EXPIREDYesTime in force elapsed — a DAY order at the close, or a GTD order past its date.
REPLACEDYesSuperseded by an amendment. Follow the link to the replacement.
SUSPENDEDNoHeld — a trading halt in the instrument, or a compliance hold on the account.
Three things that regularly surprise people

A 201 is not a fill. It means the order was accepted and routed. Terminal state arrives later, via the event stream, a webhook, or a poll.

Cancellation is a request, not a guarantee. The order moves to PENDING_CANCEL and only reaches CANCELLED once the venue acknowledges. A fill already in flight can still land — a "cancelled" order can end up FILLED.

An order can be rejected after acceptance. We accept and route it; the venue refuses it a moment later. That surfaces as a later REJECTED state, not as an error on the original call.

5.2Placing an order safely

POST/v1/accounts/{accountId}/orders
Requires orders:write  ·  Idempotency-Key header required

The request body is a discriminated union on assetClass: EQUITY for single-leg stock and ETF orders, OPTION for single- and multi-leg listed option orders.

Validation order

The service validates in this sequence and stops at the first failure, so a rejection tells you the first thing wrong, not everything wrong: 

schema  →  instrument tradability  →  market / session eligibility
        →  options approval level  →  buying power and margin
        →  risk limits             →  route to venue

The safe submission pattern

// 1. Generate the idempotency key ONCE, before the first attempt.
key = uuid4()

// 2. Preview, so the customer confirms real numbers rather than an estimate.
preview = POST /orders/preview  {order}
if (!preview.valid) { show preview.warnings; stop }

// 3. Submit. Retry ONLY with the same key — never regenerate it in the loop.
retry (max 4, full jitter) {
  response = POST /orders  {order}  Idempotency-Key: key
}

// 4. A 201 means routed, not filled. Confirm terminal state separately.
watch(response.orderId)  // SSE stream, webhook, or ETag-conditional poll

Option orders carry a legs array — one entry for a single-leg order, up to four for a combination. Multi-leg orders are priced and routed as one unit; legs never fill independently.

Requires orders:write  ·  If-Match required on both

Amendment uses JSON Merge Patch (RFC 7386). Only quantity, limitPrice, stopPrice, trailingAmount, trailingPercent, netPrice, timeInForce, and goodTilDate are amendable. Changing the instrument, the side, or the leg structure is a different order: cancel and place a new one. 

PATCH /v1/accounts/acct_…/orders/ord_…
If-Match: W/"ord-7-1755441062"
Content-Type: application/merge-patch+json

{ "quantity": "200", "limitPrice": "413.25" }

New quantity must be at least what has already filled. Amendment is best-effort against a live venue: a 200 means the amendment was accepted for routing, and the order may still fill at the old price if that fill was already in flight.

Cancellation is idempotent — cancelling an already-cancelled order returns 200 with the cancelled order rather than an error.

Webhooks

For server-side integrations that would rather be called than hold a connection open, register a webhook and receive the same OrderEvent payload by POST.

  • Signed with Webhook-Signature: HMAC-SHA256 over the raw request body, keyed by your webhook secret. Verify before parsing, and compare in constant time.
  • Return 2xx within 5 seconds. Non-2xx and timeouts are retried with exponential backoff for 24 hours.
  • Delivery is at-least-once, so handlers must be idempotent on eventId.
Verify the signature over raw bytes

Compute the HMAC over the body exactly as received, before any JSON parse and re-serialize. Round-tripping through a parser reorders keys and normalizes whitespace, which changes the bytes and breaks the signature — and the usual "fix" for that is to skip verification, which is how forged fill events get accepted.

6.2Authorization: PKCE in three languages

The same four steps everywhere: generate the pair, build the authorization URL, verify state, exchange the code.

Python

import base64, hashlib, secrets

def generate_pkce_pair():
    """32 random bytes → a 43-character verifier, the RFC 7636 minimum."""
    verifier  = base64.urlsafe_b64encode(secrets.token_bytes(32)).decode().rstrip("=")
    digest    = hashlib.sha256(verifier.encode("ascii")).digest()
    challenge = base64.urlsafe_b64encode(digest).decode().rstrip("=")
    return verifier, challenge

# `secrets`, never `random` — the verifier is the only thing stopping
# someone who intercepts the authorization code from redeeming it.

tokens = exchange_code(code, verifier)   # POST /oauth2/token, no client_secret

// Constant-time compare on `state` — habits matter more than this one leak.
function safeEqual(a, b) {
  const x = Buffer.from(a), y = Buffer.from(b);
  return x.length === y.length && timingSafeEqual(x, y);
}

public static PkcePair generatePkcePair() {
    byte[] entropy = new byte[32];
    RANDOM.nextBytes(entropy);                     // SecureRandom

    return Base64.getUrlEncoder().withoutPadding().encodeToString(raw);

Refresh with rotation — all three clients share this shape

Persist the new refresh token before using the new access token, atomically (write-temp-then-rename). On invalid_grant, stop retrying and re-authorize: the token is revoked, expired, or already spent, and there is no other recovery. Serialize concurrent refreshes behind a lock, or two threads will trip reuse detection and revoke the family.

6.6Amend and cancel with optimistic concurrency

Read, check the affordance, mutate with If-Match, and handle 412 by re-reading rather than blind-retrying.

Python

def amend_order(client, order, new_price):
    self_url      = client.link(order, "self")
    fresh, headers = client.get_with_headers(self_url)

    # Branch on the link, not on the status string.
    if not client.can(fresh, "replace"):
        return fresh

    try:
        return client.patch(self_url, {"limitPrice": new_price},
                            if_match=headers.get("ETag"))
    except ApiError as exc:
        if exc.status != 412:
            raise
        # The order changed while we were deciding. Re-read and decide
        # again — never retry with the newer ETag unexamined.
        return client.get(self_url)

Node.js

const { body: fresh, headers } = await client.getWithHeaders(selfUrl);
if (!client.can(fresh, 'cancel')) return fresh;   // already terminal

const cancelled = await client.delete(selfUrl, { ifMatch: headers.get('ETag') });
// PENDING_CANCEL, not CANCELLED — the venue has not acknowledged yet.
console.log(cancelled.status);

A 3.1/3.2 detail that silently breaks clients

OpenAPI 3.1 replaced its bespoke schema dialect with JSON Schema 2020-12, and nullable: true is not a JSON Schema keyword — it was a 3.0-ism. Left in a 3.1 or 3.2 document it is silently ignored, so a field you believe is nullable validates as non-nullable and your generated client throws on a legitimate null.

The correct spelling is a type union: type: [string, "null"], or oneOf: [{$ref: …}, {type: "null"}] when the base type comes from a $ref. This specification uses the correct form throughout; it is worth grepping any 3.1+ document you inherit for nullable.

CAppendix: Glossary

Buying power
What the account can spend. Differs by product — stock, option, and day-trading buying power are three separate numbers in a margin account (§4.2).
Contract multiplier
Shares of the underlying per option contract. Normally 100; adjusted contracts, following a split or merger, differ. Multiply option quantity by this for share-equivalent exposure.
DPoP
Demonstrating Proof of Possession (RFC 9449). Binds an access token to a key pair so a stolen token is inert without the private key (§2.9).
Good-faith violation
In a cash account, buying with unsettled proceeds and selling before they settle. Repeated violations restrict the account to settled cash.
HATEOAS
Hypermedia as the Engine of Application State. Clients discover available actions from links in the representation rather than from hard-coded URLs (§3.1).
Idempotency key
A client-generated UUID identifying one order intent, making retries safe. One key per intent, reused across every retry of that intent (§3.5).
Liquidity (added / removed)
Whether a fill posted to the book and waited (added) or crossed the spread (removed). Drives exchange rebates and fees.
Maintenance requirement
Minimum equity that must be held against margin positions. Falling below it triggers a margin call.
Net liquidation value
Total account value if every position were liquidated at current marks.
OSI symbol
The 21-character options contract identifier: AAPL  261218C00250000 — six characters of root (space-padded), YYMMDD, C/P, then strike × 1000 in eight digits.
Pattern day trader (PDT)
An account making four or more day trades in five business days. Subject to a 25,000 USD minimum equity requirement.
PKCE
Proof Key for Code Exchange (RFC 7636). Binds an authorization code to the client instance that requested it. Mandatory under OAuth 2.1 (§2.4).
Price effect
Whether a multi-leg option order's net price is paid (DEBIT) or received (CREDIT). Carries the direction, so netPrice is always positive.
Problem details
RFC 9457. The machine-readable error format used throughout this API (§3.2).
Refresh token rotation
Issuing a new refresh token on every use and invalidating the old one. Replaying a spent token is treated as theft and revokes the whole family (§2.7).
Settlement date
When cash and securities actually change hands. T+1 for US equities as of May 2024.
Strategy unit
One instance of a multi-leg option combination. A quantity of 10 on a two-leg vertical means ten spreads — twenty contracts (§5.4).
Time in force
How long an order remains working before it expires. See Appendix B.1.
