About the sample application

The brokerage in this book is fictional. Its customers, accounts and prices are invented, and its market is a simulation. The code is a teaching implementation: state lives in memory, and the authorization server is configured for local development only. It is not a trading system and must never be connected to real accounts, real markets or real credentials.

Preface

About this book

Most APIs that call themselves RESTful stop at JSON over HTTP. This book goes the whole way, and shows with one complete, tested application why the last steps are the ones that pay.

Who this book is for

You write or review HTTP APIs, probably in Java, and you want them to be boringly predictable: every error shaped the same way, every retry safe, every collection paged the same way, and clients that do not break when the server changes. You might be a developer building your first public API, an architect writing your organization's API guidelines, or a tech lead who has to decide whether hypermedia is worth it. You need Java and a working idea of what an HTTP request is. Everything else is explained as it comes up.

What you will build

The running example is a retail brokerage, the kind of API that sits behind a trading app: accounts, balances, positions, transaction history, market data, and orders for stocks and options. A brokerage makes a demanding teacher. Money must never be rounded by accident, a retried request must never buy twice, two devices editing one order must not overwrite each other, and every action must be authorized to the cent. The standards in this book exist because domains like this one need them.

How this book is built

Two rules kept the book honest. First, no code in it is typed by hand. Every code excerpt is pulled from the tested source when the book is built, and Appendix E prints every source file in full. Second, no HTTP exchange is invented. Each request and response was recorded from the running application, against freshly started servers. When you run the same request, you will see the same shape, though prices and timestamps will differ, because the market in the sample application never stops moving.

Light blocks are source code, captioned with the file they come from. Dark blocks are traffic on the wire, captioned HTTP. Long HAL documents are sometimes shortened: a comment such as /* 3 more */ marks where array items were left out, and the HAL curies entry, which every response repeats, is usually omitted after Chapter 10 introduces it.

The standard

Chapters that set a rule end with a box like this one. The boxes add up to a complete API style guide, gathered in Chapter 26 as a single checklist you can adopt, adapt or argue with.

A note on the standards

Where an Internet standard exists, this book uses it and names it: RFC 9110 for HTTP semantics, RFC 9457 for errors, RFC 7396 for merge patches, RFC 8288 for links, and so on. A few conventions are still Internet-Drafts, notably the Idempotency-Key and RateLimit header fields. The book says so each time, uses the shape the draft describes, and explains what to watch for. Where no standard exists, as with pagination cursors, the book states a convention and the reasoning behind it, so you can adopt it or replace it knowingly.
