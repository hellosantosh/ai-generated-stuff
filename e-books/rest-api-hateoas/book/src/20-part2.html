Chapter 5

Modeling a brokerage

Resource design starts from what users need to see and do, not from database tables. The trick is to turn every verb that matters into a noun with an address.

From screens to resources

Picture the trading app your API will serve. A home screen lists the customer's accounts. An account screen shows cash, buying power, holdings and recent activity. A ticket lets the customer pick a stock, see an estimate and place an order. An orders screen shows what is working and what has filled, with a button to cancel. A quote screen shows the price; an options screen shows contracts by expiration. Each of those is information a client needs, and each becomes a resource.

Two design decisions hide in that table. First, processes become resources. “Preview an order” and “cancel an order” are verbs, but REST has no custom verbs, so each becomes a noun you POST to: an order preview, a cancellation. This is not a trick to satisfy a style guide. A cancellation really is a thing with its own life. It is requested, it may fail because the order filled first, and it completes later. Naming it makes that life visible.

Second, account data hangs off the account, market data does not. Balances, positions, transactions and orders belong to one account, and their URIs say so. Instruments and quotes are the same for everyone, so they live at the top level. The URI structure mirrors ownership, and ownership is what authorization checks.

Rules for URIs

URIs are for the server to design and for clients to follow, but people still read them in logs and debuggers, so a few conventions keep them humane.

  • Nouns, plural for collections: /accounts, /orders. Singular for a resource of which there is one per parent: /balances (one balance sheet), /quote, /cancellation.
  • Lowercase, with hyphens: /order-previews, /option-chain. Never camel case, never underscores, never a file extension.
  • Nest only for ownership, and not deeply: an order belongs to an account, so /accounts/{accountId}/orders/{orderId}. Nothing in this API is nested more deeply than that.
  • Filters go in the query string: ?status=OPEN&symbol=AAPL, not /orders/open/aapl. Query parameters are optional, combinable and self-describing.
  • No verbs, except as the nouns of processes, like cancellation.
  • No version in the path: /v2/accounts would give one account two URIs. Versions travel in a header instead (Chapter 19).

Identifiers are opaque

The brokerage's identifiers look like ACC-1001, ORD-100002 and OPT-AAPL-261016-C-240. They are readable, which helps in logs and support tickets, but they are opaque to clients: a client stores an ID and sends it back, and never takes it apart. The option contract's ID happens to contain its expiration and strike, but a client that parses them out has written a bug that will fire the day the ID scheme changes. The contract's terms are in its representation, as fields, for exactly that reason.



  
One resource, one URI; one URI, one resource

  
Each resource has exactly one canonical URI, the one in its self link. That rule is why
  the API has no /v1 in its paths, and why an order has no second address such as
  /orders/ORD-100002 outside its account. Two URIs for one thing split caches, confuse
  logs and double the authorization rules. When a client needs a shortcut, the server gives it a
  link, not a second address.


  
Resources are not tables. balances has no table
  behind it: it is computed on each request from the ledger and live prices. order-previews
  stores nothing at all. The API promises what a representation contains, not how it is stored,
  which leaves the server free to change its internals.


  

    
The standard

    
    
      
  1. Model what clients need to see and do; give every such thing, including processes, a noun and a URI.
    2. 
      
  2. URIs are lowercase, hyphenated, plural for collections, nested only for ownership, with filters in the query string.
    3. 
      
  3. Identifiers are opaque strings; everything a client needs is a field in the representation.
    4. 
      
  4. Every resource has exactly one canonical URI: the self link.
    5. 
    

  







  
Chapter 6

  
Representations: money, time and identity

  
A representation is a contract written in JSON. The decisions that matter
  most are small ones: how to write a price, a timestamp, an absent value. Get them wrong once
  and every client inherits the mistake.


  
Money is a string

  
JSON has one number type, and most JSON parsers read it as a binary floating-point double.
  In binary floating point, 0.1 + 0.2 is 0.30000000000000004, and a price
  such as 232.42 cannot be represented exactly at all. A server that writes prices as
  JSON numbers is therefore trusting every client's parser not to round them. In a brokerage,
  that trust is misplaced.

  
So every price, amount and quantity in this API is a decimal string:
  "limitPrice": "450.00". A string survives every JSON parser intact, and the client
  decides how to read it, usually into BigDecimal in Java or a decimal library elsewhere.
  One bean configures this for every representation:

  

  
The OpenAPI contract describes such strings with a Decimal schema that carries a
  pattern, so a generated client knows to expect "187.50" and not 187.5.
  Counts that are naturally integers, such as a quote's traded volume, stay JSON numbers.

Every amount also travels with an explicit currency (an ISO 4217 code such as
  USD) on the account, the instrument or the balance sheet it belongs to. A client never
  guesses a currency from a symbol, and never formats one into a value.


  
Time is UTC

  
Moments are written in ISO 8601 in UTC with a Z, as Java's Instant serializes
  them: "createdAt": "2026-09-29T10:03:28.574985Z". Calendar dates that have no time of
  day, such as the date an account was opened or the date a trade settles, are plain ISO dates:
  "settlesOn": "2026-09-30". The API never sends local times or time-zone offsets. A
  client converts to the user's zone for display, and only for display.

  
The distinction matters. A trade executed at 3:59 p.m. in New York is 19:59Z; the
  date it settles is a business date defined by market rules, one business day later under
  the T+1 cycle US equity markets use:

Property names are camelCase, matching the Java records that produce them one for one.
  Enumerated values are UPPER_SNAKE_CASE strings such as MARKET, STOP_LIMIT and
  PENDING_CANCEL. Both choices are common; what matters is picking one and never

Absent is not null

  
A market order has no limit price, and an unfilled order has no average fill price. The
  API omits such fields rather than sending null, which you can see in the capture above.

  ask: does null mean “none,” “unknown” or “not loaded”? Here, a missing field
  means the concept does not apply to this resource in its current state.


  
What a representation leaves out

  
A representation is a public contract, so it should show what clients need and nothing
  else. The Order record shows three techniques at once:

  

  
    
    
  • Internal state is ignored. stopTriggered is bookkeeping for the matching engine,
    and version surfaces only as the ETag header (Chapter 15).
    • 
    
  • Derived values are computed. remainingQuantity is not stored; a method marked
    @JsonProperty computes it, so it can never disagree with quantity and
    filledQuantity.
    • 
    
  • Sensitive values are masked or hidden. An account's number is always sent as
    "****4821", and its customerId is never sent at all: the caller already knows who
    they are.

Signed amounts and self-contained entries

  
In a transaction, amount is signed from the account's point of view: money in is
  positive, money out is negative. A client can total a statement without a lookup table of
  transaction types. Each transaction also repeats the symbol it concerns, so a statement renders
  without one request per line.


  
The tolerant reader

  
The other half of a representation contract is on the client side. A client must ignore
  properties it does not recognize and treat unknown enumeration values gracefully, because
  adding a field or a status is how an API grows without breaking anyone. The book's Java client
  is configured that way from the start (Chapter 23). It even reads statuses as plain strings, so
  a status the server adds next year cannot crash it.


  

    
The standard

    
    
      
  1. Prices, amounts and quantities are decimal strings with a documented scale; every amount has a currency.
    2. 
      
  2. Moments are ISO 8601 UTC with Z; dates without a time are ISO dates.
    3. 
      
  3. Properties are camelCase; enumerated values are UPPER_SNAKE_CASE strings.
    4. 
      
  4. Absent values are omitted, never null; internal fields never appear; sensitive values are masked.
    5. 
      
  5. Clients are tolerant readers: unknown properties and values never break them.
    6. 
    

  







  
Chapter 7

  
Accounts, balances, positions and history

  
The read side of a brokerage API is where most traffic goes. It should be
  fast, obvious and impossible to misuse, and above all it must never show one customer another
  customer's money.


  
The accounts collection

  
A customer can own several accounts: here, an individual margin account and a Roth IRA.
  GET /accounts returns them embedded in a HAL collection, each with its own links.

  

  
Each account's links are its table of contents: balances, positions, transactions, orders,
  order previews and the order event stream. A client that wants an account's positions follows
  bk:positions and never needs to know that the path ends in /positions. The
  bk:transactions and bk:orders links are templated: the parameters in
  braces are optional filters the client may fill in, following RFC 6570.


  
Whose account is it?

  
The access token carries a customer_id claim, and every account lookup goes through
  one method that compares it with the account's owner. The comparison is deliberately
  strict about what it reveals:

  

  

  
Answering 403 Forbidden would be more literal, and it would also confirm that
  ACC-2001 exists. A 404 tells an unauthorized caller nothing, which is what RFC 9110
  suggests when a server does not want to reveal that a resource exists. Because every
  controller asks the ledger for the account first, there is no path to another customer's
  balances, positions or orders that skips this check.

Positions: holdings at market value

  

  
Each position carries its quantity, average cost and cost basis, and its value at the latest
  price, with unrealized profit and loss. It links to its instrument and to its quote, so a client
  can refresh a single price without re-reading the whole portfolio. Every position also has its
  own URI, /accounts/ACC-1001/positions/EQ-AAPL, for clients that track one holding.

Where are the transaction links? Transactions are
  embedded without links of their own. They are immutable entries in a statement, never

The standard

    
    
      
  1. Every read checks ownership through one code path; a resource the caller may not see does not exist (404).
    2. 
      
  2. Derived views such as balances are computed from the books of record, never stored beside them.
    3. 
      
  3. Collections that grow without bound are paged, with a next link when more exists.
    4. 
      
  4. Collection items embed their own links, so clients never assemble URIs from IDs.

Chapter 8

  
Market data: instruments, quotes and option chains

  
Market data is shared by every customer and changes every second. That
  combination shapes its design: global URIs, aggressive but private caching, and links
  that let a client walk from a stock to its options without knowing a single date.


  
Finding an instrument

  
The API root's bk:instruments link is a template, /instruments{?symbol,type}.
  A client expands it with the symbol the user typed:

  

  
Three properties answer the questions a trading screen asks before it offers a ticket.
  tradable says whether orders are accepted at all, and a halted security is not
  tradable. fractionable says whether fractional quantities are allowed.
  multiplier says how many shares one unit controls: 1 for a stock, 100 for a US equity
  option. The client reads these instead of hard-coding them per symbol.


  
Quotes: fresh for one second

  

  
Two response headers make polling cheap. Cache-Control: max-age=1, private tells
  the client, and any cache, that the quote is good for one second and must never be stored by a
  shared cache, because market data is licensed per user. The ETag identifies this
  particular tick of the market. A client that polls sends the tag back, and while the price has
  not moved it receives a bodiless 304:

  

  

  
checkNotModified compares the request's If-None-Match with the current tag and,
  when they match, completes the response as a 304. Returning null afterward is Spring's
  convention for “the response is already written.” Chapter 19 returns to quotes, because they
  are the one representation that changed shape between API versions.


  
Option chains: links instead of dates

  
An option chain is the list of option contracts for one underlying stock and one expiration.
  A naive design would make the client compute expiration dates, which are usually the third
  Friday of a month and are sometimes moved for holidays. Instead the chain offers every available
  expiration as a link, all with the same relation and each distinguished by its name:

  

  
HAL allows a relation to hold an array of links, and name is the standard way to tell
  them apart. A client renders one tab per bk:expiration link and follows the one the user
  picks. When a new expiration is listed, the client shows it with no code change.

  


  
The option contract

  
Each contract is an instrument in its own right, with an option object for its terms
  and a link back to its underlying stock:

  

  
Its symbol follows the symbology of the Options Clearing Corporation (OCC): the root
  symbol, the expiration as yyMMdd, C or P, and the strike times 1,000 in eight
  digits. AAPL261016C00240000 is the AAPL call expiring October 16, 2026 at a strike of
  240. Industry-standard symbols matter because they are what traders, statements and other
  systems use; the API's own id remains the key for every call.

  


  
A market that never stops

  
Prices in the sample application come from a simulation. Once a second, each stock takes a
  small random step, option prices follow their underlying, and the matching engine checks open
  orders against the new prices. Tests switch the simulation off and drive the matching engine
  by hand, so every price in a test is known in advance.

  


  

    
The standard

    
    
      
  1. Shared reference data lives at the top level; per-customer data lives under the customer's account.
    2. 
      
  2. Volatile resources carry an ETag and an explicit, short Cache-Control; licensed data is always private.
    3. 
      
  3. When the valid choices change over time, as expirations do, offer them as named links instead of making clients compute them.
    4. 
      
  4. Use industry-standard identifiers, such as OCC option symbols, as properties beside the API's own IDs.
