Chapter 9

HATEOAS: links as the engine of application state

A client that knows only one URL, and learns everything else from the responses it receives, can never offer an action the server would refuse, and never breaks when the server reorganizes. That is the whole promise of hypermedia.

What the acronym means

Hypermedia as the engine of application state is the last of REST's uniform-interface constraints. Application state is where the client is in its work: looking at an account, holding an open order, waiting for a cancellation to complete. The constraint says the client moves from one state to the next by following links and submitting forms that the server put in its responses, just as you move through a website by clicking links rather than typing URLs.

Consider what a trading screen needs to know about an order: whether a Cancel button should appear, and whether a Change button should. Without hypermedia, the client reimplements the server's rules: “show Cancel if the status is OPEN or PARTIALLY_FILLED, and if the user's token has orders:write, and if…”. Every copy of that rule is a place for it to go stale. With hypermedia, the rule lives in one place, and the client asks one question: is there a bk:cancel link?

The client's side of the bargain

  

    
Four rules for hypermedia clients

    
    
      
  1. Bookmark only the root. Store the API root URL in configuration; discover everything else.
    2. 
      
  2. Follow relations, not paths. Find a link by its relation (bk:orders), never by what its URL looks like.
    3. 
      
  3. Offer an action only if its link is present. The absence of bk:cancel means “you cannot cancel this, now.”
    4. 
      
  4. Store resource URIs, not IDs to rebuild them from. Keep the self link of anything you will need again.
    5. 
    

  


  
Links are guidance, not security

  
A missing link tells an honest client what it cannot do. It does not stop a dishonest or
  out-of-date one. The server still enforces every rule on every request: a client that posts to
  a cancellation URL it saved earlier, after the order filled, gets a clear refusal.

  

  
This is also why hypermedia and caching get along. A client may act on a representation that
  was accurate a second ago. The server's answer, 409 Conflict with a problem type naming
  the reason, tells it to re-read the order, whose links will now be accurate again.


  
Objections, answered

  

    
“Clients hard-code URLs anyway.”

    
Some will. They lose the benefits, and nothing breaks for anyone else. The clients in this
    book, a Java library and an AI agent, follow links, and Chapter 23 shows that doing so costs no
    more code than building URLs.

    
“Links make responses bigger.”

    
A few hundred bytes of links compress extremely well, and they save the round trips a client
    would otherwise spend asking what it may do.

    
“We will have to document the relations.”

    
Yes, instead of documenting URL patterns, parameters and state rules. A relation is a stable
    name with a meaning; a URL pattern is an implementation detail with a lifetime.

    
“It is slower to discover everything from the root.”

    
Discovery results can be cached like any other representation. A client that already holds
    an account's representation follows its links directly.

  


  

    
The standard

    
    
      
  1. Every representation links to itself and to its related resources.
    2. 
      
  2. State transitions appear as links only when the resource's state and the caller's permissions allow them.
    3. 
      
  3. The decision about which links a resource carries is made in exactly one place in the server.
    4. 
      
  4. The server enforces every rule regardless of links; a stale link earns a precise problem, such as 409.
    5. 
    

  







  
Chapter 10

  
HAL and link relations

  
Hypermedia needs a format that says, in a way every client can parse,
  “here is a link, and here is what it means.” HAL does that with two reserved
  properties and a naming scheme borrowed from the Web itself.


  
HAL in two properties

  
The JSON Hypertext Application Language, HAL, was proposed by Mike Kelly and is described in
  the Internet-Draft draft-kelly-json-hal. Its media type is application/hal+json.
  It adds exactly two reserved properties to an ordinary JSON object:

  
    
    
  • _links, an object whose keys are link relations and whose values are link
    objects, or arrays of them when a relation has several targets.
    • 
    
  • _embedded, an object whose keys are link relations and whose values are
    resources, or arrays of resources, included in the response to save round trips.
    • 
  

  
Everything else is the resource's own state. A HAL client needs no schema to find the links:
  they are always in _links, keyed by what they mean.


  

  
Link objects

  
A link object must have an href. HAL defines a handful of optional properties, and
  the brokerage uses four of them:

templatedtrue when href is an RFC 6570 template…/orders{?status,symbol,cursor,limit}

      
typeThe media type the target will returnapplication/openapi+yaml

      
nameDistinguishes links that share a relation"2026-10-16" on bk:expiration

Link relations: the vocabulary

  
A link relation names the meaning of a link: not “a URL,” but “the next page,”
  “the way to edit this,” “this order's instrument.” RFC 8288, Web Linking, defines two
  kinds. Registered relations are short names in the IANA Link Relations registry, such as
  self and next, with meanings every client already knows. Extension relations
  are URIs that the API owner defines and documents, which keeps them globally unique.

  
Extension URIs are long, so HAL provides CURIEs (compact URIs): a named template
  declared once in curies. In this API, bk:orders expands to
  https://docs.brokerage.example/rels/orders, a page that documents the relation. Here is the
  API root again, where the declaration appears:

Prefer registered relations. Before inventing a relation,
  check the IANA registry. edit, next, prev, first, last,
  collection, item, related and describedby cover a great deal. The brokerage
  invents relations only for domain concepts, such as a balance sheet or a cancellation, that no
  registry could know about.


  
Templated links

  
Some links need input from the client. RFC 6570 URI templates express that without
  giving away the URL structure. The template …/orders{?status,symbol,cursor,limit} uses
  form-style query expansion: each variable the client supplies becomes a query parameter,
  and each one it omits disappears.

  

    
Variables suppliedExpanded URI

    
      
none…/accounts/ACC-1001/orders

      
symbol=AAPL…/orders?symbol=AAPL

      
status=[OPEN, PARTIALLY_FILLED]…/orders?status=OPEN,PARTIALLY_FILLED

    
  

  
The client expands templates with a library (Spring's UriTemplate in Java) and
  never concatenates strings. The server, for its part, sends templates only for things a client
  chooses. Links a client should follow as-is, such as next, are always expanded.


  
Why HAL?

  
HAL is not the only hypermedia format. It is the simplest one that does the job, and it has
  the best support in the Spring ecosystem.

  

    
FormatStrengthsTrade-offs

    
      
HALMinimal; plain JSON plus _links/_embedded; wide library supportLinks only; actions need HAL-FORMS

      
HAL-FORMSAdds _templates: method, fields, validationA separate media type clients opt into

      
SirenEntities, links and actions in one formatA stricter envelope around every resource

      
JSON:APIComplete conventions for relationships, sparse fieldsets, pagingOpinionated document structure; weaker affordances

      
JSON-LD + HydraLinked-data semantics; rich vocabulariesSteep learning curve for most teams

    
  


  

    
The standard

    
    
      
  1. Representations are application/hal+json; links live in _links, included resources in _embedded.
    2. 
      
  2. Use IANA-registered relations where one fits; otherwise define extension relations as URIs, shortened with one CURIE.
    3. 
      
  3. Every extension relation's URI resolves to documentation of its meaning.
    4. 
      
  4. Templated links use RFC 6570; links meant to be followed as-is are always expanded.
    5. 
    

  







  
Chapter 11

  
Hypermedia with Spring HATEOAS

  
Spring HATEOAS turns hypermedia from hand-written JSON into a handful of types
  and one link builder. Links are built from controller methods, so they cannot drift from the
  routes they point to.

The override is a small workaround worth knowing about. RFC 8631 registered
  service-desc and service-doc with IANA, but Spring HATEOAS's built-in list of IANA
  relations does not include them, so without the override they would come out as
  bk:service-desc: a custom relation, which is wrong. Registered relations must never be
  prefixed.


  
Four model types

  

    
TypeRepresentsIn this API

    
      
RepresentationModelA resource defined by its links, with its own propertiesThe API root

      
EntityModel<T>A domain object plus linksAn account, an order, a quote

      
CollectionModel<T>Items (embedded) plus linksAccounts, positions, orders

      
PagedModel<T>A page of items with page metadataNot used: pages here are cursors

    
  

  
Domain records stay free of web concerns: Order knows nothing about links. The
  @Relation annotation on a record names it inside _embedded (orders, which
  the CURIE provider turns into bk:orders), and nothing else about the record needs to
  change.


  
Links from methods, not strings

  
WebMvcLinkBuilder builds links by calling the controller method they point to, on a
  proxy that records the call instead of executing it:

  
  
The builder reads the method's mapping, fills in the path variables from the arguments,
  adds any query parameters, and produces an absolute URI based on the current request. Arguments
  that are not part of the URI, such as the request body or the Jwt, are passed as
  null. If someone renames the route, every link to it follows; if someone deletes the
  method, the links stop compiling. Absolute URIs are derived from the incoming request, so behind
  a proxy you set server.forward-headers-strategy to have Spring honor the
  X-Forwarded-* or Forwarded headers.

The standard

    
    
      
  1. Build links from controller methods, never from string templates, so routes and links cannot diverge.
    2. 
      
  2. Keep domain types free of links; wrap them in models at the edge.
    3. 
      
  3. Put each resource's link rules in one assembler or method, and test them.
    4. 
      
  4. Registered relations are never prefixed with a CURIE.

Chapter 12

  
Affordances with HAL-FORMS

  
A link tells a client where it can go. An affordance tells it what it can do
  there: which method to use, what to send, and which values are allowed. HAL-FORMS adds
  exactly that to HAL.


  
From links to forms

  
A plain HAL link to bk:cancel says an action exists. It does not say whether to use
  POST or DELETE, or what body to send. Documentation fills that gap for people,
  but a generic client, or an AI agent, benefits from a machine-readable answer. HAL-FORMS, a
  specification by Mike Amundsen with the media type application/prs.hal-forms+json,
  supplies it: an extra _templates object whose entries describe the requests a client
  may send.

  
Clients opt in with the Accept header. Ask for the working order that way:

  


  
Reading a template

  

    
MemberMeaning

    
      
methodThe HTTP method to use.

      
contentTypeThe body's media type, application/json when absent. Here, a merge patch.

      
targetWhere to send it. When absent, the resource's own self URI.

      
propertiesThe fields: name, required, regex, type, min/max, options.

    
  

  
replaceOrder has no target, so it applies to the order itself, and its
  contentType is application/merge-patch+json, taken from what the controller
  method consumes. Its properties are the fields of a change, with the pattern every decimal
  must match. cancelOrder is a POST with no fields. A filled or canceled order has
  no templates at all, for the same reason it has no links.


  
The account carries two templates for a trading token. placeOrder comes from the explicit
  affordance in Chapter 11. previewOrder appears on its own: Spring HATEOAS records an
  affordance for the handler method behind every link built with linkTo(methodOn(...)),
  and HAL-FORMS renders a template for each one that is not a GET. The

Where the template comes from

  
Spring HATEOAS derives each property from the request type of the handler method, the class
  bound with @RequestBody. Bean Validation annotations become constraints: @NotNull
  and @NotBlank become required, @Size becomes min and
  max, and @Pattern becomes regex.

  

  
The remaining details come from configuration: the list of allowed values for each
  enumeration, and a pattern that describes a decimal-as-string:

  


  
A JavaBean, on purpose. OrderRequest is a
  class with getters and setters, not a record. Spring HATEOAS decides whether a property is
  writable by looking for a setter, and a record has none, so every field of a record-based request
  would be rendered readOnly, a template no client could fill in. The class Javadoc says
  so, to save the next developer from “simplifying” it. Similarly, @InputType("text")
  stops Spring HATEOAS from describing a BigDecimal as a number input, which would
  contradict the API's decimals-as-strings rule.


  
What clients do with templates

  
    
    
  • Generic user interfaces render a form per template: a dropdown for options, a
    validated text box for regex, a required marker. When the server adds a field, the form
    grows without a client release.
    • 
    
  • Client-side validation uses the same rules the server enforces, stated once.
    • 
    
  • Agents and tools learn the shape of an action at run time. A tool-using model can be
    given a template instead of a hand-written parameter list.
    • 
  

  
Templates describe the shape of a request, not every business rule. A limit order needs
  a limit price, and a sale needs shares to sell; those rules involve several fields or the
  account's state, so the server checks them and reports violations as problems (Chapter 16).
  The template narrows the space of wrong requests; it does not replace validation.


  

    
The standard

    
    
      
  1. Offer application/prs.hal-forms+json beside HAL; describe every state-changing action as a template.
    2. 
      
  2. Derive templates from the request types and their validation annotations, so forms and validation cannot disagree.
    3. 
      
  3. A template appears only when its action is available, exactly like its link.
    4. 
      
  4. Templates describe shape; the server still validates everything.
    5.
