Chapter 17

Collections: pagination, filtering and caching

A collection that can grow forever needs three things: a way to read it in pieces that never skip or repeat, a way to ask for less of it, and a way to avoid reading it again when nothing has changed.

Why not page=2?

Offset pagination (?page=2&size=25, or ?offset=25) is easy to build and wrong for any list that changes while it is read. A statement is newest first, so every new transaction is inserted at the top. If one arrives between a client's request for page 1 and its request for page 2, every item shifts down by one, and page 2 begins with an item the client has already seen. If an item is removed, one is skipped instead. Neither is visible to the client.

Cursors

A cursor encodes the sort key of the last item returned: here, its timestamp and ID, which together are unique. Filtering

  
Filters are optional query parameters that narrow a collection, and they are declared in the
  collection's link template, so clients discover them. The conventions are few and uniform:

  
    
    
  • Equality: ?symbol=AAPL, ?type=DIVIDEND.
    • 
    
  • Any of several values: repeat the parameter: ?status=OPEN&status=PARTIALLY_FILLED
    (a comma-separated list is accepted too, which is what RFC 6570 expansion of a list produces).
    • 
    
  • Ranges: from and to, inclusive, as ISO dates in UTC.
    • 
    
  • Order: fixed, newest first. A stable, indexable order is what makes cursors cheap.
    • 
  

  


  
Caching

  
HTTP caching (RFC 9111) is the cheapest performance work an API can do, because clients and
  proxies already implement it. The server's job is to say, for every response, whether it may be
  stored and for how long, with Cache-Control:

  

    
ResourceCache-ControlWhy

    
      
Accounts, balances, ordersno-cache, no-store, max-age=0, must-revalidatePrivate and changing; Spring Security's default

      
Quotesmax-age=1, privateChanges every second; licensed per user

      
The OpenAPI documentmax-age=3600Public, and changes only with a release

  application sets its own header. That is a safe default for an API full of personal data, and
  even reference data such as an instrument inherits it:

  (Chapter 8) and as the contract does:

  

  
Validation complements expiry. When a cached copy is stale, the client revalidates
  it by sending its ETag in If-None-Match, and a 304 costs almost nothing.
  Orders and quotes both support it; you saw both 304s in earlier chapters. Collections do not
  carry ETags in this API: a page of a changing list is cheap to regenerate and rarely identical
  twice.


  

    
The standard

    
    
      
  1. Page unbounded collections with opaque cursors and a next link; bound the page size and reject bad cursors with 400.
    2. 
      
  2. Sort in one stable order; filter with optional query parameters declared in the link template.
    3. 
      
  3. Every response states its cacheability; personal data is no-store, licensed data is private.
    4. 
      
  4. Resources that clients poll carry an ETag and answer If-None-Match with 304.

Chapter 18

  
Live order events with server-sent events

  
A trader wants to know the moment an order fills. Polling can tell them, one
  wasted request at a time. A stream tells them once, as it happens, and with the right design
  it never loses an event across a reconnect.


  
Choosing a push technology

  

    
OptionStrengthsCosts

    
      
PollingTrivial; works everywhere; cheap with ETagsLatency equals the interval; wasted requests

      
Server-sent eventsPlain HTTP; one-way push; built-in event IDs and reconnection with Last-Event-IDServer to client only; one long-lived connection per client

      
WebSocketsTwo-way, low overhead per messageA separate protocol; reconnection and replay are yours to build

      
WebhooksNo open connection; good for server-to-serverThe client must host a public endpoint and verify signatures

    
  

  
Order updates flow one way, from the brokerage to the client, and each one matters. Server-sent
  events (SSE), defined in the WHATWG HTML standard, fit both needs. They run over ordinary
  HTTP, through the same authentication and proxies as the rest of the API, and they were designed
  with replay in mind.


  
The event stream

  
A client opens the stream with an ordinary GET and Accept: text/event-stream, and
  the response simply never ends. Each event is a few field:value lines followed by a
  blank line. Here is the stream while a market order for NVDA is placed and fills:

  

  
id numbers every event, event names its type, and data carries a JSON
  summary of the order. The summary is deliberately small, and it links to the full order, so the
  event stream is hypermedia too: a client that needs every detail follows _links.order.

Never missing an event

  
Connections drop. When a browser's EventSource reconnects, it automatically sends the ID
  of the last event it received in a Last-Event-ID header, and any client can do the same.
  The server keeps a short history of each account's events and replays everything after that
  ID before streaming new ones:

  

  

  

  
The controller checks ownership exactly as every other account endpoint does, then hands the
  subscription to OrderEvents. Note the base URI captured at subscription time: events are
  sent later, outside the original request, where the current request is no longer available to
  build links from.

  


  
Running streams in production

  
    
    
  • History has a horizon. This implementation keeps the last 500 events per account. A
    client that has been away longer should re-read its orders, then resume the stream.
    • 
    
  • Proxies buffer. Some reverse proxies hold responses until they end, which never
    happens here. Disable response buffering for the stream's path.
    • 
    
  • Idle connections die. Load balancers close quiet connections. Streams that may be idle
    for long should send a periodic comment line (a line starting with a colon) as a heartbeat.
    • 
    
  • One process is not a cluster. Here, events live in memory. With several instances,
    publish them through a message broker so every instance can serve every subscriber, and replay
    from a durable log.
    • 
  


  

    
The standard

    
    
      
  1. Push state changes as server-sent events over the same authenticated HTTP as the rest of the API.
    2. 
      
  2. Every event has an increasing id and a typed event name; reconnects with Last-Event-ID replay what was missed.
    3. 
      
  3. Event data is a small summary that links to the full resource.
    4. 
      
  4. Document the replay horizon, and what a client should do beyond it.
    5. 
    

  







  
Chapter 19

  
Evolution: versions, deprecation and rate limits

  
An API that never changes is dead, and an API that breaks its clients is
  soon abandoned. The craft lies between: evolve without versions whenever you can, version
  precisely when you must, and tell clients well ahead of time what is going away.


  
Change without breaking

  
Most changes need no version at all, provided clients are tolerant readers (Chapter 6).
  These are safe:

  
    
    
  • Adding a property to a representation, or a new link to its _links.
    • 
    
  • Adding a resource, a link relation, an optional query parameter or a new problem type.
    • 
    
  • Adding a value to an enumeration that clients were told to treat as open-ended.
    • 
    
  • Moving a resource to a new URI, for clients that follow links. This is the change hypermedia
    makes free.
    • 
  

  
These break clients: removing or renaming a property, changing its type or shape, changing
  what a value means, adding a required input, or tightening validation. The brokerage has one
  breaking change in its history. Version 1 of a quote had flat bid and bidSize
  properties; version 2 groups each side into a price level and adds the day's change:

  


  
Where to put the version

  

    
StrategyExampleTrade-off

    
      
URI path/v2/instruments/…Visible and simple, but every resource gets one URI per version, and every link must know the version.

      
Query parameter?version=2Easy to add, easy to lose when a client follows a link.

      
Request headerAPI-Version: 2One URI per resource; links stay version-free; the client pins its version once.

      
Media type parameterapplication/hal+json;v=2Precise per representation, but awkward in tooling and caches.

    
  

  
For a hypermedia API the header wins, because links must work for every client regardless of
  version. The brokerage uses the API versioning support new in Spring Framework 7: one line
  chooses the header, and handler mappings declare the version they serve.

Rate limits

  
Quotas keep one client's bug from becoming every client's outage. The brokerage applies two
  per-client policies in fixed one-minute windows: default, for every request, and a stricter
  orders policy for requests that change orders.

  

  
A quota is only fair if clients can see it before they hit it. Every response advertises the
  policy and what is left of it, using the RateLimit-Policy and RateLimit fields from
  the IETF HTTP APIs working group's draft: q is the quota, w the window in
  seconds, r the requests remaining and t the seconds until the window resets. To
  show a limit being reached, these captures come from a second API instance configured with a
  quota of two requests per minute:

  

  

  

  
A well-behaved client slows down as r approaches zero, waits out Retry-After when it
  does not, and retries with the same idempotency key (Chapter 14). A fixed window is the
  simplest fair algorithm; a production gateway would typically use a sliding window or token
  bucket, and share its counters across instances.


  

    
The standard

    
    
      
  1. Prefer additive, backward-compatible change; clients must tolerate new properties, links and values.
    2. 
      
  2. Version the contract with a request header, never the path; unknown versions are 400 with the supported list.
    3. 
      
  3. Announce retirement with Deprecation, Sunset and a rel="sunset" link; clients pin their version.
    4. 
      
  4. Every response advertises its quota with RateLimit-Policy and RateLimit; exceeding it is 429 with Retry-After.
    5. 
    

  







  
Chapter 20

  
Securing the API with OAuth 2.1

  
A brokerage API must answer two questions on every request: who is this
  client acting for, and what has it been allowed to do? OAuth 2.1 answers both with a signed
  token, and never lets the API see a password.


  
Four roles

  
OAuth names four parties. The resource owner is the customer, Alice. The client is
  the software acting for her: a web app, her own script, an AI agent. The authorization
  server authenticates her, asks her consent, and issues tokens. The resource server is the
  brokerage API, which accepts tokens and enforces what they allow. OAuth 2.1, an IETF draft
  that consolidates a decade of OAuth 2.0 security guidance, removes the risky parts of the
  original: no implicit grant, no password grant, PKCE for every authorization code, exact
  redirect URI matching, and refresh tokens that are rotated or bound to a key.


  
Three clients, three patterns

  

    
ClientGrantPattern and limits

    
      
brokerage-webAuthorization code + PKCE, with consent; refresh tokensA web app's backend (a “backend for frontend”). A confidential client: tokens stay on the server, and the browser holds only a session cookie. Access tokens last 10 minutes; refresh tokens 8 hours, rotated on every use.

      
brokerage-cliClient credentialsA customer's own script, registered to that customer, like a personal API key. Tokens last 15 minutes.

      
brokerage-agentClient credentialsThe AI agent (Chapter 25). Registered to the customer, with tokens that last 5 minutes and a trading_limit of 5,000 USD per order.

    
  

  
The development authorization server is Spring Authorization Server, part of Spring
  Security 7. Its clients are declared in configuration:

  


  
Why the web app is a confidential client. A single-page
  app running only in the browser is a public client: it cannot keep a secret, and any token it
  holds is exposed to whatever script runs on the page. The IETF's guidance for browser-based apps
  recommends a backend-for-frontend instead: a small server that performs the OAuth flow as a
  confidential client and gives the browser only an HttpOnly session cookie. Spring
  Authorization Server agrees in its own way: it issues refresh tokens to confidential clients only.

Discovery: RFC 9728

  
How does a client that has never seen this API find out where to get a token? RFC 9728,
  OAuth 2.0 Protected Resource Metadata, answers it. The API publishes a metadata document
  naming its authorization servers and scopes, and points to it from the challenge in every 401
  (Chapter 16) and from the API root.

  

  
A generic client, or an AI agent, can go from a 401 to a token without any documentation:
  read resource_metadata from the challenge, fetch the metadata, fetch the authorization
  server's own metadata (RFC 8414) from /.well-known/oauth-authorization-server, and start
  the right flow.


  
Before production

  
    
    
  • TLS everywhere. The samples use plain HTTP on localhost only.
    • 
    
  • Durable, rotated keys. The development server generates a new signing key at each start.
    • 
    
  • Sender-constrained tokens with DPoP (RFC 9449) or mutual TLS (RFC 8705), so a stolen
    token is useless on another machine.
    • 
    
  • Secrets in a vault, never in configuration files, and never tokens in URLs or logs.
    • 
    
  • Step-up and consent for sensitive actions, and revocation when a device is lost.
    • 
  


  

    
The standard

    
    
      
  1. Authenticate every request with an OAuth 2.1 bearer token; browsers go through a backend for frontend with PKCE.
    2. 
      
  2. Tokens are audience-restricted, short-lived and carry fine-grained scopes; refresh tokens rotate.
    3. 
      
  3. Each operation's required scope is declared in one place; every query is scoped to the token's customer.
    4. 
      
  4. Publish RFC 9728 metadata and point to it from every 401 challenge.
    5.
