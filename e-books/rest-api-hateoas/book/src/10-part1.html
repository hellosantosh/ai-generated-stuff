Chapter 1

Why API standards matter

An API is a promise made to strangers. Standards are how you keep that promise when you are not in the room: when the network drops, when the server changes, and when the client was written by someone you will never meet.

Tuesday, 9:31 a.m. · a commuter train

Maya taps Buy on 100 shares. The train enters a tunnel. Her trading app waits thirty seconds, gives up, and, because its developers were careful people, tries again. The second request goes through. So, it turns out, did the first. The brokerage now holds two orders for 100 shares, and by the time the train leaves the tunnel both have filled.

That afternoon the app's developers read the API documentation looking for a way to retry safely. There isn't one. They find something else instead: errors arrive as {"code": 417, "msg": "failed"} for a dozen different reasons, so the app cannot tell “insufficient funds” from “market closed.” And a release note mentions that /v1/orders/place will move to /v2/trade/submit next quarter, which means another app release, another app-store review, and another month in which old versions of the app will break.

None of these is a bug in the usual sense. Each is a decision the API's designers did not know they were making.

Every one of those problems has a published, well-understood solution. A client that sends an Idempotency-Key header can retry an order as often as it likes, and the server will create it once. An error written as an RFC 9457 problem document carries a stable type identifier that a program can branch on. A client that follows links instead of building URLs does not care where the server moves a resource. This book is about adopting those solutions deliberately and consistently, so that the next Maya only buys once.

What a standard buys you

“Standard” here means two things. Some are Internet standards: RFCs published by the IETF, such as HTTP semantics (RFC 9110) or problem details (RFC 9457), that thousands of engineers have already argued over. Others are house conventions: choices such as “money is always a decimal string” that no RFC makes for you but that you make once, write down, and apply everywhere. Both kinds pay off the same way.

There is a quieter benefit too. Standards shrink documentation. When your API returns 428 Precondition Required, you do not need a page explaining what went wrong: RFC 6585 explains it, every HTTP library knows it, and an experienced developer recognizes it on sight. Every invented convention is something your documentation must teach and your users must remember.

The brokerage you will build

Standards are easiest to judge in a real system, so this book builds one. The sample brokerage has four parts, shown in Figure 1.1, and every one of them runs on your laptop.

The API serves accounts, balances, positions, transaction history, instruments, quotes, option chains and orders. Its market is a simulation: prices take a small random step every second and orders fill against them, so the order lifecycle is real enough to test cancellations and fills. The authorization server issues OAuth 2.1 tokens to three registered clients, each representing a different way customers reach a brokerage. The hypermedia client is a small Java library that navigates the API by following links. The agent is a conversational assistant, built with Spring AI and Claude, that uses the client as its tools and needs a person to confirm every trade.

Why a brokerage? Because it is unforgiving. A social network can show a stale like count. A brokerage that rounds a price, repeats an order or lets two edits collide costs somebody money. If a standard earns its keep here, it will earn its keep anywhere.

The standard
  1. Where an Internet standard exists, use it, and name it in your documentation.
  2. Where none exists, write the convention down once and apply it to every endpoint.
  3. Treat consistency as a feature: the second endpoint should hold no surprises for anyone who has used the first.
Chapter 2

REST in one chapter

REST is not a protocol, a format or a URL style. It is a short list of constraints, and the payoff for accepting them is an API that can change on the server without breaking the clients.

Roy Fielding described Representational State Transfer in his 2000 doctoral dissertation as the architectural style of the Web itself: the set of choices that let millions of independently written browsers and servers keep working together while both sides evolved. An API is RESTful to the degree that it adopts the same constraints. Each one costs you something, and each one buys you something specific.

The constraints

Client–server
The client owns the user interface and the server owns the data and rules. In the brokerage, buying power is computed only by the server. A client can display it, but never decides it.
Stateless
Every request carries everything the server needs to understand it: the access token, the account, the order. The server keeps no conversation state between requests. That is why the brokerage API disables HTTP sessions entirely, and why any instance behind a load balancer can answer any request.
Cacheable
Responses say whether, and for how long, they may be reused. A quote is good for one second, and only for the user who asked (Cache-Control: max-age=1, private). An account balance must never be stored by a shared cache at all.
Uniform interface
Every resource is manipulated the same way: identified by a URI, read and changed through representations, described by self-descriptive messages, and connected by links. This is the constraint that separates REST from “JSON over HTTP,” and it has four parts, covered below.
Layered system
A client cannot tell whether it is talking to the server itself, a cache, a gateway or a rate limiter. The brokerage adds its rate limiting and request IDs as layers that no endpoint has to know about.
Code on demand (optional)
A server may send code for the client to run, as web pages send JavaScript. APIs rarely use it, and this one does not.

The uniform interface, in four parts

  1. Resources are identified by URIs. The order ORD-100002 in account ACC-1001 is /accounts/ACC-1001/orders/ORD-100002, and only that.
  2. Resources are manipulated through representations. The client never touches the order itself. It receives a JSON representation, and it changes the order by sending one: a merge patch that says {"limitPrice": "455.00"}.
  3. Messages are self-descriptive. A response says what it is. For example, Content-Type: application/problem+json announces an error document before the client reads a byte of it, and ETag says which version of the order this is.
  4. Hypermedia is the engine of application state. Responses contain links to what the client can do next. An open order links to its cancellation; a filled order does not. This is HATEOAS, the subject of Part III.

The Richardson maturity model

Leonard Richardson proposed a simple way to see how far an API has gone toward REST, in four levels. Martin Fowler's write-up made it famous. Here is the brokerage's order placement at each level.

Level 0 uses HTTP only as a tunnel: one URL, one method, and the real request hidden in the body. Level 1 gives things addresses but still treats HTTP as a pipe. Level 2 uses methods and status codes as HTTP defines them, so caches, proxies and client libraries understand what is going on; 201 Created with a Location header is a sentence every HTTP developer can read. Level 3 adds hypermedia controls. The response to a new order links to the order, to a way to change it and to a way to cancel it, and the client learns what it may do from the response rather than from documentation.

Levels are not grades. A level 2 API can be excellent, and plenty of successful public APIs stop there. The argument of this book is narrower: the step to level 3 is cheaper than it looks with modern frameworks, and in a domain where actions depend on state and permissions, as trading does, it removes a whole class of client bugs. Chapter 9 makes that case in detail.

Resources and representations

A resource is anything important enough to have its own identifier: an account, an order, a quote, even an order preview. A representation is a document describing the resource's current state in some format. One resource can have several representations. The brokerage serves every order as plain HAL (application/hal+json) and, to clients that ask for it, as HAL-FORMS (application/prs.hal-forms+json), which adds descriptions of the forms a client may submit. The URI stays the same; the Accept header chooses the representation.

This distinction pays off in design. You do not have to expose your database tables. A balances resource can be computed on every request from the ledger and the market, because to the client a resource is whatever the representation says, however it came to be.

What REST is not

  • Not CRUD over tables. The brokerage has no DELETE for orders. A canceled order still exists, so canceling is a state change modeled as a resource of its own: POST …/orders/ORD-100002/cancellation.
  • Not a URL style. Pretty URLs are pleasant, but a REST client must not depend on them. Clients follow links; the server may reorganize its URLs at will.
  • Not JSON. REST is format-neutral. What matters is that the format is described by a media type and can carry links.
  • Not the opposite of RPC. Some operations are awkward as resources. Chapter 24 compares the brokerage with a real RPC-style trading API, and says when RPC is the better fit.
The standard
  1. Every request is self-contained: no server-side sessions, and the token travels with every call.
  2. Every important thing is a resource with a stable URI, including processes such as previews and cancellations.
  3. Methods and status codes mean exactly what RFC 9110 says they mean.
  4. Responses carry links to related resources and to the actions available right now.
Chapter 3

HTTP, the parts that matter

HTTP already defines most of what an API needs: verbs with guarantees, a vocabulary of outcomes, and headers for caching, concurrency and negotiation. Using them as defined is most of the work of a good API.

Methods and their guarantees

RFC 9110 gives each method two properties that clients, proxies and retry libraries rely on. A safe method does not change anything the client is responsible for, so it can be prefetched, cached and retried freely. An idempotent method has the same effect whether it is sent once or ten times, so a client can retry it after a timeout.

MethodSafeIdempotentHow the brokerage uses it
GETyesyesEvery read: accounts, positions, quotes, orders, the event stream.
HEADyesyesLike GET without the body; Spring answers it for every GET mapping.
POSTnonoPlacing an order, previewing one, requesting a cancellation. Made retry-safe with an Idempotency-Key (Chapter 14).
PATCHnonoChanging an open order, as a JSON merge patch guarded by If-Match (Chapter 15).
PUTnoyesNot used: no resource here is replaced wholesale by the client.
DELETEnoyesNot used: orders are never deleted, only canceled, and history is never erased.

Notice what drives the choice of method: the effect, not the URL. Canceling an order is not a DELETE, because the order survives with the status CANCELLED and stays readable forever. It is not a PATCH of status, because a client does not get to set a status; it can only ask for a cancellation, which the market may overtake with a fill. So it is a POST that creates a cancellation request, answered with 202 Accepted.

Status codes: the vocabulary of outcomes

A client should be able to handle a response correctly from its status code alone, and then refine its behavior from the body. These are all the codes the brokerage returns.

StatusMeaning in this APIClient's next step

201 CreatedAn order was placed. Location names it; ETag is its version.Store the Location, not a URL you built.

304 Not ModifiedYour cached copy (by If-None-Match) is still current.Reuse the cached copy.
400 Bad RequestThe request is malformed or invalid: a missing field, a bad cursor.Fix the request; do not retry as is.
401 UnauthorizedNo valid access token.Obtain a token, then retry.
403 ForbiddenThe token is valid but lacks a scope, or exceeds a delegated trading limit.Ask for more authority, or a smaller order.

409 ConflictThe order's state forbids the action: it has already filled or been canceled.Re-read the order.

Never return 200 for an error. A response like 200 OK {"success": false} hides failures from every tool that relies on status codes: monitoring, caches, retry policies, API gateways and the developer's own debugger. If something went wrong, the status line must say so.

Media types and content negotiation

The Content-Type of every message tells the receiver how to read it. The brokerage uses these types, each defined by a specification you can cite.

Media typeUsed for
application/hal+jsonEvery resource representation (the default).
application/prs.hal-forms+jsonThe same representations plus _templates, on request.
application/problem+jsonEvery error (RFC 9457).
application/jsonRequest bodies for new orders and previews.
application/merge-patch+jsonChanges to an order (RFC 7396).
text/event-streamThe live order event stream.
application/openapi+yamlThe API's own OpenAPI description.

A client picks among the representations the server offers with the Accept header. Ask for an account as plain HAL and you receive its links. Ask for application/prs.hal-forms+json and the same account also describes the order form you may submit, as Chapter 12 shows. If a client asks for a type the server cannot produce, the answer is 406 Not Acceptable; if it sends a body in a type the endpoint does not read, it is 415 Unsupported Media Type. Both come back as problem documents like every other error.

The standard
  1. Choose methods by their guarantees: GET for reads, POST for non-idempotent actions, PATCH for partial changes.
  2. Use the most specific status code that applies, and never report an error with a 2xx status.
  3. Label every body with a precise media type; use registered types and headers before inventing new ones.
Chapter 4

Your workbench

Twenty minutes from now you will have the whole brokerage running on your machine, a token in hand, and your first hypermedia response on the screen. Every later chapter assumes you can reproduce what it shows.

What you need

The code targets Java 27, the release that became generally available on September 15, 2026, so you need a JDK 27. Install one with your platform's package manager or a version manager such as SDKMAN, and check it:

You do not need Maven installed: the project includes the Maven Wrapper, a small script (mvnw, or mvnw.cmd on Windows) that downloads the exact Maven version the project was built with, 3.9.16, the first time you run it. You will also want curl.

If your IDE complains. IDE support for a new Java release often lags by a few weeks. If your editor reports errors that Maven does not, trust Maven, and update the IDE's Java tooling. The book's code compiles and its tests pass with the command-line build.

A tour of the project

The code lives in the brokerage-apis folder of the book's repository. It is a multi-module Maven build whose parent is Spring Boot 4.1.1.

The API's packages follow its domain, not its layers. Everything about orders, from the controller to the idempotency store, lives in orders; cross-cutting machinery such as error handling lives in platform. When you want to know how cancellation works, there is one package to read.

Start the servers

Open two terminals in brokerage-apis. Start the authorization server first: the API fetches its configuration and signing keys from it to validate tokens.

The API seeds two demo customers with accounts, cash, positions and a year of transaction history, and starts a market simulation that ticks once a second. Everything is in memory: restart the API and you start fresh.

Every call except the API root needs an OAuth access token. The quickest way to get one is the brokerage-cli client, which stands for a customer's own script. It uses the client credentials grant: it authenticates as itself and receives a token bound to its customer.
