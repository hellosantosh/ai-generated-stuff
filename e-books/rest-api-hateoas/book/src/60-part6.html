Chapter 21

The OpenAPI 3.2 contract

Hypermedia tells a client what it can do right now. A contract tells a developer, a code generator and a test suite what the API can do at all. A serious API needs both, and they must never disagree.

Links and contracts are complementary

An OpenAPI document describes every operation, parameter, header, schema and error an API offers. It powers documentation sites, mock servers, client generators, gateway configuration and contract tests. It does not replace hypermedia: the paths in the document are documentation of where resources currently live, not an invitation to build URLs. The brokerage's contract says so in its description, and links to it from the API root with the registered service-desc relation, so a client can find the contract the same way it finds everything else.

What is new in OpenAPI 3.2

OpenAPI 3.2.0 was published in September 2025, and 3.2.1 followed as a patch release. The brokerage's contract uses five of the version's additions:

FeatureWhat it does
$selfThe document's own URI, the base for resolving its references, even when copied elsewhere.
tags: summary, parent, kindHierarchical tags: Orders sits under Trading; kind separates navigation from badges such as Deprecated.
itemSchemaDescribes each item of a streaming response, such as each server-sent event.
oauth2MetadataUrlPoints an OAuth security scheme at the authorization server's RFC 8414 metadata.
dataValue, serializedValueExamples that separate the data from its serialized form.

The version also adds support for the QUERY method, query-string parameters described as a whole, and the OAuth device authorization flow, none of which the brokerage needs.

Design-first or code-first? This contract was written by
  hand, beside the code, and is enforced by tests (Chapter 22). Generating the document from
  annotations is the popular alternative, and it guarantees the document matches the code, but only
  in the details the annotations capture. Hypermedia rules, problem types and link relations are
  easier to describe by hand. Whichever you choose, the test that compares real responses with the
  schemas is what keeps the contract honest.


  

    
The standard

    
    
      
  1. Every API has an OpenAPI 3.2 document, served by the API and linked with service-desc.
    2. 
      
  2. The contract states each operation's scope, headers, examples and every problem response.
    3. 
      
  3. The contract is versioned with the code and tested against the running application.
    4. 
      
  4. Its paths document where resources live; clients still navigate by links.

Chapter 23

  
A hypermedia client in Java

  
A client that follows links is not harder to write than one that builds URLs.
  It is a different habit, and three small classes are enough to make it the easy one.


  
The rules the client lives by

  
    
    
  1. One configured URL: the API root. Everything else comes from links.
    2. 
    
  2. Relations, not paths: every navigation step names a link relation.
    3. 
    
  3. Tolerant reading: unknown properties and values are ignored, never fatal.
    4. 
    
  4. Problems are typed: an error becomes an exception carrying the problem type.
    5. 
    
  5. Safe retries: transient failures are retried with the same idempotency key.
    6. 
    
  6. A pinned version: every request says which API version it expects.
    7.

Generated clients and hypermedia clients

  
OpenAPI generators produce a method per operation with typed models, and they are convenient.
  They also bake the URL templates into the client, which quietly converts a hypermedia API back
  into a fixed-URL one. A good compromise is to generate the models from the contract's
  schemas and write the navigation by hand, as this client does in a few dozen lines. For
  scripts and throwaway tools, a generated client is fine; for anything that must survive the
  API's evolution, follow the links.


  

    
The standard

    
    
      
  1. Clients are configured with the API root only, and navigate by relation.
    2. 
      
  2. Clients read tolerantly and pin the API version on every request.
    3. 
      
  3. Errors surface as typed problems; transient ones are retried with the original idempotency key.
    4. 
      
  4. An action is attempted only when its link is present.
    5. 
    

  







  
Chapter 24

  
RPC or resources? Lessons from the Webull OpenAPI

  
Real brokerage APIs are often designed as remote procedure calls. Comparing
  one with this book's design, operation by operation, shows what each style gets right, and
  which standards cost nothing to adopt either way.


  
Webull publishes its OpenAPI for customers and partners at developer.webull.com. It is a
  capable, well-documented API that supports equities, options, futures and other asset classes,
  with market data over HTTP and streaming. It is also a clear example of the RPC style: operations
  named by paths, each with its own request and response shape. What follows describes the API as
  documented in September 2026, and it is a comparison of styles, not a review. Details change, so
  consult Webull's documentation before building against it.

In the RPC style, the account is a parameter: a query parameter for reads and a body field
  (account_id) for writes. Operations are verbs at the end of the path (place,
  replace, cancel, list, get), and every change is a POST. In the
  resource style, the account is part of the address of everything it owns, and the method carries
  the verb.


  

  
Point by point

  

    
Authentication: request signing versus bearer tokens

    
Webull authenticates each request with an application key and an HMAC signature: the client
    signs the path, query, body and a set of headers (x-app-key, x-timestamp,
    x-signature-nonce, x-signature-algorithm, x-signature-version, and the host)
    with its app secret, which never travels. Requests made on a customer's behalf also carry an
    x-access-token. Signing gives something a plain bearer token does not: a captured request
    cannot be replayed after its timestamp and nonce are spent, or altered in transit. OAuth's answer
    to the same threat is sender-constrained tokens (DPoP or mutual TLS, Chapter 20). The OAuth
    route wins on ecosystem: standard libraries, delegated consent, scopes, and discovery through
    RFC 9728, with no custom signing code in every client.

    
Errors: 417 versus problem details

    
Webull reports business-rule failures with HTTP 417 and a body of error_code
    and message. The structured code is the valuable part, and it is the same idea as a problem
    type. The status is the questionable part: 417 Expectation Failed is defined by HTTP for
    failures of the Expect request header, so generic tools misread it. RFC 9457 over
    400, 403, 409 and 422 says the same things in a standard shape.

    
Idempotency: client_order_id versus Idempotency-Key

    
Webull requires a client_order_id of up to 32 characters, unique per account, which makes
    a retried placement detectable. Chapter 14 compared the two approaches: the header generalizes
    the idea to any POST and defines what a replay returns.

    
Pagination: pagination_key versus next links

    
Order lists take a pagination_key, a cursor in all but name, which is the right
    algorithm. A next link carries the same cursor with nothing for the client to assemble.

    
Versions: x-version versus API-Version

    
Both put the version in a header rather than the path. The difference is only the name.

    
Naming: snake_case versus camelCase

    
Webull uses account_id; this book uses accountId. Either is fine, consistently applied.

  


  
What the RPC design does well

  
    
    
  • Composite orders. One placement request carries a new_orders array and a
    combo_type, such as a bracket or one-cancels-other group, so linked orders are accepted or
    refused together. A resource design needs an explicit resource for this, such as an
    order group posted to /accounts/{id}/order-groups that links to its member orders.
    That resource is worth designing before you need it.
    • 
    
  • SDK ergonomics. Operation-per-path maps one to one onto SDK methods, and Webull ships
    SDKs that also hide the signing.
    • 
    
  • Breadth. One uniform envelope stretches across many asset classes and market-data products.
    • 
  


  
Standards cost nothing to adopt, in either style

  
The most useful lesson of the comparison is that most of this book's standards do not depend
  on the resource style at all. An RPC API can return RFC 9457 problems with accurate statuses,
  accept an Idempotency-Key on every POST, write money as decimal strings, send
  Deprecation and RateLimit headers, link to its next page, publish RFC 9728 metadata,
  and describe itself in OpenAPI 3.2. Hypermedia is the step that needs resources. The rest is
  available to everyone.


  
Integrating with an RPC upstream. If your firm routes orders to
  a broker whose API is RPC-style, you can still offer your own clients a resource API. Put the
  upstream behind an anti-corruption layer: your resources, links and problem types on the outside,
  translated to the upstream's procedures, error codes and signing on the inside. Clients never see
  the difference, and you can change brokers without changing clients.


  

    
The standard

    
    
      
  1. Choose resources by default; use RPC-style operations only where a resource model is genuinely awkward.
    2. 
      
  2. Whatever the style, adopt the style-independent standards: problem details, idempotency keys, decimal strings, deprecation and rate-limit headers, OpenAPI.
    3. 
      
  3. Model composite actions, such as bracket orders, as resources of their own.
    4. 
      
  4. Hide a foreign API behind your own contract, not inside your clients.
    5. 
    

  







  
Chapter 25

  
Agentic AI: a trading assistant with Spring AI

  
An AI agent is a new kind of API client: capable, fast, and occasionally wrong
  with great confidence. Everything this book has built, from scopes to idempotency keys to
  problem types, is what lets such a client act for a customer without being trusted blindly.


  
What the agent does

  
The brokerage-agent module is a console assistant for one customer. Ask it about balances,
  positions, quotes or open orders, and it answers from live data. Ask it to buy or sell, and it
  checks the price, previews the order and proposes it, with an estimate and a confirmation code.
  Nothing happens until the customer types /confirm with that code.


  

  
Configuration

  leaves room for tool use and thinking in each response. The agent is also an OAuth client in its
  own right, with its own registration:

  every request the hypermedia client makes:

  

  
The system prompt sets the agent's role and its limits in plain language. It explains
  why the agent cannot act alone, so the model can explain it to the customer:

  


  
Tools: thin wrappers over the client

  
A Spring AI tool is an annotated method. Its description and parameter descriptions become the
  schema the model sees. Each brokerage tool is a one-line call to the hypermedia client, so the
  model sees exactly what the API allows, and no URL ever passes through the model:

  

  
Tools that would change anything only propose. proposeOrder resolves the symbol,
  previews the order through the API, and either returns the preview's issues or records a proposal:

  


  
The human in the loop

  
A proposal is a closure waiting in memory. The model receives only its code, summary and
  instructions, and has no tool that can confirm one. Confirmation happens in PendingActions,
  called only from the console:

  

  

  
Three details make the gate robust. Commands starting with / are handled by code and never
  reach the model, so no prompt, however cleverly injected, can type /confirm for the
  customer. Proposals expire after five minutes, so a stale estimate cannot be confirmed tomorrow.
  And the confirmation code is the order's Idempotency-Key: confirming twice, or retrying
  after a timeout, can never place two orders.


  
Defense in depth: the API has the last word

  
Suppose everything above failed: a bug in the gate, or a confused model that proposes a trade
  far larger than asked. The API still refuses anything beyond the limit the customer delegated to
  this client, because the limit is in the agent's token (Chapter 20) and the API checks it on every
  order:

  

  
The agent's scopes, its five-minute tokens, its trading limit and the customer's own accounts
  are all enforced by the resource server, not by the agent. The agent is trusted exactly as much as
  its token says, which is the only safe way to trust software that reasons.


  
Refusals and fallbacks

  
A model may decline a request. The console checks why the model stopped before reading its
  answer, and shows a clear message for a refusal rather than an empty reply:

  

  
The sample also opts in to a Claude API feature called server-side refusal fallbacks, in
  beta as of this writing. When a safety classifier declines a request, the API re-runs it on the
  fallback model Anthropic recommends for that category, instead of returning the refusal. Spring
  AI has no option for this request field, so a small OkHttp interceptor adds the beta header and
  "fallbacks": "default" to each Messages API request. It is an explicit opt-in: remove the
  RefusalFallbacks component to turn it off.

Running the agent

  
With the authorization server and the API running, build the agent and start it with your
  Anthropic API key in the environment:

  
  
Without a key, the console still starts and /status checks the API and the agent's token by
  calling a tool directly, with no model involved:

  

  
With a key, a request such as “buy 5 AAPL in my margin account” unfolds in a fixed
  sequence. The model calls getQuote for the price, then proposeOrder. The tool
  previews the order through the API and returns a proposal with its estimated total and code, and
  the model relays both. The customer types /confirm with the code, the console calls
  PendingActions, and the order is placed with the code as its idempotency key. The model
  never touched the order itself.


  
Hypermedia and agents. Agents benefit from hypermedia
  more than any other client. Links let an agent discover what it may do at run time instead of
  relying on stale training data about URL patterns; HAL-FORMS templates are already
  machine-readable descriptions of actions, close to the tool schemas models consume; and problem
  types give an agent a precise reason to explain to its user. An API designed by this book's
  standards is, almost by accident, an agent-ready API.


  

    
The standard

    
    
      
  1. An agent is an OAuth client with its own registration, short-lived tokens and least-privilege scopes.
    2. 
      
  2. Delegated limits, such as a maximum order value, live in the token and are enforced by the API.
    3. 
      
  3. Agents propose; people confirm through a path the model cannot reach; confirmations are idempotent and expire.
    4. 
      
  4. Tools are thin wrappers over a hypermedia client; test their guarantees without a model.
    5. 
    

  







  
Chapter 26

  
The standard on one page

  
Every rule from the chapters, gathered as a checklist you can adopt as your
  own API style guide, adapt to your organization, or argue with in a design review.


  

    

      
Resources and URIs

      
    
        
  • Everything important, including processes, is a noun with one canonical URI.
    • 
        
  • Lowercase, hyphenated, plural collections, nested only for ownership.
    • 
        
  • Filters in the query string; no verbs, no versions in paths.
    • 
        
  • Identifiers are opaque strings.
    • 
      

      
Representations

      
    
        
  • Money and quantities are decimal strings with a stated scale and currency.
    • 
        
  • Moments are UTC ISO 8601; dates are ISO dates.
    • 
        
  • camelCase properties, UPPER_SNAKE_CASE values.
    • 
        
  • Absent values omitted; internals hidden; sensitive values masked.
    • 
        
  • Clients read tolerantly.
    • 
      

      
Hypermedia

      
    
        
  • HAL with _links and _embedded; one root URL.
    • 
        
  • Registered relations first; extension relations as documented URIs via one CURIE.
    • 
        
  • Transitions appear only when state and permissions allow; decided in one place.
    • 
        
  • HAL-FORMS templates derived from request types.
    • 
      

      
HTTP semantics

      
    
        
  • Methods by their guarantees; precise status codes; never an error with 2xx.
    • 
        
  • 201 with Location for creation; 202 for work in progress.
    • 
        
  • Registered media types and headers before invented ones.
    • 
      

      
Errors

      
    
        
  • Every error is RFC 9457 problem details from one catalog of type URIs.
    • 
        
  • Invalid fields listed in one errors array; facts as extension members.
    • 
        
  • 401 with a challenge, 403 for scope, 404 for others' data.
    • 
        
  • Request IDs everywhere; no internals revealed.
    • 
      

    

    

      
Safety

      
    
        
  • An Idempotency-Key on every valuable POST; replays marked.
    • 
        
  • ETag on mutable resources; If-Match required (428/412).
    • 
        
  • Partial updates as JSON merge patch.
    • 
        
  • Previews use the same rules as the real action.
    • 
        
  • Records that must be kept are never deleted.
    • 
      

      
Collections, caching, events

      
    
        
  • Opaque cursors and next links; bounded pages; one stable order.
    • 
        
  • Explicit Cache-Control; no-store for personal data; 304 on If-None-Match.
    • 
        
  • Server-sent events with IDs and Last-Event-ID replay; events link to resources.
    • 
      

      
Evolution and quotas

      
    
        
  • Additive change first; version with a header when breaking.
    • 
        
  • Deprecation, Sunset and a sunset link before removal; clients pin versions.
    • 
        
  • RateLimit and RateLimit-Policy on every response; 429 with Retry-After.
    • 
      

      
Security

      
    
        
  • OAuth 2.1 bearer tokens: audience-restricted, short-lived, scoped.
    • 
        
  • Browsers through a backend for frontend with PKCE; refresh tokens rotate.
    • 
        
  • Scopes decided in one place; every query scoped to the token's customer.
    • 
        
  • RFC 9728 metadata, linked from every 401.
    • 
      

      
Contracts, clients and agents

      
    
        
  • An OpenAPI 3.2 contract, served and tested against real responses.
    • 
        
  • Clients configured with the root only, navigating by relation.
    • 
        
  • Agents propose, people confirm, and the API enforces delegated limits.
    • 
      

    

  


  
Epilogue: the train, again

  

    
A Tuesday, some months later · the same tunnel

    
Maya taps Buy. The train enters the tunnel, and the app waits, gives up, and tries again,
    exactly as before. This time the second request carries the same idempotency key as the first. The
    brokerage recognizes it, returns the order it created a few seconds earlier, and marks the response
    as a replay. Maya owns 100 shares.

    
At the office, the app's developers barely notice the day. When an order is refused, the app
    shows the problem's detail and branches on its type. When the brokerage moved its order URLs last
    month, the app did not change, because it had never known them. When version 1 of the quotes
    endpoint began sending Deprecation headers, an alert opened a ticket, and the move to
    version 2 was a morning's work.

    
None of it is remarkable. That is the point of a standard: it turns the decisions nobody knew
    they were making into decisions somebody made on purpose, once, for everyone.
