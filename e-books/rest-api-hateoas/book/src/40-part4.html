Trading Safely

Orders move money, so every weakness in an API becomes somebody's loss. This part places orders through layered validation, makes retries harmless with idempotency keys, stops concurrent edits from colliding, and turns every failure into a precise, documented problem.

Chapter 13

Placing orders

Placing an order is the most consequential request a brokerage API accepts. The design goal is simple to state: a well-formed, permitted order is accepted in one round trip, and anything else is refused with a reason a program can act on.

The order request

An order names an instrument, a side, a type, a quantity and, depending on the type, prices. The four order types behave as they do at any US broker:

TypeExecutesPrices required
MARKETImmediately, at the best available price: the ask when buying, the bid when selling.none
LIMITOnly at the limit price or better.limitPrice
STOPAs a market order once the last price reaches the stop.stopPrice
STOP_LIMITAs a limit order once the last price reaches the stop.both

timeInForce is DAY (the default) or GTC, good till canceled. clientOrderId is the caller's own reference, up to 64 safe characters, which the API stores and echoes but never interprets. Options use the same request: the instrument decides the multiplier and the commission. Fractional quantities are accepted only for market orders on fractionable stocks.

  rule is still a successful response. The preview itself worked; the answer is

For an option, the same request shape yields option economics: two contracts at 3.10 control
  200 shares, so the notional is 620.00, plus a commission of 0.65 per contract.

  


  
Placing the order: 201 Created

  

  
Everything in that response has a job. 201 Created says a new resource exists.
  Location says where, and it is the URI the client should keep. ETag is the order's
  version, needed to change it later (Chapter 15). Idempotent-Replayed: false says this
  request created the order rather than replaying an earlier result (Chapter 14). The body is the
  order itself, with its links, so the client needs no second request to display it.

  


  
Five layers of refusal

  
An order can be wrong in five different ways, and each is caught by a different layer with a

Execution

  
A new order starts OPEN. Each second the matching engine looks at every working order.
  A buy executes at the ask and a sell at the bid, never beyond a limit, and never for more than the
  size displayed at that price, which is how partial fills happen. Every execution is booked to
  the ledger as a trade with a T+1 settlement date, and published as an event.

  


  

    
The standard

    
    
      
  1. Offer a preview resource that applies exactly the rules placement applies, and link from an acceptable preview to placement.
    2. 
      
  2. A new order returns 201 Created with Location, ETag and the full representation.
    3. 
      
  3. Malformed or invalid requests are 400 with every field error listed; valid requests the account cannot honor are 422; exceeding delegated authority is 403.
    4. 
      
  4. Every rule lives in one server-side method shared by every path that needs it.

Chapter 14

  
Idempotency: retries that can never buy twice

  
Networks fail in the middle of requests. When they do, the client cannot know
  whether its order was placed. An idempotency key turns that uncertainty from a hazard into a
  non-event.


  
The problem with a timeout

  
Remember Maya's train from Chapter 1. When a POST times out, one of three things has
  happened, and the client cannot tell which:

  

  
GET, PUT and DELETE are idempotent by definition, so retrying them is always
  safe. POST is not, and placing an order must be a POST, because each order is new.
  The fix is to let the client make any particular POST idempotent by naming it.


  
The Idempotency-Key header

  
The IETF HTTP APIs working group's Internet-Draft The Idempotency-Key HTTP Header Field
  standardizes a practice that payment APIs have used for years. The client generates a unique
  key, a UUID works well, and sends it with the request. The server remembers the key along with
  the result. If the same key arrives again, the server returns the stored result instead of doing
  the work again.

  
    
    
  • Same key, same request: the original order, marked Idempotent-Replayed: true.
    • 
    
  • Same key, different request: a client bug; refused with 422 rather than guessed at.
    • 
    
  • No key: refused with 400. In this API every new order must be retry-safe.
    • 
  

  

  

  


  
How the server remembers

  
Recognizing “the same request” needs a definition. OrderRequest computes a
  fingerprint from its normalized fields. Quantities are stripped of trailing zeros, so
  "10" and "10.00" count as the same order, and the default time in force is
  filled in:

  

  
The key store keeps each key for 24 hours, scoped to the client and the account, so two
  different applications can never collide on a key:

  

  
The placement method checks the key before anything else, and records it only after the
  order exists:

  


  
In production. This store is an in-memory map, and the
  service is synchronized, so two concurrent requests with one key can never both succeed.
  A real deployment runs several instances, so the store belongs in a shared database, and the key
  must be claimed atomically before the order is created. A unique constraint on (client,
  account, key) is the usual tool. The draft specifies 409 Conflict for a request that
  arrives while an earlier one with the same key is still in flight.


  
The client's half

  
An idempotency key is only useful if the client reuses it on retries. The book's client
  generates one key per order and retries timeouts and transient failures with that same key:

  

  
    
    
  • Retry network failures and transient statuses (429, 502, 503, 504), never 400s or 422s.
    • 
    
  • Honor Retry-After when the server sends it; otherwise back off progressively.
    • 
    
  • Generate the key when the user presses Buy, not when the request is sent, so that
    every retry, even after an app restart, carries the same key.
    • 
  


  
Is clientOrderId enough?

  
Many brokerage APIs, including the RPC-style one compared in Chapter 24, deduplicate on a
  client-supplied order ID instead. It is a workable idea: the ID must be unique per account, so a
  retry with the same ID cannot create a second order. The Idempotency-Key header is the
  more general version of the same idea. It works for any POST, not only orders; it separates
  “my reference for this order” from “this attempt”; and it defines what a replay
  returns, which a unique-ID rule usually leaves unsaid.


  

    
The standard

    
    
      
  1. Every non-idempotent request that creates something valuable requires an Idempotency-Key.
    2. 
      
  2. The same key and request replay the original response, marked Idempotent-Replayed: true; the same key with a different request is 422.
    3. 
      
  3. Keys are scoped to the client and retained for at least 24 hours; claim them atomically.
    4. 
      
  4. Clients generate the key once per user intent and reuse it on every retry.
    5. 
    

  







  
Chapter 15

  
Changing and canceling orders

  
A working order is shared state: the customer's phone, their laptop and the
  exchange can all touch it at once. HTTP's conditional requests keep those writers from
  silently overwriting each other, and 202 Accepted tells the truth about cancels
  that take time.


  
The lost update

  
Maya's phone and laptop both show her open order for 10 MSFT at 450.00. On the laptop she
  raises the limit to 455.00. A moment later, on the phone, which still shows the old order, she
  cuts the quantity to 8. Without protection, the phone's request is applied to an order it has
  never seen, and nobody is told.


  

  
ETags and If-Match

  
Every order carries a strong entity tag that changes whenever the order does:

  

  
A client that changes an order must send the tag of the version it saw in If-Match. The
  server compares it with the current tag before applying anything. The API goes one step
  further than HTTP requires and makes the header mandatory: a change without
  If-Match is refused with 428 Precondition Required, defined for exactly this purpose
  by RFC 6585.

  

  

  

  
The currentEtag extension member saves the phone a guess: it can re-read the order, show
  the user what changed, and let them decide.


  
Merge patch: sending only what changes

  
The change itself is a JSON merge patch (RFC 7396), sent as
  application/merge-patch+json. A merge patch is a partial document: each member present
  replaces the same member of the resource, and members that are absent stay as they are. That
  makes the request both minimal and self-evident: {"limitPrice": "455.00"} changes the
  limit price and nothing else.

  

  
Only a working order's quantity, prices and time in force can change. The instrument, side
  and type cannot. A different instrument is a different order, so the client cancels and places
  a new one. The server re-runs the business rules on the new terms, discounting the cash the order
  had already reserved:

  

  


  
Polling cheaply with If-None-Match

  
The same tag makes polling almost free. A client that has an order sends its tag in
  If-None-Match. While nothing has changed, the answer is a bodiless 304 Not Modified:

  

  


  
Canceling: 202 Accepted

  
On a real exchange, a cancel is a request, not a command. It travels to the market, and a
  fill may arrive first. The API models that honestly. A cancellation request is accepted at once
  with 202 Accepted, the order moves to PENDING_CANCEL, and Location points at
  the order, whose status will settle:

  

  
Notice that the edit and bk:cancel links are already gone: a pending cancel
  cannot be changed or canceled again. On the matching engine's next pass, the order becomes
  CANCELLED, unless a fill wins the race, in which case it becomes FILLED and the
  cancel is moot. You saw the final state in Chapter 9.

  

  
Asking twice is harmless: a second request while the cancel is pending returns the same pending
  order, so a client can retry a cancel without an idempotency key. Once the order is final, the
  request is refused with 409 Conflict.


  
Why not DELETE?

  
DELETE /orders/ORD-100002 reads naturally, but it promises the wrong thing: that the
  resource will be gone. A canceled order must remain readable for the customer's records, for
  regulators, and for the client that asked. Modeling the cancellation as its own resource keeps
  every guarantee true: the order is never deleted, the request is accepted rather than
  completed, and the final state is visible on the order itself.


  

    
The standard

    
    
      
  1. Every mutable resource has a strong ETag; changes require If-Match (428 without, 412 when stale, with the current tag in the problem).
    2. 
      
  2. Partial updates are JSON merge patches with application/merge-patch+json.
    3. 
      
  3. Operations that complete later answer 202 Accepted with a Location to watch.
    4. 
      
  4. Records that must be kept are never deleted; ending them is a state change.
    5. 
    

  







  
Chapter 16

  
Problem details: errors as RFC 9457 documents

  
An error response is an API's most important documentation, because it is the
  one a developer reads when something is already wrong. RFC 9457 gives every error the same
  shape, and a stable identifier that code can depend on.


  
Anatomy of a problem

  
RFC 9457, Problem Details for HTTP APIs, replaced RFC 7807 in 2023 and defines the
  media type application/problem+json. Every error from the brokerage API is one:

  

  
The most important rule is the division of labor. Code branches on type, never on
  title or detail, which are prose and may be reworded or translated. The type is
  a URI, so it is globally unique. In this API it also resolves to a page that documents the
  problem: what it means, when it happens, and what to do about it.


  
A catalog, not a free-for-all

  
Every problem the API can return is declared in one enumeration, with its type, status and
  title. There is no other way to produce an error, so the catalog is complete by construction:

  ApiException with a type, a detail and any extension members:

Security errors are problems too

  
Authentication and authorization failures happen in Spring Security's filter chain, before any
  controller runs, and by default they produce an empty body. The API keeps what Spring Security
  does well, the standard WWW-Authenticate challenge of RFC 6750, and adds the problem
  document by handing the exception to the same MVC exception handling:

  

  

  

  
Three statuses, three meanings. 401: I do not know who you are; get a token (the challenge
  even says where, through the resource_metadata parameter of RFC 9728). 403: I know
  who you are, and your token does not allow this. 404: as far as you are concerned, it does not
  exist, which is also the answer for another customer's account.


  
Request IDs

  
Every response carries an X-Request-Id, and every problem repeats it as
  requestId. A client may supply its own ID so that its logs and the server's share one
  value. The server accepts only IDs that are short and plain, so the header cannot be used to
  inject text into logs:

  


  
What never goes in a problem

  
    
    
  • Stack traces, exception class names, SQL, file paths or server names.
    • 
    
  • Anything that confirms the existence of a resource the caller may not see.
    • 
    
  • Secrets, tokens or the full contents of the request.
    • 
  

  
An unexpected exception becomes a generic 500 problem with a request ID, and the
  details go to the server's log, where the request ID finds them.


  

    
The standard

    
    
      
  1. Every error is application/problem+json with type, title, status, detail and instance.
    2. 
      
  2. Problem types are stable URIs from one catalog, each documented; clients branch on type only.
    3. 
      
  3. Facts a client needs travel as typed extension members; invalid fields are listed in one errors array.
    4. 
      
  4. 401 carries a WWW-Authenticate challenge; 401, 403 and 404 are used precisely.
    5. 
      
  5. Every response and problem carries a request ID; no problem reveals internals.
    6.
