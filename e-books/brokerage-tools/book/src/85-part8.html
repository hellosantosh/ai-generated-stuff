Chapter 35

The review gate

Six questions worth asking out loud, and everything else a machine asks for you.

A tool review that spends forty minutes on naming conventions and five on whether the description tells the truth has got the proportions exactly backwards. The entire purpose of Parts II and III is to make the first forty minutes unnecessary.

What the machine has already decided

The name. The risk tier. The approval mode. The entitlement floor. The classification floor. Whether every property has a description. Whether every string is constrained. Whether the schemas are inside the profile. Whether cross-references resolve. Whether the governance block is complete. Whether the identifier patterns match the ontology. Whether a tier 2 tool names a kill switch and cites an evaluation suite. None of that is review material.

The six questions

1. Is the description true?

Read it as if you were the model, with no other knowledge. Does every sentence hold? The common failures are a “when to use” written in the firm's vocabulary rather than the customer's, and a “how to read the result” that describes a field that was renamed two versions ago.

2. What is the nearest tool, and does each say so about the other?

Almost every selection error in a mature catalog is between two tools that a human would also hesitate between. Find the nearest neighbor and check that both descriptions name each other. If the reviewer cannot immediately say which tool a given utterance should hit, neither can the model.

3. What is the worst thing a confused agent could do with this?

Not a malicious one — a confused one, acting in good faith on a plausible misreading. For a read tool the answer is usually “say something wrong” and the follow-up is “would the customer be able to tell?”. For a write tool, if the answer is anything other than “get stopped by the gate”, the design is not finished.

4. Does the confirmation show the consequence?

Render it. Actually render it, with real arguments, and read what the customer will see. This is the question that catches the (not given) bug from chapter 9, and it is not catchable any other way.

5. What does the agent do when this fails?

Walk each error the tool can return and say the next move out loud. If any of them leads to “try a different tool” or “try again” when it should not, the remediation text is wrong.

6. What happens when we turn it off?

Trip the kill switch in the console and watch the catalog shrink. If anything downstream breaks rather than simply becoming unavailable, the tool has a dependency nobody wrote down.

Reviewing a change, not a tool

Most reviews are of a change to an existing tool, and the question is narrower: does this change what the model will do?

A change toNeeds
The handler only Contract tests. The model's view has not moved.
An output field's value Contract tests, and a look at whether any description mentions it.
The description A live evaluation run. The cassettes for this tool are stale by definition.
The input schema A live run, and chapter 36's table on what is breaking.
The risk tier or approval A new signature at the new tier, and the refusal suite.

Chapter 36

Versioning and deprecation

The list of things that break a model is not the list that breaks a compiler.

Semantic versioning on a tool descriptor versions the contract, and the contract has two consumers with very different sensitivities: code that calls the tool, and a model that decides whether to.

What is breaking

ChangeFor code For a modelVersion
Adding an optional parametersafesafeminor

The three highlighted rows are the ones that surprise people, so each gets a sentence.

A new enum value in an output is safe for code that switches with a default and breaking for a model that was taught the old set by the description and will now encounter a value it has never been told how to read.

A rewritten description changes nothing about the interface and changes everything about which tool gets chosen. It is the single most behavior-affecting edit available and the one least likely to be reviewed as such.

A changed default changes the behavior of every call that omits the parameter, which for a model is most of them. Moving brokerage_orders_list's default from WORKING to ALL would not break a single caller and would change what the agent reports to every customer who asks about their orders.

Deprecation

Renaming a tool breaks a model and nothing compiles differently. Every recorded evaluation references the old name; every audit record for the retention period references the old name. So deprecation is a window, not a switch.

  1. Publish the replacement as active, with a description that says what it replaces.
  2. Mark the old one deprecated and edit its description to say so and to name the replacement. The linter warns when a deprecated tool's description does not.
  3. Both are published for the window. The model will migrate on its own, because the new description is the one that says it is current.
  4. Measure. When the old tool's call rate reaches zero across the evaluation suites and production, mark it retired. The registry stops serving it.
  5. Keep the descriptor. A retired descriptor is still the only explanation of what an audit record from four years ago means.

Do not publish both for longer than you have to. Two tools that do the same thing are two descriptions a model has to choose between, and the choice is a coin flip until one of them says it is deprecated. The window exists to drain traffic, not to avoid a decision.

Versioning the catalog, not just the tools

One more number is worth keeping: the ontology's own version. A change to the operation vocabulary, the policy table or an identifier pattern affects every tool at once, and the build's response should be to re-lint the entire catalog — which it does, because the linter takes the ontology as an argument. 








  
Chapter 37

  
When it goes wrong

  

    Six incidents, and the control that would have caught each one. None of them is a model
    behaving badly.
  


  

    These are composites, disguised, and none is hypothetical in shape. The point of the chapter is
    that in every case the fix was a control the firm could have had, and in no case was it
    “use a better model”.
  


  
One — the wrong Apple


  

    
What happened

    

      A customer said “put a thousand dollars into Apple”. The instrument lookup returned
      the best match and the agent bought a hospitality REIT. It was a real company, a real order,
      and a real fill.
    

  


  

    The control. A search tool that returns candidates rather than a choice, and an
    exactMatch flag the description tells the agent to read. The decision
    was never the model's to make; it had been moved there by a tool that silently resolved
    ambiguity.
  


  
Two — the double order


  

    
What happened

    

      A socket closed after the order reached the venue and before the response came back. The agent
      retried. Two orders, two fills, one customer who wanted one.
    

  


  

    The control. An idempotency key derived from a single-use confirmation token, and a
    duplicateOfPreviousCall field so the agent describes one order rather
    than two. Note that the usual fix — asking the model to supply a key — would not
    have worked: a retry is exactly when a model is most likely to generate a fresh one.
  


  
Three — “I've canceled that for you”


  

    
What happened

    

      The customer asked to cancel. The order filled while the cancellation was in flight. The
      cancel tool returned a 409 and the agent, reading a conflict as a transient failure, retried
      twice, then told the customer it was canceled. They found out at the statement.
    

  


  

    The control. Two of them. A successful envelope with
    cancelled: false and status: FILLED,
    because nothing failed. And an explanation written to be read aloud, so the agent relays the
    fill rather than summarizing an outcome it inferred.
  


  
Four — the enumeration


  

    
What happened

    

      A customer pasted a document into the chat. It contained a line addressed to the assistant
      asking it to check a list of account numbers. The balances tool returned
      403 Forbidden for accounts that existed and
      404 for accounts that did not, and the agent — being helpful
      — reported which were which.
    

  


  

    The control. NOT_FOUND for both, from the account guard. Since
    the agent cannot act on either answer there is no cost to the uninformative one, and a real cost
    to the informative one.
  


  
Five — the approval that was not one


  

    
What happened

    

      The confirmation dialog rendered from the tool's arguments. It showed the side, the quantity
      and the ticker correctly, and (not given) where the cost should have
      been. Customers approved it, because the part they recognized was right.
    

  


  

    The control. An approval context that asks the domain for the figures the arguments do
    not carry, and a review question that says render it and read it. This one is in the
    book because it is the failure mode that is hardest to find by testing: everything passes, and
    the dialog is wrong in a way only a human reading it notices.
  


  
Six — the quiet drift


  

    
What happened

    

      A handler started returning null for
      averageFillPrice on partially filled orders, where it had
      previously returned the running average. No test covered it. The output schema still said the
      field was a decimal string. The agent started reporting that orders had filled at no price.
    

  


  

    The control. Output validation in the pipeline, failing closed. The output schema is the
    only description of the payload the model will ever see, and a handler that drifts from it is
    misleading the model with a document the firm published.
  


  
The pattern


  

    In all six, the model did something reasonable with what it was given. The defect was in what it
    was given.
  


  

    That is not a comforting conclusion, because it means the work is in the catalog rather than in
    the prompt. It is a useful one, because the catalog is a thing you can test.
  







  
Chapter 38

  
The first year

  

    An adoption plan that survives contact with a delivery schedule.
  


  

    The failure mode for a specification like this one is not rejection. It is enthusiastic adoption
    followed by quiet erosion: a team adopts it, hits a deadline, takes one exemption, and the
    exemption becomes the pattern. So the plan below is ordered by what buys the most for the least,
    and every stage ends with something mechanical.
  


  
Quarter one — make it mechanical


  

    
DoBecause

    
      
Write descriptors as files
        Everything else depends on it. If the descriptor is inside a Java annotation, no linter,
          no review and no second runtime is possible.

      
Write the linter
        Start with ten rules, not a hundred: name grammar, closed objects, described properties,
          constrained strings, all four annotations, an owner, an entitlement, an audit event, a
          retention, and no reserved parameter names.

      
Put it in CI
        A linter that runs on demand is a style guide.

      
Build the console's catalog page
        Direct invocation and a verbatim descriptor remove most of the guesswork from building
          tools, and both work before any agent exists.

    
  


  

    Deliverable: every existing tool passes ten rules, and anyone can see what the model is shown.
  


  
Quarter two — make it consistent


  

    
DoBecause

    
      
Write the capability table
        One row per tool. That alone gives the naming rule, the completeness question and the
          producer graph.

      
Derive names from it
        And rename what does not match, now, while the catalog is small enough that renaming is
          an afternoon.

      
Add the ontology rules to the linter
        Names, tiers, approval modes, entitlement floors, identifier patterns.

      
Adopt the result envelope and the taxonomy
        Fifteen codes, and a guidance sentence per code that the system prompt is generated
          from.

    
  


  

    Deliverable: a catalog a model can generalize over, and a prompt nobody maintains by hand.
  


  
Quarter three — make it measurable


  

    
DoBecause

    
      
Write twenty scenarios
        Ten selection, ten refusal. Take them from support tickets rather than inventing
          them.

      
Record cassettes
        So the suite runs on every commit for free, and the live run is reserved for
          descriptor changes.

      
Report four scores, not one
        And gate hardest on refusal accuracy.

      
Publish the scores into the governance blocks
        So the number is an assertion rather than a slide.

    
  


  

    Deliverable: a number that moves when somebody edits a description, visible before the pull
    request merges.
  


  
Quarter four — take one tool to L3


  

    
DoBecause

    
      
Pick the first state-changing tool
        And build it properly once: preview and place as two tools, a single-use token, an
          approval gate keyed to the arguments, a rendered confirmation, a kill switch, a trajectory
          suite and a refusal suite.

      
Run the review as a review
        Six questions, two signatures, and the confirmation rendered and read aloud.

      
Then copy it
        The second state-changing tool should take a week, not a quarter. If it does not, the
          first one was not finished.

    
  


  
What to resist


  
    
    
  • 
      A hundred rules in quarter one. Ten rules everyone passes beats a hundred that get an
      exemption clause.
    
    • 
    
  • 
      An ontology before a catalog. It is a description of what you have, generalized. Write
      ten tools first and the entities will be obvious.
    
    • 
    
  • 
      Trading tools in quarter one. The controls that make them safe are the ones you will
      build in quarters two and three. A state-changing tool shipped before the gate exists is a
      tool shipped without the gate.
    
    • 
    
  • 
      A hand-written system prompt listing the tools. It will be wrong within a month and it
      will be wrong in a way that changes behavior.
    
    • 
    
  • 
      Treating the console as a nice-to-have. It is the cheapest thing in this book and the
      one that makes the rest of it usable.
    
    • 
  


  
And the thing to measure all year


  

    
The one metric

    

      How long does it take to publish a correct new tool? In quarter one it is a fortnight
      of meetings. If by quarter four it is not a day, the specification has become overhead rather
      than scaffolding, and the thing to fix is the specification.
