Chapter 1

What a tool is

A tool is not an endpoint with a description attached. The difference is the caller, and the caller changes almost everything.

Here is the sentence that most teams start from: we already have a REST API, so we will expose it as tools. It is a reasonable instinct and it produces a catalog that works in a demonstration and disappoints in production. The reason is worth being precise about, because it is not that language models are unreliable. It is that an API and a tool are contracts with different parties, and almost every property an API contract leaves to convention, a tool contract has to state.

Five differences that matter

 An API endpointA tool
The caller A developer who read the documentation once, wrote code, and now calls it the same way forever. Mistakes are found at compile time or in a test. A model that re-reads the description on every turn and decides fresh each time. Mistakes are found in a conversation, by a customer.
Discovery Out of band. The developer browses the docs, picks the endpoint, and nothing in the API itself has to help them choose. In band. Choosing which tool is the hard part, and the only thing that helps is the prose in the description — which is therefore the most load-bearing field.
Arguments Constructed by code from typed values. A malformed request is a bug in the client, and there is one client. Generated from a conversation that may contain anything the customer typed. The schema is the only thing standing between that and your handler.
Errors A status code and a body. The client decides what to do about it, once, in code that was reviewed. Something the model has to read and act on in the moment. A bare 403 teaches it to try the next tool; a sentence teaches it to stop.
Retries Deliberate, bounded, and configured by the client's author. Enthusiastic. A model that reads an error as transient will try again politely for as many turns as it has, and the only thing that stops it is the error saying not to.
An API is read once by a person and then called forever by a program. A tool is read on every single call by something that is reasoning about it afresh.

What follows from that

Four consequences run through the rest of this book, and it is worth meeting them now.

The description is not documentation

In an API, the description is a courtesy. In a tool, it is the decision procedure. When an agent picks the wrong tool, the cause is almost never that the model is incapable; it is that two descriptions did not distinguish themselves, or that one of them failed to say when not to use it. Chapter 6 spends its whole length on this one field, which is the right proportion.

The schema is a boundary, not a type signature

A model follows a closed object schema with narrow patterns very reliably. “Very reliably” is a probability, and the right standard for an order ticket is not a probability. So the schema exists to be enforced at the boundary, every call, before a handler sees an argument — and when it fails, the failure has to name the field, because the caller is going to try again and should try again correctly.

Failures are data

A tool that throws gives the runtime a stack trace and gives the model a wall of text it was never taught to read. A tool that returns ok: false with a code from a closed set gives the model something to branch on and gives the agent's author something to assert in a test. Every tool in this book returns the same envelope whether it succeeded or not; chapter 8 is about that envelope and the fifteen codes inside it.

Some things cannot be left to the model's judgment

The model is a participant in the conversation, and the conversation contains whatever the customer typed. So identity is never an argument. Approval is never a boolean the model sets. The authority to place an order is a single-use token that only a read-only pricing tool can mint. None of this is distrust of the model; it is the same reason a bank teller cannot approve their own withdrawal.

The one-sentence test. If a property of your tool is enforced only by the model choosing to respect it, it is not enforced. Write it down, then ask what in the runtime makes it true. If the answer is “the description asks nicely”, you have a convention, not a control.

What a tool is, then

A tool is a contract with four parts, three audiences and one promise.

Definition

A tool is a named, independently invocable capability, described well enough that a language model can decide when to use it, constrained well enough that the firm can let it, and governed well enough that somebody can be held responsible for it afterwards.

  • For the model: a name, a description and an input schema.
  • For the runtime: an output schema and four behavioral annotations.
  • For the firm: a governance block that never reaches the model at all.

That is the whole of chapter 4, and the next three hundred pages are what each part has to contain, why, and what goes wrong when it does not.

Chapter 2

The five components

Five things, one boundary, and a rule about which side each decision is made on.

Every tool system has the same five parts, whether or not anyone named them. Naming them is useful because the most expensive mistakes are all mistakes about which component owns a decision.

The model
Reads the catalog, decides which tool to call and with what arguments, reads what comes back, and decides again. It is on the untrusted side of the boundary, which is not a judgment about its competence — it is a statement about where its inputs come from.
The runtime
Everything that happens between the model emitting a call and a handler running: resolving the name, validating the arguments, establishing who the call is for, checking entitlements, applying the rate limit, consulting the approval gate, wrapping the result and writing the audit record. This is where the controls live, because it is the first component on the trusted side.
The registry
The one place that knows what tools exist, what each one promises, who may call it and what code is behind it. Without one, the catalog is whatever happened to be on the classpath, and four questions become unanswerable: what is the model being shown, who may call these, which have been reviewed, and what breaks if we turn one off.
The handler
The domain code behind one tool. In a well-built catalog it is startlingly short, because everything generic happens around it. If a handler is long, the tool is usually doing two things.
The system of record
The brokerage itself: the ledger, the order management system, the risk engine, the market data feed. It does not know a model exists and must not have to. Every rule it enforces for a human caller it enforces identically here.

Where the boundary runs

The trust boundary is between the model and the runtime, and it is worth saying plainly what that means, because it is routinely drawn in the wrong place.

It does not mean the model is adversarial. It means that everything the model emits is derived from a conversation, and a conversation contains text that arrived from outside the firm. A customer can type an account identifier that is not theirs. A document the customer pasted can contain a sentence addressed to the model. An email the agent was asked to summarize can say “ignore your previous instructions”. None of that is the model failing; it is the model doing its job on an input it has no way to vet.

So the rule is mechanical:

The boundary rule

A decision may be made on the model's side of the boundary only if a wrong answer is recoverable by the firm's own side. Everything else — identity, entitlement, approval, limits, idempotency — is decided by the runtime, from state the model cannot reach.

Applied to this book's catalog, that is a short and specific list.

DecisionDecided byWhy
which tool to callthe model A wrong choice is refused, costs a turn, and nothing happens.
which accountthe model It can only choose between accounts the customer holds; the handler checks.
how many sharesthe model The risk engine prices it, the customer sees the number, and a human agrees.
who the customer isthe runtime A customer identifier the model can set is an account anyone can read.
what scopes are heldthe runtime A scope the caller can name is not a scope.
whether a human agreedthe runtime A boolean the model sets is a boolean the model will eventually set.
the idempotency keythe runtime A model asked for a unique key will reuse one, or invent a new one on a retry.
how often it may callthe runtime The failure mode being guarded against is a loop, and a loop will not self-limit.

The anatomy of one invocation

Here is a single call, end to end, with the component responsible for each step. Chapter 21 implements it; this is the shape to keep in mind until then.

  1. The model emits a call. A name and a JSON object. Nothing more. It has no session, no identity and no way to set one.
  2. The runtime resolves the name against the registry's view for this principal. A tool this session cannot use is not merely refused; it was never published.
  3. The runtime validates the arguments against the descriptor's input schema. A failure names the field, because the model is about to try again.
  4. The runtime establishes the principal from the session — never from the arguments — and checks every entitlement the descriptor requires.
  5. The runtime applies the rate limit for this principal and this tool.
  6. The runtime consults the approval gate. For a tier 2 or 3 tool with no live grant, the call stops here and the customer is shown what they are being asked to agree to.
  7. The handler runs. It sees a descriptor, validated arguments and a principal. It does not see the conversation, which is why it cannot be talked into anything.
  8. The handler calls the system of record, which applies every rule it would apply to any other caller.
  9. The runtime validates the payload against the descriptor's own output schema and fails closed if it has drifted.
  10. The runtime wraps and records. One envelope, with provenance; one audit record, with field names and never values.

Steps 6 and 9 are the ones people leave out. Chapter 21 argues for both at length. The short version: an approval the model can grant is not an approval, and an output schema nobody enforces is a document the firm published and then stopped honoring.

Chapter 3

Conformance levels

Four levels, so that “is this tool ready?” has an answer shorter than a meeting.

A specification with no levels gets applied unevenly, because the first team to hit a deadline discovers that most of it is optional in practice. Levels fix that by making the exemption explicit: a tool is allowed to be L1, it is simply not allowed to be L1 and also place orders.

LevelMeansRequires
L0 Draft
Not published		 A name and something resembling a description. Fine for an experiment on a branch. An L0 tool may not be served to a model by the registry, which refuses to start with one in an active catalog.
L1 Structurally conformant
Read-only, internal		 All eight fields present. Name matches the grammar. Both schemas are closed objects inside the profile, with a description on every property. All four annotations stated. A governance block with an owner, an entitlement, an audit event and a retention. Passes the linter with no errors.
L2 Contract tested
Customer-facing reads		 Everything in L1, plus: the description follows the seven-part template; every identifier parameter carries the ontology's pattern; the handler has contract tests covering the claims the description makes; the result envelope is enforced; the tool appears in a named evaluation suite and its selection accuracy is recorded.
L3 Certified
Anything that changes state		 Everything in L2, plus: a risk tier agreed at review rather than asserted by the author; an approval mode with a confirmation template that shows the customer the priced consequence; a named kill switch; a refusal suite; a trajectory suite; dual sign-off on the descriptor; and re-certification each quarter against the live catalog.

The rule that makes levels bite

TS-GOV-08 · TS-ANN-04

An active tool must be at least L1. A tool at risk tier 2 or above must be L3 and must require approval. There is no path by which a tool that changes a customer's position reaches a model without a human having signed the descriptor and a human being asked at the moment it runs.

In this book's catalog that works out as ten tools at L2 and four at L3. The four are the preview, which is read-only but mints authority, and the three that change something.
