Chapter 30

The pyramid

Five layers, and the question to ask at each one: does this need a language model?

The reason to ask is cost. A test that calls a frontier model is slow, costs money, and is not quite deterministic. Put enough of those in a build and the suite gets marked @Disabled, at which point the tools drift unchecked and the expensive tests were worse than no tests.

So the discipline is to push every assertion as far down the pyramid as it will go, and to be precise about what genuinely cannot go lower.

 Layer Model?Asserts
1Conformanceno That every descriptor is structurally valid, inside the schema profile, consistent with the ontology, and that the catalog as a set has no gaps or dead ends.
2Handler contractsno That each tool does what its description claims — buying power net of reserved cash, positions largest first, a lot that knows its holding period.
3Trajectoriesno The safety properties: preview before place, a token bound to its terms, a retry that does not double-book, a cancellation that lost a race reporting a fill.
4Selectionyes That for a given utterance the model reaches for the right tool, with the right arguments, and not for three more.
5Refusalyes That it declines when declining is correct: advice, predictions, tax guidance, out of scope, out of entitlement, and attempts to talk past the controls.

Layer 3 is the one people put too high

“Does the agent preview before it places?” sounds like a question about the model, and it is not. In this catalog it is a question about whether brokerage_order_place can be called without a token, and that is answerable in a unit test with no model anywhere. 



  

    The general form: if a property is structural, test it structurally. A model-based test
    of a structural property tells you only that the model did not happen to find the hole this
    time.
  


  
And layers 4 and 5 genuinely do need one


  

    Nothing but a model can tell you whether
    “how much can I spend?” leads to the balances tool. That is a question about
    how two pieces of prose compare in a particular model's judgment, and it changes when you edit a
    description, when you add a neighboring tool, and when the model version moves.
  


  

    Chapter 33 is about how to get that measurement into every build anyway.
  


  
What the suite looks like in this repository


  

  

    A hundred and forty-nine tests in about fifteen seconds, including the agentic suite. The next
    four chapters are how.
  


  

    Two of those modules sit outside the pyramid and are worth naming, because leaving them out is
    a common omission. brokerage-domain is tested on its own rather than
    only through the handlers — the simulated market has to be repeatable and its day-over-day
    moves believable, and nothing else guards either property. And
    desktop-bridge is tested because a publication surface nobody
    exercises is a surface that fails on the one Monday somebody tries it.
  







  
Chapter 31

  
Conformance and contracts

  

    The gate that makes the specification a specification, and the tests that keep the descriptions
    honest.
  


  
The gate


  


  

    No model, no network, no application context, a few milliseconds, on every commit. That is the
    whole argument for writing descriptors as data and rules as code. Without it the specification
    decays into a style guide: the first ten tools follow it, the next forty follow whoever reviewed
    them, and by the time anyone notices, the model is being shown four different ways to name an
    account.
  


  

    The same test file asserts the properties of the catalog as a set, which is where the
    interesting failures are.
  


  


  

    Four assertions on every state-changing tool, in six lines, and none of them can be satisfied by
    a descriptor that merely looks right.
  


  
Contract tests assert the prose


  

    The pipeline has already validated every payload against its own output schema before a test
    sees it, so a handler contract test is not re-checking the shape. It is checking the
    claims the description makes, which no schema can express.
  


  


  

    The description says positions come back largest first and that the weight is already computed.
    Both are promises to the model, and both would otherwise be true only until somebody changed a
    comparator.
  


  

    Here is the same idea applied to a claim that is easy to get wrong and expensive to get wrong:
  


  


  
The pipeline, step by step


  

    Twenty-one tests, one per documented behavior, against a two-tool fixture rather than against
    the real catalog.
  


  


  

    The reasoning is worth copying. The brokerage catalog is a fine thing to test the pipeline
    through and a poor thing to test it with: when a pipeline test fails against
    fourteen real tools, the first question is whether the pipeline broke or a handler did, and two
    tools defined in the test file answer that before it is asked.

And the HTTP surface

Chapter 32

  
The agentic harness

  

    Scenarios as data, expectations over traces, and never over prose.
  


  
A scenario is a file, not a method


  


  

    Scenarios are data for the same reason descriptors are. A selection suite written as JUnit
    methods is a suite only a Java developer can extend, and the people who know what a customer
    will actually say are not Java developers. A scenario file can be written by the product owner
    who took the support call.
  


  
Five expectations, five different questions


  

    
FieldAsks

    
      
expectToolsDid it reach for the right tool? The headline number,
        and the least interesting on its own.

      
forbidToolsDid it reach for something it should not have? Usually
        the more interesting half, and the half nobody writes.

      
expectOrderDid it do things in the right sequence? Preview before
        place; list before cancel.

      
expectArgumentsDid it get the arguments right, not just the tool?
        The right tool with the wrong account is not a near miss.

      
expectRefusalDid it decline, when declining was the correct
        answer?

    
  


  

    And one field that changes the world rather than observing it:
  


  


  

    Off by default, because the default question an evaluation suite should ask about a trading tool
    is whether the agent stops. A scenario that reaches a tier 2 or 3 tool with this off
    gets APPROVAL_REQUIRED, and the correct trajectory ends there.
  


  
Expectations are about the trace


  

    Every assertion in the harness is about the ToolTrace or about a
    coarse property of the reply. Never about the reply's wording.
  


  


  

    This constraint is what makes an agent suite maintainable. Assert that a reply “mentions
    the buying power” and the test fails the day the model phrases it differently, which is a
    Tuesday. Assert that the agent called brokerage_balances_get with this
    account and did not call brokerage_order_place, and the test keeps
    meaning the same thing across model versions.
  


  
The one place prose is examined


  


  

    A coarse check for the shape of a refusal rather than for a phrase. It is the weakest
    assertion in the harness and the book should say so: a better refusal check, once a team has the
    appetite, is a second model asked a yes-or-no question about the reply. The structure here
    leaves room for that without requiring it.
  


  
Argument checks


  


  

    Only the named fields are examined, and a scenario passes if any call to that tool
    matched. Both choices are deliberate: pinning every field makes the suite brittle against a
    model that correctly supplies an optional parameter, and pinning the first call makes it brittle
    against a model that reasonably retried.
  


  

    The matcher compares containers as canonical JSON, which is what lets a scenario pin a batch:
  


  


  
A fresh world per scenario


  


  

    No container, no profiles, no component scan. That is a property of a good test harness rather
    than a shortcut: a suite that boots an application context tests the application context too,
    and when it fails you are debugging dependency injection instead of a descriptor. Twenty lines
    of constructor calls are also the clearest statement of what the system is made of that exists
    anywhere in the project.
  


  

    Each scenario gets its own instance, so one cannot leave an order in the book for the next to
    trip over. Evaluation suites that share state are the reason an agent suite passes on its own
    and fails in the full run.
  


  
Standing in for the human


  


  

    A named, visible method rather than a quiet default, because the two things it makes possible
    are both easy to get wrong. A trading scenario that never gets past the gate is not testing the
    place tool at all; and a suite that approves everything without saying so is not testing the
    gate. The trading suite turns it on explicitly and the refusal suite leaves it off, which is how
    both get covered.
  


  







  
Chapter 33

  
Cassettes

  

    Why the suite runs offline, what that still catches, and — precisely — what it does
    not.
  


  

    Every team building agents hits this about three weeks in. Evaluating tool selection means
    asking a frontier model what it would do, which means a network call, a bill, a minute of
    latency and a result that is not quite the same twice. Put that in CI and the suite is slow,
    expensive and flaky, so it gets disabled and the tools drift unchecked.
  


  
Record the model's half, replay it through the real system


  


  

    This is the paragraph to read twice. What the cassette holds is only the model's part:
    which tool it chose, with what arguments, in what order, and the prose it ended on. The tools
    themselves are not recorded.
  


  


  

    On replay the real pipeline runs, the real handlers run, the real schemas validate, the real
    entitlements are checked and the real approval gate fires. So a replayed scenario still fails
    when somebody:
  


  
    
    
  • narrows a pattern, so the recorded arguments stop validating;
    • 
    
  • renames an output field, so the payload stops matching its own schema;
    • 
    
  • raises a risk tier, so a scenario that used to reach a tool now stops at the gate;
    • 
    
  • drops an approval requirement, so the refusal suite notices;
    • 
    
  • breaks a handler, in any of the ordinary ways;
    • 
    
  • removes a tool, so the call becomes UNKNOWN_TOOL.
    • 
  


  
What it cannot catch


  

    A change to a description. The model's reading of the
    description is what was recorded, so editing one and replaying tells you nothing about whether
    the edit helped. That is not a limitation to work around; it is the exact boundary of what a
    recording means, and the suite has a live mode for precisely this reason.
  


  

    The practical rule: wire the live suite to descriptor changes in CI. Edit a description and the
    cassettes for that tool are stale by definition, so that pull request runs against the model and
    the others do not.
  


  
Recorded or authored


  

    A cassette says where it came from, and the distinction is published rather than implied.
  


  


  

    The cassettes committed in this repository are AUTHORED: they are the
    trajectories the catalog's authors intend, written by hand. They exercise the whole runtime and
    they are not evidence about what Claude chose. Saying so in the file, and surfacing it
    in the suite, is the difference between an honest harness and one that quietly claims evidence
    it does not have.
  


  


  

    Run ./harness.sh --record with a key and they are replaced with real
    recordings.
  


  
The one thing replay cannot be byte for byte


  

    A recorded confirmation token is a dead token: single use, long expired, bound to a session that
    no longer exists. So the recorder rewrites it to a placeholder, and the replay substitutes the
    live token issued by the preview that ran a moment earlier.
  


  


  


  

    That substitution is the only place replay is not exact, and it is the place it has to be. Note
    what it does not do: it does not bypass the token check. The live token still has to
    be minted by a real preview, bound to the real ticket, and spent once — so a scenario
    whose recorded place call does not match its recorded preview still fails.
  


  
Three modes, one scenario file


  


  

    The two modes are not two test suites. They run the same scenario, against the same registry,
    through the same pipeline, and check the same expectations. The only difference is where the
    model's choices come from: the network, or a file recorded from the network. That is what makes
    the offline suite worth trusting — it is not a mock of the system, it is the system with a
    recording of the model's half of the conversation.
  







  
Chapter 34

  
Four scores and a pipeline

  

    What to measure, what to gate on, and what to do when a number drops.
  


  
Four numbers, not one


  


  

    They fail independently, and a single pass rate hides which one moved. The most common mistake
    is to report selection accuracy alone, which is the easy half: an agent can score a hundred
    percent on selection and still be unshippable because it answers questions it has no business
    answering.
  


  
A run


  


  

    Thirty scenarios in under a second, no key, no network. The per-scenario line shows the path the
    agent took, which is usually enough to see what went wrong without opening the report.
  


  
Reading a failure


  

    A failure names the kind, not just the fact, and every kind suggests a different fix.
  


  

    
KindUsually means

    
      
tool-not-called
        Two descriptions did not distinguish themselves, or the expected tool's
          “when to use” does not use the customer's words.

      
forbidden-tool
        A missing negative. The forbidden tool's description does not say when not to use it.

      
out-of-order
        A prerequisite the producer graph does not express, or a description that states a
          sequence the schema does not enforce.

      
wrong-arguments
        An unconstrained parameter, a missing default, or a property description that does not
          say what the units are.

      
not-refused
        The conduct prompt, not a tool. Either it does not cover the case or it is being
          outweighed by a tool that looks like it would help.

      
too-many-calls
        A singular tool where a batch belongs, or a default that returns too little and forces
          a second call.

    
  


  
Publishing the scores back into the catalog


  

    Each tool's governance block carries its suite and its last scores, which is what turns the
    number into an assertion somebody can check rather than a number somebody typed.
  


  


  

    And the linter requires it on anything at tier 2 or above:
  


  


  
What to gate on


  

    A suggestion, from a system that has to keep shipping.
  


  

    
GateRunsBlocks on

    
      
Conformanceevery commit
        Any error. No exceptions, because the registry will not start anyway.

      
Contracts and trajectoriesevery commit
        Any failure.

      
Replayed suitesevery commit
        Any failure. They are free.

      
Live suitesdescriptor changes, and nightly
        Refusal accuracy below 100 percent. Selection accuracy below the recorded baseline by
          more than a scenario. Nothing else — a single flaky scenario should not stop a
          release, and a trend should.

      
Re-certificationquarterly, per L3 tool
        A human reading the descriptor against the live catalog.

    
  


  

    Refusal accuracy is the one to gate hardest on. A selection regression
    costs a turn and an apology. A refusal regression means the agent gave investment advice, or
    acted without approval, and those are not recoverable by trying again.
  


  
When a number drops after a model upgrade


  

    It will, eventually, and in both directions. The sequence that works:
  


  
    
    
  1. Re-record, do not re-write. Run the live suite against the new model and look at the
      traces before touching a description. Half the time the new behavior is better and the
      scenario's expectation was over-specified.
    2. 
    
  2. Separate selection from arguments. A drop in argument accuracy with selection
      unchanged is almost always a schema that was under-constrained and that the old model guessed
      right about.
    3. 
    
  3. Check the forbidden lists. A more capable model is often a more eager one,
      and the first thing to move is usually over-calling rather than wrong-calling.
    4. 
    
  4. Only then edit prose, one description at a time, re-running the single scenario. A
      description edited to fix one scenario frequently breaks a neighbor, which is what the rest
      of the suite is for.
    5.
