Part II

The descriptor

Eight fields. Four of them decide what the model does, one is a promise to the caller, and three never reach the model at all. This part is what each one has to contain and what goes wrong when it does not.

Chapter 4

The eight fields

And only eight. Anything else is an implementation detail of whoever happens to be serving it.

A descriptor is a JSON document. That is a design decision rather than a format preference, and it is worth defending before we look at the fields, because the alternative — assembling the descriptor in code, from annotations — is what most teams reach for first.

Why the descriptor is data

There is no @Tool annotation anywhere in this book's repository. Each tool is a file. The consequences are concrete:

  • A reviewer who does not write Java can read it, and a change to a description shows up in a pull request as a diff of prose.
  • A linter can check it, which is how 58 rules become a build step rather than a style guide.
  • A desktop client can be handed it without the application running.
  • You can answer “what exactly is the model being shown right now?” by reading a file, instead of starting a service and inspecting a builder.
  • Publishing to a second runtime is an adapter of about forty lines that renames nothing.

The annotated approach is faster for the first three tools and does not scale past a dozen, because the thing that needs review is prose, and prose inside a Java string literal is prose nobody reviews.

The eight fields, by audience

name
model

The identity the model emits. Permanent. Lowercase, underscores, three segments.

title
model & humans

A short label for an approval dialog or an audit screen. Not a second description.

description
model

The decision procedure. Seven parts. The field the model's choice actually turns on.

inputSchema
model

A closed object inside the profile. Every property described, every string constrained.

outputSchema
caller

A promise about the payload, enforced on the way out so it cannot quietly become false.

annotations
runtime

Four booleans, all stated explicitly, that tell the runtime how much to trust the call.

icons
interfaces

Decorative only. No control anywhere may depend on an icon being present.

_meta
the firm

Governance, under a reverse-DNS key. Never rendered into the model's context.

What the model actually receives


  

    This is worth internalizing early, because it changes how you write every other field. When the
    catalog is published, the model's context contains, for each tool, three strings: the name, the
    description and the serialized input schema. That is all.
  


  

    It does not contain the output schema. It does not contain the annotations, the risk tier, the
    owner, the entitlements or the retention period. A model cannot read
    destructiveHint: true and be careful, because it never sees it. If
    you want the model to know that a tool cannot be undone, the description has to say so in
    words.
  


  

    
The context rule

    

      Anything the model must know in order to behave correctly belongs in the description.
      Anything the runtime must know in order to behave correctly belongs in the
      annotations or the governance block. Writing a fact in the wrong one of those
      places is the same as not writing it.
    

  


  
What it costs


  

    The catalog in this book is fourteen tools. Published to a trading session, the names,
    descriptions and schemas come to about 26,000 characters — on the order of sixty-six
    hundred tokens — and the generated briefing adds roughly fifteen hundred more. That is a real cost on every single turn, and it is the reason
    chapter 6 gives the description a budget and chapter 7 gives the schema one.
  

  

    It is also the reason the catalog is filtered by entitlement before it is published rather than
    after. A research session sees three tools and pays for three; a read-only desktop session
    sees ten and pays about fifteen thousand characters.
  







  
Chapter 5

  
Names

  

    A name is the one field you can never change, so it is worth the twenty minutes.
  


  
The grammar


  

    
TS-NAM-01 · TS-NAM-02

    

      ^[a-z][a-z0-9_]{2,63}$, with the shape
      <domain>_<entity>_<operation>.
    

    

      Lowercase and underscores because that is the intersection of what every tool-calling runtime
      accepts. Three segments because two leave the model guessing which catalog a tool belongs to
      when a firm has six of them.
    

  


  

    The character set is not an aesthetic choice. Runtimes differ on hyphens, on dots, on
    camelCase, on length and on leading digits, and the differences are discovered at the worst
    possible time: when you publish an existing catalog somewhere new and a third of it is rejected
    or, worse, silently renamed. The intersection is small and boring and it travels.
  


  
Dots never cross the wire


  

    A catalog wants a hierarchy — brokerage.orders.place reads
    better than brokerage_orders_place and sorts into a tree. So the
    descriptor carries both, and they are derived from each other rather than maintained separately.
  


  


  

    The dotted form appears in the console, in dashboards and in configuration. The underscore form
    is what the model emits. Because one is computed from the other, they cannot disagree.
  


  
The name is derived, not chosen


  

    This is the part that surprises people, and it is the single highest-leverage idea in Part III.
    In this catalog nobody picks a tool name. The ontology declares one capability row per
    tool, and the name falls out of it:
  


  


  

    The entity supplies the term, the operation supplies the verb, and the capability's cardinality
    decides between the singular and the plural form. So
    brokerage_order_cancel could not have been called
    cancelOrder, or brokerage_cancel_order, or
    brokerage_orders_cancel. A linter rule compares the two and fails the
    build if a descriptor has drifted.

    Seven verbs, and a tool may use no others.

          have, which is what makes it a safe first move.

    A closed vocabulary pays for itself twice. First, the model generalizes: having learned what
    list means on one tool, it is right about it on the other four.
    Second — and this is the part that matters at review time — the annotations and the
    risk tier can be checked against the name instead of trusted from the descriptor,
    which is the one place a tool author's optimism is most expensive.
  


  
Titles


  

    Three to sixty characters, no trailing period, and unique across the catalog. The title is what
    a human sees in an approval dialog and in an audit screen, which is the whole of its job.
  


  

    The rule that caught this book's own test fixture.
    Two tools may not share a title. A person approving one of two things both called
    “a fixture tool” cannot tell which they are approving. The first thing the
    linter found when the pipeline's test fixtures were written was exactly that, in this
    book's own repository.
  


  
Names are permanent


  

    Renaming a tool is a breaking change of an unusual kind: it breaks a model, and nothing
    compiles differently. Every recorded evaluation references the old name. Every audit record for
    the last six years references the old name. Any prompt a customer saved references the old
    name. Chapter 36 covers the deprecation path, which is to publish both for a window and retire
    one — but the cheaper answer is to spend twenty minutes on the ontology first.
  







  
Chapter 6

  
The description is the contract

  

    This is the field. Everything else in the descriptor constrains what happens after the model
    has chosen; this is the only field that affects whether it chooses correctly.
  


  

    When an agent does the wrong thing, there are three candidate causes and they are not equally
    likely. It is rarely that the model is incapable. It is sometimes that the toolset is missing a
    tool. It is usually that two descriptions did not distinguish themselves, or that one of them
    never said when not to use it.
  


  
The seven parts


  

    A description is plain prose — no markdown, no bullet lists, no headings — and it
    covers seven things in roughly this order.
  


  

    
 PartWhat it has to do

    
      
1What it does
        One sentence, naming the fields it returns. Specific enough that the model knows what
          it will get back without calling it.

      
2When to use it
        The situations in the customer's words, not yours. “Use when the customer asks
          what they can spend”, not “retrieves account balance information”.

      
3When not to use it
        And what to use instead, by name. This is the half nobody writes and the half that
          does the work.

      
4What has to happen first
        Which identifiers it needs and where they come from. Redundant with the ontology, and
          worth repeating because the model reads this and not the ontology.

      
5What it changes
        For a read tool, one sentence saying it changes nothing. For anything else, what the
          change is and whether it can be undone.

      
6How to read the result
        Which field to look at first, and what a particular value means. This is where you
          spend the model's attention well.

      
7Limits and caveats
        Staleness, estimates, pagination, anything that makes the answer less than it looks.

    
  


  
A description, annotated


  

    Here is the description of brokerage_quotes_get, which is a tool with
    nothing clever about it, broken into its seven parts.
  


  

    
1 — what it does.
      “Returns the current two-sided market for each symbol given: last price, bid, ask,
      size, change on the day, volume, the spread in basis points, and the session the venue is
      in.”

    
2 — when to use it.
      “Use when the customer asks what something is trading at, asks to compare
      instruments, or before explaining what an order would cost. Pass every symbol in one call
      rather than calling once per symbol.”

    
3 — when not to.
      “Do not use to look up a company by name — that is
      brokerage_instruments_search — and do not use it for past prices, which is
      brokerage_price_history_get.”

    
6 — how to read it.
      “Read asOf before quoting a number to the customer: a quote is perishable and one
      taken minutes ago is not the market now. Read session too, and say so when it is not regular.
      Read spreadBasisPoints before recommending a market order; above about 25 basis points the
      fill can be well away from the last price and a limit order is the better advice.”

    
5 and 7 — effect and caveats.
      “This changes nothing and may be called freely.”

  


  

    Four hundred and sixty words of schema and about a hundred and thirty words of prose, and the
    prose is what makes the model batch the call, warn about a wide spread, and not reach for this
    tool when the customer said “Apple”.
  


  
The budget


  

    
TS-DSC-01 · TS-DSC-02

    

      At least 120 characters, at most 2000. Below the floor a description cannot
      have said when not to use the tool. Above the ceiling it crowds out the conversation and the
      model starts skimming — and a skimmed description is worse than a short one, because
      the part it skips is unpredictable.
    

  


  

    The fourteen descriptions in this catalog run from 650 to 1,500 characters. The longest is the
    preview tool, which earns it: it is the only tool whose misuse cannot be undone and the only
    one that mints authority.
  


  
Writing for a model, not about a tool


  

    Five habits, each of which measurably changes behavior.
  


  
Use the customer's words

  

    The model is matching against an utterance. “Use when the customer asks what they can
    spend” matches “how much can I spend?”. “Retrieves account balance
    information” matches nothing a customer has ever said.
  


  
Name the alternative

  

    “Do not use this for X” leaves the model with a prohibition and no plan. “Do
    not use this for X; that is brokerage_other_tool” moves it
    somewhere. The linter checks that every tool named in a description exists in the catalog,
    because a dangling redirection is worse than none — the model will try it.
  


  
Say which field to read first

  

    A payload with twelve fields has an order of importance that the JSON does not express. The
    preview tool's description says “Read canPlace first: false means the order would be
    refused.” That one sentence is the difference between an agent that relays a blocker
    and an agent that reports a cost for an order that cannot be placed.
  


  
Give the stop condition

  

    Models are helpful, and helpfulness under a refusal looks like trying something else. So the
    descriptions say so explicitly: “tell the customer rather than retrying”,
    “do not try another account on their behalf”, “never preview again
    simply to obtain a fresh token for an order the customer has not re-approved”.
  


  
Write the consequence, not the mechanism

  

    Compare “this operation is not idempotent” with “the effect is immediate and
    cannot be undone: a filled order can only be reversed by trading in the opposite direction, at
    whatever the market then is, and the customer bears that difference”. The second is
    longer and it is the one that changes behavior.
  


  
What the linter can check


  

    Prose quality is a review matter, but four things about it are mechanical, and mechanical
    things belong in the build.
  


  


  

    Length, the presence of a “when to use” and a “when not to”, markdown,
    the first person, cross-references that resolve, and — for anything that changes state
    — whether the description says so. None of that is a substitute for someone reading it.
    All of it is a substitute for someone having to read it before they can get to the
    interesting question.
  


  

    A reviewer should be arguing about whether the description tells the truth. Everything
    mechanical belongs in the linter.
  







  
Chapter 7

  
Schemas and the profile

  

    JSON Schema is much larger than any tool-calling runtime supports, and the parts supported
    unevenly are exactly the parts that fail silently.
  


  

    The failure mode is specific and worth seeing before the rules. You write a schema with
    oneOf, describing two legitimate shapes of request. A runtime on the
    way to the model drops the keyword, because its own schema translation does not support it. The
    model is now shown a schema in which both branches' fields are simply optional. It produces an
    object matching neither, cheerfully, and the runtime that dropped the keyword has no way to say
    so. Your handler receives it, and whatever it does next, nobody was warned.
  


  
The profile is a whitelist


  


  

    The rule behind it: a keyword is permitted when it either constrains a scalar in a way every
    runtime forwards, or describes structure. Keywords that express alternation, negation or
    conditionals are not, because they are the ones that get dropped.
  


  

    Prohibited keywords are rejected rather than ignored, and each rejection carries the reason the
    author needs to hear:
  


  


  
Six rules that do most of the work


  

    
Close every object

    

      additionalProperties: false, everywhere, without exception. An open
      object means the model's invented extra field is silently accepted and silently ignored
      — and the model has no way to learn that the field did nothing. Closing it turns an
      invisible misunderstanding into an error that names the field.
    


    
Describe every property

    

      The field name is not the contract. quantity could be shares or
      dollars; price could be a limit or a last trade;
      since could be a date or a cursor. Where the name is ambiguous the
      model will pick the common reading, and the common reading is wrong about a third of the time
      in a brokerage.
    


    
Constrain every string

    

      An unconstrained string accepts anything the model invents. Every string in this catalog
      carries an enum, a pattern, a
      format, or at minimum a maxLength. A
      pattern is best, because it is also what stops a malformed identifier reaching the handler.
    


    
Money is a decimal string

    

      Never a JSON number. IEEE-754 binary doubles cannot represent 0.1, so a thousand shares at
      $10.10 totals $10099.999999999998, and the model will read that back to a customer. The
      linter warns on any number in an input schema for exactly this
      reason. The pattern this book uses is
      ^-?[0-9]{1,15}(\.[0-9]{1,6})?$.
    


    
Bound every array in an output

    

      maxItems, always. An unbounded array in a result is an unbounded
      token bill, and it is discovered by a long-standing customer whose four years of fills arrive
      in one payload on the first turn of a conversation.
    


    
Twelve parameters is the practical ceiling

    

      Past about a dozen, a model starts omitting the ones it is least certain about, and the ones
      it is least certain about are usually the ones you added last because they were subtle. A
      tool with eighteen parameters is almost always two tools.
    

  


  
Reserved parameter names


  

    Some names a tool may never use, because the runtime has claimed them and a tool that accepts
    one has created a way around a check somebody wrote on purpose.
  


  


  

    Note where the line is drawn. accountId is not reserved,
    because choosing between the accounts a customer holds is exactly what the model is for.
    customerId is reserved, because a customer identifier the model can
    set is an account anyone can read. The distinction is between scope within an established
    identity and the identity itself.
  


  

    The ones that look harmless.
    dryRun, force,
    skipValidation, override. Each is a flag
    that turns a control off, settable by the party the control exists to constrain. If a tool
    genuinely needs both behaviors, that is two tools with two risk tiers and two descriptions
    — which is precisely what preview and
    place are.
  


  
Validation is not optional


  

    Every invocation is validated against the input schema before a handler sees an argument, and
    every payload is validated against the output schema before it is returned. The second surprises
    people, so chapter 21 defends it properly. The short version is that the output schema is the
    only description of the payload the model will ever see, and a handler that drifts from it is
    misleading the model with a document the firm published.
  


  


  

    When validation fails, the violations are rendered for the model, pointer first, and capped at
    five — because a model handed twenty violations fixes the first three and re-sends.
  


  







  
Chapter 8

  
The envelope and the errors

  

    Every tool returns the same shape whether it worked or not, and a failure is something the
    model reads rather than something it survives.
  


  
One envelope


  


  

    Four fields. ok is the discriminator the model branches on.
    data is the payload, and it is the thing the descriptor's
    outputSchema describes. error is present
    exactly when ok is false. And meta is
    never optional.
  


  

    The envelope is specified once, here, rather than repeated inside fourteen output schemas. That
    is a deliberate trade: the model learns the shape once and carries it across the whole catalog,
    and the schemas stay about the domain. It does mean the envelope has to be described to the
    model somewhere, which is one short paragraph of the generated briefing in chapter 26.
  


  
Why meta is mandatory


  

    Three of its fields answer questions that come up constantly and that a handler, left to its
    own judgment, will sometimes omit.
  


  


  
    
    
  • asOf is the instant the data describes, not the instant
      the envelope was written. The moment a quote is involved this is the difference between a
      number and a misquote.
    • 
    
  • complete says whether the model is looking at everything
      or at a page. An agent that summarizes page one as though it were the whole is a specific and
      very common failure, and this field is what prevents it.
    • 
    
  • requestId is the only thing a customer can quote back to
      support. Every error's remediation tells the agent to give it to them.
    • 
  


  
Failures are data


  

    A handler says no by throwing a ToolFailure, which the pipeline turns
    straight into an ok: false envelope. An exception is the handler's
    convenience — a guard clause reads better than threading a result type through five calls
    — and the model never sees an exception, a class name or a stack trace.
  


  


  

    Nothing else may escape a handler. An unexpected exception is caught by the pipeline, logged
    with the request identifier, and returned as INTERNAL_ERROR with no
    detail — because the alternative is leaking a database constraint name into a customer
    conversation. There is a test for exactly that.
  


  


  
The taxonomy is closed


  

    Fifteen codes, and a tool may return no others. A closed taxonomy exists so that the agent can
    be taught once what to do about each code instead of inferring it from prose every time.
  


  

    Each code carries three things: whether an identical retry could plausibly succeed, whether the
    caller has anything to change, and the sentence the generated briefing shows the model. Keeping
    the sentence next to the flags it has to agree with is the difference between a prompt that
    matches the taxonomy and a prompt that used to.
  


  


  

    The two flags combine into four behaviors, and every code is one of them.
  


  

    
retryablecallerCanFix
      The agent shouldCodes

    
      
noyesFix the call and try the same tool again
        INVALID_ARGUMENT, UNKNOWN_TOOL, NOT_FOUND, APPROVAL_REQUIRED,
          CONFIRMATION_EXPIRED, CONFLICT, AMBIGUOUS_REQUEST

      
yesnoWait if told how long, then report and stop
        RATE_LIMITED, UPSTREAM_UNAVAILABLE, UPSTREAM_TIMEOUT, INTERNAL_ERROR

        NOT_ENTITLED, PRECONDITION_FAILED, QUOTA_EXCEEDED, UNSUPPORTED

        There is no fourth combination: a code that is both retryable and the caller's to fix would
        be telling the agent two different things at once, which is how retry loops start.

    
  


  
Three fields that make an error actionable


  
remediation, in the imperative

  

    Not “the account was not found” but “call
    brokerage_accounts_list to get the accounts this customer actually
    holds, and use an accountId from that result”. The imperative
    is the form an agent follows most reliably, and naming the next tool is what turns a dead end
    into a step.
  


  
  


  
retryAfterSeconds

  

    Only on RATE_LIMITED, and always when it appears. “Too many
    requests” tells an agent to wait and gives it no way to decide how long, which in practice
    means it waits for zero seconds.
  


  
candidates

  

    Only on AMBIGUOUS_REQUEST. The whole point of that code is that the
    tool refuses to choose, and a refusal without the choices attached makes the agent guess from
    memory. In this catalog ambiguity is usually surfaced as a successful search returning
    several candidates rather than as an error — which is a better design where it is
    available, because an error is a thing to recover from and a list is a thing to ask about.
  


  
One mistake worth naming


  

    Do not map upstream status codes straight through. A 404 from the
    position service and a 404 from the market data service mean different things to an agent: one
    means the customer does not hold it, the other means the ticker does not exist, and the right
    next move differs. Map deliberately, at the handler, where you know which upstream it was.
    Appendix B has the mapping table this catalog uses.
  







  
Chapter 9

  
Annotations, tiers and approval

  

    Four booleans the runtime trusts, four tiers it does not take on faith, and the difference
    between the two.
  


  
The four annotations


  


  

    
AnnotationTrue when

    
      
readOnlyHint
        The tool changes nothing anywhere. Not “nothing the customer can see” —
          nothing.

      
destructiveHint
        A change may be irreversible or may overwrite existing state. A placed order is
          destructive; a cancellation is not, because it removes exposure rather than creating it.

      
idempotentHint
        Repeating the identical call has no additional effect. Read tools get this for free.
          A write tool earns it, usually with a key.

      
openWorldHint
        The tool reaches outside the firm's controlled domain — a market data feed, a
          venue. It is the field that says “the answer can change without anyone here doing
          anything”.

    
  


  

    
TS-ANN-01

    

      All four are stated explicitly on every descriptor, even where the value is the
      specification's default. “Absent” and “false” are read differently by
      different runtimes, and a trading tool cannot afford that ambiguity.
    

  


  

    Two combinations are contradictions and the linter rejects them: a tool cannot be both read-only
    and destructive, and a read-only tool is idempotent by construction.
  


  
Why the annotations are not enough


  

    The annotations are asserted by the tool's author. They are useful — the runtime uses
    them to decide what to log and what to show — and they are exactly the wrong thing to
    hang a control on, because the author is also the person most likely to be optimistic about
    their own tool.
  


  

    So the control hangs on the risk tier, which is agreed at review and, in this catalog,
    derived from the ontology rather than written by hand.

    The tier-1 line is the one that gets argued about, so here is the case.
    brokerage_order_preview is read-only: it changes nothing a customer
    can observe, and its description truthfully tells the model to call it as often as it likes
    while the customer adjusts an order. It is nevertheless not tier 0, because it reaches the risk
    and margin engines and because it mints a ConfirmationToken, and
    minting authority is not nothing.
  


  
The cancel asymmetry


  

    brokerage_order_cancel is tier 2 where the other two writes are tier
    3, and it is the one asymmetry in the catalog worth defending out loud.
  


  

    Cancelling reduces exposure. Requiring a priced preview before a customer can stop an order
    would mean that in the one situation where speed matters — a price running away from them
    — the system is at its slowest. So cancel needs no confirmation token. It still requires
    the customer's explicit approval at the moment it runs; what it does not need is a round trip
    through the risk engine to find out what stopping something would cost.

ModeMeans

        are safe but surprising.

        it runs. Everything at tier 2 and 3 in this catalog.

        value above 250,000, an account under review, or any restricted-classification tool.

        honest answer when a capability is too consequential to automate but too useful to
        omit.

    
  


  
What a confirmation has to show


  

    This is where the design most often goes quietly wrong, so it gets its own rule and its own
    worked failure.
  


  

    
TS-ANN-05

    

      An approval mode above notify requires a
      confirmationTemplate, and the rendered template must state the
      priced consequence — not the tool name, not the arguments, the consequence.
      A dialog that says “allow this tool?” is not informed consent.
    

  


  

    The template for brokerage_order_place wants to say
    “Estimated cost 10,978.20 USD” and “in Everyday brokerage”.
    Neither is an argument. The arguments are an account identifier, a ticker, a side and a
    quantity; the cost does not exist until something prices it, and the nickname lives in the
    account record. Render the template from the arguments alone and the customer sees this:
  


  

  

    A customer will approve that, because the part they recognize is correct. They will have
    approved an order whose cost they never saw. The fix is an ApprovalContext:
    the runtime asks the domain for the figures the arguments do not carry, at the moment of the
    confirmation.
  


  


  

    With it, the same call produces the dialog the customer should see — and the figures are
    computed now, not carried forward from a preview that may be a minute old.
  


  


  

    Chapter 22 implements the gate behind it, and chapter 17 explains why the token and the approval
    are two separate mechanisms rather than one.
  







  
Chapter 10

  
Governance metadata

  

    The part of the descriptor the model never sees, and the part somebody will be reading in an
    incident review two years from now.
  


  

    Governance lives in _meta, under a reverse-DNS key, so that it
    travels with the descriptor and is never rendered into the model's context. Every field in it
    answers a question that gets asked eventually.
  


  


  
Field by field


  

    
version

    

      Semantic, and it versions the contract rather than the implementation. A handler fix
      is a patch. A new optional parameter is a minor. Narrowing a pattern, renaming an output
      field or removing an enum value is a major — see chapter 36, because the list of what
      breaks a model is not the list that breaks a compiler.
    


    
lifecycle

    

      draft, active,
      deprecated, retired. The registry serves
      only active, however complete a draft looks.
    


    
conformanceLevel & riskTier

    

      Asserted by the owner, verified at review. In this catalog the tier is checked against the
      ontology on every build, so an author cannot quietly demote a tool to avoid an approval
      requirement.
    


    
owner

    

      A team, a mailbox and a paging escalation. All three, because at two in the morning a mailbox
      is not a person. An unowned tool in production is an incident waiting for a volunteer.
    


    
dataClassification & piiFields

    

      The highest classification the tool can return, and JSON pointers to any personal data in the
      output. Pointers rather than a boolean, because masking and retention are mechanical and need
      to know where to look. The linter rejects
      containsPii: true with an empty pointer list.
    


    
entitlements

    

      Scopes the principal must hold, all of them. This is the field the registry filters on, so a
      tool with no entitlement is a tool anybody can call — which the linter treats as an
      error rather than a default.
    


    
approval

    

      The mode, the confirmation template, and an expiry. An approval with no window is a standing
      instruction, and nobody means to give one of those.
    


    
recordKeeping

    

      An audit event name, an ISO 8601 retention, and the obligations driving it. In this catalog
      the trading tools are P6Y against books-and-records and order audit
      trail; the tax lot tool is P7Y; market data is
      P2Y and is driven by licensing rather than by regulation.
    


    
cost & rateLimit

    

      A cost class, a p95 latency and a per-principal budget. The limits that matter differ by two
      orders of magnitude — 180 quote calls a minute is normal, 180 order placements a minute
      is an incident — which is why the limit is per tool and not per catalog.
    


    
dependencies & availability

    

      What it calls, its SLO, and a named kill switch. Every tool at tier 2 or above must name one,
      because when a tool starts behaving badly the options are to turn it off or to roll back, and
      only one of those takes less than a build.
    


    
evaluation

    

      The suite that measures whether the model picks this tool correctly, when it last ran, and
      what it scored. A tier 2 or 3 tool that cites no suite does not pass the linter. This is what
      makes the number an assertion somebody can check rather than a number somebody typed.
    

  


  
A governance block, in full


  


  
The JSON spellings are pinned


  

    One detail that looks fussy and is not. The enumerations in the governance block declare their
    wire spellings explicitly rather than deriving them from the Java constant names.
  


  


  

    These strings appear in published descriptors and in audit records with six-year retentions.
    Renaming a Java constant must never silently change a wire value, and the only way to guarantee
    that is to write the wire value down.
  


  

    The same argument applies to one enumeration in the domain.
    CANCELLED keeps its double-L spelling throughout this book, in a text
    that is otherwise US English, because it is the spelling in the systems of record the domain
    borrows from. An enumeration member is a name rather than prose, and renaming it to match the
    surrounding prose would break every consumer already matching on the string.
