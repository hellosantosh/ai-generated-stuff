Chapter 15

The first tool, end to end

From a capability row to a passing test, with every decision shown. If you read one chapter of this book before writing a tool, read this one.

We are building brokerage_accounts_list: the tool that answers “what accounts do I have?”. It is the right first tool for a reason that is not obvious — it is the only tool in the catalog that consumes nothing, which makes it the only possible starting point for every conversation that touches a customer's money.

Step 1: the capability row

Before anything else, a row in the ontology. This is the design, and everything after it is implementation. 



  

    Four decisions are made in those six lines, and the build will hold us to all of them.
  


  

    
DecisionConsequence

    
      
operation: list
        Read-only and idempotent, by the ontology's own declaration. The annotations are now
          determined, not chosen.

      
entity: Account
        Classification floor customer-confidential, entitlement floor
          brokerage:accounts:read.

      
cardinality: many
        The plural term, so the name is accounts and not
          account.

      
consumes: []
        No prerequisites. This tool appears in the generated briefing as a starting point and
          in the producer graph in column zero.

    
  


  

    The name follows: brokerage +
    accounts + list. The risk tier follows from
    the operation: T0. The approval mode follows from the tier:
    none. None of those three is a judgment call now.
  


  
Step 2: the description


  

    Write this before the schema. It is the field the model's choice turns on, and writing it first
    tends to expose that the tool is doing two things.
  


  

    

      What it does. Returns every brokerage account the signed-in customer holds, with its
      identifier, nickname, type, currency and whether it can currently trade.
    

    

      When to use it. Use when the customer mentions an account by nickname, refers to
      “my account” without saying which, or when any other brokerage tool needs an
      accountId and none is in hand yet — this is the only tool that needs nothing to run, so
      it is the safe first call.
    

    

      When not to. Do not use to find out how much money is in an account; that is
      brokerage_balances_get.
    

    

      How to read it. Read the type field before advising on anything: a CASH account
      cannot borrow, an IRA_TRADITIONAL or ROTH_IRA account cannot sell short, and any account whose
      tradeable field is false cannot place orders at all. Read restriction when tradeable is false
      and tell the customer the reason rather than retrying.
    

    

      And the useful behavior. When the customer has more than one account and has not
      said which, ask; nickname and type together are usually enough for them to choose. This
      changes nothing and may be called freely.
    

  


  

    982 characters. Notice how much of it is about the result rather than the call. That is
    the right proportion for a read tool: the call is trivial and the interpretation is where an
    agent goes wrong.
  


  
Step 3: the output schema


  

    Also before the input schema, because what you return decides what the description had to say.
  


  


  

    Three decisions worth naming.
  


  
tradeable is computed, not inferred

  

    The restriction field already tells a model that
    FROZEN means no trading. The tradeable
    boolean says it again, as a certainty rather than an inference. The general rule: where a
    conclusion matters and is cheap to compute, compute it. A model is perfectly capable of
    working it out, and “perfectly capable” is a per-call probability.
  


  
The enum includes null

  

    "enum": ["UNSETTLED_FUNDS", "DAY_TRADE_RESTRICTED", "FROZEN", null]
    with "type": ["string", "null"]. Null is a legitimate value —
    it means healthy — and leaving it out of the enum would make every healthy account fail
    the output validation the pipeline performs.
  


  
maxItems: 50

  

    Nobody has fifty brokerage accounts. The bound is there because an unbounded array in a result
    is an unbounded token bill, and the one customer who has forty is a customer this tool should
    still work for.
  


  
Step 4: the input schema


  


  

    One optional boolean. The interesting part is what is not here: there is no
    customerId. The customer is established by the runtime from the
    session, and the linter rejects the parameter by name. This is the single most important line
    of the chapter and it is a line that does not exist.
  


  
Step 5: the governance block


  


  

    Every field here was decided in step 1 or is a fact about who maintains the tool. The tier, the
    approval mode and the entitlement all come from the ontology and are checked against it.
  


  
Step 6: the handler


  

    And now the code, which is nineteen lines.
  


  


  

    Read what it does not do. It does not validate arguments — the pipeline did. It does not
    check entitlements — the pipeline did. It does not catch exceptions, wrap a result, write
    an audit record or format an error. It takes the customer from the principal, maps four fields,
    and stops.
  


  

    The handler-length heuristic. If a handler is long, it is usually
    because the tool is doing two things, and the fix is two tools. The second most common reason
    is that it is re-validating arguments the pipeline already validated — which means
    somebody did not trust the schema, and an untrusted schema is a schema the model is also being
    misled by.
  


  
Step 7: register it


  

    There is no registration step. The handler is a Spring component, the descriptor is a file, and
    the registry matches them by name at startup. If either exists without the other the
    application does not start:
  


  


  
Step 8: the test


  

    Two tests, and neither of them re-checks the schema — the pipeline already validated the
    payload against the descriptor's own output schema before the test saw it. What these assert
    are the claims the description makes.
  


  


  

    And the one that matters more, which is about an account the customer does not hold:
  


  


  

    NOT_FOUND and not NOT_ENTITLED. An
    authorization error tells the caller the account exists and belongs to somebody else; a
    not-found error tells them nothing. Since an agent cannot act on either, there is no cost to
    the uninformative answer and a real cost to the informative one — an enumeration oracle,
    driven by a model that will happily try a hundred identifiers if a prompt suggests it.
  


  
Step 9: run it


  


  

    Nine steps, one of which was writing nineteen lines of Java. That proportion is the point of
    the whole book: in a well-built catalog the code is the small part, and the artifact that needs
    care is the contract.
  







  
Chapter 16

  
The nine other reads

  

    Nine more tools, and eight ideas worth stealing.
  


  

    The remaining read tools are variations on chapter 15, so rather than walking each one this
    chapter takes the design decision each exists to demonstrate.
  


  
1. Batch, and name it plural


  

    brokerage_quotes_get takes up to ten symbols. An agent comparing
    three holdings will call a singular quote tool three times, and three round trips cost three
    times the latency, three audit records and three opportunities for one to fail on its own.
  


  

    Batching is the cheapest performance decision in a catalog and it is made in the descriptor
    rather than the handler: the parameter is an array, the cardinality in the ontology is
    many, and the name is therefore plural. The description then has to
    say it out loud, because a model will otherwise do the obvious thing: “Pass every
    symbol in one call rather than calling once per symbol.”
  


  

    There is an evaluation scenario that asserts exactly this, and it is the one that would catch a
    regression if somebody split the tool.
  


  


  
2. Name what you could not do


  

    The same tool returns an unresolved array. A tool that quietly drops
    the symbols it could not price leaves the agent to notice that it asked for three and got two,
    and it will not notice.
  


  


  
3. Refuse to choose


  

    brokerage_instruments_search is the only tool here whose entire
    design is a refusal. It returns candidates and an exactMatch flag,
    and leaves the choosing to the agent, which will put it to the customer.
  


  


  

    The temptation to choose is strong, because ninety percent of queries have an obvious answer and
    returning one row makes the agent's job easier. The ten percent is the problem: “buy me
    some Apple” has two plausible tickers, “buy Google” has two share classes, and
    an order is not reversible. A tool that silently resolves ambiguity has moved a decision from
    the customer to a ranking function, and nobody reviewed the ranking function.
  


  

    When the query is unambiguous the tool says so, so the agent need not ask:
  


  


  
4. Compute what the model would have to


  

    brokerage_price_history_get returns bars and also the period high,
    the period low and the total return. A model given 120 rows of OHLCV will read some of them and
    do arithmetic in its head, and the arithmetic it is most likely to get wrong is the one it is
    most likely to be asked for.
  


  

    
A rule worth generalizing

    

      If a model will have to compute something from your payload, and the computation is
      deterministic, compute it yourself. Payload size and arithmetic error go down together.
    

  


  

    The same idea appears in brokerage_positions_list, which carries
    portfolioWeight per holding. A question about concentration is then
    one tool call and no division.
  


  
5. Order the result


  

    Positions come back largest first. This is not cosmetic: a model reads a list from the top, and
    a long list from the top only. Putting the largest holdings first means that whatever gets
    dropped from a truncated answer is the part that mattered least. Ordering a result is the
    cheapest form of prioritization a tool has.
  


  
6. Default to the question that gets asked


  

    brokerage_orders_list defaults state to
    WORKING. “Do I have any orders open?” is the question nine
    times in ten, and a tool whose default is six months of history makes the model pay for the
    other one and then summarize the wrong thing.
  


  

    Defaults in a tool schema are not conveniences. They are the behavior you get, because a model
    omits an optional parameter far more often than it sets one.
    brokerage_executions_list makes the same decision with a 30-day
    window.
  


  
7. Cursors, never page numbers


  

    The order book moves while the agent reads it. Page two of an offset-paginated list can repeat
    a row or skip one, and the agent will report whatever it was handed.
  


  


  

    Two properties matter. The cursor is opaque, so moving to a keyset cursor over
    (placedAt, orderId) later is a day no caller has to change. And a
    malformed cursor is an INVALID_ARGUMENT rather than a silent reset to
    the first page — because silently starting over means an agent paging through a long list
    can loop forever, each time reporting the same first page as new.
  


  


  
8. Say when the answer does not apply


  

    brokerage_tax_lots_list returns a taxable
    flag. In a retirement account none of the holding-period and wash-sale machinery means anything,
    and an agent that launches into a long-versus-short-term explanation inside a Roth IRA has
    wasted the customer's time and damaged their confidence in the whole system.
  


  


  

    Rather than leaving the model to infer irrelevance from the account type, the tool says so.
  


  
What is deliberately absent


  

    There is no brokerage_lots_select in this catalog. Choosing which
    tax lots to sell has consequences that outlive the conversation, and this firm's position is
    that a human instructs it. The agent's job is to put the choice in front of the customer, which
    it can only do if it can see the lots — so the read tool exists and the write tool does
    not.
  


  

    That is a design pattern, not a gap. “Readable but not
    writable” is often the right answer for a capability that is genuinely useful and
    genuinely consequential. It gives the agent everything it needs to be helpful and nothing it
    needs to be dangerous, and it is a much easier conversation with a risk committee than
    “we built it with an approval step”.
  







  
Chapter 17

  
Preview and place

  

    Two tools, one of which is read-only, and the mechanism that makes an agent physically unable
    to trade without pricing the trade first.
  


  

    This is the design the rest of the catalog exists to support, so it is worth starting from the
    requirement rather than the solution.
  


  

    
The requirement

    

      An order may be sent to the market only if (a) the exact terms were priced, (b) the customer
      was shown the price, (c) the customer agreed to those terms, and (d) a retry of the
      same approved instruction produces one order rather than two.
    

  


  
Three designs that do not work


  
A confirmed flag

  

    brokerage_order_place(..., confirmed: true). A boolean the model sets
    is a boolean the model will eventually set — by a model that has convinced itself the
    customer already agreed three turns ago, which is a reasonable inference from a conversation
    and a catastrophic one from a control. The linter rejects the parameter name outright.
  


  
A dryRun flag

  

    One tool, with dryRun: true meaning price it and
    false meaning do it. Better, in that the pricing and the placing
    cannot diverge. Worse in every other way: one tool means one description, one risk tier and one
    approval mode for two operations whose consequences differ by everything. Also rejected by name.
  


  
A rule in the system prompt

  

    “Always call preview before place.” This one actually works most of the time, which
    is what makes it dangerous. It is a convention, enforced by the model's cooperation, and the
    conversations where it fails are the conversations where something unusual happened —
    which is also when you least want it to fail.
  


  
The design that does


  

    Two tools and a single-use token.
  


  
    
    
  • brokerage_order_preview is read-only, tier 1. It computes
      everything about the order and places nothing. When the order would be accepted, it issues a
      ConfirmationToken.
    • 
    
  • brokerage_order_place is tier 3 and requires a token.
    • 
    
  • Exactly one capability in the catalog produces a token, and it is the preview.
    • 
  


  

    The agent cannot skip the preview because the argument does not exist anywhere else. That is a
    structural property, not a behavioral one, and it is checked by a test rather than hoped for.
  


  
What the token is bound to


  


  

    A fingerprint of the exact ticket, the session it was issued to, and an expiry. All three earn
    their place:
  


  

    
Bound toStops

    
      
the fingerprint
        Placing 500 shares on a token minted for 50. Any change — quantity, price, side,
          time in force, account — is a different order and needs a new preview.

      
the session
        A token leaking between conversations, or a token from a transcript being replayed.

      
the expiry
        An order placed at a price the customer agreed to twenty minutes ago. Two minutes is
          long enough to read a summary and say yes, and short enough that the price is still
          roughly the price.

    
  


  

    And it is single use, which is where the idempotency comes from.
  


  


  

    Every refusal path returns a Rejection rather than throwing, because
    each one is something the agent can act on and the customer can be told — and the five
    are genuinely different. “That was already used” and “that is not the order
    you priced” need different next moves.
  


  
The preview


  

    The preview's job is to compute everything the customer needs in order to agree, and to be
    honest about what would stop the order.
  


  


  

    canPlace first, as the description instructs. Then the estimate, with
    isEstimate: true because a market order's fill is not knowable in
    advance. Then the token and its expiry.
  


  
Blockers and warnings are different things


  

    This is the most load-bearing distinction in the risk engine. A blocker means the order
    would be refused: the agent must not proceed, and the right move is to tell the customer why. A
    warning means the order would go through but the customer may not want it to.
  


  

    Collapsing them into one list of “issues” produces an agent that either ignores real
    refusals or refuses to place anything at all.
  


  


  

    Two blockers, and they are not the same problem. One is a per-order notional ceiling; the other
    is that the account does not have the money. Each carries a
    maxPermissibleQuantity, which turns a dead end into an offer: the
    agent can say “the most this account could buy is 17 shares — would you like
    that?” instead of “I can't do that”.
  


  

    Make a refusal actionable. When a tool refuses because of a limit, it
    almost always knows what would have been allowed. Returning that number costs nothing and is
    the difference between an agent that helps and an agent that reports.
  


  

    And when the blocker is not about size, the field is explicitly null, so the agent does not
    offer a smaller version of something that is categorically disallowed:
  


  


  
No token when it cannot be placed


  

    confirmationToken is null whenever
    canPlace is false. A refused order has nothing to approve, and
    handing back a token “just in case” would let an agent carry authority past the
    reason it was refused.
  


  


  
The place


  

    Read the order of operations, because it is the whole design.
  


  


  
    
    
  1. The token is redeemed before the order is sent. Redeeming it is what proves these
      exact terms were priced and approved.
    2. 
    
  2. A spent token is answered with the original order. Not an error — a retry is
      recognizably the same call, and duplicateOfPreviousCall tells the
      agent so in a field it cannot misread.
    3. 
    
  3. The risk check runs again. Two minutes have passed and the market has moved. A
      preview is a promise about the moment it was taken, not a license.
    4. 
    
  4. The idempotency key is derived from the token, not supplied by the model.
    5. 
  


  

    That last point is one line with a large consequence.
  


  


  

    A model asked to supply a unique key will sometimes reuse one and sometimes invent a new one on
    a retry, and either failure mode defeats the guarantee. Deriving it from a single-use token
    means the guarantee does not depend on the model at all.
  


  
The whole chain, captured


  

    Here is what the agent sees at each step, from the running system.
  


  
One. It calls place with a valid token, and the approval gate stops it:


  


  
Two. The customer is shown this, and says yes:


  


  
Three. The agent calls again, byte for byte, and the order goes:


  


  
Four. The agent, unsure whether that went through, retries:


  


  

    One order. The same identifier. And a field that tells the agent to describe one order rather
    than two, which is the part a customer would otherwise notice.
  


  
The token and the approval are two mechanisms


  

    A fair question at this point: if the customer has to approve at the gate anyway, why is there
    also a token?
  


  

    Because they guarantee different things, and each is useless alone.
  


  

    
MechanismGuaranteesDoes not guarantee

    
      
The token
        The terms were priced, by this service, moments ago, and have not changed since. And
          that a retry is not a second order.
        That any human was involved.

      
The approval gate
        A human was shown a summary and said yes to these arguments in
          this session.
        That the summary was true, or that anything priced it.

    
  


  

    Together they give you: a human agreed to a priced instruction that had not changed, and it
    happened once. There is a test for each half, and chapter 22 is about the gate.
  







  
Chapter 18

  
Replace and cancel

  

    Two tools that change something, and the asymmetry between them that is worth defending out
    loud.
  


  
Replace is tier 3, like placing


  

    This is the one people push back on, so here is the argument in one sentence: raising a limit
    from 495 to 512 and buying at 512 are the same economic act. The customer's exposure
    changes by exactly the same amount either way.
  


  

    A catalog that treats amendment as a lesser operation has given the agent a cheaper route to
    the same outcome, and cheaper routes get used. So replace needs the same approval, the same
    confirmation token, and the same evidence as place.
  


  
The order keeps its identifier


  

    A customer who was told “your order number is ord_CZ9R...” and then hears about
    ord_7K2M has lost the thread, and an agent asked to “move my limit up a dollar” has
    no business creating a second order. So an amendment is in place.
  


  


  
Some fields an amendment cannot change


  

    Quantity, limit price and stop price are amendable. Side, order type and time in force are not:
    they are properties of the order, and a request to change one is a request to cancel and
    re-enter. The handler takes them from the order rather than from the arguments, and a
    conflicting argument is an error rather than a silent reinterpretation.
  


  


  

    That method is also what keeps the fingerprint honest, and the comment explains a bug this book
    actually had: when the preview took the time in force from the arguments rather than from the
    order, previewing an amendment to a good-till-canceled order minted a token the replace tool
    could never spend. The failure surfaced as “the order does not match the one that was
    confirmed” — which is true, and completely unhelpful.
  


  
Cancel is tier 2, and needs no token


  

    The one asymmetry in the catalog. Cancelling reduces exposure. Requiring a priced preview before
    a customer can stop an order would mean that in the one situation where speed matters — a
    price running away from them — the system is at its slowest.
  


  

    A human still approves the call. What it does not need is a round trip through the risk engine
    to find out what stopping something would cost.
  


  
The race, reported honestly


  

    This is the part of the cancel tool that justifies its existence as a separate chapter. An order
    can fill in the moment between the customer asking and the venue hearing. When that happens:
  


  


  

    Read the envelope. ok is true. Nothing failed: the call
    worked, and the answer is that the order filled. cancelled is false,
    status is FILLED, and
    explanation says it in words the agent can read aloud.
  


  

    Returning an error here would be wrong twice over. Nothing failed, and an agent that sees an
    error will retry — which in this case means asking the venue to cancel an order that no
    longer exists, repeatedly, while telling the customer nothing.
  


  

    The failure this prevents is specific. An agent that says
    “I've canceled that for you” about an order that filled leaves a customer who
    believes they are flat and is not. They find out at the next statement, or when the position
    moves against them. It is the single most expensive thing a well-meaning agent can say.
  


  

    The contrast is worth seeing side by side — the same tool, on an order that was still
    working:
  


  


  

    Same shape, different values, and the agent branches on
    cancelled rather than on the absence of an error. The description
    tells it to: “Read cancelled and status together rather than assuming success.”
  


  
Partial fills


  

    On a partially filled order the shares that already filled remain, and only the unfilled
    remainder is canceled. The explanation says so, with the numbers, because reporting the order
    as CANCELLED
    on an order that was half done is another way to leave a customer with a position they do not
    know about.
  


  


  
Repeating a cancellation is harmless


  

    Calling cancel on an already canceled order reports the same final state and does nothing. The
    description says so, which matters because an agent that is unsure whether its cancellation
    landed should feel free to check, and the cheapest way to check is to ask again.
  







  
Chapter 19

  
What a schema cannot say

  

    Cross-field rules, and where to put them so that the model still learns them.
  


  

    “A limit price is required when the order type is LIMIT” is expressible in JSON
    Schema. It is a conditional, and conditionals are banned by the profile in chapter 7. This
    chapter is the bill for that decision, and the argument that it is worth paying.
  


  
Why the conditional is not an option


  

    Most tool-calling runtimes drop if/then on
    the way to the model. So the model is shown a schema in which
    limitPrice is simply optional, produces a LIMIT order without one,
    and the handler has to catch it anyway. You have written the rule twice — once in a
    schema the model never saw, once in the handler — and the schema is now a document that
    lies.
  


  

    
The trade

    

      State a cross-field rule in the description, where the model reads it, and enforce it
      in the handler, where a violation becomes an error the model can act on. That is two
      places. The alternative is also two places, plus a schema that disagrees with both.
    

  


  
Where the rules live


  


  

    Four lines of rule-checking, each covering a pair of order types, and each producing an error
    that names the field and says what to do:
  


  


  


  

    Note the remediation: “Ask the customer what price they want and re-send with
    limitPrice set.” Not “provide limitPrice”. The agent's next move is a
    question to a human, and saying so is the difference between an agent that asks and an agent
    that invents a price.
  


  
The rules that are not about arguments at all


  

    Most of what stops an order has nothing to do with the shape of the request. The risk engine
    checks nine things, and every one of them is about the state of the world rather than the
    contents of the ticket.
  


  


  

    
CheckProduces

    
      
sessionA blocker when the market is closed and the order would
        expire, or when a market order is entered outside the regular session. A warning otherwise
        in pre-market and after-hours.

      
permissionsBlockers for a frozen account, a short sale in a cash or
        retirement account, a non-marginable instrument bought on margin, a day-trade
        restriction.

      
sizeA share ceiling and a notional ceiling, each with the size that
        would have been allowed.

      
fundingBuying power in a margin account, settled cash in a cash
        account — which is why the balances tool returns both.

      
inventorySelling more than is held, which is a short sale and must
        be entered as one deliberately.

      
pricingA blocker at more than 30 percent from the market, a warning
        at more than 10. The first is a mistyped-price guard; the second is a “this will sit
        unfilled” guard.

      
concentrationA warning above 25 percent of the account.

      
taxesWarnings about wash-sale exposure and mixed holding periods,
        suppressed entirely in a retirement account.

    
  


  
One detail worth stealing


  

    The concentration check only runs when there are no blockers.
  


  


  

    Without that guard, an order for four thousand shares in an account that cannot afford forty
    produces the warning “MSFT would be 6,794 percent of the account”. It is
    arithmetically true and it is noise, and noise in a warnings array is how an agent learns to
    skim it.
  


  
And the rules that are about the account, not the order


  

    A frozen account is refused before anything is priced, by a guard every handler that takes an
    account calls:
  


  


  


  

    “Do not try another account on their behalf.” That clause is in the
    remediation because the obvious helpful thing to do with a frozen account is to suggest a
    different one, and the obvious helpful thing is wrong: the customer said which account, and an
    agent that moves an order somewhere else has substituted its judgment for theirs on a question
    about money.
