Chapter 20

The registry

It sounds like plumbing and it is in fact the main architectural decision in a tool system.

Without a registry, the set of tools a model sees is whatever beans happened to be on the classpath. That sounds harmless until somebody asks one of these four questions, all of which get asked:

  1. What is the model being shown right now?
  2. Who is allowed to call each of these?
  3. Which of them have been reviewed?
  4. What breaks if we turn one off?

With a registry, all four are lookups.

Three rules, enforced at construction



  

    Deliberately early, so that a misconfigured catalog fails at startup rather than in a
    conversation.
  


  

    
Every descriptor has a handler and every handler has a descriptor

    

      A handler with no descriptor is dead code. A descriptor with no handler is worse: a tool the
      model will choose and then be told does not work, which costs a turn and teaches it nothing.
    


    
Every descriptor passes the conformance linter

    

      A registry that serves a non-conformant descriptor has made the specification advisory. The
      findings are kept, so the console can show a reviewer what the gate saw, but any error stops
      the application.
    


    
Only active tools are served

    

      Draft and retired tools are skipped, however complete they look. The lifecycle field is the
      switch between “this exists in the repository” and “a model can call
      this”, and those should not be the same thing.
    

  


  
The selection view


  

    The registry's most-used method is one line, and the reasoning behind it is the whole chapter.
  


  


  

    Filtering before publication rather than refusing at execution is not an optimization. A tool
    the principal cannot use, published into the model's context, costs tokens on every turn and
    buys a wrong turn: the model will choose it, be refused, apologize, and choose again. Showing a
    model only what it can do is the cheapest accuracy improvement available.
  


  
One catalog, three products


  

    The same fourteen descriptors, the same handlers and the same pipeline, published to three
    sessions that differ only in their entitlements.
  


  

    
RoleTools
      Sees

        instruments_search, quotes_get, price_history_get

          tax_lots_list, orders_list, order_get, executions_list

          order_cancel

    
  


  

    Nothing is reconfigured to make that happen, and no tool is rewritten. There is an HTTP test
    that asserts the three counts, because the day one of them changes silently is the day a
    research session can read a customer's balances.
  


  


  
And what is hidden, for the humans


  

    The registry can also answer the inverse question — which tools this principal
    cannot see, and which scope is missing. That is never shown to the model; it is for
    the console, and for the support engineer wondering why the agent said it could not do
    something.
  


  







  
Chapter 21

  
The invocation pipeline

  

    Ten steps, in an order that is argued for rather than assumed. This is the system.
  


  

    A handler is domain code. The pipeline is the part that makes a tool catalog safe to point a
    language model at, and it is identical for all fourteen tools — which is precisely why it
    belongs in one place and not in any of them.
  


  


  
Steps 1 and 2: resolve, and check the switch


  


  

    Note that an unknown name and a name this principal cannot see produce the same error.
    Telling the model “that tool exists but is off limits” is an oracle it will probe,
    and since it cannot act on either answer there is no cost to the uninformative one.
  


  
Steps 3 and 4: parse and validate


  


  

    The remediation is as important as the message. “Fix the fields named above and call
    the tool again. Do not try a different tool.” An agent that reads an argument error as
    “this tool does not work” will go looking for another one, and the other one will
    have the same problem.
  


  
Step 5 after step 4, which looks backwards


  

    Arguments are validated before entitlements are checked. For a human-facing API that is
    the wrong order: you refuse the unauthorized caller first and tell them nothing else.
  


  

    For a model it is the wrong order for a different reason. The useful answer to a malformed call
    is “your third argument is wrong”, and giving it a bare
    NOT_ENTITLED teaches it to retry the same malformed call against a
    different tool. Nothing leaks, because the tool was already in this principal's
    visible catalog before the pipeline ran — step 1 saw to that.
  


  

    
The general form

    

      Information is withheld at the point where visibility is decided, not at the point
      where a call is refused. Once a tool is visible to a session, that session may learn
      everything about how to call it correctly.
    

  


  
Step 6: the rate limit


  

    Rate limiting a tool catalog is not about load. It is about the one failure mode a language
    model has that a human caller does not: a loop. An agent that misreads an error as transient
    will retry it, politely, for as many turns as the budget allows.
  


  


  

    The limit is per tool, not per catalog, because the limits that matter differ by two orders of
    magnitude. And the error carries the wait, because “too many requests” with no
    number means the agent waits zero seconds.
  


  
Step 7: the approval gate


  

    Chapter 22 is about the gate itself. What matters here is where it sits: after validation, after
    entitlement, after the rate limit, and before the handler. A human is asked about a
    call that is already known to be well-formed and permitted, which is the only kind of call it is
    reasonable to ask a human about.
  


  


  
Step 8: the handler runs


  

    And only now. Note what the handler is given.
  


  


  

    A descriptor, validated arguments, a principal and a request identifier. Note what is
    not there: the conversation. A handler cannot read the chat history, cannot see the
    system prompt, and cannot be talked into anything, because it is never shown the talking. That
    is the whole reason a tool is a safer surface than a prompt.
  


  
Step 9: verify the payload


  

    This is the step people leave out, and the one worth the most argument.
  


  


  

    Validating your own handler's output sounds like distrust of your colleagues. It is distrust of
    drift. The output schema is the only description of the payload the model will ever
    see. The day a handler adds a field, renames one, or starts returning null where it used to
    return a number, the model is being misled by a document the firm published — and nothing
    else in the system will notice.
  


  

    Failing closed turns that into a caught bug with a request identifier, rather than a confusing
    conversation three weeks later. The error returned to the model carries no detail at all,
    because the model cannot act on it and a customer should not read it.
  


  
Step 10: envelope and audit


  

    And the two things that happen on every path, successful or not.
  


  


  
Everything a handler may throw


  

    Exactly one thing, and the pipeline catches the rest.
  


  


  

    A ToolFailure becomes the envelope the handler intended. Anything
    else is logged with the request identifier and returned as
    INTERNAL_ERROR with no detail — because the alternative is a
    database constraint name in a customer conversation, and there is a test asserting it does not
    happen.
  


  
What this buys, in one table


  

    
Without the pipelineWith it

        Every call validated against the published schema, once, in one place

        Checked for every tool, from the descriptor's own declaration

Chapter 22

  
Approval, limits and switches

  

    Where a human says yes, how to stop a loop, and how to turn a tool off at two in the morning.
  


  
The approval gate


  

    The mechanism is a reference rather than a flag, and that distinction is the whole
    design. A flag can be set by the thing being checked. A reference is a hash of the tool name,
    the exact arguments and the session.
  


  


  

    Canonical JSON, so that a re-ordered argument object is still the same approval and a changed
    value is not. An approval granted for “buy 50 AAPL at market” cannot be spent on
    “buy 500”, and an approval from one conversation cannot be spent in another.
  


  
Three steps, and it survives a restart


  
    
    
  1. The agent calls a tool that needs approval. The gate has no grant for that reference,
      so the pipeline returns APPROVAL_REQUIRED with the reference and a
      rendered summary of what is about to happen.
    2. 
    
  2. Something outside the model shows the summary to a human and records their answer
      against the reference. In this repository that is the Angular console; in production it is
      whatever surface the customer is actually on.
    3. 
    
  3. The agent calls the tool again, byte for byte. Now the grant matches and it runs.
    4. 
  


  

    Nothing about that flow requires the agent process to be the same one, or even to be running,
    between steps 1 and 3.
  


  
Grants are single use and they expire


  


  

    An approval with no window is a standing instruction, and nobody means to give one of those.
    There are three tests, and between them they say the whole thing:
  


  


  


  


  
The dialog, and the context behind it


  

    Chapter 9 made the case; here is the mechanism. The template is rendered from the arguments
    plus whatever the domain supplies, and the domain's values win.
  


  


  

    An unresolved placeholder is left visible as (not given) rather than
    blanked, because a dialog with a quietly empty field is how somebody approves an order whose
    quantity they never saw. And the brokerage's own context re-prices the order at the moment of
    the confirmation:
  


  


  

    If the order can no longer be placed at all, the dialog says so instead of quoting a cost. A
    confirmation prompt for an order that would be refused is worse than useless: the customer says
    yes, the tool refuses, and they have learned that the approval step is theatre.
  


  
Rate limits


  


  

    A sliding window per principal and per tool. The numbers in this catalog range from 180 a minute
    for quotes to 10 a minute for placing an order, and the ratio is the point: a tool that is cheap
    and idempotent should be generous, and a tool that spends money should not.
  


  
Kill switches


  

    Every tool at tier 2 or above must name one, and the linter enforces it. The reason only becomes
    obvious the first time you need it: when a tool starts behaving badly at two in the morning, the
    options are to turn it off or to roll back, and only one of those takes less than a build.
  


  


  

    Switches are hierarchical by prefix, so tools.brokerage.trading
    disables tools.brokerage.trading.place and its siblings with it. That
    matters when the thing misbehaving is a dependency rather than a tool.
  


  

    And the effect on the agent is the point: a tripped switch does not produce an error the agent
    will retry. The tool leaves the catalog on the next turn, so the model does not see it at all.
  


  







  
Chapter 23

  
The audit record

  

    What to write, what never to write, and why it is written twice.
  


  


  
Written before, completed after


  

    A record is written before the handler runs and completed after, so that a call which hangs or
    crashes the process still leaves evidence it was attempted. Logging on the way out loses exactly
    the invocations an incident review cares about.
  


  
What is deliberately absent


  

    Arguments are recorded as a hash and a list of field names, never as values.
  


  


  

    The reasoning: the record has to prove which call was made and let a reviewer match it against
    an approval, and a hash does both. Storing the values themselves would put account identifiers,
    order sizes and whatever the customer typed into a log with a six-year retention and a much
    wider readership than the account itself.
  


  


  
What an incident review actually needs


  

    Here is the trail left by the preview-then-place sequence from chapter 17.
  


  


  

    Four things an auditor can do with that, none of which require the application to be running:
  


  
    
    
  • Join the action to the approval. Both place records carry the same approval
      reference; one is the request and one is the execution.
    • 
    
  • Prove the order of operations. The preview preceded the place, and the timestamps
      say by how long.
    • 
    
  • Know the retention and the basis. Each record carries its own, from the descriptor,
      so a record does not have to be joined to a catalog that may have changed.
    • 
    
  • Find the conversation. The session identifier, and the request identifier the
      customer was given if they complained.
    • 
  


  

    There is a test for the first of those, because it is the one that matters and the one a
    refactor would silently break.
  


  


  
In production


  

    This implementation keeps the last few thousand records in memory so the console can show them
    and the tests can assert on them. In a real firm it writes to the immutable store, and the
    interesting design question is not where but what else: the audit record is the only
    artifact that survives the conversation, so anything you will want to ask later has to be in it
    now.
  


  

    One field worth adding that this implementation does not have. The
    model and model version that made the call. When selection accuracy moves after a model
    upgrade, the first question is which calls were made by which version, and the only place that
    can be answered is here.
  







  
Chapter 24

  
Publishing to Spring AI

  

    The whole binding, in one class, with no annotations anywhere.
  


  

    Everything in this book so far has been about a contract that names no framework. This is where
    it meets one, and the measure of whether the preceding chapters were right is how little code
    this takes.
  


  


  

    Spring AI wants three strings per tool: a name, a description and a serialized input schema.
    The descriptor has all three, so the adapter reads them off and hands them over. There is no
    translation, no mapping table and no annotation processor.
  


  
What the callback deliberately does not do


  


  

    It hands the raw argument string to the pipeline and returns whatever JSON comes back. It does
    not validate, authorize, catch or format — because doing any of those here would mean
    they happened only for callers who came through Spring AI, and the desktop connector and the
    test harness would each need their own copy.
  


  
Contrast with the annotated approach


  

    Spring AI supports @Tool on a method, which is the obvious thing to
    reach for and is faster for the first three tools. Here is what it costs at fourteen.
  


  

    
 @Tool on a methodA descriptor file

    
      
The description
        A string literal in a Java file. Nobody lints it; a reviewer reading the diff is reading
          Java.
        Prose in a file, linted against ten rules, and a diff a product owner can read.

      
The input schema
        Inferred from parameter types. You get the types; you do not get patterns, enums,
          bounds or per-property descriptions without more annotations.
        Written explicitly, and checked against a profile.

      
Seeing what the model gets
        Start the application and inspect.
        cat the file.

      
Publishing elsewhere
        Another framework's annotations, or a reflection pass.
        An adapter of about forty lines that renames nothing.

      
Governance
        Nowhere obvious. Usually a spreadsheet.
        In the file, next to the thing it governs.

    
  


  
Publishing per turn, not per application


  


  

    Each call builds fresh callbacks bound to this session's principal and to a fresh trace. Two
    consequences follow: a research session and a trading session running at the same moment see
    different catalogs, and every turn comes back with a complete record of what was called.
  


  
The agent


  


  

    There is no hand-rolled tool-call loop. Spring AI runs it, because there is nothing to gain from
    driving it manually: the trace is collected inside each callback, so the visibility a manual
    loop is usually written for is already there. Less machinery, same evidence.
  


  
The trace


  

    Which brings us to the most useful artifact in the whole system, and the one that is almost
    always missing.
  


  


  

    When an agent gives a wrong answer, the question is never “what did the model say”
    — you have that. It is “which tools did it call, with what arguments, in what order,
    and what came back”. Without a trace you are reduced to reading the final prose and
    guessing.
  


  

    The trace is also what makes the test harness possible. Selection accuracy, argument accuracy
    and trajectory assertions are all statements about this list, so the harness becomes a set of
    expectations over a trace rather than a set of expectations over English. Part VII is about
    that.
