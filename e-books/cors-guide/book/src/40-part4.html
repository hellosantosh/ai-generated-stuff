Caches and Vary: Origin

The bug that makes CORS “work sometimes” is usually not in your CORS code at all. It is in a cache that doesn't know your answer depends on who asked.

How a correct policy goes wrong

Suppose Harbor Pay allows two origins, the dashboard and a partner portal. The API names whichever one is asking — a correct policy. Now put a CDN or reverse-proxy cache in front of it, keyed only on the URL:

The fix: tell every cache what the answer depends on

Vary: Origin

Vary lists the request headers a response depends on. With Vary: Origin, a cache stores a separate copy per origin, and each origin gets its own correct answer. The rules are short:

  • Send Vary: Origin whenever Access-Control-Allow-Origin can differ between requests — that is, on every response from a dynamic policy, including the ones where you send no CORS headers at all.
  • A fixed Access-Control-Allow-Origin: * does not vary, so it doesn't need it.
  • If your response already varies on other headers, combine them: Vary: Origin, Accept-Encoding.
Why it is a security issue too. The same mechanism can serve a response containing one user's data, or one origin's permission, to a different requester. Caches in front of personalized, credentialed responses need Cache-Control: private (or no-store) as well as correct Vary. The 2018 study in Chapter 15 found missing Vary: Origin to be widespread.

Chapter 18

The local network

Your browser sits on two networks at once: the public internet, and the private one around you — your router, your printer, services on localhost. For most of the web's history, public pages could send requests to both.

Why the local network is special

Devices and apps on private networks were often built on the assumption that “only people on my network can reach me.” But every web page you open runs inside your browser, which is on your network. The Zoom and Transmission cases in Chapter 15 both followed from this. CORS helps only partly: it stops a public page from reading a local service's responses, but simple requests still arrive, and a local service that acts on them can be driven from any website.

What browsers did about it

Chromium first proposed Private Network Access: before a public page could reach a private address, the browser would send a special preflight (Access-Control-Request-Private-Network: true) and require the device to opt in. Deployment revealed compatibility problems, and the design evolved into Local Network Access. Beginning with Chrome 142 in October 2025, a public site that tries to reach the local network or loopback triggers a permission prompt: the user, not the device, decides whether that site may talk to local devices. Other browsers have been evaluating similar protections; check current documentation for each.

What this means for you. If your product legitimately talks to a local device from a web page (a printer setup page, a hardware wallet bridge, a developer tool), expect a permission prompt in Chromium browsers, explain it to your users, and never rely on the prompt as your only defense.

DNS rebinding, and why names are not enough

The same-origin policy compares names. DNS decides what machine a name refers to, and a domain's owner can change that answer at any time, even to a private address. That lets a hostname that began as an ordinary public site later point at 127.0.0.1, while the browser still treats both as one origin. This is DNS rebinding, the issue behind the Transmission fix in Chapter 15. Browser-level defenses such as Local Network Access help, but the reliable fixes live in the local service itself.

Chapter 19

Beyond CORS

CORS controls what a page may read through fetch(). A newer family of headers controls everything else: what may embed you, what you may embed, and who may share your process.

The turning point: Spectre

In January 2018, researchers disclosed Spectre, a class of CPU vulnerabilities that let code infer data from memory it was never allowed to read. For browsers the implication was stark: if a cross-origin resource was loaded into the same process as a hostile page — even as an “embedded” image or script it could not officially read — its bytes might be exposed. Browsers responded with Site Isolation (separate processes per site) and by blocking sensitive responses from ever reaching the wrong process: first Cross-Origin Read Blocking (CORB), now specified as Opaque Response Blocking (ORB) in the Fetch Standard. Servers got new headers to state their intentions explicitly.

Cross-origin isolation

A page served with both Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp (or credentialless) becomes cross-origin isolated: self.crossOriginIsolated is true. Browsers then unlock powerful features they otherwise restrict, such as SharedArrayBuffer and more precise timers, because nothing from another origin can end up in the page's process without having agreed to it.

How CORS fits. Under COEP: require-corp, a cross-origin resource is accepted if it either sends a suitable CORP header or is fetched in CORS mode and passes the CORS check. CORS and CORP are the two ways a resource can say “yes, you may have me.”

Fetch Metadata: the browser tells you the context

Modern browsers attach Fetch Metadata request headers that describe how a request came about. A page cannot forge them.

HeaderTells the server
Sec-Fetch-SiteThe relationship between the requesting page and the target: same-origin, same-site, cross-site, or none (typed in the address bar, a bookmark).
Sec-Fetch-Modenavigate, cors, no-cors, same-origin or websocket.
Sec-Fetch-DestWhat the response will become: document, image, script, empty (fetch), and so on.
Sec-Fetch-User?1 when a navigation was triggered by a user action.

A resource isolation policy

With these headers, a server can refuse unexpected cross-site traffic before it reaches any business logic — a strong complement to CORS (which governs reading) and to CSRF defenses (which govern writing):

// Allow same-origin and same-site requests, browser navigations, and old browsers
// that don't send the header. Refuse everything else from other sites.
function allowRequest(req) {
  const site = req.headers['sec-fetch-site'];
  if (!site) return true;                               // older browser
  if (['same-origin', 'same-site', 'none'].includes(site)) return true;
  if (req.headers['sec-fetch-mode'] === 'navigate' && req.method === 'GET') return true;
  return isPublicEndpoint(req.url);                     // explicit exceptions
}

Cross-site leaks: the frontier

Even when a page cannot read a response, it can sometimes observe side effects: how long a load took, whether a frame loaded, how many windows a site opened. The research community calls these cross-site leaks (XS-Leaks). They are the reason browsers keep adding isolation features and keep CORS errors deliberately vague (Chapter 10). The defenses are the ones in this chapter: SameSite cookies, Fetch Metadata checks, COOP, and CORP.

For APIs

Precise CORS allowlist, Vary: Origin, Fetch Metadata policy, CORP: same-site on private JSON.

For apps

COOP: same-origin, a strict content security policy, and SameSite session cookies.

For public assets

Allow-Origin: * without credentials, and CORP: cross-origin so isolated pages can use them.

Chapter 20

Designing a secure CORS policy

The safest CORS policy is the one you never need. The next safest is short, explicit, and boring. Here is how to choose, and how to write it.

Three architectures

Rules for a credentialed allowlist

  1. Exact strings only. Full origins (https://host, plus port if not default), compared with equality. No substring, prefix, suffix or regular-expression checks.
  2. Never null, never http in production, and no development origins in production configuration.
  3. Headers only on a match. Unknown origins get no Access-Control-* headers at all — not an error message, not a default origin.
  4. Vary: Origin on every response the policy touches, allowed or not.
  5. Minimal methods and headers, listed by name; Max-Age of minutes to an hour.
  6. Preflights answered before authentication, and never running business logic.
  7. Expose only what the client needs in Access-Control-Expose-Headers.
  8. Configured in one place — app or gateway, not both.

Reference configurations

Three stacks, one allowlist. Check your framework version's documentation first.

Node.js with Express and the cors package

const cors = require('cors');
app.use('/api', cors({
  origin: ['https://app.harborpay.example'],   // an exact list, never true or '*'
  credentials: true,
  methods: ['GET', 'POST', 'PUT'],
  allowedHeaders: ['Content-Type'],
  exposedHeaders: ['X-Request-Id'],
  maxAge: 600,
}));

Spring (Java) with WebMvcConfigurer

@Override
public void addCorsMappings(CorsRegistry registry) {
  registry.addMapping("/api/**")
      .allowedOrigins("https://app.harborpay.example")
      .allowedMethods("GET", "POST", "PUT")
      .allowedHeaders("Content-Type")
      .exposedHeaders("X-Request-Id")
      .allowCredentials(true)
      .maxAge(600);
}

nginx in front of any application

# Unknown origins map to "", and nginx omits empty headers.
map $http_origin $cors_origin {
    default                          "";
    "https://app.harborpay.example"  $http_origin;
}
location /api/ {
    add_header Access-Control-Allow-Origin      $cors_origin always;
    add_header Access-Control-Allow-Credentials "true" always;
    add_header Vary                             Origin always;
    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin      $cors_origin always;
        add_header Access-Control-Allow-Credentials "true" always;
        add_header Access-Control-Allow-Methods     "GET, POST, PUT" always;
        add_header Access-Control-Allow-Headers     "Content-Type" always;
        add_header Access-Control-Max-Age           600 always;
        add_header Vary                             Origin always;
        return 204;
    }
    proxy_pass http://api_backend;
}

Inner add_header blocks replace inherited ones, hence the repetition.

Test the policy like code

Policies drift: a new front end is added in a hurry, a gateway is upgraded, someone “temporarily” adds a test origin. Put the policy under automated tests so drift fails a build instead of reaching production. A useful suite sends preflight and actual requests with a range of Origin values and asserts on the headers that come back:

The design-review checklist

  • ☐ Could this be same-origin instead (architecture A)?
  • ☐ Does any response depend on cookies or network location?
  • ☐ If * is used, are responses identical for every caller?
  • ☐ Is every allowed origin a full, exact https string?
  • ☐ No null, no http, no dev origins in production?
  • ☐ Does every trusted origin have XSS defenses and a named owner?
  • ☐ Vary: Origin on every response of a dynamic policy?
  • ☐ Preflights answered before authentication, no side effects?
  • ☐ Methods, headers and exposed headers listed minimally, by name?
  • ☐ CORS headers present on error responses too?
  • ☐ Configured in exactly one layer?
  • ☐ State-changing endpoints protected against CSRF (Chapter 16)?
  • ☐ Local services validate Host and authenticate (Chapter 18)?
  • ☐ Automated tests cover allowed and refused origins?
If you remember one design rule. Let the browser say no by default, and make every yes a named, reviewed, tested decision. That is what Access-Control-Allow-Origin was designed to express.

Chapter 21

Epilogue: the review

Every story about security ends the same way: not with a dramatic rescue, but with a list of boring things done well.

Harbor Pay · Six weeks after launch

The ten tickets are closed. The five services that checked whether an origin ended with the company domain now compare against exact lists. The two that trusted null have lost their decade-old test harness. The reporting service that echoed every origin turned out to need exactly one: the finance dashboard. The transfer endpoint accepts only JSON and checks Origin on every write. The card-reader helper asks the cashier to confirm pairing and ignores requests addressed to any unexpected host name.

The bigger change is quieter. The dashboard team has moved the API behind the app's own origin, at app.harborpay.example/api. For the dashboard, CORS is simply gone — no preflights, no allowlist to maintain, first-party cookies. The build pipeline now runs a CORS test suite against every service, and a failing test names the origin and the header.

On a Friday afternoon, a new engineer posts in the team channel: “Getting a CORS error on the partner portal — can I just set Allow-Origin to star?”

You smile, and start typing. “Before anybody touches that header,” you write, “can you tell me what it actually protects?”

Seven things to carry with you

  1. The same-origin policy is the default; CORS is a set of exceptions to it, granted by servers and enforced by browsers.
  2. It governs reading, not sending. Simple requests reach the server regardless; protect state changes separately.
  3. An origin is scheme, host and port. Sibling subdomains and different ports are different origins.
  4. Credentials raise the bar: an exact origin, Allow-Credentials: true, and no wildcards — and that bar exists for good reason.
  5. Compare origins with exact equality against a reviewed list. Every clever rule is a future incident.
  6. Send Vary: Origin whenever the answer depends on the asker.
  7. The best CORS policy is often none at all: serve the API from the app's origin.
