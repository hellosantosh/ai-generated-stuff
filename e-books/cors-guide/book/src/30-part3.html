Part III

When the Wall Has Holes

A CORS policy is a security decision written as a response header. Written well, it opens one precise door. Written carelessly, it quietly switches off the browser's protection for every user of your API. This part explains why that matters, the mistakes behind real incidents, the attack patterns they enable, and one thing CORS was never meant to do.

Chapter 12

Why CORS is a security priority

A CORS policy is often the only thing standing between a page your users happen to visit and the data your API holds about them. That makes a single response header one of the most consequential lines in your codebase.

Three weeks later · Security review, 10:00 a.m.

Ren's backlog ticket has become a meeting. On the screen: a spreadsheet of every Harbor Pay service and the CORS headers it returns. Forty-one rows, some from teams that no longer exist.

“Before we look at any row,” Ren says, “let's agree on why this is worth a morning.”

Six reasons it deserves attention

1 · It guards the user's own session

Your authentication works perfectly and still doesn't help: the request really is from the signed-in user's browser, carrying their real cookie. The only question is which page gets to read the answer. That question is CORS.

2 · APIs are the product now

Single-page apps, mobile back ends and partner integrations put account data, payment details and personal records behind JSON endpoints. Those are exactly the responses CORS decides about.

3 · Mistakes are silent

A too-strict policy produces red errors and angry tickets. A too-loose policy produces nothing at all — every test passes. The feedback loop rewards loosening and never punishes it.

4 · The fix is tempting and tiny

Under launch pressure, the difference between a correct policy and a dangerous one is a few characters. Forums are full of snippets that make errors disappear by trusting everyone.

5 · Reach is multiplied

A policy bug is not one user's problem. It affects every signed-in user of that API, from every browser, until someone notices.

6 · Standards bodies track it

The weakness has its own entries — CWE-942 (Permissive Cross-domain Policy with Untrusted Domains) and CWE-346 (Origin Validation Error) — and the OWASP Web Security Testing Guide has a dedicated test, WSTG-CLNT-07.

What is actually at stake

If a policy lets an untrusted origin read credentialed responses, any page a signed-in customer visits can see what that customer sees in your app, through their own session. No password is stolen and no server is breached, so the logs show only normal requests.

The one-line summary. CORS misconfiguration turns your users' browsers against them. It is a privacy and data-exposure problem first, and its blast radius is every signed-in user.

Where risk actually lives

Not every permissive header is a problem. Risk depends on two questions: does the response depend on who is asking (cookies, network location, or other ambient credentials), and whom does the policy allow to read it?

“But we have authentication”

This is the most common objection in a review, and it misses the point. Authentication answers “is this request from Alice?” In the danger zone the answer is honestly yes — Alice's browser sent it, with Alice's cookie. What went wrong is that a page Alice didn't intend to trust got to read the reply. Token-based APIs that never use cookies are far less exposed for the same reason: the browser does not attach a bearer token automatically, so there is no ambient credential to misuse.

What a good review asks

  1. Which responses from this service depend on cookies, sessions or network location?
  2. For those responses, exactly which origins can read them, and who approved each one?
  3. How is the Origin header compared — whole-string equality, or something cleverer (and therefore riskier)?
  4. Are the pages on every trusted origin themselves well defended against script injection?
  5. Do all responses, including errors and cached ones, carry the right headers and Vary: Origin?

Chapter 13

Configuration mistakes that matter

Almost every serious CORS problem is one of six patterns. Each one looks reasonable in a code review, and each one has a simple, boring fix.

Mistake 1 · Echoing any origin, with credentials

“Copy back whatever Origin arrives”

The server reads the request's Origin and repeats it in Access-Control-Allow-Origin, together with Allow-Credentials: true. It always “works,” which is why it spreads. It is also exactly the combination the browser's *-with-credentials rule exists to prevent: every origin on the internet is now trusted with your users' sessions. Watch for framework settings with friendly names — in some popular middleware, setting the origin option to true means “reflect the request's origin.”

Fix: compare the origin against an explicit list and repeat it only on an exact match. If the data is truly public, use * without credentials.
Mistake 2 · Loose matching

Prefixes, suffixes, substrings and hand-written patterns

Checks like “the origin contains our domain,” “ends with our domain,” or a regular expression with an unescaped dot or a missing anchor all accept more than their authors intended — including hostnames that someone else can register. The researchers in Chapter 15 found this class of bug to be widespread.

Fix: don't pattern-match origins. Keep a list of complete origin strings (scheme, host and port) and use exact equality. If you must support many subdomains, parse the origin with a URL parser and compare the parsed hostname against an exact set.
Mistake 3 · Trusting null

Allowing Origin: null “for local testing”

Developers add null to an allowlist so that a page opened from disk can call the API. But null is shared by every sandboxed iframe, every data: document and every local file on every machine (Chapter 3). Trusting it trusts all of them at once.

Fix: never allowlist null. Serve test pages from a real local origin such as http://localhost:8080, and keep development origins out of production configuration.

Mistake 4 · Trusting plain http

Allowing http://app.harborpay.example as well as https

An http origin is only as trustworthy as every network between the user and the server. On a hostile Wi-Fi network, content served over plain HTTP can be altered in transit, so trusting the http version of your own site extends your API's trust to whoever controls that network.

Fix: allow only https origins in production, and use HSTS so that your sites are never loaded over plain HTTP in the first place.
Mistake 5 · Trusting every subdomain

“Anything under harborpay.example is ours”

A company domain accumulates marketing microsites, old campaign pages, third-party-hosted help centers and forgotten staging servers. Trusting all of them means your most sensitive API is only as safe as your least-maintained subdomain — including any with a cross-site scripting bug or a dangling DNS record pointing at a service someone else can claim.

Fix: list the specific origins that need access. Treat adding one as a security decision, and remove entries when the site that needed them is retired.
Mistake 6 · Network location as a credential

Allow-Origin: * on an internal API

“It's only reachable from the office network, so * is fine.” But the code that makes the request runs inside an employee's browser, which is on the office network. A wildcard on an unauthenticated intranet API lets any page an employee visits read it. Local services on localhost have the same problem (Chapter 18).

Fix: require real authentication on internal services, and never combine “trusted because of where it is” with *.

Plus one that breaks things before it breaks security

A dynamic policy (one that names different origins for different requests) without Vary: Origin lets caches serve one origin's permission to another. Chapter 17 covers it in depth; the fix is one header, on every response.

The pattern behind all six. Every mistake here replaces a short, explicit list of trusted origins with a rule that trusts a category — “whoever asks,” “anything that looks like us,” “anything local.” Categories grow without anyone deciding. Lists only grow when someone does.

Chapter 14

Attack patterns, drawn

You cannot defend against a shape you have never seen. This chapter draws the seven patterns behind real cross-origin incidents, so you can recognize them in a design review, spot their traces in your logs, and know exactly where to break the chain.

Security review · 1:30 p.m.

After lunch Ren stands at the whiteboard. “Tickets fix today's bugs,” Ren says. “Patterns stop next year's. Every cross-origin attack I've seen is one of seven shapes.” Ren draws the first one.

How to read the diagrams

Red dashed arrows are steps an attacker can cause or influence — usually just by getting a signed-in user to open a web page.

Solid arrows are the normal behavior of browsers and servers. Most attacks need nothing unusual from either.

Green shields mark where a defense breaks the chain. One shield anywhere on the path is enough.

Pattern 1 · The borrowed session

A hostile page reads your API through the user's own session

What happens. Nothing is stolen from the server and no password is guessed. The API does what it always does — answers the user's browser — and its CORS policy tells the browser that the untrusted page may read the answer.

Warning signs. Credentialed responses whose Access-Control-Allow-Origin names an origin you never approved; Origin values in your logs that no team recognizes.

Break the chain. An exact allowlist (Chapter 13), no credentials where the data isn't personal, and cookies with SameSite so the session isn't attached cross-site in the first place.

Pattern 2 · The look-alike

An origin that merely resembles yours passes a loose check

What happens. A string test written to recognize your domain also accepts names that contain or end with the same characters — names anyone can register.

Warning signs. Origin checks built from includes, endsWith, or hand-written regular expressions; allowlists described in words rather than listed.

Break the chain. Exact equality against complete origin strings, and tests that prove near-miss origins are refused (Chapter 20).

Pattern 3 · The compromised friend

A trusted origin is taken over, and brings its trust with it

What happens. The policy is correct, but one of the origins it trusts is no longer trustworthy. Anything running there speaks with that origin's voice.

Warning signs. Allowlist entries nobody owns; subdomains whose DNS points at deleted cloud resources; old sites without a content security policy.

Break the chain. Trust only what you maintain, give every entry an owner, remove retired sites, and monitor DNS for dangling records.

Pattern 4 · The anonymous frame

Trusting null trusts everyone who can be anonymous

What happens. Many unrelated documents share the same null origin, and some of them can be created by any website. Warning signs: null in an allowlist or a test configuration that reached production. Break the chain: serve test pages from a real local origin and refuse null everywhere.

Pattern 5 · The blind write

The response is hidden, but the action already happened

What happens. CORS only protects reading (Chapter 16), so a request a form could send changes data even though its answer is withheld. Warning signs: write endpoints that accept form encodings; state changes arriving with Sec-Fetch-Site: cross-site. Break the chain: SameSite cookies plus a server-side check on every write.

Pattern 6 · The confused cache

One requester's answer is served to another

What happens. A cache that doesn't know the response depends on who asked hands one requester's permission, or one user's data, to the next. Warning signs: CORS errors that come and go; personalized responses served with public cache headers. Break the chain: Vary: Origin on every dynamic CORS response, and private or no-store caching for anything personal (Chapter 17).

Pattern 7 · The inside-out request

A public page reaches into the user's own network

What happens. Devices and helpers that trust “anyone on my network” receive requests from web pages, because the browser is on that network. Warning signs: local services with no authentication; requests with unexpected Host headers. Break the chain: the practices in Chapter 18.

Being prepared: detect, respond, learn

A prepared team knows what an attempt looks like in its logs and what to do in the first hour. Most of these signals are already in your access logs.

Signals worth alerting on

SignalWhere to lookWhat it may mean
A credentialed response names an origin that isn't on your listResponse logging, API gatewayA reflecting or loosely matched policy (patterns 1, 2). Should be impossible; treat as an incident.
Unfamiliar Origin values on authenticated endpointsAccess logsSomeone probing your policy, or an integration nobody documented.
Origin: null on API trafficAccess logsSandboxed or local documents calling you (pattern 4).
State changes with Sec-Fetch-Site: cross-siteAccess logs, WAFPossible forged writes (pattern 5).
Unexpected Host headers on local or internal servicesService logsPossible DNS rebinding (pattern 7).
Subdomains pointing at deleted cloud resourcesDNS inventoryA trusted origin waiting to be claimed (pattern 3).

The first hour of a CORS incident

  1. Contain. Replace the faulty rule with an exact allowlist, or temporarily remove Allow-Credentials, and deploy. This is usually a one-line configuration change.
  2. Purge. Clear CDN and proxy caches that may hold responses with the old headers.
  3. Scope. Search logs for credentialed requests whose Origin was not on the approved list: which origins, which endpoints, which users, over what period.
  4. Protect users. If personal data may have been read, invalidate the affected sessions and follow your notification obligations.
  5. Prevent recurrence. Add the offending origin pattern to your CORS test suite (Chapter 20) so the same mistake fails a build next time.
The preparation that matters most. An inventory of every service's CORS policy, an owner for every allowed origin, and automated tests that fail on anything broader. Teams that have these three rarely need the incident checklist above.

Chapter 15

Case studies from the real world

These are public incidents and published research, summarized from the original disclosures. Each one is told for its lesson: what the system trusted, why that trust was misplaced, and what fixed it.

Research · October 2016 · OWASP AppSec USA

“Exploiting CORS Misconfigurations for Bitcoins and Bounties”

James Kettle of PortSwigger surveyed how real websites validated the Origin header and found that many used simple string operations — reflection, prefix and suffix checks — rather than exact comparison. Among the findings he described were cryptocurrency exchanges whose CORS policies could have let another website read sensitive account data from signed-in users; the issues were reported to the affected organizations. The talk also showed how CORS mistakes combine with other bugs, such as cache behavior and trusted-but-vulnerable subdomains.

Lesson: the way you compare origins is security-critical. The most common bugs were not exotic; they were convenient string checks (Chapter 13, mistakes 1 and 2).
Research · August 2018 · USENIX Security Symposium

“We Still Don't Have Secure Cross-Domain Requests: an Empirical Study of CORS”

Jianjun Chen and colleagues measured CORS deployments across a large set of popular websites. They found insecure misconfigurations to be common, identified weaknesses in how CORS interacts with other web mechanisms, and noted that many sites whose policies varied by origin failed to send Vary: Origin. The authors released an open-source scanner, CORScanner, and proposed clarifications, some of which were incorporated into the specification.

Lesson: CORS mistakes are not rare accidents but a systematic pattern, driven by an inexpressive policy language and poor developer understanding. Treat CORS as something to test, not assume.
Web security history · October 2005

The Samy worm

A cross-site scripting flaw on MySpace let a user named Samy Kamkar put a script in a profile page. Anyone who viewed the profile ran the script, which added Samy as a friend and copied itself to the viewer's own profile. It reached over a million profiles in about a day, and MySpace went offline to clean it up.

Lesson for CORS: the same-origin policy only separates origins; it cannot protect an origin from script running inside it. Every origin on your CORS allowlist extends its trust to your API, so each one must be defended against script injection — a bug on a trusted origin is a bug in your API's security.

Vulnerability · July 2019 · CVE-2019-13450

A video-conferencing app's localhost web server

Security researcher Jonathan Leitschuh disclosed that the Zoom client for macOS installed a local web server, listening on localhost port 19421, so that websites could launch meetings with one click. Any website could send it requests, and it could join a user to a meeting — with video on in some configurations — without meaningful confirmation. Because CORS prevented pages from reading the server's responses, the app reportedly signaled results through the dimensions of an image instead. The server also remained installed after the app was removed. Zoom shipped updates removing the server, and Apple pushed a silent macOS update to remove it from affected machines.

Lesson: a local service is reachable from every web page the user opens. CORS only limits reading; requests still arrive and actions still happen. Local services need explicit user confirmation and real authentication, not reliance on being “only on localhost” (Chapter 18).
Vulnerability · January 2018 · CVE-2018-5702

A BitTorrent client's control interface and DNS rebinding

Tavis Ormandy of Google Project Zero reported that the Transmission BitTorrent client's daemon, which accepted JSON-RPC requests on a local port, could be reached through a DNS rebinding attack: a hostname that first resolves to an attacker's server and later to 127.0.0.1, so the browser believes it is still talking to the same origin. The fix added a check on the HTTP Host header, so that the daemon only answers requests addressed to names it expects.

Lesson: the same-origin policy is based on names, and DNS can change what a name points to. Services on local or private addresses must validate the Host header and require authentication. Chapter 18 shows how browsers have since added their own protections.

Chapter 16

CORS is not CSRF protection

CORS decides who may read a response. Cross-site request forgery is about requests that change something. Confusing the two leaves real holes.

The gap, stated plainly

Simple requests (Chapter 7) reach the server before any CORS check, often with the user's cookies. If one moves money or deletes a record, the server does it; the browser then hides the response, but the damage is done. That is cross-site request forgery (CSRF), and no CORS header prevents it.

Defenses that do protect state-changing endpoints

DefenseHow it works
SameSite cookiesLax or Strict keeps the session cookie off cross-site requests. A strong default, but it is about sites, so sibling subdomains are not separated.
Anti-CSRF tokensA secret per-session value in the server's own pages, required on every state change. Other sites cannot read it, so they cannot include it.
Require a non-simple requestAccept state changes only as strictly checked application/json or with a custom header. Forms cannot send those, and scripts must pass your preflight.
Check Origin on writesReject state-changing requests whose Origin is present and not on your list. Cheap, and effective against browser-based forgery.
Fetch MetadataModern browsers send Sec-Fetch-Site (same-origin, same-site, cross-site, none). A server can refuse cross-site requests to sensitive endpoints outright (Chapter 19).
Layer them. Use SameSite cookies and at least one server-side check on every state-changing endpoint.
