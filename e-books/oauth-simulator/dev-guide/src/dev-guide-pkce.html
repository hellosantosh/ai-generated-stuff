PKCE, from the Beginning3
Chapter 01

The handoff

Before PKCE can make sense, one thing has to: what is actually happening when an app says “Sign in with …” and a different website appears.

You install a photo-printing app. It wants the photos in your cloud drive. There are two ways it could get them, and only one of them is sane.

The first way is to ask for your cloud password and log in as you. This is a disaster for reasons that are easy to list once you start: the app now has access to everything, not just photos; the only way to take that access back is to change your password, which breaks every other app at the same time; the cloud provider cannot tell the app's requests from yours, so nothing can be audited; and your two-factor authentication has nowhere to fit.

The second way is the one the whole industry settled on. The app never sees your password. Instead you are sent to the cloud provider, you log in there, you are asked whether this app may read your photos, and if you agree the provider hands the app a token — a narrow, expiring credential that permits exactly that and nothing else. That arrangement is called delegated authorization, and OAuth is the protocol that performs it.

The valet key. Some cars come with a second key that opens the door and starts the engine but will not open the boot and limits the car to 30 miles an hour. You hand it to someone you trust a little, for one job, and you can have it back. A token is a valet key. Your password is the key to the house.

The four parties

Every OAuth conversation has the same cast. Learning the names now makes the rest of this book shorter.

NameIn our exampleWhat it does
Resource ownerYouOwns the data and is the only one who can agree to share it.
ClientThe printing appWants the data. Confusingly, “client” means the application, not you.
Authorization serverYour cloud provider's loginAuthenticates you, asks your consent, and issues tokens.
Resource serverThe cloud photo APIHolds the photos and accepts the token as permission to serve them.

Two of those often live at the same company but they are separate jobs, and keeping them separate in your head matters later: the authorization server is the only party that ever sees your password, and the resource server is the only party that ever sees your photos.

Chapter 01 · continued

What the handoff looks like

The app cannot simply ask the authorization server for a token, because the authorization server has no idea who you are until you have logged in — and you must log in somewhere the app cannot watch you type. So the app steps aside. It sends your browser to the authorization server, and waits.

Notice what arrives at step 5. Not a token — a code. The app is not trusted with a token just because a browser turned up carrying something. It has to perform one more step, in private, to trade that code for the real credential. The next chapter looks at why the protocol is built that way.

One word is worth being precise about. When we say the app “redirects your browser”, nothing clever is happening: the app returns an ordinary HTTP redirect, or opens a URL, and the browser goes there. Everything the app wants the authorization server to know is simply part of that URL — and everything on arrows 2 to 5 is therefore a URL that you, your browser, your operating system, and any software installed alongside them can read.

Chapter 02

The authorization code

A short string that is worth a token. Understanding why the protocol bothers with it is the last thing you need before the attack makes sense.

At step 5 the browser came back to the app carrying something like this:

// the browser lands back on the app's redirect URI
com.printingapp://callback?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj

That code is the authorization code. It has four properties worth committing to memory, because every one of them exists for a reason:

Short-livedTypically valid for 30 to 60 seconds. It is meant to be used immediately.
Single useThe server marks it spent the first time it is redeemed. A second attempt fails — and a good server also revokes any token it already issued for that code, on the assumption that two parties are fighting over it.
Bound to one clientIt was issued for a particular client_id and redirect URI.
Not a credentialOn its own it opens nothing. It has to be exchanged.

Why not just send the token?

An older version of OAuth did exactly that: the authorization server put the access token straight into the redirect URL. It was called the implicit flow, and OAuth 2.1 removes it. The reason is the one thing you now know about arrows 2 to 5: they are URLs.

A URL is written into browser history. It is sent in the Referer header to whatever the page loads next. It is logged by proxies, by the browser's own diagnostics, and by any extension with permission to read tabs. Putting a token that is valid for an hour into a URL means putting it into all of those places.

The authorization code exists so that the valuable thing — the token — never travels that way. The code goes through the browser; the token comes back over a direct, private connection from the app to the server. Even if the code leaks into a log, it expires in under a minute and can only be spent once.

This is good design. The code is deliberately a low-value, fast-expiring bearer of a one-time right, precisely so that the channel that cannot be kept private carries as little value as possible.

So where is the problem?

Everything above is sound — as long as one assumption holds. The server hands the token to whoever turns up with a valid code, so the whole design rests on the code reaching only the app that started the flow.

On a web server that assumption is reasonable. On a phone, or in a single-page app, it turns out not to be. That is the subject of the next chapter.

Chapter 02 · The authorization code6
Chapter 03

How the code gets stolen

The authorization code has to be delivered back to the app somehow. On a phone, “somehow” turns out to be a door that more than one app can stand behind.

A website's redirect URI is a URL: https://app.example.com/callback. The browser resolves that name through DNS and TLS, so it is genuinely hard for another party to receive it.

A mobile app has no domain name. For years the way an app said “send the browser back to me” was to register a custom URL scheme with the operating system:

// the printing app claims this scheme at install time
com.printingapp://callback

When the browser is told to go to a com.printingapp:// address, the operating system looks up which installed app claimed that scheme and hands it over. Here is the problem, and it is embarrassingly simple: on classic custom schemes, nothing stops a second app from claiming the same one. There is no registry, no proof of ownership, and no check. An attacker publishes a free wallpaper app that quietly declares com.printingapp in its manifest, and waits.

What happens when two apps claim one scheme is platform-specific and, from a security point of view, all of the answers are bad: the system may pick the one installed first, or last, or show the user a chooser they will not understand. The attacker does not need to win every time. Winning sometimes is enough.

This is not theoretical. Authorization code interception through custom-scheme collision is the attack RFC 7636 was written to stop. Its abstract says so in the first sentence. Every mitigation in this book exists because this worked.

Other doors into the same room

The custom-scheme collision is the classic case, but the code is exposed anywhere the redirect is visible:

  • A malicious or compromised browser extension that can read tab URLs.
  • An open redirector on the client's own domain, which lets an attacker bounce the code to a site they control.
  • Referer leakage, where the callback page loads a third-party script and the browser helpfully sends the full URL along.
  • Shoulder-level logging: proxies, crash reporters, analytics tools and server access logs that record full URLs by default.
  • On a shared or infected device, anything reading browser history.

Notice that none of these require breaking TLS or guessing a secret. They require only being somewhere the URL passes.

Chapter 03 · How the code gets stolen7
Chapter 03 · continued

The theft, step by step

Follow the code. Everything up to step 4 is the normal, correct flow — which is exactly what makes this attack unpleasant. Nothing has gone wrong yet at the point where everything goes wrong.

Step 7 is the one to sit with. The server is behaving correctly by its own rules. It received a code it issued minutes ago, unexpired and unspent, for a registered client, and it did what the specification says: it returned a token. The server cannot distinguish the thief from the app, because the code is the only evidence it has.

Why the operating system cannot help

It is natural to ask why the phone does not simply refuse to give the redirect to an app that does not own the scheme. The answer is that, with a classic custom scheme, it has nothing to check against.

Redirect mechanismCan the platform verify the claim?
https:// (web)Yes. DNS and TLS prove who owns the domain.
Custom schemeNo. The string is declared in a manifest. Nothing anywhere states who is entitled to it.
App Links (Android)
Universal Links (iOS)		Yes. The app declares a domain, and the platform fetches a file from that domain to confirm the association before honoring the link.

Verified links are the right long-term answer, and worth adopting. But they are a platform feature: they need a domain, a published association file, a recent OS, and an app installed from a store. PKCE needs none of those and does not depend on the attacker's environment being well behaved — which is why it is the mandatory part.

Chapter 03 · How the code gets stolen8
Chapter 04

Why a client secret will not save you

There is an obvious objection: make the app prove who it is when it redeems the code. It is a good instinct, and for a whole class of application it is impossible.

Web applications already do this. When a server-side app exchanges a code it also sends a client secret, issued at registration. The thief in the last chapter has the code but not the secret, so step 6 fails. Problem solved — for a server. For anything the user installs or downloads, no, because of a distinction OAuth draws at the start.

Client typeDefinition, and what it means in practice
ConfidentialCan keep a secret, because the secret lives on a machine the developer controls. A server-side web app, a backend service, a daemon.
PublicCannot keep a secret. The whole application is in the user's hands. A mobile app, a desktop app, a single-page app, a CLI tool.

“Cannot” is a strong word. Is it really?

It really is. Put a secret in a mobile app and it ships inside the binary. Anyone can download that binary from the store, and the tools to look inside it are free, standard and a single command:

# pull the strings out of an app bundle — no skill required
$ unzip -q PrintingApp.ipa -d x && strings x/Payload/PrintingApp.app/PrintingApp \
    | grep -iE 'secret|client_id'
client_secret=7Fd2c9Ab...      ← there it is

A single-page application is worse still: its “secret” is served to the browser as JavaScript, one View Source away. Obfuscation changes nothing. The secret must be present for the app to use it, so it is present for the attacker too. It is not a secret; it is a slightly inconvenient constant.

What we actually need

So the requirement is sharper than “prove who you are”. A public client cannot prove who it is, because any proof it carries can be copied out of it before the flow even starts. What it can do is prove something narrower:

Prove that the party redeeming this code is the same party that requested it — without shipping any long-lived secret at all.

That is a much smaller claim, and it has a neat solution: instead of using a secret the developer baked in, the app invents a fresh secret for every single login. Nothing is shipped, so nothing can be extracted. That idea is PKCE, and Part II is about how four lines of arithmetic turn it into a working proof.

Chapter 04 · Why a client secret will not save you9
Chapter 05

The idea

PKCE is one sentence long. Everything else — the parameter names, the hashing, the base64 — is mechanics in service of that sentence.

Before starting a login, the app invents a random secret. It sends a one-way fingerprint of that secret with the authorization request, and the secret itself with the token request. The server checks that they match.

The name is an acronym: Proof Key for Code Exchange. It is said “pixy”. The “proof key” is the random secret; the “code exchange” is step 6, the moment the code becomes a token. PKCE attaches a proof to that exchange.

Follow what that buys us against the thief in Chapter 3. The fingerprint went out in the authorization URL, so the attacker may well have seen it. The code came back through the redirect, so the attacker has that too. But the secret itself never went anywhere near the browser — it stayed in the app's memory the entire time. Without it, the code the attacker stole cannot be redeemed.

Chapter 05 · The idea10
Chapter 06

The three parameters

PKCE adds two parameters to the authorization request and one to the token request. That is the entire protocol change.

ParameterSent inWhat it is
code_verifiertoken request The secret. A high-entropy random string, 43 to 128 characters, from the set A–Z a–z 0–9 - . _ ~. Generated fresh for every authorization attempt and never reused.
code_challengeauthorization request The fingerprint. With S256, the base64url encoding of the SHA-256 hash of the verifier.
code_challenge_methodauthorization request How the challenge was derived: S256 or plain. Always send S256. Chapter 10 explains why the other one is a trap.

The rules, precisely

Length and alphabet

The verifier must be at least 43 and at most 128 characters, drawn from the unreserved URL characters. The lower bound is not arbitrary: 43 base64url characters carry 256 bits of entropy, which is the point. The alphabet is chosen so the value survives being placed in a URL or a form body without any escaping.

43 characters, not 43 bytes. The usual mistake is to generate 43 random bytes and base64url-encode them, producing a 58-character verifier. That is perfectly legal and slightly stronger than required. The mistake that bites is the reverse: generating 32 bytes, encoding them to 43 characters, and then assuming the bytes are the verifier. The verifier is the text you produced, and it is that text you must hash and that text you must send later.

The derivation

// S256 — the only method you should use
code_challenge = BASE64URL-ENCODE( SHA256( ASCII( code_verifier ) ) )

// plain — permitted by the RFC, and a bad idea (chapter 10)
code_challenge = code_verifier

Three details hide in that one line, and each of them is a source of bugs:

  • Hash the characters, not a decoding of them. SHA-256 runs over the ASCII bytes of the verifier string exactly as you will later transmit it.
  • The hash is 32 raw bytes. Hash them, do not hex-encode them first. A hex string base64s to 64 characters, and a 64-character challenge is the classic symptom of this bug — the correct length is 43.
  • base64url, without padding. That means - and _ instead of + and /, and no trailing =. Chapter 8 shows what that means concretely.

What the server does

The server's side is three lines of logic, and it is worth knowing them because every error message you will meet comes from one of them:

  1. At the authorization request: store code_challenge and code_challenge_method alongside the code it is about to issue.
  2. At the token request: take the code_verifier the app sent, apply the stored method to it, and compare the result to the stored challenge.
  3. Equal, and the code is valid and unspent? Issue the token. Otherwise refuse, and do not say why in any detail.

Step 1 — the app invents a secret

The app generates 43 random bytes and base64url-encodes them. Count the result: it is 58 characters, not 43. That is the distinction from the last chapter — the RFC's minimum of 43 is a count of characters, and 43 bytes of randomness comfortably exceeds it.

M25iVXpKU3puUjFaYWg3T1NDTDQtcW1ROUY5YXlwalNoc0hhakxifmZHag

Step 2 — the app derives the fingerprint

SHA-256 over the ASCII of that string, base64url-encoded, unpadded.

// code_challenge — 43 characters, safe to publish
qjrzSW9gMiUgpUvqgEPE4_-8swvyCtfOVvg55o5S_es

Step 3 — the authorization request

The app opens this URL in the system browser. The two PKCE parameters are the last two.

GET https://login.example.com/authorize
  ?response_type=code
  &client_id=printing-app

You log in and consent. The server stores the challenge and the method against the code it is about to mint.

HTTP/1.1 302 Found

The app checks that state is the value it sent, then proceeds. Note what is not in this URL: the verifier. It has not left the app.

Chapter 08

Why a hash, and what base64url is

Two pieces of machinery that everything above depends on, explained for someone who has not met either.

A one-way function

SHA-256 takes any input and produces 32 bytes. It has one property that makes PKCE work: computing the output from the input is instant, and computing the input from the output is, as far as anyone knows, impossible.

Watch how completely the output changes when the input barely does:

// one character different
SHA256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e7304…
SHA256("hellp") = fdd7585e08c4e2afd71dcabdb4636c89d557a3f42db9e2040c8b…

There is no partial credit and no gradient to climb. An attacker holding a challenge has no better strategy than guessing verifiers and hashing each one, and the verifier has at least 256 bits of entropy. The number of guesses required is not large; it is unreachable — more operations than there are atoms available to perform them.

This is why the challenge is safe in a URL. Publishing the fingerprint gives an attacker nothing they can use, because the only way back to the secret is through a door that does not exist.

Why not send the secret both times?

A fair question. If the app sent the same random string in the authorization request and again in the token request, the server could compare them directly — no hashing at all. That is exactly what plain does, and it is broken for one reason: the authorization request travels through the browser. An attacker who can read the redirect can read the authorization URL too. They would capture the secret on its way out, and use it on the way back.

The hash exists so that the thing sent through the untrusted channel is not the thing needed to redeem the code.

Chapter 08 · continued

base64url, concretely

Hashes are raw bytes, most of which are not printable characters. base64 is the standard way to write arbitrary bytes as text: it takes three bytes at a time and emits four characters from a 64-character alphabet.

Ordinary base64 uses + and / as its last two characters and pads the end with =. All three are hostile inside a URL: + means a space in a form body, / is a path separator, and = separates a parameter from its value. base64url is the same encoding with those three problems removed.

Characterbase64base64url
62nd+-
63rd/_
padding= (kept)= (removed entirely)
 
// the same 32 bytes, both ways
base64     qjrzSW9gMiUgpUvqgEPE4/+8swvyCtfOVvg55o5S/es=
base64url  qjrzSW9gMiUgpUvqgEPE4_-8swvyCtfOVvg55o5S_es
                                ^^                 ^  ← and no trailing =

Three bytes in, four characters out

base64 works in blocks. It takes 24 bits — three bytes — and re-cuts them into four groups of six bits, because a 6-bit number has 64 possible values, one per character of the alphabet.

// the three bytes 0xAA 0x3B 0xF3
bytes    10101010  00111011  11110011
regroup  101010 100011 101111 110011
value        42     35     47     51
base64        q      j      v      z

Since three bytes always become four characters, a 32-byte hash is not a multiple of three: 32 bytes is ten full blocks with two bytes left over. Those two bytes produce three characters, giving 43 in total. Standard base64 then adds one = to round the final block up to four; base64url drops it. That is the whole reason the number 43 keeps appearing in this book.

Getting it wrong, and how you will know

Almost every PKCE bug a beginner hits is an encoding bug, and each has a distinctive fingerprint. Learn to read the length of a challenge and you can diagnose most of them at a glance.

LengthWhat you producedThe mistake
43base64url of 32 raw bytesCorrect. This is what a valid S256 challenge always looks like.
44base64 with padding keptYou left the trailing = on. Strip it.
64base64url of a 64-character hex stringYou hex-encoded the hash before base64ing it. Hash to bytes, then encode the bytes.
58the verifier itselfYou sent the verifier as the challenge — that is plain, while claiming S256. It will fail.
86base64url of a SHA-512 hashWrong algorithm. S256 means SHA-256, always.
The one that is hardest to see. If your challenge contains a +, a / or an =, you used standard base64. It may even work in testing, because some servers tolerate URL-encoded forms of those characters — and then fail in production behind a proxy that normalizes them differently. The character set is part of the specification, not a formatting preference.

A note on randomness

The verifier must come from a cryptographically secure random source. The distinction matters more than it sounds:

Do not useUse
Math.random()crypto.getRandomValues()
random.random()secrets.token_urlsafe()
new Random()SecureRandom
rand()/dev/urandom, arc4random_buf()

An ordinary random number generator is built to be fast and statistically even, not unpredictable. Given a few of its outputs, its internal state — and therefore every future output — can often be reconstructed. An attacker who can predict your next verifier does not need to steal it.

Do not derive the verifier from anything else either: not the time, not a session identifier, not a hash of the user's name. It has exactly one job, which is to be unguessable.

Chapter 09

The attack, defeated

The same thief, the same stolen code, the same server. One field has been added to the token request, and the theft is now worth nothing.

Run Chapter 3 again with PKCE in place. Steps 1 to 5 are unchanged — the attacker still wins the race for the custom scheme and still ends up holding a perfectly valid authorization code. The difference is entirely in what happens next.

Worth saying plainly. PKCE is not a lock on the door the code came through. It is the rule that the code is only redeemable by whoever knows a secret that never went through that door at all.
Chapter 09 · The attack, defeated18
Chapter 10

plain, S256, and the downgrade

RFC 7636 defines two methods. Only one of them is worth using, and the existence of the other creates an attack of its own.

What plain does

// plain: the challenge IS the verifier
code_challenge = code_verifier
code_challenge_method = plain

Now re-read Chapter 3. The attacker who can intercept the redirect can almost always also observe the authorization request — they are the same channel, often the same URL bar, the same history file, the same proxy log. With plain, that request contains the verifier in clear text. The attacker copies it, waits for the code, and redeems both together.

plain restores the original attack. It satisfies the letter of “we implemented PKCE” while removing the property that made PKCE work. The RFC itself says clients must use S256 if they can, and that they can unless the platform genuinely has no SHA-256 — a condition that has not meaningfully existed for years.

So why is it in the specification?

RFC 7636 was published in 2015, when it was still plausible that some constrained device had no SHA-256 available. plain was the concession that let such a client participate at all, on the reasoning that a weak binding is better than none: it still defeats an attacker who sees the redirect but not the original request.

That reasoning has not aged well, because the two are usually the same channel. Current guidance is unambiguous — the OAuth 2.1 draft and RFC 9700 both expect S256, and a server built today has no reason to offer the alternative.

Chapter 10 · continued

The downgrade attack

Here is the subtler problem, and it is a server bug rather than a client one. Suppose an app correctly sends S256. An attacker intercepts the authorization request, and rewrites two parameters before it reaches the server:

// what the app sent
code_challenge=qjrzSW9gMiUgpUvqgEPE4_-8swvyCtfOVvg55o5S_es&code_challenge_method=S256

// what the attacker rewrites it to
code_challenge=attacker-picked-value&code_challenge_method=plain

The server now stores the attacker's own value with the method plain. When the attacker later presents code_verifier=attacker-picked-value, it matches perfectly — and the real app's carefully generated secret was never involved.

How a server must prevent it

  • Support only S256, and reject plain outright. This is what the OAuth 2.1 draft expects of a new server, and it closes the hole completely.
  • If plain must be supported for a legacy client, record per client whether it is permitted, and refuse a downgrade for any client that has ever used S256.
  • Reject a token request with no code_verifier when a challenge was stored. Silently ignoring the missing field is the same bug wearing a different hat: the attacker just omits the parameter.

How a client can tell

An authorization server publishes what it supports in its discovery document. Look for this before you trust it:

GET /.well-known/oauth-authorization-server

{
  "code_challenge_methods_supported": ["S256"]      ← good
  "code_challenge_methods_supported": ["plain", "S256"]   ← usable, but ask why
  // field absent entirely → the server may not support PKCE at all
}

Chapter 11

Generate the pair

The whole of PKCE on the client side is these few lines. Each example produces a 58-character verifier and its 43-character challenge.

At a shell prompt

Useful for poking at a server by hand, and the quickest way to convince yourself the arithmetic is nothing special.

# generate a verifier, then derive its challenge
VERIFIER=$(openssl rand -base64 43 | tr '+/' '-_' | tr -d '=\n')
CHALLENGE=$(printf %s "$VERIFIER" | openssl dgst -binary -sha256 \
            | openssl base64 | tr '+/' '-_' | tr -d '=\n')

echo "verifier  ${#VERIFIER}"    # 58
echo "challenge ${#CHALLENGE}"   # 43
Note printf %s, not echo. echo appends a newline, and hashing that newline gives a different, wrong challenge. This single byte is one of the most common sources of invalid_grant when testing by hand.

JavaScript — Node 16 and later

import { randomBytes, createHash } from "node:crypto";

const b64url = (buf) => buf.toString("base64url");

const verifier  = b64url(randomBytes(43));
const challenge = b64url(createHash("sha256").update(verifier).digest());

JavaScript — the browser

There is no base64url convenience in the browser, so the conversion is explicit. crypto.subtle is asynchronous and is only available on a secure origin.

const b64url = (bytes) =>
  btoa(String.fromCharCode(...new Uint8Array(bytes)))
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");

const verifier = b64url(crypto.getRandomValues(new Uint8Array(43)));
const digest   = await crypto.subtle.digest(
                   "SHA-256", new TextEncoder().encode(verifier));
const challenge = b64url(digest);

sessionStorage.setItem("pkce_verifier", verifier);  // survives the redirect

Build the authorization request

Where the challenge goes, what every other parameter is for, and the two values you must keep hold of while the browser is away.

// the URL you open in the system browser (line-broken for reading only)
https://login.example.com/authorize
  ?response_type=code
  &client_id=printing-app
  &redirect_uri=com.printingapp%3A%2F%2Fcallback
  &scope=photos.read
  &state=af0ifjsldkj

ParameterWhat it is for
response_type=codeAsks for the authorization code flow. In OAuth 2.1 this is effectively the only value you should ever send.
client_idWhich application is asking. Public, not secret.
redirect_uriWhere to send the browser afterwards. Must exactly match one the server has pre-registered, character for character. URL-encode it.
scopeWhat you are asking permission for. Ask for the least you need.
stateRandom, per-request. Protects against a different attack; Chapter 16.
code_challengeThe fingerprint. 43 characters for S256.
code_challenge_methodAlways S256.

Two things to keep, and where

While the browser is away, the app must remember the verifier and the state; losing either means the login cannot be completed. A mobile app keeps them in memory, a single-page app in sessionStorage, and a server-side web app in the user's session.

Not localStorage, and not a cookie you can read from JavaScript. localStorage persists indefinitely and is shared across every tab on the origin, so a verifier left there outlives the login it belonged to. Use sessionStorage, and delete the value the moment the token request returns.

Opening the browser

Do not open this URL inside an embedded web view you control. A web view is a window the app can read — including the password the user types into it — which gives back exactly the property OAuth existed to remove. Use the platform's in-app browser tab API instead: ASWebAuthenticationSession on iOS, Custom Tabs on Android. They render the real browser, with its real address bar and its real cookie jar.

Chapter 14

Break it on purpose

The fastest way to trust a security control is to watch it refuse. Four deliberate failures, and the exact response each one produces.

Run these against any conformant server, or the simulator in the next chapter. Start from a working flow, then change one thing.

1 — The wrong verifier

Complete the flow normally, but send a verifier you made up.

-d "code_verifier=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"

HTTP/1.1 400 Bad Request
{ "error": "invalid_grant",
  "error_description": "PKCE verification failed" }

This is the attack from Chapter 3, failing. The attacker is in exactly this position: a valid code, and no verifier.

2 — No verifier at all

Omit code_verifier entirely. A server that lets this through has the bug from Chapter 10 — an attacker would simply leave the field out.

HTTP/1.1 400 Bad Request
{ "error": "invalid_grant",
  "error_description": "code_verifier required" }

3 — The code used twice

Exchange a code successfully, then exchange the same code again with the same, correct verifier.

HTTP/1.1 400 Bad Request
{ "error": "invalid_grant",
  "error_description": "authorization code already used" }

A good server also revokes the tokens it issued the first time: two parties redeeming one code means one is a thief, and the server cannot tell which.

4 — The challenge that is really the verifier

Send code_challenge_method=S256 but put the raw verifier in code_challenge. The commonest beginner bug, and it fails one step later than you expect: the authorization request succeeds, the token request does not.

HTTP/1.1 400 Bad Request
{ "error": "invalid_grant",
  "error_description": "PKCE verification failed" }

Chapter 14 · continued

Reading the error you actually got

Every PKCE failure comes back as invalid_grant: the server will not help an attacker narrow things down. That makes error_description your only clue, and some servers offer none. This is the decision tree to run in your head.

What you observeAlmost always
Fails every time, from the first attempt A derivation bug. Check the challenge is 43 characters (Chapter 8) and compare against the fixed vector.
Works in curl, fails in the app The app is hashing something different from what it sends — usually a trailing newline, or bytes where the text was meant.
Works on the first login, fails on later ones The verifier is being reused or cached. Generate a new one per attempt.
Works for one user, fails when two log in at once The verifier is stored somewhere shared — a module-level variable, a singleton, a global. It belongs to the attempt, not the process.
Intermittent, especially on mobile The app was suspended during the browser step and lost the verifier from memory. Persist it for the duration of the flow.
invalid_request, not invalid_grant Not PKCE. Usually a redirect_uri mismatch or a missing parameter.
Everything is correct and it still fails Log the challenge your app sent and the challenge derived from the verifier it later sent, and compare them character by character. They differ; the question is only where.
A debugging trick worth knowing. Temporarily hard-code the verifier and challenge from Chapter 7 in your client. If the flow then succeeds, your generation code is the problem. If it still fails, your transmission is — something between your variable and the wire is altering the value.

Chapter 16

PKCE, state and nonce

Three random values in one flow, doing three unrelated jobs. Confusing them is the most common conceptual mistake in OAuth, and it leads people to skip one.

ParameterAnswers the questionProtects against
code_verifier
code_challenge		 Is the app redeeming this code the app that requested it? Authorization code interception. Checked by the authorization server, at the token endpoint.
state Did this response come back to a request I actually made? Cross-site request forgery on the redirect — an attacker tricking your browser into completing their login, so your app ends up holding a token for the attacker's account. Checked by the client.
nonce Was this ID token minted for this particular login? ID token replay. An OpenID Connect concept, not an OAuth one. Checked by the client, inside the ID token.

Why you need more than one

The tempting conclusion is that PKCE, being the strongest, makes the others redundant. It does not, because they defend different directions.

  • PKCE protects the server from issuing a token to the wrong app. It says nothing about whether the user at the browser is the user who started the flow.
  • state protects the user from being logged into someone else's account. An attacker starts a login with their own credentials, captures the redirect containing their code, and feeds that URL to your browser. With PKCE alone, your app holds a valid verifier, redeems the attacker's code successfully, and now stores your photos in the attacker's account. state is what makes your app notice that it never started this flow.
  • nonce protects the identity claim. PKCE secures the code; it does not bind an ID token to a login.
Both, always. The RFCs and the current security best-practice document are explicit: PKCE does not replace state. Generate both, from the same secure random source, per attempt. If you are doing OpenID Connect and asking for an ID token, generate a nonce as well.

Do not reuse one value for two jobs

It is occasionally suggested that state can be derived from the verifier, or that the challenge can serve as the state. Do not. state comes back through the browser in clear text, so anything derived from it is public — and the verifier's entire value is that it is not.

Chapter 17

The mistakes beginners make

Ten of them, in roughly the order you are likely to meet them. Most cost an afternoon; two of them cost the security property entirely.

1  Hashing the wrong thing

Hashing raw random bytes instead of the verifier text. The authorization request then carries a challenge that has nothing to do with the string you later send. symptom fails every time, from the very first attempt.

2  Standard base64 instead of base64url

+, / and = in a challenge. symptom works locally, fails behind a proxy, or fails only for roughly one attempt in four — whenever the hash happens to contain one of those characters.

3  The trailing newline

echo instead of printf %s in a shell script; a text editor adding a final newline to a fixture file. symptom consistently wrong challenge with obviously correct code.

4  Reusing the verifier

Generating it once at start-up rather than once per login. security a leaked verifier then compromises every future login, not one. symptom often none — it keeps working, which is what makes it dangerous.

5  Storing the verifier somewhere shared

A module-level variable, a singleton, a global. Two concurrent logins overwrite each other. symptom works in development, fails under load, fails when the user opens two tabs.

6  Losing the verifier across the redirect

Keeping it only in memory in a single-page app, so a full page load wipes it; or on mobile, the app being suspended while the browser is in front. symptom intermittent, and worse on slow networks and older phones.

Chapter 17 · The mistakes beginners make30
Chapter 17 · continued

7  Using plain because it worked first

It is easier to get right, so it is what people reach for when debugging — and then it stays. security restores the original attack in full (Chapter 10). symptom none whatsoever.

8  Sending the verifier in the authorization request

Adding code_verifier to the URL “so the server has it”. security publishes the secret in the one channel it must never travel in. symptom the flow works perfectly, which is precisely the problem.

9  An ordinary random number generator

Math.random(), random.random(), new Random(). security a predictable verifier is not a secret. symptom none. This one is only ever found by reading the code.

10  Assuming the server checks

Sending a challenge and trusting that it is enforced. Some servers accept the parameter and never verify it, and some accept a token request with the verifier omitted. symptom Chapter 14, tests 1 and 2, pass when they should fail.

Test for number 10 before you ship. Send a deliberately wrong verifier, and then no verifier at all. If either is accepted, you do not have PKCE — you have a parameter. This is a five-minute test and it is the only one that checks the property you actually care about.

The two that are not bugs

Two things look like mistakes and are not, so that you do not go looking for them:

  • The challenge appears in logs and browser history. That is expected and safe. It is a hash, and Chapter 8 explains why publishing it costs nothing.
  • The verifier is longer than the challenge. Also expected. The challenge is a 43-character hash; the verifier is whatever length you generated, commonly 58.

Chapter 18

What PKCE does not do

Knowing a control's limits is part of using it. PKCE is narrow on purpose, and several things people expect of it belong to someone else.

It does not…Which means
Authenticate the user PKCE says nothing about who is at the keyboard. That is the authorization server's login, and if your app needs to know who the user is, that is OpenID Connect and an ID token.
Authenticate the client It proves the redeemer started the flow, not that it is the genuine app. A malicious app can run its own complete PKCE flow perfectly well — with its own verifier, and the user's explicit consent on screen.
Protect the access token Once issued, the token is a bearer credential: whoever holds it can use it. PKCE protects the exchange, not what comes out of it. Binding a token to a client key is a separate mechanism (DPoP, or mTLS).
Stop a malicious app being installed Scheme hijacking is still possible; PKCE only makes the stolen code worthless. Preventing the interception itself needs verified redirects — App Links on Android, Universal Links on iOS — which are worth adopting as well.
Replace state Different attack, different direction, different checker. Chapter 16.
Help if the server does not enforce it It is a two-party protocol. A client doing PKCE perfectly against a server that ignores it has achieved nothing at all.

What to add alongside it

  • Exact redirect URI matching on the server — no wildcards, no prefix matching. A sloppy match is an open redirector by another name.
  • Verified redirects on mobile: App Links and Universal Links prove domain ownership, so the collision in Chapter 3 cannot happen in the first place.
  • Short code lifetimes and one-time use, with token revocation on reuse.
  • Refresh token rotation, so a stolen refresh token is detected on second use.
  • A real browser, never an embedded web view (Chapter 12).

Each of those has a chapter in the companion volume; this book stops at the boundary of PKCE on purpose.

The checklist

What to verify before you ship. The client half takes ten minutes; the server half is the one people skip.

In the client

☐The verifier comes from a cryptographically secure random source.
☐A new verifier for every authorization attempt — never cached, never reused.
☐Length between 43 and 128 characters, from the unreserved set.
☐code_challenge_method=S256. Never plain.

☐The verifier is stored per-attempt, survives the redirect, and is deleted after the token request.

In the server

☐The challenge and method are stored with the code, and both are checked at the token endpoint.
☐A token request with no code_verifier is rejected when a challenge was stored.
☐plain is refused, or at minimum cannot be downgraded to.
☐Codes are single-use, short-lived, and reuse revokes the tokens already issued.
☐redirect_uri is matched exactly, with no wildcards.

☐code_challenge_methods_supported is published in discovery metadata.

Glossary

Every term this book uses, in the sense this book uses it.

Access token

The credential the app finally gets. Presented to the API to prove it may act. Short-lived, narrow, and a bearer credential — whoever holds it can use it.

Authorization code

A short-lived, single-use string returned through the browser, exchanged at the token endpoint for tokens. Worth stealing; that is what PKCE addresses.

Authorization server

The party that authenticates the user, asks consent, issues codes and tokens, and verifies the PKCE challenge.

base64url

base64 with - and _ in place of + and /, and padding removed, so the result is safe in a URL.

Bearer token

A token that requires no further proof of identity to use. Its holder is its owner, which is why tokens must not travel through the browser.

Client

The application asking for access. Not the user.

code_challenge

The public fingerprint of the verifier, sent in the authorization request. 43 characters under S256.

code_verifier

The per-login secret, 43–128 characters, sent only in the token request.

Confidential client

A client that can keep a secret, because it runs on a machine the developer controls.

Front channel / back channel

The front channel goes through the user's browser and is visible; the back channel is a direct call between app and server and is not.

ID token

An OpenID Connect artifact describing who logged in. Not an access token, and not something PKCE protects.

Implicit flow

An older flow that returned the access token directly in the redirect. Removed by OAuth 2.1.

invalid_grant

The error returned for every PKCE failure, and for several other things. Deliberately uninformative.

nonce

A random value binding an ID token to one login. OpenID Connect, not OAuth, and not a substitute for anything else.

PKCE

Proof Key for Code Exchange, RFC 7636, said “pixy”. Proves the party redeeming a code is the party that requested it.

plain

The PKCE method where the challenge is the verifier, unhashed. Permitted by the RFC and effectively broken; use S256.

Public client

A client that cannot keep a secret: mobile, desktop, single-page, CLI. Everything shipped to a user is public.

Redirect URI

Where the authorization server sends the browser afterwards. Must be pre-registered and matched exactly.

Refresh token

A longer-lived credential for getting new access tokens without another login. Should rotate on every use.

S256

The PKCE method where the challenge is the base64url of the SHA-256 of the verifier. The one to use.

Scope

What the app is asking permission to do. Ask for the least that works.

state

A random per-request value the client sends and checks on return, defending against a forged redirect. Not replaced by PKCE.

Questions people ask

The ones that come up every time, and where to read next.

My client has a client secret. Do I still need PKCE?

Yes. OAuth 2.1 requires PKCE for all clients using the authorization code flow, confidential ones included. The secret proves which application is calling; PKCE proves the call finishes the flow it started. They are different guarantees, and the second one also protects against a leaked code inside your own infrastructure.

Is PKCE only for mobile apps?

No. It was written with mobile in mind and is now the baseline for every client type. Single-page apps need it most acutely, since they are public clients whose redirect is a plain browser URL.

Can I reuse one verifier for a session?

No. One per authorization attempt. A reused verifier turns a single leak into a permanent one, and if two flows run concurrently they will overwrite each other.

The challenge shows up in my server logs. Is that a problem?

No. It is a hash, and it is useless without the verifier. That is exactly why PKCE hashes it. The verifier in a log would be a problem — check that your token endpoint does not log request bodies.

What if the authorization server does not support PKCE?

Then you do not have this protection, and no amount of client-side correctness supplies it. Check code_challenge_methods_supported in the discovery document. If it is absent, raise it with whoever runs the server; if it is your server, Chapter 19 lists what it must do.

Does PKCE mean I can put a token in a single-page app safely?

It means the code exchange is safe. What happens to the token afterwards is a separate question with a separate answer — token storage, XSS, and rotation are all covered in the companion volume.
