The lab server

Everything runs on your own machine. Nothing is installed, nothing is downloaded, and nothing listens beyond localhost.

What you need

  • Node.js 18 or later. Check with node --version.
  • A modern browser with DevTools, open to the Network and Console tabs.
  • The file server.js, from this book's companion folder or typed in from Listing A at the end of this part. It is a single file with no dependencies.

Start it

$ node server.js
Harbor Pay app  http://localhost:8080
Harbor Pay API  http://localhost:8081   (request log: /log)
Allowed origins: http://localhost:8080

What is running

AddressWhat it is
http://localhost:8080The app origin: one page with four buttons, each making a different cross-origin fetch() to the API.
http://localhost:8081The API origin: /api/rates (public), /api/profile (needs a session cookie), /api/notes (JSON POST), and /login, which sets the cookie.
http://localhost:8081/logThe last 40 requests the API received: your proof of what really reached the server.

The two addresses differ only in port: different origins but the same site (Chapter 3), so no third-party cookie settings get in the way.

How every lab works

  1. Open the file and find the POLICY object near the top.
  2. Make the lab's one-line change and restart (Ctrl+C, node server.js).
  3. Predict the result, then press the button and check the page, Console, Network tab and /log. Undo the change before the next lab.

node server.js check shows the policy without a browser: it sends preflights from an allowed and an unlisted origin and prints the headers each receives.

For learning only: plain HTTP, in-memory data and a deliberately simple sign-in. Never expose it to a network or reuse it as production code.

Labs 1–3: first contact

Watch the basic exchange from Chapter 6, the preflight from Chapter 8, and the single most important fact about CORS: a blocked request still arrives.

LAB 1 · CHAPTER 6

The permission slip

open http://localhost:8080 → press “Lab 1”

In the Network tab, select the rates request. Under Request Headers, find Origin: http://localhost:8080, added by the browser. Under Response Headers, find Access-Control-Allow-Origin naming the same origin. The page shows:

Lab 1: status 200
x-request-id visible to script: req-6abac081
{ "USD": 1, "EUR": 0.92, "GBP": 0.79 }

Notice: there is no OPTIONS row. A plain GET is a simple request (Chapter 7).

LAB 2 · CHAPTER 8

The preflight

press “Lab 2” → then open http://localhost:8081/log

This button sends a JSON POST. The Network tab now shows two rows for notes: an OPTIONS preflight (status 204) and then the POST (status 201). Compare the preflight's Access-Control-Request-Headers: content-type with the answer's Access-Control-Allow-Headers. The log (newest first) confirms the order:

POST /api/notes origin http://localhost:8080
OPTIONS /api/notes origin http://localhost:8080 preflightFor POST

Try this: in the Network tab, check that the preflight carried no Cookie header, even after Lab 4 has signed you in.

LAB 3 · CHAPTERS 4 AND 10

Blocked, but delivered

open http://127.0.0.1:8080 → press “Lab 1”

127.0.0.1 and localhost reach the same server, but they are different hosts, so this page has a different origin that is not on the allowlist. The page reports only a generic failure:

Lab 1: TypeError: Failed to fetch
The script cannot tell why. Check the Console and Network tabs.

The Console explains that no Access-Control-Allow-Origin header was present. Now open /log: the GET /api/rates from http://127.0.0.1:8080 is there. The server received it and answered; the browser withheld the answer.

Why it matters: this is Chapter 16 in one screen. Had this request changed data, the change would have happened.

Labs 4–6: credentials and headers

The strict rules of Chapter 9, and the two header lists that trip up almost every team at least once.

LAB 4 · CHAPTER 9

Two opt-ins for credentials

press “Lab 3” → visit http://localhost:8081/login → press “Lab 3” again

The first press returns 401 not signed in — readable, because the policy allows this origin. After visiting /login, the browser holds a session cookie for the API, and the page's credentials: 'include' sends it:

Lab 3: status 200
{ "user": "demo-user", "plan": "Harbor Pay Plus" }

Now change allowCredentials: true to false and restart. The same button fails, and the Console says Access-Control-Allow-Credentials must be 'true'. The cookie was sent and the server answered; the browser refused to share a credentialed response the server hadn't agreed to share.

LAB 5 · CHAPTER 10

Visible in DevTools, invisible to code

press “Lab 4”, then set exposeHeaders: [] and press it again

With the default policy the page prints x-request-id visible to script: req-…. After emptying exposeHeaders and restarting, it prints:

x-request-id visible to script: (null)

Yet the Network tab still shows x-request-id in the response headers. The browser received it; the page was not allowed to read it.

LAB 6 · CHAPTERS 8 AND 11

A header the preflight didn't approve

remove 'content-type' from allowHeaders → press “Lab 2”

The preflight still returns 204, but its Access-Control-Allow-Headers no longer lists content-type. The browser stops there: the POST is never sent, and /log shows only the OPTIONS row. The Console names the header that wasn't allowed.

Compare with Lab 3: there, a simple request arrived anyway. Here, the preflight protected the server from a request it hadn't agreed to receive. That difference is the whole reason preflights exist.

Labs 7–8: caching and allowlists

Measure what a preflight costs, then change the allowlist the right way and put it under test.

LAB 7 · CHAPTER 8

Counting preflights

press “Lab 2” five times → count OPTIONS rows in /log

With maxAgeSeconds: 600, you should see a single OPTIONS followed by five POSTs: the browser cached the preflight answer. Now set maxAgeSeconds: 0, restart, open the page in a fresh private window, and repeat. Every POST is now preceded by its own OPTIONS — twice the round trips.

Tip: the preflight cache belongs to the browser session. If results look stale, use a fresh private window; and leave DevTools' Disable cache setting off for this lab so you are measuring the browser's normal behavior.

LAB 8 · CHAPTERS 13, 17 AND 20

Adding an origin, properly

node server.js check

First read the output: the preflight from http://localhost:8080 gets the full set of permission headers; the one from http://127.0.0.1:8080 gets only Vary: Origin. Now add 'http://127.0.0.1:8080' to allowedOrigins, restart, and repeat Lab 3: it succeeds.

Preflight from an origin not on the list
  OPTIONS /api/notes Origin: http://127.0.0.1:8080
  -> 204
     vary: Origin
     (no Access-Control-Allow-Origin: the browser will not share the response)

Extend it: turn the check function into the test suite from Chapter 20. Add probes for Origin: null and for an https version of the app origin, and make the script exit with an error if any of them receives an Access-Control-Allow-Origin header. You have just written the CI check that ended Harbor Pay's story.

Where to go next

Put the lab server behind a reverse proxy that serves both the page and the API from http://localhost:8080 (architecture A from Chapter 20). Watch every CORS header and every preflight disappear from the Network tab — the most satisfying lab of all.
