Part II

How CORS Works

CORS is a short conversation in HTTP headers. The browser says who is asking; the server says who may read. For anything unusual, the browser asks permission first. This part walks through that conversation one header at a time, and ends with the launch-night bug fixed properly.

Chapter 6

Enter CORS

CORS does not tear down the wall. It gives the server a way to hand the browser a permission slip: “responses from me may be read by this origin.”

The core idea, in three sentences

  1. On every cross-origin request, the browser sends an Origin header naming the page's origin.
  2. The server answers normally, and adds Access-Control-Allow-Origin naming the origin it is willing to share with — or * for anyone.
  3. The browser compares the two. If they match, the page may read the response; if not, the page gets an error and never sees the body.
Opt-in by design. A server that has never heard of CORS sends no Access-Control-* headers, so its responses stay unreadable to other origins — exactly as they were before CORS existed. Nothing old became less safe when CORS arrived.

The whole vocabulary on one page

Three headers are sent by the browser, six by the server. Every chapter in this part is about some subset of this table.

Where CORS lives today

CORS became a W3C Recommendation in January 2014; in 2017 the W3C marked it obsolete because the living definition had moved into the WHATWG Fetch Standard, today's authority for every edge case. The origin itself is defined in RFC 6454 (2011).

Three myths to drop now

“CORS protects my API.”

It protects browser users of your API. Scripts and command-line tools ignore it; your API still needs real authorization.

“A CORS error means the request failed.”

Often the request reached the server and succeeded. The browser only refused to show the page the response. Lab 3 proves it.

“I fix CORS in the front end.”

Permission comes from the server's response headers. No option in fetch() can grant a page access the server didn't give.

Chapter 7

Simple requests

Some cross-origin requests go straight to the server with no questions asked. The reason is historical, and once you see it, the rules stop looking arbitrary.

The logic: nothing a form couldn't already do

Long before CORS, any page could build an HTML form that submitted a GET or a POST to any server, with a handful of content types. Servers already had to live with those requests arriving from anywhere. So CORS reasoned: if a script sends a request that a form could have sent, letting it through creates no new danger. Such a request is called simple (the Fetch Standard's term is a request that needs no CORS-preflight).

What makes a request simple

PartAllowed valuesNotes
MethodGET, HEAD, POSTAnything else (PUT, PATCH, DELETE…) needs a preflight.
Headers set by the pageAccept, Accept-Language,
Content-Language, Content-Type		The CORS-safelisted request headers (plus a simple Range). Any other header, such as Authorization or X-Request-Id, needs a preflight.
Content-Typeapplication/x-www-form-urlencoded
multipart/form-data
text/plain		The three types a form can send. application/json is not on the list.

There are a few rarer conditions too (for example, safelisted header values have length limits, and upload progress listeners force a preflight). Browsers apply them for you; the three rows above cover almost every real case.

The consequence to remember. A simple request is sent before any permission is checked. If it changes data on the server, the change happens even when the browser then refuses to show the response. CORS decides who may read; it was never designed to decide who may write with a form-like request. Chapter 16 turns this into concrete defenses.

Designing with simple requests in mind

Knowing the rule lets you choose deliberately. Read-only public endpoints can stay simple and fast. Endpoints that change data should require something a form cannot send — a JSON body or a custom header — so that browsers must preflight them, and your policy gets a say before anything happens. The lab server's notes endpoint does exactly this: it refuses any request that is not application/json.

Chapter 8

The preflight

For any request a form couldn't send, the browser asks first. The question is an OPTIONS request, and nothing else is sent until the server says yes.

What the browser checks in the preflight answer

  • The status is a success (2xx). A redirect or a 401 fails the preflight.
  • Access-Control-Allow-Origin matches the page's origin (or is * when no credentials are involved).
  • The requested method appears in Access-Control-Allow-Methods. Simple methods are always allowed.
  • Every header in Access-Control-Request-Headers appears in Access-Control-Allow-Headers.

Why the preflight carries no credentials

The preflight is sent without cookies and without a body, even when the real request will include them. It is a question about policy (“would you accept this kind of request from this origin?”), not about any user. Two practical consequences follow:

  • Don't require authentication on OPTIONS. An API gateway that answers unauthenticated preflights with 401 breaks every non-simple request from the browser. Answer the preflight from policy alone, then authenticate the actual request.
  • A preflight never performs the action. Your handler for the real PUT should not run for an OPTIONS request. Most frameworks route preflights to CORS middleware automatically; hand-written servers must do it themselves, as the lab server's applyCors function does.

Wildcards in a preflight answer

The Fetch Standard allows * in Access-Control-Allow-Methods and Access-Control-Allow-Headers, meaning “any” — but only for requests without credentials. With credentials, * is treated as a literal name that matches nothing useful. One more exception: the wildcard in Allow-Headers never covers Authorization, which must always be listed by name. Listing exactly what you use is clearer anyway, and it documents your API's contract.

Caching the answer

A preflight costs a full round trip before every non-simple request. Access-Control-Max-Age lets the browser remember a successful answer, keyed on the origin, the URL, and the method or header being allowed.

SituationEffective cache lifetime
No Max-Age header5 seconds (the Fetch Standard's default)
Max-Age: 60010 minutes
Max-Age: 86400Capped by the browser: Chromium limits it to 2 hours, Firefox to 24 hours

A value of a few minutes to an hour is a sensible default. Long caches mean a policy change takes that long to reach browsers that already asked; short ones cost latency. Lab 7 lets you count preflights as you change the value.

Performance tip. Preflights are cached per URL, so an API with identifiers in its paths pays for a fresh preflight on every new URL. Serving the API from the app's own origin (Chapter 20) removes the cost entirely.

Chapter 9

Credentials and cookies

Reading public data across origins is easy. Reading data that belongs to a signed-in user is where CORS gets strict — deliberately, because that is where the danger is.

Two opt-ins, from two different parties

By default, fetch() sends cookies only to the page's own origin. For a cross-origin request to carry the user's cookies and have its response readable, both sides must opt in:

The rules with credentials

HeaderWith credentials
Access-Control-Allow-Origin: *Rejected must be the exact origin
Access-Control-Allow-CredentialsRequired exactly the string true
Allow-Methods / Allow-Headers: *No wildcard list the names
Access-Control-Expose-Headers: *No wildcard list the names

Why “*” and credentials may never meet

A * says “this response is fit for anyone.” That is safe only for a response that is the same for everyone. A response computed from a user's cookies is, by definition, not for anyone — it is for that user, in pages that the server trusts. The browser enforces the distinction so that a single careless header cannot publish every signed-in user's data to every website. Chapter 13 shows the tempting workaround that defeats this protection, and why it must be avoided.

Cookies have rules of their own

CORS decides whether a page may read a credentialed response. Whether the cookie is attached in the first place is decided separately, by cookie attributes and browser privacy settings:

  • SameSite limits cookies on cross-site requests (Chapter 3's “site,” not origin). Strict never sends them cross-site, Lax sends them only on top-level navigations such as following a link, and None sends them everywhere but requires Secure. Chrome treats a cookie without the attribute as Lax.
  • Third-party cookie restrictions in Safari and Firefox block or partition cookies for cross-site requests by default, and other browsers let users choose. If your app and API are on unrelated sites, credentialed CORS may work in one browser and silently lose its cookie in another.

Harbor Pay is lucky: app.harborpay.example and api.harborpay.example are the same site, so a SameSite=Lax session cookie is attached to the dashboard's credentialed requests. If your front end and API live on different registrable domains, prefer serving the API from the app's own origin (Chapter 20), or use tokens in an Authorization header instead of cookies.

When a request's Origin is on that list, the server names it exactly, adds Allow-Credentials: true, and answers preflights with the three methods and one header the dashboard actually uses. // The launch-night fix, in outline (the lab server implements it in full)
const ALLOWED = ['https://app.harborpay.example'];

if (ALLOWED.includes(req.headers.origin)) {           // exact match, nothing clever
  res.setHeader('Access-Control-Allow-Origin', req.headers.origin);
  res.setHeader('Access-Control-Allow-Credentials', 'true');
}
res.setHeader('Vary', 'Origin');                          // Chapter 17 explains why
Why this is safe. The server only ever repeats an origin it has already decided to trust, compared as a whole string against a list someone wrote down and reviewed. There is no pattern to get wrong and no way for a caller to talk its way onto the list.

Chapter 10

Reading the response

Even when CORS allows a response, the page does not see all of it. And when CORS refuses, the page is told almost nothing — on purpose.

Only some headers are visible

A script reading a cross-origin response can see the body and the status, but only a small set of CORS-safelisted response headers:

Cache-Control · Content-Language · Content-Length · Content-Type · Expires · Last-Modified · Pragma

Anything else — a request ID, a rate-limit counter, a pagination link — is hidden from res.headers.get() unless the server lists it:

Access-Control-Expose-Headers: X-Request-Id, X-RateLimit-Remaining, Link

DevTools will still show the header in the Network tab, which makes this one of the most confusing CORS behaviors: you can see it, but your code gets null. Lab 5 reproduces exactly that.

Opaque responses and mode: 'no-cors'

Developers fighting a CORS error sometimes discover fetch(url, {mode: 'no-cors'}) and think the problem is solved, because the error disappears. It isn't. A no-cors request returns an opaque response: status 0, no headers, and an empty body. The browser may use it (a service worker can cache it for an image tag), but your script can never read it. no-cors is how the browser keeps old embedding behavior working — not a way around the same-origin policy.

Why the error says so little

When a CORS check fails, fetch() rejects with a generic error — TypeError: Failed to fetch in Chromium, NetworkError when attempting to fetch resource in Firefox, Load failed in Safari. The script cannot learn the status code, whether the server was reachable, or which header was wrong.

That vagueness is a security feature. If a page could distinguish “server said 404” from “server said 200 but CORS refused,” it could probe other origins — including servers on your private network — and learn about them without ever being allowed to read them. The detailed explanation is written only to the DevTools console, for the human at the keyboard.

Debugging rule of thumb. Never debug CORS from your application's error handler. Open the Console for the reason and the Network tab for the raw headers; the next chapter shows how to read them.

Chapter 11

Debugging CORS like a pro

Every CORS failure is one of a handful of mismatches between what the browser asked and what the server said. Find which, and the fix is usually a single header.

Tools that tell the truth

  • Console: the browser's exact reason, in plain language (next page).
  • Network tab: filter by the API's host; look for the OPTIONS row and compare request and response headers side by side.
  • curl: replay what the browser sent, to see exactly what the server returns. It ignores CORS itself, so use it to inspect headers, never to conclude “it works.”

The Console messages, decoded

Chromium's wording, abbreviated; Firefox and Safari phrase the same conditions differently.

The message says…What it means, and the usual fix
No 'Access-Control-Allow-Origin' header is presentThe server didn't opt in — or an error page, proxy or CDN stripped the header. Check the actual response, including 4xx/5xx ones.
…has a value 'X' that is not equal to the supplied originThe server named a different origin: a typo, a missing port, http vs https, or a cached response for another origin (Chapter 17).
…must not be the wildcard '*' when the request's credentials mode is 'include'Name the exact origin and add Allow-Credentials: true, or stop sending credentials if the data is public.
…'Access-Control-Allow-Credentials' header… must be 'true'The page sent credentials; the server didn't agree. Add the header for trusted origins only.
Response to preflight request… does not have HTTP ok statusThe OPTIONS request hit authentication, a 404, or a redirect. Answer preflights before auth.
Request header field X is not allowed by Access-Control-Allow-HeadersAdd the header name to Allow-Headers — or stop sending it if you don't need it.
Method X is not allowed by Access-Control-Allow-MethodsAdd the method to Allow-Methods for the routes that accept it.

Inspecting headers with curl

Replay a preflight exactly as the browser would send it, and read what comes back:

curl -i -X OPTIONS https://api.harborpay.example/v1/transfers \
  -H 'Origin: https://app.harborpay.example' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: content-type'

Repeat it with an origin that should not be allowed: a correct policy answers only the first with permission headers. node server.js check prints this comparison.

Four traps that waste an afternoon

  • Only the error path fails. The framework adds CORS headers on success but not on the 500 page, so real errors look like CORS errors.
  • Two layers both add headers. The app and the proxy each send Allow-Origin; two values are invalid and the browser rejects both.
  • A redirect in the middle. http→https or a missing trailing slash redirects the preflight, which fails.
  • A trailing slash in the allowlist. https://app.example/ is not an origin; https://app.example is.
