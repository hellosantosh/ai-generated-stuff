The honest test

You've shipped OAuth. Could you defend it?

Most of us wire up a library, the redirect works, and we move on. These are the questions that come up in an incident review — or a security interview.

  5. Someone sends an ID token as a Bearer token and it works. What went wrong, and on whose side?

Why a hash is enough

The attacker sees the challenge — it's right there in the authorization URL. To use a stolen code they'd need a string that hashes to it, which is a SHA-256 preimage. Nobody can compute that.

And they can't guess the verifier: it's 256 bits of randomness with no structure to attack.

Change one character above. The challenge changes completely. That's the property the whole flow rests on — and the book shows you the server code that checks it, in constant time.

Questions

Do I need the code from anywhere else?
No. Part II prints all 1,363 lines — four files, complete, nothing elided. You need Node.js 18 or newer and nothing else: there's no package.json and no dependency to install.
What format is it, and can I copy the code out?
A single PDF, Letter size, with embedded fonts and a real text layer — so the listings are searchable and the code is selectable and copyable, not screenshots.
Is this OAuth 2.0 or 2.1?
2.1, which is mostly a list of deletions: the implicit and password grants are gone, PKCE is required for every client, and redirect URIs match exactly. Chapter 10 covers exactly what changed and why. If you know 2.0, that chapter is your migration.
Does it cover OpenID Connect?
The part that matters for most developers: the openid scope, ID tokens, nonce, and the difference between authentication and authorization. Chapter 7 is largely about not confusing an ID token with an access token — the single most common bug in production OAuth code.
How long does it take to read?
About two hours for the 13 chapters. The labs are as long as you want them to be — the first one is a single command.
Can I use this code in production?
Please don't. It's a teaching implementation that deliberately includes insecure modes so you can watch them fail, and it keeps everything in memory on plain HTTP. Use a maintained, audited library in production — the book's point is that you'll then configure it correctly and understand the errors.
