Chapter 01

The problem OAuth solves

An application needs data that belongs to you, held by somebody else. There is an obvious way to arrange that, and it is a catastrophe.

Suppose a budgeting app wants to read your bank transactions. The naive design is to ask you for your banking username and password and log in as you. Every single thing wrong with that idea turns out to be something OAuth fixes.

The one-sentence definition

OAuth 2.1 is a protocol for letting an application act on your behalf, in a limited way, without ever seeing your password. You authenticate to the party that already knows you; that party issues the application a scoped, expiring, revocable token.

The rest of this guide is about doing that safely when the exchange must pass through a web browser — the single constraint, explored in Chapter 3, that makes OAuth look harder than the sentence above.

Three things OAuth is not

Not authentication

An access token says what may be done, not who is here. Treating one as proof of identity is a vulnerability class of its own; identity is a separate token (Chapter 7).

Not encryption

A bearer token is a password-equivalent in plain text: anyone who copies it can use it. OAuth assumes TLS everywhere.

Not a permission system

Scopes are coarse labels on an app's authority. Whether this user may touch this record stays your API's decision, on every request.

Two kinds of client, and why it matters so much

This distinction decides how a client may authenticate, and it is why PKCE exists.

Confidential client has a secret

Code that runs on a server you control. It can keep a client_secret because nobody can read its memory or disk.

Examples: a server-rendered web app, a backend service. Proves identity by: sending its secret to the token endpoint.

Public client cannot keep a secret

Code that runs on someone else's device. Anyone can read the JavaScript bundle or decompile the binary, so any embedded secret is published to the world.

Examples: a single-page app, a mobile app, a CLI. Proves identity by: PKCE, and nothing else.

The mistake to avoid. A single-page app is a public client however private your bundle feels: a secret shipped to a browser or an app store is not a secret. OAuth 2.1's answer is to stop depending on one — PKCE is mandatory for every client, so correctness no longer rests on this classification.

Chapter 03

Front channel and back channel

If you remember one idea from this guide, make it this one. Every rule in OAuth 2.1 — including all of PKCE — follows from the difference between these two ways of moving data.

The client and the authorization server need to talk twice, and the two conversations travel by completely different routes with completely different security properties. They are not alternatives — in the Authorization Code flow you use both, in order. The next page sets out exactly which grants use which.

The rule that follows

May cross the front channel

  • client_id — public by definition
  • redirect_uri, scope, state
  • code_challenge — a hash, not a secret
  • the code — useless on its own (this is the whole trick)

Must never cross it

  • client_secret
  • code_verifier
  • access_token, refresh_token, id_token
  • the user's password, obviously
This is why the implicit grant was removed. It returned an access token on the front channel, in the URL fragment — landing it in browser history and in any Referer header the page emitted. Chapter 11 has the full list of what OAuth 2.1 deleted and why.

“Front channel” does not mean unencrypted

Both channels run over TLS in production. The front channel is dangerous not because it is exposed in transit, but because of where the data comes to rest: browsers write URLs into history, servers into access logs, pages leak them through Referer. TLS does nothing about any of that. OAuth 2.1 still requires https everywhere, with two carve-outs — http://localhost for development, and private-use schemes like com.example.app:/callback for native apps. That is why the simulator may run on plain HTTP, and why nothing else should.

Do you need both?

Three questions this trips people on: are the channels alternatives, which grant uses which, and does the answer depend on who owns the application. Taken in order.

The short answer. They are not alternatives. In the Authorization Code flow both are used, always, in this order: the front channel obtains the code, then the back channel exchanges it for tokens. Neither half is optional and neither can do the other's job. Some other grants use the back channel alone — and nothing safe uses the front channel alone, which is precisely what OAuth 2.1 removed.

One connection, both channels, in order

Sarah connects a budgeting app to her bank. Watch which channel carries each step, and what is on it:

  1. front The app redirects Sarah's browser to the bank. On the URL: client_id, scope, state, code_challenge. Nothing secret.
  2. front Sarah signs in at the bank and approves. The bank redirects her browser back to the app carrying a code — which is useless on its own.
  3. back The app's server posts that code, plus its code_verifier and secret, straight to the bank's /token endpoint. Sarah's browser never sees this call, and never sees the tokens it returns.
  4. back Five minutes later the access token expires. The app's server refreshes it — back channel only. Sarah is asleep; no browser is involved, and none is needed.

Steps 1–2 cannot be done on the back channel: only a browser can show Sarah a login screen. Steps 3–4 must not be done on the front channel: they carry secrets. That is the whole reason there are two.

First party, third party, and why it changes nothing

The last of the three questions, and the one that causes the most trouble in design reviews: does any of this depend on who owns the application?

Who owns the client is a different question

The back channel is defined by the network path — a direct server-to-server call that does not pass through anybody's browser. It says nothing about who wrote the application. Both of these are back-channel calls:

Third party back channel

A budgeting app built by a different company POSTs to your bank's /token endpoint from its own server. Nothing is shared but a registered client_id and a secret.

First party back channel

Your company's own web app POSTs to your company's own authorization server. Same wire, same rules, same PKCE requirement.

Three properties get conflated constantly. They are independent, and only the first one is about channels:

PropertyThe question it answers What it actually changes
ChannelDoes it pass through the browser? What may travel on it. Nothing secret on the front channel, ever.
Client typeCan this code keep a secret? Whether it authenticates at the token endpoint. A question of deployment, not ownership — a third-party server app is confidential; your own SPA is public.
OwnershipWho wrote it? Registration and trust policy — chiefly whether you skip the consent screen for your own apps. It changes no protocol rule.
The trap this clears up. “Back channel” does not mean “internal” or “trusted”, and “front channel” does not mean “third party”. A third-party integration uses both channels; so does your own first-party web app. The only question a channel answers is whether the user's browser can see the data.

The Authorization Code flow

All of OAuth 2.1 in one picture; the next two pages walk it step by step.

Three things to notice

The user is a participant

Steps 2–6 happen in a browser because a human has to be asked. That is not overhead — it is the consent.

The code is a claim ticket

It is not a token and grants nothing: a single-use reference, valid about a minute, redeemable only by whoever started the flow.

Step by step: the front channel

The same flow again, this time as real HTTP. Every value below was taken from an actual run of the simulator.

1 · The client invents a secret it will not send

Before anything touches the network, the client generates a high-entropy random string and hashes it. The random string is the code_verifier; the hash is the code_challenge.

# 32 random bytes, base64url-encoded => exactly 43 characters
code_verifier  = 3TbF_QUTBOiHthQdOrRr_6GcCTQKN_nPqc9j3P0FCBg

# BASE64URL(SHA256(ASCII(code_verifier)))
code_challenge = kPX0H7VuZIrt1ZXIk7nOC2HkA6r0YNI3lDys2XF1Crk

The verifier is stored in the client's own session. It must survive until step 7 and must never appear in a URL, a cookie readable by script, or a log line.

2–3 · Redirect the user to the authorization endpoint

The client does not call /authorize itself. It sends a 302 so that the browser goes there, carrying the parameters in the query string.

GET /authorize?response_type=code
              &client_id=demo-web-app
              &redirect_uri=http%3A%2F%2Flocalhost%3A9020%2Fcallback
              &scope=openid+profile+accounts%3Aread
              &state=cclt66TixPmn7BXxpsyNEA
              &code_challenge=kPX0H7VuZIrt1ZXIk7nOC2HkA6r0YNI3lDys2XF1Crk

Step by step: the exchange

The user takes over, and hands back a code that is worth nothing by itself. Turning it into a token takes a direct call, and a proof.

4–6 · The user authenticates, consents, and comes back with a code

Everything in this step happens on the authorization server's own origin. The client is not running, cannot see the password, and cannot influence the consent screen. When it is done, the server redirects the browser back:

HTTP/1.1 302 Found
Location: http://localhost:9020/callback?code=bnBKJfGg0H4Mm_fzI4bE622-5t0w7U8kbKIHpudbQ4o
                                       &state=cclt66TixPmn7BXxpsyNEA
                                       &iss=http://localhost:9000
Two checks the client must make here. First, state has to equal the value it generated in step 2 — otherwise this callback was not started by this browser session, and the code must be dropped. Second, iss must name the authorization server the flow began with (RFC 9207), which prevents a code from one server being replayed at another.

7 · Redeem the code, and prove you started the flow

This is a server-to-server POST. The browser is not involved and never sees any of it.

POST /token HTTP/1.1
Host: localhost:9000
Content-Type: application/x-www-form-urlencoded
Authorization: Basic ZGVtby13ZWItYXBwOndlYi1hcHAtc3VwZXItc2VjcmV0   <- only if confidential

grant_type=authorization_code
&code=bnBKJfGg0H4Mm_fzI4bE622-5t0w7U8kbKIHpudbQ4o
&redirect_uri=http://localhost:9020/callback
&code_verifier=3TbF_QUTBOiHthQdOrRr_6GcCTQKN_nPqc9j3P0FCBg

8 · What the authorization server checks, in order

  1. Does this code exist, and has it been used before? A replay means someone has a copy; every token it produced is revoked.
  2. Has it expired? Codes live about a minute, because they cross the browser.
  3. Was it issued to this client_id? A code belongs to one client.
  4. Does redirect_uri match the one from step 3? Both halves of the flow must agree.
  5. Does SHA256(code_verifier) equal the stored code_challenge?
  6. If the client is confidential, did it authenticate correctly?

Any failure returns 400 invalid_grant and no token — and check 5 is the only one an attacker holding a stolen code cannot satisfy.

Chapter 05

The attack PKCE prevents

The authorization code has to cross the browser, and the browser is not a private place. So assume the code leaks — and ask what it is worth.

How codes actually leak

None of these are exotic. Every one has produced real CVEs:

  • A malicious app on the same device registering the same custom URI scheme (myapp://callback) — the OS may hand the redirect to either app.
  • Server access logs. The callback URL, complete with code, is written to disk by every proxy and web server in the path.
  • The Referer header leaking the callback URL to any third-party script or image on the landing page.
  • An open redirect on the client's own domain, used to bounce the code to the attacker's server.
  • Browser history on a shared or managed machine.
  • A TLS-terminating proxy on a corporate or hostile network.
Why OAuth 2.1 requires PKCE even for confidential clients. A server-side app with a secret is already protected against most of this — the attacker would need the secret too. But PKCE also protects against a code being injected into an honest client's session, costs nothing, and removes any need to reason about which category a client falls into. Universal rules fail safe; conditional ones get misapplied.

Chapter 06

PKCE, precisely

Proof Key for Code Exchange (RFC 7636). One random string, one hash, one comparison — and the authorization code stops being worth stealing.

The name is unhelpful; the idea is simple. Before starting the flow the client invents a secret, sends only a fingerprint of it through the browser, and later proves it holds the original. Only the app that began the flow can finish it.

Why a hash is enough

The attacker sees the challenge

It is right there in the authorization URL. To use the stolen code they would need a string that hashes to it — that is a SHA-256 preimage, which nobody can compute. The challenge is public by design.

The attacker cannot guess the verifier

It is 256 bits of randomness. There is no dictionary, no pattern and no structure to attack. This is why the specification insists on a cryptographically secure generator, not Math.random().

Never use code_challenge_method=plain. With plain, the “challenge” is the verifier, sent in the clear through the browser — so anyone who sees the authorization request can redeem the code. It exists in RFC 7636 only for devices that genuinely could not compute SHA-256 in 2015. Worse, RFC 7636 says that an omitted code_challenge_method defaults to plain. Always send S256 explicitly.

The check, and how to write it

What the server does with the two halves, and the code that produces them.

Generating the pair

Browser (Web Crypto)

const b64url = (b) => btoa(
  String.fromCharCode(...b))
  .replace(/\+/g, '-')
  .replace(/\//g, '_')
  .replace(/=+$/, '');

const verifier = b64url(
  crypto.getRandomValues(new Uint8Array(32)));

const hash = await crypto.subtle.digest(
  'SHA-256',
  new TextEncoder().encode(verifier));

const challenge = b64url(new Uint8Array(hash));

Node.js

const crypto = require('node:crypto');

const verifier = crypto.randomBytes(32)
  .toString('base64url');

const challenge = crypto.createHash('sha256')
  .update(verifier).digest('base64url');

Python

import base64, hashlib, os

b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b'=')

verifier  = b64(os.urandom(32))
challenge = b64(hashlib.sha256(verifier).digest())

In all three, the SHA-256 is taken over the base64url text of the verifier, never over the raw random bytes. Getting that backwards is the most common PKCE bug and the hardest to spot, because both values still look like valid base64url.

One pair per authorization request. A verifier is a nonce, not a configuration value: generate a fresh one every time and discard it the moment the code is exchanged. On the server side, compare with timingSafeEqual rather than ==, and treat a mismatch as a security event — invalidate the code, return the generic invalid_grant, and never reveal which check failed. The common implementation mistakes are collected in Chapter 13.

Anatomy of a token

An access token is usually a JWT: three base64url segments joined by dots. Two of them are plain text that anyone can read.

What the segments say once decoded

// segment 1 - the header
{ "alg": "RS256", "typ": "at+jwt", "kid": "sim-EarHfCN6MZTqOJjo" }

// segment 2 - the claims
{ "iss":       "http://localhost:9000",          // who issued it
  "sub":       "u-1001",                         // whose data it acts on
  "aud":       "http://localhost:9010",          // which API may accept it
  "client_id": "demo-web-app",                   // which app is holding it
  "scope":     "openid profile accounts:read",   // what it may do there
  "jti":       "78e3f1b14a7c70e11fac6fc1",       // unique id, for revocation
  "iat": 1789228222, "nbf": 1789228222,        // issued at / not before
  "exp": 1789228522 }                          // expires - 300 seconds later

Why typ: at+jwt matters

RFC 9068 gives access tokens their own type, so an API can reject anything that is not one — an ID token, for instance. Without it, two different tokens from the same issuer look interchangeable.

Opaque tokens are also fine

Plenty of servers issue random strings instead. The API then calls /introspect to find out what a token means. Same protocol, different trade-off — see Chapter 12.

A token is a bearer credential. Whoever holds it can use it, exactly as with a password. There is no cryptographic binding to the client that received it, which is why they are short-lived, scoped and audience-restricted — three ways of limiting the damage rather than preventing the theft.

Three tokens, three jobs

A single token response can contain three completely different things. Confusing two of them is the most common OAuth bug in production code.

The mistake, and why the API must refuse it

An ID token is a JWT from the same issuer, so it is tempting to send it as a Bearer token. It looks valid. It is not:

# The ID token's own claims say who it is for:
"aud": "demo-web-app"          # the CLIENT, not the API
"typ": "JWT"                   # not at+jwt
# ...and it carries no `scope` at all, so there is nothing to authorize.
GET /api/accounts  Authorization: Bearer <id_token>   ->  401 invalid_token

An API accepting an ID token is accepting a credential minted for somebody else, with no statement of what it may do — and in a federated setup that is exploitable.

The habit to build. When a call fails with 401, check which token you sent before you check anything else. “I sent the ID token” accounts for a remarkable share of lost afternoons. Lab 8 in the simulator does exactly this, twice.

Where OpenID Connect fits

OAuth alone never tells the client who the user is; it only hands over authority. OpenID Connect is a thin identity layer on top that adds exactly that — one scope, one extra token, one endpoint. “Sign in with Google” is OpenID Connect; “let this app read your Drive” is plain OAuth, and most deployments do both at once in the one flow from Chapter 4.

Chapter 8 covers it properly: the ID token claim by claim, the six checks a client must run on it, why nonce and state are different things, and /userinfo. Lab 12 runs all of it.

Choosing between them

The honest summary: opaque tokens buy control, JWTs buy independence, and almost everyone ends up buying a bit of both.

Reach for opaque when…

  • Instant revocation is a hard requirement — payments, admin consoles, anything a security team must be able to kill now.
  • The API and the authorization server are close: same company, same network, a round trip you can afford.
  • Token contents are sensitive. Roles, internal ids and email addresses in a JWT are readable by anyone who gets the token.
  • The token must be small — constrained devices, tight headers, QR codes.

Reach for JWT when…

  • Many services validate tokens independently — microservices, a service mesh, validation at the edge or in a gateway.
  • Third parties call your API and you cannot have them, or your AS, absorbing an introspection call per request.
  • Throughput is high enough that a round trip per call is a real cost.
  • The authorization server must not be a single point of failure for every API in the estate.

What most people actually do

The common production answer is a deliberate compromise, and it is the one this book has been arguing for since Chapter 9: self-contained access tokens with deliberately short lifetimes. You get offline validation, and you bound the revocation gap to the token's lifetime rather than eliminating it.

  • Five to fifteen minutes is the usual window. Long enough to avoid hammering the token endpoint, short enough that a revoked token dies quickly.
  • Refresh tokens carry the real revocation power. They are almost always opaque and checked against a database on every use — so revoking a session stops the next refresh even though the current access token lives out its few remaining minutes.
  • Use introspection selectively. Keep JWT validation for ordinary reads and introspect only on the operations that genuinely cannot tolerate a stale answer. Lab 10's two endpoints are exactly this pattern.
A rule for clients, regardless of shape. Never parse an access token. Even when it is obviously a JWT, its format is a private contract between the authorization server and the API — either may switch to opaque tomorrow without telling you, and nothing in the specification promises you can read it. If your client needs to know who the user is, that is what the ID token is for (Chapter 8). If it needs to know whether a token is still good, it should try the call and handle 401.
The other two tokens have no choice to make. An ID token is always a JWT — it exists to be read and verified by the client, so it could not be anything else. A refresh token is almost always opaque, because it is redeemed only at the authorization server, which can simply look it up.

Chapter 08

OpenID Connect: who is this?

OAuth hands an application authority. It never says whose. If you need to know who just signed in, you need the thin identity layer that sits on top of it — and you need to stop reaching for the access token.

The shortcut that does not work

The tempting move is to treat a successful token request as proof of identity: the user approved something, so they must be here. That reasoning fails in three separate ways.

  • An access token is not addressed to you. Its aud names the API. Nothing in it says which client obtained it, so a token your app received from somewhere else looks identical to one it earned.
  • It says nothing about when anyone authenticated. A token minted from a refresh token six weeks later looks exactly like one from a fresh login.
  • It may be opaque. You are not entitled to read an access token at all — it is the API's to interpret, not yours.
The whole of it, in one line. Ask for the openid scope and the token response gains an id_token: a JWT whose aud is your client_id, saying who signed in and when. That is the difference between “let this app read your Drive” and “sign in with Google”.

Validating an ID token

Chapter 12 lists the four checks an API runs on an access token. These are the checks a client runs on an ID token. They are not the same list, and the last two are the ones that get skipped.

  1. Verify the signature against the issuer's published key, selected by the kid in the header. Pin the algorithm in your code — never trust the token's own alg.
  2. Check iss is exactly the issuer you expect. String equality, no prefix matching.
  3. Check aud contains your client_id. If it is an array, also check azp names you. This is what stops another client of the same issuer replaying its ID token at you.
  4. Check exp has not passed, allowing a little clock skew.
  5. Check nonce equals the value you generated for this authorization request. Without it, a token captured from an earlier login can be fed back to you.
  6. Check auth_time if you asked for max_age, or if this operation needs a recent authentication rather than an old session.

const v = C.verifyJwt(idToken, {
  getKey: () => keyFromJwks,      // signature, by kid
  issuer: 'http://localhost:7000',  // iss
  audience: 'demo-web-app',        // aud == our client_id
  requiredTyp: 'JWT' });            // exp is checked inside

// and the one no library can do for you, because only you know it:
if (claims.nonce !== theNonceWeGenerated) reject();

nonce and state are not the same thing

They look alike — both random, both sent out and checked on return — but they protect different things, and you need both.

Travels Protects

nonce On the authorization request, echoed inside the ID token. The token itself. Proves this ID token was minted for this login, and is not one replayed from a different session.

Scopes and consent

A scope is a label for a slice of authority. What an application asks for and what it gets are two different things, and it is narrowed three separate times.

Designing scopes people can consent to

Good

  • accounts:read, payments:write — resource plus verb
  • Separate read from write, always
  • Few enough to fit on one screen
  • Named for what the user loses if abused

Bad

  • admin, full_access — unconsentable
  • One scope per API endpoint — unreadable
  • Scopes encoding record ids (account:4410)
  • Internal role names leaked into the UI

Scope is not the same as permission

This distinction causes real vulnerabilities. A scope says this application may perform this kind of operation on this user's behalf. It says nothing about which records that user may touch.

# The token carries scope=accounts:read and sub=u-1001.
GET /api/accounts/ACC-7100        # <- an account belonging to u-1002

# A scope check alone would ALLOW this. The API must also check ownership.

The simulator's API takes the user from the token's sub and never from the request, which is the habit worth copying. An object reference supplied by the caller must always be authorized against the token's subject.

Chapter 10

Refresh tokens and rotation

Access tokens expire in minutes. Users expect to stay signed in for weeks. The refresh token bridges that gap — and needs careful handling because of it.

An access token cannot be recalled once issued, so it is given a short life: a leak is a problem for five minutes, not five months. The refresh token mints replacements without troubling the user.

What this buys you

  • A stolen refresh token stops working. Whichever party refreshes second is refused, and the theft is detected rather than lasting for months.
  • The theft becomes observable. A reuse event is a high-quality security signal, because correct clients never replay a retired token. This is why OAuth 2.1 requires rotation (or sender-constraining) for public clients.

How long should each one live?

CredentialTypicalWhy
authorization code30–60 sIt crosses the browser and is redeemed immediately. Anything longer is pure exposure.
access token5–15 minCannot be recalled, so its lifetime is the exposure window.
refresh tokenhours–monthsLong, but rotating and revocable. Shorter for public clients.
IdP sessionhoursDecides whether a new authorization needs a fresh login.
The operational catch. If a client crashes after sending a refresh but before storing the new token, it will replay the old one and get the whole family revoked — logging the user out for no good reason. Persist the rotated token before you use the access token that came with it, and serialise refreshes so two tabs cannot race.

What OAuth 2.1 changed

OAuth 2.1 invents almost nothing. It deletes what proved dangerous and makes the best existing practice mandatory — and that is precisely why it is an improvement.

OAuth 2.0 is a framework of options. A decade of deployments showed which options were traps, and the security Best Current Practice (RFC 9700) documented them. OAuth 2.1 consolidates that guidance into the core, so that the default reading of the specification is now the safe one.

OAuth 2.0 (2012)OAuth 2.1Why it changed
PKCE optional, recommended for mobileRequired for every authorization code requestCodes leak in ways nobody predicted, the defence costs almost nothing, and a universal rule cannot be misapplied.
Implicit grant (response_type=token)RemovedIt put an access token in the URL fragment: browser history, Referer headers, any script on the page — and the client could not be authenticated at all.
Password grant (grant_type=password)RemovedThe application handled the real password, so there was no consent, no MFA, no federation, and no way for a user to tell a real app from a phishing one.
redirect_uri matching left to the serverExact string comparisonWildcards and prefix rules let an attacker append a path and have codes delivered to themselves.
Bearer tokens allowed in query stringsHeader onlyQuery strings are written to every access log, proxy log and browser history on the path.
Refresh tokens static and long-livedRotate, or bind to the clientA stolen static refresh token is permanent, undetectable access. Rotation makes the theft visible and recoverable.
Little guidance on mixing up serversiss in the authorization responsePrevents a mix-up attack where a code from a malicious server is replayed at an honest one.

If you already know OAuth 2.0

You know OAuth 2.1. Add PKCE everywhere, stop using implicit and password, match redirect URIs exactly, and rotate refresh tokens. That is the entire migration.

On the specification's status

OAuth 2.1 is an IETF draft that consolidates published, stable RFCs. Nothing in it is speculative — every requirement already exists as a standard somewhere. Implementing it is not a bet on a draft.

The pattern worth noticing. Every deletion removes a choice a developer could get wrong. The most reliable security improvement is not a new mechanism but the removal of an unsafe option — which is the actual lesson of OAuth 2.1.

Chapter 12

How an API validates a token

The resource server is the part most tutorials skip. On every single request it asks four questions, in this order.

Local validation or introspection?

Verify the JWT locally

Fetch the issuer's public keys once from /jwks.json, cache them by kid, verify offline.

Fast and needs no network. But it cannot see a revocation: a revoked token stays acceptable until exp.

Ask the authorization server

Call /introspect (RFC 7662) per request. Works with opaque tokens too.

Always current, including revocation. But it adds a round trip to every call and makes the AS a hard dependency.

This trade-off is the real reason access tokens are short-lived: a five-minute window is the compromise between not calling the AS on every request and not honouring a revocation for too long. Lab 13 in the simulator revokes a token and then calls both kinds of endpoint, so you can watch one accept it and the other refuse.

Three ways to get validation wrong

  • Trusting the token's own alg header. If you let the token choose its algorithm, an attacker sends alg: none (no signature at all) or swaps RS256 for HS256 and signs with your public key as the HMAC secret. Pin the expected algorithm in your code and reject everything else.
  • Skipping the aud check. Then any token from that issuer works at your API, including one minted for a low-value service that has no business here. A valid signature only says who issued a token, not who it was for.
  • Caching keys without handling rotation. Cache by kid, refetch when an unknown kid appears, and rate-limit that refetch. An issuer that rotates keys should not take your API down — nor should an unknown kid let an attacker trigger unbounded fetches.

OAuth 2.1 for agentic AI

An agent is a client that acts when nobody is watching. Every assumption in Chapters 3 and 4 bends here — but the protocol needs no replacing, only three extensions and stricter administration.

What actually changes

  • There is no browser. A redirect has nowhere to land, so the authorization code flow cannot start in the usual way.
  • The human is absent at the moment of the call. Consent happens once, minutes or weeks before the action it authorizes.
  • One authorization fans out into many calls. An agent plans, retries and chains requests, often across several services.
  • Scopes stop being expressive enough. “May move money” is a reasonable thing to tell a human at a consent screen and a dangerous thing to hand an autonomous process.
The mistake to refuse, first and loudest. An agent reaching user data with client_credentials is not OAuth. Nobody consented, the token names no user, and your audit log can never answer “on whose behalf?” If a team asks for this because “the agent needs access to everything”, the answer is Pattern A or C.

Pattern B, and when it is actually right

It takes a paragraph rather than a page because the only hard part is knowing when it applies. It is correct when the agent touches nobody's data — rotating certificates, reindexing a catalogue, pruning logs. There is no resource owner, so nothing to delegate and nobody to consent: client_credentials is right, and Pattern A would be theatre.

The test that settles it. Ask whose data the agent touches. If the answer names a person, Pattern B is wrong however convenient it looks; if it is “the company's own”, B is right and the rest of this chapter mostly does not apply. Lab 9 shows both halves: a token issued with no browser and no consent, sub set to the client id, and /api/me returning 404 — no user behind it.

Pattern A: an agent with no browser

The device authorization grant (RFC 8628) was written for televisions. It turns out to be exactly what an autonomous agent needs: the agent gets a short code, and the human approves it somewhere else entirely.

The exchange, as HTTP

Pattern C: who is acting, on whose behalf

An agent rarely calls the API directly. It calls a service, which calls another. Each hop must carry the user’s authority without impersonating the user — and without quietly acquiring authority of its own.

The wrong answers, first

Passing the user’s token onward

Every downstream service now holds a credential that works everywhere the user does, for as long as it lives. One compromised service becomes total compromise, and the audit log shows only “alice” at every hop.

Each service using its own machine token

The user disappears entirely. The API sees a service acting as itself and cannot tell an authorized request from a bug or an attacker who reached that service.

Token exchange, and the act claim

RFC 8693 lets a service hand in the token it received and get back one scoped for the next hop. The sub stays the user; a new act claim records who is acting, nested outward.

POST /token
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<the token the service received>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&scope=accounts:read          # same or less. never more.
&resource=https://api.example.com  # bind it to one audience

When a scope is not specific enough

A scope is a label fixed at registration time. It cannot say “up to $100, from this account”. For a human clicking one button that is usually fine; for a process acting a thousand times unattended, it is not.

What a scope can say

scope=payments:write

“This agent may move money.” Any amount, from any of the user’s accounts, to anywhere, for as long as the token lives. The API has nothing finer to check.

What authorization_details can say

[{ "type": "payment_initiation",
   "actions": ["initiate"],
   "maxAmount": "100.00",
   "fromAccount": "ACC-4410" }]

The same permission, bounded. The consent screen can show it, the token carries it, and the API enforces it.

How it flows

RFC 9396 adds one JSON parameter, authorization_details. In the lab it is accepted at /device_authorization, approved by the human, embedded in the token as a claim, and checked by the API on every payment.

# 1. the agent asks for bounded authority, not a broad scope
POST /device_authorization
  scope=payments:write
  &authorization_details=[{"type":"payment_initiation","maxAmount":"100.00",
                          "fromAccount":"ACC-4410"}]
# 2. it ends up inside the access token, alongside the scope
{ "sub": "u-1001", "client_id": "demo-agent", "scope": "payments:write",
  "authorization_details": [{ "type": "payment_initiation", … }] }
# 3. the API treats it as binding, not advisory
   amount 50   from ACC-4410  -> 201 created
   amount 5000 from ACC-4410  -> 403 insufficient_authorization
   amount 10   from ACC-9982  -> 403 insufficient_authorization
Note what happened in that last block. The scope payments:write was satisfied on all three requests. Two were refused anyway. That is the entire argument for structured grants: the coarse permission stays true while the specific limit does the work. Lab 13 runs exactly these three calls.

Administering it

  • Publish the types you accept as authorization_details_types_supported, and reject unknown types rather than ignoring them — silently dropping a limit is worse.
  • Render them in plain language at consent. A structured grant the user cannot read is not consent.
  • Be consistent on a mismatch: 403 with a body naming the granted limit, so a caller can tell “not allowed” from “not allowed this much”.

Running the resource server

The API is where an agent’s authority becomes an action. The four checks of Chapter 12 all still apply — these are the ones agents add.

Five additional checks

  1. Read the actor chain, and log it. If the token carries act, the request came through one or more services. Record the whole chain next to the action, or you will never reconstruct an incident.
  2. Enforce authorization_details as binding. If the token carries a structured grant covering this operation, the request must fit inside it. A scope check alone is not sufficient.
  3. Never accept an identity from the request body. Always take the user from sub. Agents assemble requests from model output; a caller-supplied account id is exactly the value that will be wrong.
  4. Make writes idempotent. Agents retry — on timeouts, on slow_down, on their own planning loops. Require an idempotency key on anything that moves money or sends a message.
  5. Rate-limit and profile per client_id. A human makes a payment a minute at most. An agent can make a thousand. Alert on the shape of the traffic, not just its volume.

Anti-patterns, and what to do instead

Instead of…Do this
A long-lived API key in the agent’s config Device grant plus rotating refresh tokens. Same convenience, revocable, and attributable to a user.
client_credentials to reach user data Pattern A or C. If no human ever consented, the agent has no business with that data.
One shared client_id for the whole fleet One per agent. Revocation and attribution both depend on it.
A broad scope “so it does not break” Narrow scope plus authorization_details for the magnitude.
Forwarding the user’s token between services Token exchange, so each hop is scoped, audience-bound and recorded in act.
Putting tokens anywhere a model can read them Keep credentials out of prompts, context windows and tool output. A token in a context window is a token in every log you own.

Glossary

Every term used in this guide, in one place.

access token

A credential saying what an application may do, on whose behalf, at which API, until when. Usually a signed JWT. Sent to the resource server.

authorization code

A short-lived, single-use reference handed to the client through the browser, exchanged at the token endpoint for tokens. Worthless on its own.

authorization server (AS)

The service that authenticates the user, collects consent, and issues tokens. Publishes its metadata and public keys.

aud — the “audience” claim: which recipient a token is for. A resource server must reject tokens naming anyone else.

back channel

A direct server-to-server HTTPS call, invisible to the browser. Safe for secrets. See Chapter 3.

bearer token

A token usable by whoever holds it, with no further proof required — like a password. Hence short lifetimes.

client

The application requesting access. Confidential if it can keep a secret (server-side), public if it cannot (SPA, mobile, CLI).

code_challenge / code_verifier

The PKCE pair. The verifier is a random secret held by the client; the challenge is its SHA-256 hash, safe to send through the browser.

front channel

Communication via browser redirects. Visible in URL bars, history, logs and Referer headers. Never carries secrets.

grant type

How a client obtains a token. OAuth 2.1 keeps authorization_code, refresh_token and client_credentials; implicit and password are gone.

identity provider (IdP)

The service holding user accounts and performing authentication. Usually packaged with the authorization server, but a distinct job.

ID token

An OpenID Connect JWT stating who signed in and when, addressed to the client. Not an API credential.

introspection — RFC 7662: an endpoint where a resource server can ask whether a token is still active. Sees revocation immediately.

iss — the “issuer” claim: which authorization server minted a token. Checked on every validation.

JWKS — JSON Web Key Set: the public keys an authorization server publishes so anyone can verify its signatures offline.

JWT

JSON Web Token: header, payload and signature, base64url-encoded and dot-separated. Signed, not encrypted.

kid — key id: names which published key signed a token, so keys can be rotated without downtime.

nonce

A random value echoed inside the ID token, proving it was minted for this login.

PKCE

Proof Key for Code Exchange (RFC 7636). Binds an authorization code to the application that requested it. Mandatory in OAuth 2.1.

refresh token

Exchanged for new access tokens without user interaction, and rotated on every use.

resource server

The API holding the data. Validates tokens and enforces scope.

scope

A label for a slice of authority (accounts:read): requested, capped by registration and entitlement, then approved by the user.

state

A random per-request value echoed back on the callback, so a client can recognise a flow it started.
